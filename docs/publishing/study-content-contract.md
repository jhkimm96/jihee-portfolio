# Study 콘텐츠 계약

이 문서는 `publish-study`가 새 Study를 작성하거나 기존 Study의 핵심 내용을 개편할 때 따른다.
다른 게시 기록에 Study 형식을 강제하지 않는다.

## 초안 전 조사

모델의 기억이나 기존 Study만으로 작성하지 않는다. 실제 오늘 날짜를 확인한 뒤 일반 검색,
공개 블로그·영상·SNS, 공식 문서와 현재 프로젝트 근거를 조사한다.

- Google·Naver 같은 검색은 설명 자료와 공식 자료를 찾는 출발점이다.
- Instagram·YouTube·공개 SNS는 어려운 지점, 쉬운 비유와 전개 방식을 참고하는 자료다.
- 공식 문서, 명세, 릴리스 노트, 공식 구현 소스는 기술적 사실의 기준이다.
- 프로젝트 코드, 설정, 테스트, 이슈와 PR은 실제 사용 여부와 기여 범위의 기준이다.

버전, 지원 상태, 보안 기본값, API나 운영 방식처럼 바뀔 수 있는 주제는 프로젝트 사용 버전과
최신 안정 버전을 따로 확인한다. deprecated, removed, experimental, preview 상태를 섞어 쓰지
않는다. 날짜가 중요한 주장에는 조사 기준일과 확인한 버전을 남긴다.

## 한 질문의 학습 단위

Study 하나는 핵심 질문 하나에 답한다. 첫 화면에서 질문, 한 줄 답과 답이 성립하는 최소 조건을
알 수 있어야 한다. 독립 질문이 여러 개라면 기존 글을 장 개요로 유지하고 짧은 Study로 분리하거나,
이미 있는 Study에 연결한다.

고정 글자 수나 강제 scroll snap을 사용하지 않는다. 대신 한 이해 단위를 다음 순서로 편집한다.

```text
상황 → 사건 → 결과 → 이유
```

## 발생 상황에서 확인과 적용으로 연결하기

초안 조사에서 다음 질문까지 점검하고 필요한 설명 또는 후속 Study를 함께 제안한다. 사용자가
빠진 질문을 먼저 발견하기를 기다리지 않는다.

- 이 개념을 왜 공부하는가? 어떤 기능과 조건에서 문제가 발생하거나 이 지식이 필요한가?
- 무엇을 관찰하거나 재현하면 원인을 확인할 수 있는가? 증상만으로 원인을 단정하지 않는다.
- 어디를 왜 바꾸며, 변경이 효과가 있는지 어떤 결과로 확인하는가?

현재 글 초반에는 발생 상황과 공부할 이유를 짧게 넣는다. 확인·적용 설명이 별도의 질문으로
길어지면 후속 글로 연결한다. 개념, 진단, 구현은 편집 관점이며 고정된 글 유형이나 필수 3부작이
아니다. 짧은 내용은 같은 글에 담고, 미작성 후속 글은 내부 백로그에 제안한다.

구현 기술은 프로젝트가 사용하는 언어와 도구, 문제가 발생한 계층, 효과를 검증할 수 있는 최소
변경을 기준으로 선택한다. Java에 고정하지 않으며 Python·C 등의 코드, SQL, Kubernetes 설정을
필요에 맞게 사용하고 함께 다룰 수도 있다. 초안에 선택 이유, 변경 위치와 검증 방법을 명시한다.
프로젝트와 무관한 예제는 원리를 잘 보여주는 기술을 선택하고 실제 프로젝트 구현과 구분한다.

프로젝트 연결은 관련 게시 기록을 찾은 뒤 해당 주장에 필요한 코드·설정·테스트와 대조한다.
과거 발견, 현재 미해결 위험, 구현 완료와 검증된 효과를 구분한다. 연결 근거가 없으면 사례를
만들지 않는다. 관련 노트는 선수 개념, 원인 이해 또는 후속 적용에 도움이 되는 글로 선택한다.

## 비전공자 설명

본문의 첫 목표는 비개발자도 '언제 필요하고, 어떻게 쓰며, 무엇이 달라지는지' 이해하는 것이다.
코드를 읽어야만 핵심 답을 알 수 있게 쓰지 않는다. 시각적으로 예시를 들 수 있으면 구체적인
사용 장면과 변화 전후를 먼저 보여준다. 장면마다 쉬운 설명을 짧게 붙이고, 그림만으로 추측하게
하지 않는다. 캐릭터·물건·값 등 같은 대상을 이어 보여주며 기술 이름뿐인 상자와 화살표를 피한다.

구현 글도 '사용 상황과 시각적 예시 → 필요한 최소 코드와 실행 변화 → 선택적 전체 구현' 순으로
깊어진다. 핵심 원리와 적용 조건은 본문에 남기고, 문법 상세와 전체 코드는 토글 또는 관련 글에
둔다. 시각화가 설명에 도움이 되지 않는 주제에 그림을 강제하지 않는다.

핵심 용어는 쉬운 말, 현재 예시에서의 역할, 기술 용어 순으로 본문에서 설명한다. 이 설명이 없으면
다음 장면을 이해할 수 없는 경우 토글로 숨기지 않는다. 구현 변형, 엄밀한 정의, 선택적 배경만
`<details>` 토글에 둔다.

### 처음 보는 코드의 출처와 실행 모습

Java 기본 클래스처럼 개발자에게 익숙한 기능도 독자가 안다고 가정하지 않는다. 이해에 필요한
클래스·함수·설정이 처음 등장하면 출처(언어 기본 제공, 외부 라이브러리, 프로젝트 자체 코드),
별도 설치 필요 여부와 현재 예시에서 맡은 역할을 짧게 설명한다. 이름이나 import 위치만 나열하지
않고, 무엇을 직접 해주며 무엇은 우리가 구현해야 하는지 구분한다. 모호한 '도구'로 뭉뚱그리지 않는다.

코드 흐름만 설명해서는 부족하다. 구체적인 입력 하나를 정하고 다음을 연결한다.

```text
실행 전 값·상태 → 관련 코드 몇 줄 → 생성·조회·변경된 값·상태 → 요청자가 받는 결과
```

변수, 보관 자료구조, 객체와 객체를 만드는 메서드를 혼동하지 않게 설명한다. 예를 들어
`completed`는 결과 보관함, `completedFuture(value)`는 이미 완료된 Future를 만드는 호출,
`new CompletableFuture<>()`는 아직 완료되지 않은 Future 생성이라는 차이를 드러낸다.
비유는 실제 역할과 연결하고, 개념 그림을 실제 메모리 내부 구조처럼 단정하지 않는다.

객체 공유, 값이 채워지는 시점이나 실행 순서가 핵심인데 글만으로 상상하기 어렵다면 같은 이름과
값을 유지한 전후 그림·작은 상태표·단계 시각화를 붙인다. 화살표뿐인 전체 흐름도로 대체하지 않는다.
애니메이션이나 새 UI를 항상 만들 필요는 없다. 본문은 한 번에 한 변화만 보여주고 전체 구현과
선택적 문법은 토글에 둔다. 이해에 필수인 설명을 토글이나 선수 글로만 떠넘기지 않는다.

초안 검토에서는 코드를 건너뛰어도 사용 상황과 해결 효과가 이해되는지 먼저 확인한다. 이어서
코드를 읽는 독자가 '어디서 온 기능인지, 지금 무엇이 들어 있는지, 이 줄 뒤에 무엇이 바뀌는지'
답할 수 있는지 확인한다. 설명을 늘려도 여러 독립 질문이 섞이면 짧은 선수 Study로 분리·연결한다.

## 다이어그램

다이어그램 하나는 질문 하나에 답한다. 정상·실패·복구를 한 장면에 섞지 않고, 화살표에는 실제
사건을 적는다. 요청 수, 재고 값, `eventId`처럼 추적할 값은 다음 장면에서도 유지한다. 그림 바로
아래에 결과를 한 문장 또는 작은 표로 붙인다. 그림이 문장보다 복잡하면 그림을 제거한다.

## 로드맵 연결

새 글이나 개편 글은 다음을 제안한다.

- 선수 Study
- 이 글에서 얻는 한 줄 답
- 다음 Study
- 관련 프로젝트 적용 근거

공개 로드맵에는 실제로 읽을 수 있는 글만 넣는다. 아직 작성하지 않은 공부할 개념 목록은 내부
백로그로 관리한다.

## 회상과 검증

본문 끝에는 조건을 바꾼 사례에도 답할 수 있는 회상 질문을 둔다. 질문을 풀어야 본문이나
프로젝트 근거를 볼 수 있게 잠그지 않는다. 중요한 외부 근거는 주장 가까이에 연결한다.
