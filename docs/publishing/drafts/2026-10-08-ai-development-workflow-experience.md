# AI 개발 도구의 요구사항·설계·구현·검증 흐름 구성

## 경험의 핵심

포트폴리오를 AI 코딩 도구와 함께 수정하며 반복된 임의 변경, 정형적인 화면 구성, 추천안 하나로 유도되는 질문을 발견했다. 매번 수정 요청을 반복하는 대신 요구사항 확인, 역할별 대안 검토, 화면 선택, 코드 계획, 구현 기준과 검증을 단계별 규칙으로 구성했다.

AI 모델 개발이나 제품의 AI 기능 구현 경험이 아니라, AI를 개발 도구로 사용하며 그 작업 흐름과 확인 기준을 직접 설계한 경험이다.

## 본인이 결정한 내용

- 기존 프로젝트는 코드와 자료를 먼저 읽고, 신규 프로젝트는 목적·사용자·제약부터 질문하도록 구분했다.
- 약한 들러리 없이 각기 다른 조건에서 강한 2~3개 대안을 비교하도록 질문 규칙을 수정했다.
- 구조를 먼저 선택한 뒤 시각 언어와 필요한 모션·3D를 적용하게 했다.
- 기존 문구와 사실은 요청 없이 변경하지 않도록 했다.
- 특정 브랜드를 떠올리게 하는 색을 기본값으로 쓰기보다 제품 맥락에서 시각적 근거를 찾게 했다.
- 모든 UI 스킬을 읽는 방식 대신 필요한 스킬과 reference만 읽는 모듈형을 선택했다.
- 초기 비교는 Visualize, 확정 시안은 Figma 또는 MagicPath, 사용 불가 시 로컬 시안으로 이어지게 했다.
- 채용 전용 관점 토론과 일반 제품의 관점 토론을 분리했다.
- 구현 가능한 규칙을 계획의 테스트 조건에 연결하고 코드 가독성과 최소 구현 기준을 함께 적용했다.

Code Planner 등 기존 도구를 어떤 범위까지 본인이 최초 작성했는지 전체 변경 이력을 이번 조사에서 확인하지 않았다. 설치된 코드와 사용자 설명을 근거로 구성·사용·검토 경험을 기술하며 외부 도구 전체를 단독 개발했다고 쓰지 않는다.

## 실제 검증과 한계

2026-10-08 설치된 Code Planner의 훅 검사, 계획 파싱, 작은 수정 예산 테스트 40개를 실행해 모두 통과했다.

훅은 승인된 계획 범위와 테스트 파일 존재 여부를 확인한다. 테스트가 실제 실패한 뒤 통과했는지, assertion이 적절한지까지 검사하지 않는다. 과거 TDD 실패 실행 로그는 이번 조사에서 확인하지 못했다.

범용 토론 스킬의 파일 설치와 형식 검증은 확인했다. 독립 에이전트 토론이나 실제 사용자 평가의 개선 효과는 아직 측정하지 않았다. Figma·MagicPath 호출 한도 대체는 규칙으로 구현했으며 이번 기록에서 장애를 재현하지 않았다.

보안 검증, 배포, 패키징을 포함한 전 과정 자동화는 완료하지 않았다. 토큰 감소, 개발 시간 단축, 오류 감소도 측정하지 않았다.

## 자소서·면접에 사용할 때

적합한 문항은 AI 도구 활용, 개발 방식 개선, 주도적인 문제 해결, 반복 업무 표준화다. 스킬 이름을 나열하기보다 화면 변경 문제 한 가지와 이를 절차로 바꾼 판단을 중심으로 쓴다.

사용할 수 있는 주장:

- 모호한 요청을 사용자 목적과 완료 조건으로 구체화했다.
- 합의 전 구현 문제를 구조·시각 언어·모션의 선택 단계로 나눴다.
- 반복되는 협업 기준을 재사용 가능한 스킬과 reference로 정리했다.
- 계획 지침과 실행 훅의 보장 범위를 코드와 테스트로 구분했다.

사용하면 안 되는 주장:

- AI 기능이나 모델을 개발했다.
- 전체 개발 수명주기를 완전 자동화했다.
- 보안과 접근성 인증을 획득했다.
- 모든 코드 변경에서 TDD가 강제된다.
- 측정하지 않은 시간·토큰·오류 감소율이 있다.
- 모의 토론이 실제 전문가나 사용자 검증이다.

## 직접 설명할 수 있어야 할 질문

1. 지침과 훅의 차이는 무엇인가?
2. 어떤 규칙은 구현 전에 테스트할 수 있고 어떤 것은 이후 검증하는가?
3. 필요한 스킬만 선택한다는 것을 어떻게 규칙으로 표현했는가?
4. 외부 시안 도구가 막히면 어떤 결과물을 남기는가?
5. 아직 검증하지 않은 효과와 다음 확인 방법은 무엇인가?
