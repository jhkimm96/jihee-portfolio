## Redis 본문

### 01 · 한 사람의 요청이 서버 A와 B로 나뉘어 들어온다

사용자 민지가 상품 검색을 다섯 서버 중 어느 곳으로든 보낸다. 정책은 “같은 사용자에게 고정된 1초 구간당 3번”인데 각 서버가 혼자 세면 어떻게 될까? 학습 예시이며 실제 장애 기록이 아니다.

```text
서버 A의 민지 한도: 3번
서버 B의 민지 한도: 3번
서버 C/D/E도 각각: 3번
────────────────────
서버별 한도의 합: 15번 ≠ 전체 한도 3번
```

**같은 사용자의 사용량을 한곳에서 공유하고, 확인과 변경을 끊기지 않게 처리한다.** 이 방식으로 여러 서버의 한도를 맞출 수 있다. **Redis**는 여러 서버가 접속해 작은 상태를 빠르게 읽고 바꾸는 별도 저장 시스템이다. Java 기본 클래스가 아니다.

### 02 · 같은 저장소라도 다른 이름으로 세면 공유가 아니다

```text
서버 A ── 민지의 검색 요청 ──┐
서버 B ── 민지의 검색 요청 ──┼→ Redis: 민지 / 검색 / 이번 구간
서버 C/D/E ────────────────┘          사용량 0 → 1 → 2 → 3
```

저장 위치를 찾는 이름을 **키(key)**라고 한다. 같은 제한 대상이라면 모든 서버가 같은 키와 시간 구간 규칙을 사용해야 한다. 서버 번호를 키에 넣으면 다시 서버별 한도가 된다. 외부 서비스 전체 호출량을 제한하려면 사용자 키가 아니라 그 공유 경계에 맞는 키를 정한다.

### 03 · 남은 한 번을 두 서버가 동시에 읽으면

기본적인 “읽기 → 비교 → 저장”을 서버마다 따로 실행하면 같은 사용량을 읽을 수 있다.

```text
사용량 2 / 한도 3
A: 2를 읽음 → 허용 → 3 저장
B: 2를 읽음 → 허용 → 3 저장
결과: 두 요청을 허용했는데 기록은 한 번만 증가
```

이 충돌을 막으려면 판정에 필요한 읽기와 갱신을 Redis 안에서 한 작업으로 처리한다. **원자적 처리**는 그 작업 사이에 다른 요청이 끼어들지 못하게 한다는 뜻이다.

```text
A의 작업: 2 확인 → 허용 → 3 기록 → 끝
B의 작업: 3 확인 → 거절 → 끝
```

Redis에서는 Lua 스크립트로 필요한 명령들을 묶을 수 있다. Lua는 Redis에서 실행하는 스크립트 언어다. 단순 증가 명령 `INCR`도 원자적이지만, 따로 하는 판정/만료 설정까지 자동으로 한 작업이 되지는 않는다. 긴 스크립트는 다른 작업을 막으므로 짧게 유지한다. [Lua의 원자적 실행](https://redis.io/docs/latest/develop/programmability/eval-intro/), [카운터와 만료를 묶는 이유](https://redis.io/docs/latest/commands/incr/)

### 04 · Redis가 응답하지 않으면 정책을 먼저 정한다

| 선택 | 이득 | 잃는 것 |
| --- | --- | --- |
| 제한 확인 실패 시 임시 허용 | 기능을 계속 제공할 여지 | 공유 한도를 넘길 수 있음 |
| 제한 확인 실패 시 보류/거절 | 보호 대상의 부담을 줄임 | Redis 장애가 사용자 실패로 이어짐 |

어느 쪽이 항상 맞지는 않다. 보호할 기능과 비용에 따라 결정하고 Redis 대기도 제한한다. 이미 소비했는데 응답만 못 받았다면 다시 소비해 이중으로 셀 수도 있다. 원자적 실행과 네트워크 결과 확인은 다른 문제다.

<details>
<summary>원자적 스크립트면 장애 때도 한도를 절대 넘지 않을까?</summary>

그렇지 않다. 만료/삭제/상태 유실로 한도가 초기화될 수 있고, Redis 기본 복제는 비동기여서 장애 전환 때 기록이 사라질 수 있다. `WAIT`도 모든 상황의 강한 일관성을 보장하는 것은 아니다. 정책에 필요한 장애 허용 범위를 정하고 시험한다. [Redis 복제의 보장 범위](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)

</details>

### 05 · 프로젝트의 현재 한도는 공유 한도가 아니다

PromptHub의 `TossRateLimiterConfig`는 메모리 Registry를 만든다. 확인한 코드/설정 검색에서는 Redis 기반 RateLimiter 연결을 찾지 못했다. 따라서 이 글은 **분산 제한의 학습 설계**이며 프로젝트 구현 완료가 아니다.

구현한다면 같은 사용자 요청을 두 서버로 보내 총 허용량이 3인지, 구간 변경·Redis 실패·응답 유실에서 정책대로 동작하는지 확인한다. 실제 Redis 연결/스크립트/부하 시험은 이번에 수행하지 않았다.

### 자기 말로 답해보기

모든 서버가 같은 Redis를 쓰지만 키에 서버 번호를 넣었다. 사용자 전체 한도 3번을 공유할까?

<details>
<summary>답 확인하기</summary>

아니다. 서버별 다른 상태를 센다. 같은 제한 대상은 같은 키와 판정 규칙을 공유해야 한다.

</details>

## HTTP 본문

### 01 · 실패 숫자만 보고 다시 보내면 안 된다

서버 A가 상품 7을 외부 API에서 조회했더니 `429 Too Many Requests`와 `Retry-After: 2`를 받았다. 학습용 응답이다.

```text
상품7 조회 → 외부 API
          ← 429 / Retry-After: 2
바로 재호출 ×     우선 2초 대기 지침 확인
```

**응답을 보낸 곳, 기다리라는 시간, 남은 호출 예산과 재시도 안전성을 함께 본다.** `429`는 요청량 제한을 뜻하며 기다릴 지침이 반드시 들어 있는 것은 아니다. [429의 의미](https://www.rfc-editor.org/rfc/rfc6585#section-4)

### 02 · 2는 횟수가 아니라 기다릴 초다

`Retry-After`는 응답에 붙는 추가 정보인 **HTTP 헤더**다. 위의 숫자 2는 응답을 받은 뒤 기다릴 2초를 뜻한다. 특정 날짜/시각으로 올 수도 있다. 해당 지침을 따른 뒤 보내더라도 성공을 보장하지는 않는다. [Retry-After 형식](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3)

```text
응답 수신     대기                 다시 요청할 수 있는 후보 시점
0초 ───────── 2초 ───────────────→
```

헤더가 없거나 잘못된 형식이면 무한 대기가 아니라 정한 제한 안의 Backoff/Jitter 정책을 적용한다. 기다리는 중에는 같은 요청을 즉시 반복하지 않는다.

### 03 · 남은 예산이 1초인데 2초를 기다리라면

```text
요청 전체 예산: 앞으로 1초 남음
외부 대기 지침: 최소 2초
─────────────────────────
이번 요청 안에서는 재시도하지 않음
```

대기 지침을 1초로 잘라 더 빨리 재시도하지 않는다. 대기 후 재시도 시간을 감당하지 못하면 이번 요청을 종료하고, 별도 작업으로 미룰지 실패를 알릴지 결정한다. [Retry의 전체 예산](/study/cs/retry-backoff-jitter-budget)과 연결해서 생각한다.

### 04 · 응답 없는 결제는 “안 됐다”가 아니다

| 받은 상황 | 먼저 할 판단 |
| --- | --- |
| 429 | 누가 어떤 한도를 적용했는지, 대기 지침과 예산 |
| 일시적 5xx | 재시도 가능한 실패인지, 중복 방지와 횟수 |
| 잘못된 입력/권한 거절 | 입력이나 권한 문제 해결 없이 반복하지 않음 |
| 결제 응답이 안 옴 | 처리됐는지 모름. 상태 확인과 멱등 계약부터 확인 |

**멱등성**은 같은 작업을 다시 보내도 업무 효과가 중복되지 않게 하는 성질이다. POST라는 이름이나 헤더 하나만으로 보장되지 않는다. 서버가 약속한 키 범위·유효 기간·요청 내용 규칙까지 필요하다. [안전한 자동 재시도의 조건](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)

### 05 · 현재 프로젝트가 하는 일과 하지 않는 일을 나눈다

PromptHub `TossRetryPredicate`는 특정 서버 오류와 일부 네트워크 예외를 재시도 대상으로 분류한다. 직접 cause가 `SocketTimeoutException`인 네트워크 예외는 제외한다. 모든 중첩 timeout을 빠짐없이 제외한다는 뜻은 아니다.

`TossPaymentGateway`는 승인 요청에 멱등 키를 넣지만, 확인한 실행 경로에는 `Retry-After`를 읽어 동적 대기 시간을 정하는 처리가 없다. 외부 4xx 응답은 오류 코드로 바뀌며, 내부 RateLimiter 거절은 별도로 `PG_RATE_LIMITED`가 된다. 그 오류는 503으로 선언되어 있다.

그러므로 이 글의 429 대응은 **개념과 설계 지침**이다. 프로젝트가 외부 429를 자동 재시도하거나 사용자에게 원래 헤더를 전달한다는 구현 설명이 아니다. 실제 응답·테스트·PG 운영 동작을 실행 검증하지 않았다.

### 자기 말로 답해보기

조회 응답의 Retry-After는 10초인데 내 요청 예산은 3초다. 3초만 기다리고 다시 보내면 될까?

<details>
<summary>답 확인하기</summary>

안 된다. 지침보다 빨리 보내지 말고 이번 요청의 재시도를 포기하거나 별도 지연 작업 정책을 선택한다. 안전성과 총예산도 함께 확인한다.

</details>

## 비교 본문

### 01 · 상품 조회 하나가 느려지면 문제가 여러 곳에 생긴다

서버 A에서 상품 7의 외부 조회가 느려졌다고 해 보자. 새로운 요청이 계속 들어오고, 처리 자리가 묶이며, 재시도까지 늘어난다. 하나의 학습 상황이며 실제 장애 기록은 아니다.

```text
들어오는 요청 → 실행 자리 → 외부 조회 대기 → 재시도 → 사용자 응답
    많아짐       묶임          길어짐        늘어남      늦어짐
```

**보호 장치는 같은 장애에서도 서로 다른 경계를 지킨다.** 이름이 비슷하다고 하나가 나머지를 모두 대신하지 않는다.

### 02 · 같은 길에서 서로 다른 질문을 한다

| 장치 | 이번 장면에서 묻는 질문 |
| --- | --- |
| Rate Limiting | 이 시간 동안 이렇게 많이 보내도 되는가? |
| Bulkhead | 이 기능이 지금 처리 자리를 너무 많이 쓰는가? |
| Timeout | 이번 외부 호출을 얼마나 더 기다릴까? |
| Retry | 다시 보낼 안전한 실패인가? 몇 번, 언제 보낼까? |
| Circuit Breaker | 최근 계속 나쁜 상대에게 새 호출을 보내도 될까? |
| Fallback | 실패 뒤 결과의 뜻을 지키면서 무엇을 대신 줄까? |

Rate Limiting을 통과해도 느린 호출은 자리를 붙잡을 수 있다. Bulkhead를 통과한 호출도 너무 오래 기다릴 수 있다. Timeout 뒤에도 상대가 일을 완료했을 수 있다. [Bulkhead의 격리와 다른 보호 장치 조합](https://learn.microsoft.com/en-us/azure/architecture/patterns/bulkhead)

### 03 · 서로의 빈틈을 메우되 무조건 모두 붙이지 않는다

```text
조회량이 과함     → 유입량과 전체 외부 호출량부터 제한
한 기능만 느림    → 공유 자원과 동시 점유부터 확인
대기가 끝나지 않음 → 호출별 대기와 전체 요청 예산 확인
반복해서 실패함   → 실패 분류와 차단/회복 정책 확인
결과를 못 받음    → 안전한 대체 또는 실패 안내 선택
```

측정한 실패 원인과 보호하려는 경계에 맞는 최소 장치를 선택한다. 대체 DB로 부하를 옮기거나 Retry를 여러 계층에 겹치면 보호하려던 장애를 키울 수 있다. 개별 장치 설명은 [Fallback](/study/cs/fallback-safe-results)과 [Retry](/study/cs/retry-backoff-jitter-budget)로 이어 읽는다.

### 04 · 프로젝트에서는 코드 작성 순서와 실행 순서도 다르다

PromptHub 승인 Gateway는 안쪽부터 래퍼를 만들지만 실제 호출은 바깥쪽에서 시작한다. **래퍼**는 원래 호출 전후에 판단을 추가하는 감싸기다.

```text
실행 진입
Circuit Breaker → Retry → RateLimiter → Bulkhead → 외부 승인 호출
```

이 배치에서는 Retry가 각 시도마다 RateLimiter와 Bulkhead를 다시 지난다. 호출권을 얻은 뒤 Bulkhead가 거절하면 실제 HTTP 호출 없이도 구간 호출권을 쓸 수 있다. Breaker는 내부 Retry 묶음의 최종 결과를 본다. 다른 배치가 같은 통계와 효과를 낸다고 보지 않는다.

Timeout은 HTTP 클라이언트에도 별도로 있다. 확인한 코드는 연결 대기 5초와 읽기 대기 60초를 설정한다. 두 값이나 내부 대기를 단순히 하나의 요청 전체 제한으로 해석하지 않는다. 이번에는 소스만 읽었으며 운영 효과를 측정하지 않았다.

### 05 · 비교의 끝은 어떤 결과를 확인할지다

같은 느린 상품 조회 상황에서 실제 외부 호출 수, 진행 중 호출 수, 거절 이유, 대기 시간, 재시도 수와 다른 기능의 지연을 함께 본다. 지표 하나가 좋아졌다고 전체 흐름이 개선됐다고 단정하지 않는다.

## 조사 기록

- 2026-10-09. Redis Lua/INCR/복제 문서의 관련 구간과 RFC6585/9110의 429/Retry-After/자동 재시도 구간 확인.
- Redis 상태 공유와 원자적 작업은 네트워크 응답 확인, 장애 전환의 내구성 보장과 다르다. Redis 실제 연결/실행 없음.
- 로컬 Java/Gradle/Lua/YAML에서 RedisRateLimiter/RequestRateLimiter/TokenBucket/Bucket4j 사용 검색은 없음.
  전체 런타임/외부 설정 부재를 증명한 것이 아니다. 불필요한 gateway 경로 후보는 존재하지 않아 저장소 범위 검색으로 대체했다.
- TossRetryPredicate/Config/ErrorCode/Gateway/RateLimiterConfig 소스를 읽었다. 테스트/운영 호출은 하지 않았다.
- 기존 watermark의 429 절은 색인/임베딩 맥락이다. 새 HTTP 글은 대기 지침과 남은 예산의 충돌 및 안전한 요청 재시도라는 질문으로 분리한다.
- 비교 글은 기존 개별 글의 알고리즘을 반복하지 않고 보호 경계와 프로젝트 감싸기 위치를 대조한다.
- Token Bucket은 기존 초안 본문을 그대로 사용한다. Java 예제는 API 대조 수준, 설치/컴파일/실행 미검증.
- 모두 학습 예시와 현재 소스 사실을 분리하며 내부 URL/가짜 Secret/개인정보를 공개하지 않는다.
