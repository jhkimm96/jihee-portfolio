## 대상

포트폴리오를 AI 코딩 도구와 함께 수정하면서 만든 개발 절차와 그 구현을 점검했다. 새로운 AI 모델이나 사용자에게 제공하는 AI 기능을 개발한 사례가 아니라, 개발 도구의 작업 방식과 판단 기준을 직접 구성한 사례다.

처음에는 화면마다 수정 요청을 했다. 작업이 이어지면서 같은 문제가 반복됐다. 구성 변경의 이유가 합의되지 않았고, 큰 제목이 중요한 정보를 밀어냈으며, 대안을 물어도 추천안 하나를 확인받는 흐름이 됐다. 그때마다 다시 설명하는 대신 어떤 단계에서 무엇을 확인해야 하는지 스킬로 정리했다.

이번 글은 그 규칙을 작성한 뒤 실제 스킬, 계획 문서, 훅과 테스트를 다시 읽은 리뷰다. 공개 이슈나 PR 번호가 있는 작업은 아니므로 없는 번호를 붙이지 않았다. 포트폴리오 적용 자료는 점검 시점의 커밋 `75800d3`를 기준으로 확인했다. 사용자 전역 스킬과 설치된 플러그인은 별도 로컬 파일이므로 해당 커밋이 그 파일들까지 고정하는 것은 아니다.

<details>
<summary><b>스킬과 훅은 어떻게 다른가요?</b></summary>

스킬은 AI가 작업할 때 읽는 절차와 판단 기준이다. 훅은 특정 도구 실행 전후에 실제 프로그램을 실행하는 연결 지점이다. 작업 지침에 “계획을 먼저 세운다”고 쓰는 것과, 파일 작성 전에 계획을 확인하는 프로그램을 실행하는 것은 보장 범위가 다르다.

</details>

## 발견한 문제

### 합의하지 않은 화면 변경을 구현 뒤에 발견했다

System Map을 고민하는 과정에서 구성이 다른 형태로 바뀌자, 나는 먼저 아이디어를 비교한 뒤 변경하자고 요구했다. 문구와 디자인을 한꺼번에 바꾸면 무엇에 동의했는지 분리하기 어려웠다. 먼저 사용자 목적과 콘텐츠를 확인하고 구조를 고르는 단계가 필요했다.

### 여러 선택지가 있어도 판단은 하나로 기울었다

질문마다 한 안이 추천되고 나머지는 추천을 확인하는 선택지처럼 보였다. 색이나 모양만 다른 안을 만드는 것으로는 구조를 비교할 수 없었다. 각기 다른 조건에서 채택할 수 있는 대안과 반론을 남겨야 했다.

### 디자인 스킬을 모두 적용하면 서로 다른 전제가 충돌했다

설치된 UI 스킬에는 큰 타이포그래피, 고정된 페이지 구성, 특정 스타일과 모션을 선호하는 규칙이 있었다. 모든 제품에 동시에 적용할 수는 없었다. 어떤 스킬을 언제 읽고 사용자 요구와 충돌할 때 무엇을 우선할지 정해야 했다.

### 테스트 우선 지침과 실행 보장을 구분하지 않았다

Code Planner 문서에는 테스트를 먼저 작성하고 실패를 확인한 뒤 구현하는 절차가 있다. 그러나 실제 훅은 짝으로 지정한 테스트 파일의 존재를 확인한다. 테스트 실행 결과나 assertion의 품질까지 판정하지는 않는다.

## 조치

### 1. 요구사항 탐색과 화면 선택을 분리했다

`design-discovery`에서는 기존 자료로 확인할 수 없는 핵심 질문만 한 번에 하나씩 묻고, 사실과 가설을 구분하도록 했다. `ui-ux-orchestrator`에서는 구조, 시각 언어, 필요한 모션과 3D를 순서대로 선택하게 했다.

기존 문구를 더 자연스럽게 고치는 작업도 사용자 승인 범위에 포함하도록 했다. 디자인 변경 승인이 문구 변경 승인까지 뜻하지 않게 했다.

완성 시안 하나를 먼저 만들고 수정하는 방식도 가능하다. 다만 이번 작업에서는 정보 구조와 시각 표현을 한 번에 바꿀 때 합의 범위를 놓쳤으므로 단계별 비교를 선택했다. 스킬 구현에는 이 승인 순서가 들어 있지만, 모든 실제 작업이 항상 이를 따른다고 보장하는 실행 장치는 아니다.

### 2. 비교안과 반론의 품질을 규칙으로 남겼다

`design-discovery`의 질문 규칙을 수정해 약한 들러리 안을 제외하고, 각 안이 적합한 조건과 포기할 점을 설명하게 했다. 이후 채용 전용 `career-debate`의 관점 검토 방식을 제품 설계에도 쓸 수 있도록 `perspective-debate`를 별도로 만들었다.

범용 버전은 질문에 맞춰 사용자, UX, 개발, 데이터, 보안, 운영 등 관련 역할을 선택한다. 독립 제안, 교차 반론, 수정, 최종 비교의 순서로 판단 변화를 남긴다. 채용 역할을 모든 제품에 넣는 대신 참가 역할을 바꾸는 방법을 선택했다.

모의 역할의 수나 합의 자체를 근거로 취급하지 않는다. 16개 MBTI 관점은 요청한 심층 토론에서만 사용하는 추가 렌즈다. 범용 스킬의 작성과 설치는 확인했지만 실제 사용자 조사나 독립 에이전트 토론의 효과를 측정한 것은 아니다.

### 3. 필요한 규칙과 도구만 선택하도록 모듈을 나눴다

`ui-ux-orchestrator`는 공통 라우터와 여섯 reference로 구성했다. 공동 설계, 시각 언어, 모션·3D, 도구 선택, 검증, 포트폴리오 추가 규칙을 필요한 단계에서 읽는다.

모든 원칙을 한 문서에 넣는 방식과 검사 스크립트까지 만드는 방식도 비교했다. 사용자가 다양한 웹 UI에 쓰되 매번 전체 스킬을 읽는 비용은 피하고 싶어 했으므로 모듈형을 선택했다. 작은 CSS 수정에는 자동으로 전체 절차를 적용하지 않게 했다. 실제 토큰 감소량은 측정하지 않았다.

초기 시안 비교는 Visualize, 확정 시안은 Figma 또는 MagicPath 중 한 곳으로 분리했다. 외부 도구가 모두 막히면 로컬 HTML/CSS 시안으로 이어가는 규칙을 넣었다. 호출 잔량이 제공되지 않으면 잔량을 추정하지 않고 확인된 오류에 따라 한 번 전환한다. 이 글에서 그 대체 경로를 실제 장애 상황으로 재현한 것은 아니다.

### 4. 코드 계획을 변경 범위와 테스트 대상에 연결했다

Code Planner 계획은 변경 파일, 함수 책임, 기존 코드와의 관계, 제외할 것, 품질 점검과 테스트 계획을 함께 담는다. 포트폴리오의 Study 로드맵 계획에는 구현 파일과 테스트 파일의 짝이 명시돼 있다.

```yaml
tests_first:
  - impl: lib/study-roadmap.ts
    test: lib/study-roadmap.test.ts
```

로드맵에 없는 글의 자동 노출을 막는 규칙, 중복 없는 순서, 선수·이전·다음 글 계산을 테스트 대상으로 연결했다. UI 전체를 먼저 단위 테스트로 고정하기보다 외부 시스템 없이 확인 가능한 순서 규칙부터 검증하는 방법이다.

구현 기준에는 `write-readable-code`와 `ponytail`을 연결했다. 함수와 변수 이름으로 업무 흐름을 드러내고, 기존 기능과 브라우저 기능으로 충분하면 새로운 추상화와 의존성을 추가하지 않도록 했다.

### 5. 지침과 훅의 보장 범위를 나눴다

설치된 Code Planner의 `PreToolUse` 훅은 파일 작성 요청을 검사한다. 대상 코드가 승인된 계획 범위에 없으면 차단하고, `tests_first`에 연결된 테스트 파일이 없으면 구현 파일의 작성을 막는다.

```javascript
const missingTestPath = findMissingFirstTest(plans, projectRoot, projectPath);
if (missingTestPath) return block(`테스트 파일을 먼저 작성하세요: ${missingTestPath}`);
if (isCoveredByPlan(plans, projectPath)) return allow();
```

문서 지침만 사용하는 것보다 파일 변경 시점에 범위를 확인할 수 있다. 다만 이 검사로 테스트 실패와 통과의 순서, 테스트의 적절성, 모든 편집 도구의 통과 경로까지 증명할 수는 없다. 설치 파일의 훅 설정은 Claude의 도구 이벤트를 대상으로 하며, 다른 환경에 동일한 실행 제약이 있다고 단정하지 않았다.

## 직접 만들었다가 고친 것

처음에는 개인 스킬의 적용 범위를 포트폴리오 중심으로 생각했다. 질문을 통해 모든 웹 UI에 공통으로 적용할 판단과 포트폴리오에서만 필요한 규칙을 분리했다. 채용 담당자의 탐색 기준을 ERP나 일반 서비스에도 그대로 적용하면 사용자 목적이 달라지는 문제가 있기 때문이다.

또한 토론을 범용화하면서 채용 전용 스킬의 이름만 바꾸지 않았다. 참가 역할과 자료 선택을 바꾸고, 채용 전용 절차는 기존 스킬에 남겼다. 항상 모든 성향과 영상 조사를 실행하는 대신 결정의 범위에 맞는 검토를 선택하도록 했다.

## 판단이 틀렸던 것

“여러 스킬을 연결했으니 개발 전 과정을 커버한다”는 설명은 범위가 너무 넓었다. 실제 파일을 대조하면 요구사항, 화면 설계, 관점 검토, 구현 계획과 일부 테스트 조건은 있지만, 보안 검증과 배포·패키징의 완료 근거까지 연결한 것은 아니다.

또 “테스트 우선 훅”이라는 이름만 보고 실패한 테스트 실행까지 강제한다고 생각하면 틀린다. 구현은 파일 존재를 검사한다. 이번 리뷰에서는 훅 코드와 테스트를 직접 대조해 이 차이를 확인했다.

## 남긴 것 · 하지 않은 것

보안, DB 변경, 외부 연계, 배포, 패키징을 모두 자동 처리하는 상위 스킬은 만들지 않았다. 실제 프로젝트에서 해당 단계의 산출물과 확인 방법이 필요해질 때 추가하는 편이 적절하다.

반응형과 접근성 기준은 UI 스킬에 들어 있다. 그러나 기준이 있다는 사실과 사이트가 접근성 기준을 모두 충족했다는 사실은 다르다. 이번 리뷰에서 별도의 접근성 인증이나 실사용자 평가를 수행하지 않았다.

Code Planner 테스트 파일은 실행했지만, 과거 작업에서 실제로 실패한 테스트를 먼저 실행했는지에 대한 로그는 이번 조사에서 확보하지 않았다. 새 범용 토론 스킬 역시 실제 적용 전후의 비교 사례가 후속 과제다.

## 검증

2026-10-08에 다음 근거를 대조했다.

- 현재 `design-discovery`, `ui-ux-orchestrator`, `perspective-debate`, `write-readable-code` 지침
- UI 오케스트레이터의 여섯 reference와 범용 토론의 추가 렌즈
- Code Planner의 계획 지침, 훅 설정과 파일 검사 구현
- 포트폴리오의 Study 로드맵 계획과 실제 테스트 파일

설치된 Code Planner의 파일 검사, 계획 파싱, 작은 수정 예산 테스트 40개를 실행해 모두 통과했다. 이는 플러그인의 현재 테스트 결과이며 모든 개발 작업의 품질이나 생산성 향상을 증명하는 수치가 아니다.

스킬 형식 검증과 포트폴리오의 테스트, 타입 검사, 빌드 결과는 게시 전 최종 검증에서 확인한다. 작업 시간, 토큰 사용량, 오류 감소량은 측정하지 않았다.
