## 기존 네 편의 메인 장면

### Java 코드를 읽는 첫 순서

상품 가격은 1,000원이다. 200원을 올린 뒤 새 가격을 돌려주려고 한다.

```java
int price = 1000;
int changedPrice = price + 200;
```

첫 줄에서 `price`라는 이름에 1000을 넣는다. 둘째 줄은 그 값을 꺼내 200을 더하고,
`changedPrice`에 1200을 넣는다. `price`는 여전히 1000이다.

장면: `price: 1000` → `1000 + 200` → `changedPrice: 1200`.

`int`는 정수를 담는 타입, 변수는 값을 부르는 이름이다. 메서드는 이름을 붙인 실행 묶음이다.
객체와 참조는 다음 선수 글에서 같은 상품을 가리키는 예시로 이어간다.
DTO, Repository, 도메인처럼 프로젝트 구조를 뜻하는 용어는 첫 장면의 전제에서 뺀다.
기존 서비스 예시는 별도 토글에 보존하되 `...`를 실행 가능한 완성 코드처럼 제시하지 않는다.

회상: 둘째 줄이 끝난 뒤 `price`도 1200이 될까? → 아니다.

### CompletableFuture: 결과가 아직 없는 경우와 이미 있는 경우

이름부터 소개한다. `CompletableFuture`는 Java 표준 라이브러리의 클래스다.
캐시 라이브러리가 아니고, 이름만 사용한다고 작업 스레드가 자동으로 생기지도 않는다.

같은 검색 결과를 기다리는 A와 B가 있다. 이 예시에서는 둘 다 같은 객체 F1을 받는다.

1. F1을 만들었지만 아직 결과는 없다. A와 B가 F1을 기다린다.
2. 검색 작업이 끝나면 `F1.complete("검색 결과")`로 그 객체를 완료한다.
3. A와 B는 같은 결과를 받는다. 결과를 공유할 뿐 검색을 실행하는 기능은 별도다.

시각 장면은 위에서 아래로 읽는 세 컷으로 만든다. `빈 F1 + A/B` → `F1에 결과 도착` → `A/B가 같은 결과 받음`.

`completedFuture("검색 결과")`는 처음부터 완료된 새 객체를 만든다.
이것과 기존 F1에 결과를 넣는 `complete(...)`는 다르다. 결과가 자동으로 캐시 Map에 들어가는 것도 아니다.

토글에는 import, 생성, 완료, 반환 값을 순서대로 보여준다. 단일 스레드의 단순 상태 예시와
여러 호출자의 공유 구현을 분리한다. 콜백, 실패 완료, 취소는 다음 글 또는 심화 토글에서 설명한다.
기존 DB 선점과 Kafka 완료 확인 내용은 삭제하지 않고 별도 프로젝트 심화로 남긴다.

근거: [Java 21 CompletableFuture API](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/CompletableFuture.html).
선수: Java 코드 읽기 → 기본형/참조형 → 값/참조/객체.
후속: 기존 `cs/single-flight-shared-future`와 `cs/cancellation-propagation`.

### N+1: 화면 한 번, 조회 여러 번

예시 조건: 상품 10개, 서로 다른 판매자 10명, 판매자 정보가 없는 영속성 컨텍스트, LAZY 연관.
상품 목록 조회 한 번 뒤 각 판매자 이름을 읽을 때 추가 조회가 발생하는 상황이다.
실제 SQL 횟수는 매핑과 쿼리, 캐시 상태에 따라 달라진다.

장면 1: `상품 목록 1회` → `상품1의 판매자 조회` → `상품2의 판매자 조회` → … → `상품10의 판매자 조회`.
이 예시에서는 총 11회다. 화면을 한 번 열었다는 것과 DB에 한 번 물었다는 것은 다르다.

장면 2: 해당 조회에서 판매자까지 fetch join으로 함께 가져오면, 추가 판매자 조회를 없앨 수 있다.
컬렉션 fetch join과 페이지네이션 문제까지 무조건 해결하는 방법은 아니다.
배치 조회는 여러 판매자 ID를 묶는 다른 방법이며, 항상 전체 SQL이 2회라고 일반화하지 않는다.

코드와 배치 설정은 토글로 옮기고, 방법 선택 표는 유지한다.
프로젝트 기록은 당시 정적 점검 결과로 표시한다. 실제 운영에서 SQL 11회를 측정했다고 쓰지 않는다.

### 마지막 재고 1개를 두 사람이 살 때

장면 1: A가 1개를 읽는다 → B도 1개를 읽는다 → 둘 다 구매 가능하다고 판단한다.
각자 계산한 0을 저장하면 DB 재고는 0인데 구매 성공을 두 번 허용할 수 있다.

장면 2: 확인과 차감을 DB의 한 조건부 UPDATE로 묶는다.
같은 행에 대한 PostgreSQL READ COMMITTED 예시에서 A가 먼저 성공하고 커밋하면,
기다리던 B는 바뀐 행의 조건을 다시 확인한다. 재고가 0이라 조건을 만족하지 않아 갱신 0건이다.
A가 롤백하거나 다른 격리 수준을 쓰는 상황까지 같은 결과라고 단정하지 않는다.

숫자는 처음부터 끝까지 재고 1 → 0, 구매자 A/B로 통일한다.
영향 받은 행 수 1/0을 성공/실패 판단에 사용한다는 핵심은 메인에 남긴다.
SQL/JPA 코드, 낙관적·비관적 락과 Redis 대안은 토글 또는 짧은 비교로 보존한다.
프로젝트에서 수정 완료했거나 장애를 측정했다는 새 주장은 만들지 않는다.

## 신규 1: 느린 주문을 로그·메트릭·트레이스로 살펴보기

핵심 질문: “주문이 느리다”는 말을 어떤 증거로 좁힐까?

학습용 상황이다. 주문 7이 평소보다 늦게 끝났다.

첫 컷 — 메트릭: 주문 API의 응답 시간이 여러 요청에서 함께 올라갔다.
메트릭은 여러 실행을 숫자로 모아 서비스의 상태와 추세를 보여준다.
이것만으로 주문 7의 상세 실패 이유를 알 수는 없다.

둘째 컷 — 트레이스: 주문 7의 요청 흐름에서 재고 확인보다 결제 호출이 오래 걸렸다.
트레이스는 서비스와 작업 사이의 경로, 작업에 걸린 시간을 연결한다.
연결에 필요한 정보가 전달되고 해당 작업이 기록돼 있어야 한다.

셋째 컷 — 로그: 그 결제 호출에 “응답 대기 시간 초과” 사건이 남아 있다.
로그는 특정 시점에 일어난 일을 기록한다. 원인 확정에는 외부 결제 시스템의 증거도 필요할 수 있다.

정리: 메트릭으로 이상 범위를 찾고, 트레이스로 느린 작업을 좁히고, 로그로 그때의 사건을 읽는다.
이것은 유용한 조사 예시이지 반드시 지켜야 하는 조사 순서는 아니다.

토글: 로그가 있다고 트레이스가 자동 생성되지는 않는다. 수집·저장·검색 도구는 별도 역할이다.
회상: 주문 7 하나의 오류 문장을 찾으려면 세 가지 중 무엇부터 확인할까?

근거: [OpenTelemetry 신호](https://opentelemetry.io/docs/concepts/signals/),
[트레이스](https://opentelemetry.io/docs/concepts/signals/traces/),
[로그](https://opentelemetry.io/docs/concepts/signals/logs/).
선수: 없음. 후속: 구조화 JSON 로그.

## 신규 2: 오류 문장을 필드로 나눠 찾기

핵심 질문: 결제 시간 초과만 골라 보려면 로그를 어떻게 남길까?

같은 주문 7의 사건을 두 가지 방식으로 기록한다. 아래 값은 학습용이다.

전: `주문 7 결제 실패, 3000ms 기다림`

후:

```json
{"event":"payment_timeout","orderId":7,"durationMs":3000}
```

문장을 그대로 검색하면 표현이 바뀔 때 놓칠 수 있다.
필드로 나누면 “event가 payment_timeout인 기록”처럼 같은 조건으로 찾을 수 있다.
JSON은 키와 값을 담는 데이터 형식이다. DB도 검색 엔진도 아니다.
수집 도구와 검색 저장소가 그 필드를 읽고 적절한 타입으로 저장해야 필드 검색을 할 수 있다.

숫자 `3000`과 문자열 `"3000"`은 타입이 다르다. 필드 이름과 타입을 일정하게 유지한다.
토큰, 비밀번호, 결제 정보, 요청 본문 전체를 그대로 기록하지 않는다.

토글 — Spring Boot 설정 예시:

```yaml
logging:
  structured:
    format:
      console: logstash
```

조사일의 공식 문서가 제공하는 구조화 출력 설정이다. 위의 세 필드 예시가 이 설정만으로
자동 생성된다는 뜻은 아니다. 프로젝트 버전과 별도 Logback 설정도 확인해야 한다.
필드 생성 → JSON 출력 → 수집 → 검색 저장을 서로 다른 단계로 보여준다.

프로젝트 연결: 로컬 GatewayAccessLogWriter에서 `eventType`, `requestId`, `status`, `durationMs` 등을
SLF4J 키-값으로 구성하는 코드는 확인했다. 최종 JSON 출력과 운영 수집 결과는 이번 조사에서 확인하지 않았다.
공개 글에는 로컬 절대경로나 내부 운영 정보 대신 기존 공개 프로젝트 글을 대조해 연결한다.

회상: JSON 로그를 남기기만 하면 Kibana에서 바로 검색할 수 있을까? → 수집과 저장 설정도 필요하다.
근거: [Spring Boot Logging — Structured logging](https://docs.spring.io/spring-boot/reference/features/logging.html).
선수: 로그·메트릭·트레이스. 후속: 추적 번호 구분.

## 신규 3: 요청 흐름, 작업, 이벤트의 번호는 왜 다를까?

핵심 질문: 같은 주문에서 traceId, spanId, eventId는 각각 무엇을 구분할까?

주문 7이 API를 거쳐 결제를 호출하고, 주문 이벤트를 발행하는 학습용 상황이다.
그림의 T1, S1, S2, E1은 읽기 쉬운 별칭이며 실제 표준 ID 형식이 아니다.

첫 컷: 요청 흐름 T1 안에서 주문 처리 S1이 결제 호출 S2를 부른다.
`traceId`는 연결된 요청 흐름을, `spanId`는 그 안의 작업 한 구간을 구분한다.
다음 서비스에 추적 맥락을 전달해야 같은 흐름으로 연결할 수 있다.

둘째 컷: 주문 이벤트 E1이 전달됐다가 같은 이벤트로 다시 전달된다.
`eventId`는 그 이벤트 자체를 식별하는 애플리케이션 약속이다.
중복 전달에도 같은 이벤트 ID를 유지하면 중복 처리 판단의 근거로 쓸 수 있다.
ID가 있다는 것만으로 멱등성이 보장되는 것은 아니다.

셋째 컷: 재처리 작업은 새 트레이스에서 실행되고 원래 흐름과 연결될 수도 있다.
이벤트 ID가 같다고 모든 재처리의 traceId와 spanId까지 같아야 하는 것은 아니다.

프로젝트 연결: 로컬 RequestIdMdcFilter의 UUID `requestId`는 요청 로그를 묶는 번호다.
이 코드만으로 W3C trace context나 분산 트레이싱이 구현됐다고 볼 수 없다.
표준 추적 도구가 만든 ID와 앱에서 만든 요청 번호를 같은 개념으로 소개하지 않는다.

토글: `traceparent`는 서비스 사이에서 표준 추적 맥락을 전달하는 HTTP 헤더다.
비동기 전파, 새 트레이스와 span link, 실제 계측 설치는 후속 구현 범위로 남긴다.
회상: E1을 다시 처리하면 spanId도 반드시 같아야 할까? → 아니다.

근거: [OpenTelemetry Traces](https://opentelemetry.io/docs/concepts/signals/traces/),
[W3C Trace Context](https://www.w3.org/TR/trace-context/).
선수: 구조화 JSON 로그, 기존 Kafka 소비 흐름. 후속 백로그: 수집·검색 흐름과 실제 계측.

## 승인 후 확인할 사항

- 신규 슬러그 세 개와 같은 파일명은 조사 시점에 없었다. 작성 직전에 다시 대조한다.
- N+1은 빈 컨텍스트/서로 다른 판매자라는 조건, 재고는 DB와 격리 수준을 메인에 남긴다.
- 그림은 상태 변화나 여러 요청의 관계를 설명할 때 사용한다. 숫자 한 줄을 위해 큰 다이어그램을 만들지 않는다.
- 기존 심화와 근거 링크를 보존하고, 새 선수 관계에 순환·없는 파일이 없는지 확인한다.
- Java 예시는 표준 클래스 출처를 명시한다. 실행 검증하지 않은 코드를 검증했다고 쓰지 않는다.
- 프로젝트 근거는 읽은 로컬 코드 범위에 한정한다. 운영 로그, 장애, 성능 측정으로 확대하지 않는다.
- 승인 범위의 최종 파일을 민감정보 자동 검사한다. 불명확한 항목만 사용자에게 확인한다.
- 테스트, 타입 검사, 콘텐츠 빌드와 화면 확인 결과를 별도로 기록한다.
- 이전 5편은 정적 검증됐지만 localhost 화면이 브라우저 정책으로 차단돼 화면 검수는 남아 있다.

## 적용 결과

- 기존4편의 URL/최초 날짜를 유지하고 updatedAt을 갱신했다. 신규3편은 2026-10-08로 작성했다.
- Java를 공유 Future 구현 앞, JPA를 OSIV 앞, GC 도달 가능성을 회수 글 앞에 배치했다.
  새 관측성3편은 Kafka 이후, 배포·운영 이전에 연결했다. 프로젝트 Learning Path는 수정하지 않았다.
- 변경 전 정책 테스트4개 실패를 확인한 뒤 순서 데이터를 변경했다. 전체 테스트85개 통과.
- `npx tsc --noEmit` 통과. 기존 서버를 유지하고 별도 임시 소스에서 `npm run build` 통과.
- 빌드의 203개는 사이트 전체 정적 페이지 재생성 수다. 이번 신규 Study 수는 3개다.
- Java21.0.7에서 본문과 동일한 Future 예제를 실행해 `false / 검색 결과 / 검색 결과 / true / false` 확인.
  가격 메서드는 입력1000→1200, 입력2000→2200을 검사했다.
- 생성된 콘텐츠7편의 날짜, 공개 여부, question, details를 확인했다. 내부 링크와 선수 파일 검사 통과.
- 공개7편, 관련 diff와 인용 소스의 민감정보 자동/수동 점검 통과. 내부 경로·자격증명 후보 없음.
- Mermaid를 Node 단독으로 파싱하려는 추가 검사는 DOM 환경 부재로 실행되지 않았다.
  빌드는 브라우저에서의 다이어그램 렌더링 검증을 대신하지 않는다. 화면·다이어그램 렌더 검수는 남아 있다.
- 추가 패키지나 UI를 만들지 않았다. 다른 작업의 변경은 커밋 범위에 포함하지 않는다. push하지 않는다.
- 공개7편, 로드맵2파일, 승인 계획을 `c3fcb12`로 커밋했다. 내부 초안과 감사 기록은 별도로 남겼다.
