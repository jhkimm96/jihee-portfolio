# Study 개편 조사와 설계안

- 조사 완료: 2026-10-06
- 화면 캡처: 2026-10-05
- 범위: Study 목록, Study 상세, Mermaid 다이어그램, 짧은 학습 콘텐츠와 자동화 가능성
- 구현 상태: 조사와 설계만 수행했으며 제품 코드는 수정하지 않음

이 보고서는 최초 조사 시점의 기록이다. 2026-10-07 사용자 요청으로 임시 캡처와 비교 시안을
백업 없이 삭제하고 이미지 링크를 제거했다. 당시 관찰과 설계 근거는 아래에 유지한다.

## 결론

Study가 안 읽히는 주된 이유는 긴 글 자체보다 **첫 선택이 많고, 글의 핵심 답이 상세 첫 화면에 없으며, 일부 그림과 그 결론이 서로 떨어져 있는 것**이다.

새 카드뉴스 시스템을 먼저 추가하면 같은 내용을 원문, 요약, 카드로 중복 관리하게 된다. 우선 기존 `summary`를 상세 첫 화면에 노출하고, 구조가 다른 대표 글 3편만 다시 편집한다. 이 실험에서도 읽기와 회상이 개선되지 않을 때 선택형 예측 카드나 작은 시뮬레이터를 추가한다.

## 실제 화면 감사

### Step 1. Study 진입 — 주의 필요

화면에는 76개 글, 12개 주제, 검색, 개인 학습 지도, 프로젝트 검증 경로가 함께 등장한다. 자료를 찾는 기능은 풍부하지만 “지금 무엇 하나를 배울지”를 정하는 부담이 크다. 학습 지도와 프로젝트 경로도 같은 무게의 큰 패널로 나란히 보여 첫 행동이 선명하지 않다.

강점은 검색과 분류가 첫 화면에 있고, 학습 순서와 프로젝트 연결이라는 두 목적이 드러난다는 점이다. 가장 작은 개선은 검색 위나 제목 아래에 “오늘 답할 질문” 하나를 보여주는 것이 아니라, 먼저 각 글의 기존 요약을 목록과 상세에서 충분히 읽히게 해 현재 선택 구조만으로 시작할 수 있는지 확인하는 것이다.

### Step 2. 상세 진입 — 주의 필요

제목과 비유는 이미 흥미롭다. “롤백해도 안 되돌아가는 것들”과 택배 비유는 새 인스타식 훅을 만들 필요가 없다는 반례다. 그러나 MDX의 `summary`는 메타데이터에만 쓰이고 상세 화면에는 전달되지 않는다. 사용자는 제목 다음에 바로 긴 본문으로 들어간다.

상세 첫 화면에는 다음 네 가지가 필요하다.

1. 한 문장 답 또는 기존 요약
2. 이 글을 읽고 답할 질문 하나
3. 정답이 성립하는 최소 조건
4. 원문, 프로젝트 사례, 코드 증거로 바로 가는 링크

예측 질문은 선택 사항이어야 한다. 퀴즈를 풀어야 본문이나 증거를 볼 수 있는 구조는 만들지 않는다.

### Step 3. 다이어그램과 결과 — 개선 필요

롤백 글의 처리 흐름은 여섯 노드가 세로로 이어져 864×726 화면을 넘는다. 사용자는 그림의 앞부분을 기억한 채 아래로 내려가야 하며, 정작 어떤 변경이 롤백되고 무엇이 남는지 보여주는 결과표는 다음 화면에 있다. 확대 기능과 가로 스크롤은 이미 구현돼 있으므로 확대 버튼을 더 만드는 것은 해결책이 아니다.

다이어그램은 다음 규칙으로 편집한다.

- 그림이 답할 질문을 바로 위에 한 문장으로 적는다.
- 구성요소 관계와 시간 순서를 같은 화살표 표현으로 섞지 않는다.
- 주문 ID, eventId, 재고 값처럼 추적할 값을 모든 장면에서 유지한다.
- 화살표에 `저장`, `승인`, `실패`, `재시작`, `재수신`처럼 사건을 적는다.
- 바뀐 값과 그대로 남은 값을 같은 장면에 보여준다.
- 정상, 실패, 복구를 한 그림에 몰아넣지 않는다.
- 그림 바로 아래에 최종 결과를 한 문장이나 작은 표로 붙인다.
- 노드 수나 한 화면을 절대 규칙으로 삼지 않고 실제 화면에서 그림과 결론을 오가야 하는지 확인한다.

전체 인과 흐름을 보존할 필요가 있으면 전체 그림을 심화 영역에 함께 둔다.

## 콘텐츠 근거

76개 Study MDX는 마크업과 frontmatter를 포함해 평균 약 4,573자다. 가장 긴 글은 약 16,851자이며 코드 블록이 39개다. 반면 N+1 글처럼 핵심 설명, 실제 사례, 해결의 세 절로 끝나는 짧은 글도 있다. 따라서 모든 글이 길어서 안 읽힌다고 일반화할 수 없다.

대표적인 문제 유형은 세 가지다.

| 유형 | 관찰 | 개편 방향 |
|---|---|---|
| 선택 과부하 | 76개 글과 12개 분류, 지도와 프로젝트 경로가 함께 등장 | summary와 대표 질문으로 선택 근거 강화 |
| 백과사전형 장문 | 재고 동시성 글은 약 11,470자이고 선수 개념 7개 뒤에 본문 11절이 이어짐 | 한 번에 판단할 질문별로 학습 경로 재배치 |
| 그림과 결론 분리 | 롤백 글의 세로 흐름과 결과표가 서로 다른 화면에 있음 | 사건, 상태 변화, 결과를 같은 학습 단위로 묶기 |

Cache Stampede 글은 이미 문제형 제목, 비유, Mermaid 다섯 개가 있다. 새 훅보다 같은 현상을 텍스트, 그림, 정의로 반복하는 순서와 조건 배치를 고치는 편이 낫다. Kafka 글은 Producer, Topic, Partition, Consumer, DB, Offset을 초반에 동시에 소개한다. 비동기 기초 글의 첫 그림은 개념 목차를 화살표로 연결해 실행 순서처럼 보일 위험이 있다.

## 인스타 계정에서 가져올 것

Instagram 네 프로필은 공개 페이지 접근이 안정적이지 않아 각 계정의 게시물 구조를 모두 직접 검증하지 못했다. 확인하지 못한 계정의 스타일이나 제작 파이프라인은 단정하지 않는다.

[게으른 빌더 공식 사이트](https://lazyowen.com/)에서는 다음 패턴을 확인했다.

- 독자가 겪는 문제를 짧게 제시한다.
- 바로 실행할 수 있는 복사 가능한 예시를 준다.
- 단계와 예상 시간을 먼저 보여준다.
- 긴 설명은 순서가 있는 가이드와 챌린지로 연결한다.

포트폴리오에는 이 패턴을 그대로 복제하기보다 `짧은 문제 → 예상 → 사건과 결과 → 원문과 증거`로 번역한다. 인스타 말투와 장식, 매일 발행 빈도를 목표로 삼지 않는다.

## 학습 콘텐츠 설계

### 상세 첫 화면

```text
제목
한 문장 답: DB 롤백은 같은 트랜잭션의 DB 변경만 되돌린다.

읽고 답할 질문
결제 승인 뒤 주문 저장이 실패하면 무엇이 남을까?

최소 조건
하나의 DB 트랜잭션과 별도 외부 결제 시스템을 사용한다.

[예상해 보기]  [바로 본문 읽기]  [실제 적용 근거]
```

### 본문 학습 단위

```text
상황 → 결과를 먼저 예상 → 같은 ID와 값으로 사건 진행
     → 바뀐 값과 남은 값 확인 → 왜 그런지 설명
     → 조건 또는 반례 하나 → 선택형 확인 문제
```

확인 문제는 점수를 매기기 위한 시험이 아니라 기억에서 답을 꺼내게 하는 장치다. 원문과 프로젝트 증거는 언제든 바로 열 수 있어야 한다.

### 추천 표현 세 가지

| 표현 | 어울리는 내용 | 예시 |
|---|---|---|
| 전후 상태 | 값이 어떻게 달라지는가 | 재고 1에서 두 요청이 동시에 읽은 뒤 최종 값 |
| 사건 타임라인 | 순서와 실패 시점이 중요한가 | DB 반영, 장애, 재시작, 같은 eventId 재수신 |
| 대안 비교 | 선택 기준과 비용이 중요한가 | 비관적 락, 낙관적 락, Redis 분산 락 |

모든 글을 같은 장수의 카드로 강제하지 않는다. 정적 전후로 설명되지 않는 상태 변화 주제에서만 작은 시뮬레이터를 검토한다.

## 첫 파일럿

구조가 다른 세 글을 고른다.

1. Cache Stampede: 중간 길이, 비유와 그림이 이미 많은 글
2. 재고 동시성: 긴 비교형 글
3. N+1: 짧은 실제 사례형 글

세 글에서 아래 세 안을 비교한다.

| 안 | 변경 |
|---|---|
| A | 현재 화면 유지 |
| B | 기존 summary를 상세 첫 화면에 노출하고 문장만 다듬음 |
| C | summary와 함께 질문, 사건, 결과, 선택형 확인 문제까지 재편 |

검증 질문은 다음과 같다.

- 처음 훑은 뒤 이 글이 답하는 질문을 말할 수 있는가.
- 그림을 보고 최종 값과 이유를 설명할 수 있는가.
- 조건 하나를 바꾼 새 사례에도 답할 수 있는가.
- 다음 날 핵심 내용을 자기 말로 회상할 수 있는가.
- 프로젝트 증거를 찾는 독자가 학습 UI에 막히지 않는가.

조회 수, 완독률, 발행 개수는 보조 지표다. 이 개편의 핵심 성공 기준은 본인이 다시 찾아 읽고 설명할 수 있는지다.

## 자동화 설계

자동화는 게시보다 초안과 검수부터 시작한다.

```text
기존 MDX 선택
  → 질문 하나와 핵심 주장 추출
  → 사건 예시, 최소 조건, 회상 질문 초안 생성
  → 원문 섹션과 공식 근거 대조
  → 로컬 미리보기
  → 사람 검수
  → 기존 Git과 배포 흐름으로 반영
```

초기에는 새 CMS, 카드 스키마, source hash 시스템을 만들지 않는다. 기존 MDX와 Git diff로 세 글을 관리할 수 있다. 파생 콘텐츠가 늘어나 원문 변경 누락이 실제로 발생할 때 source hash와 stale 표시를 도입한다.

자동 생성 규칙은 다음을 지킨다.

- 학습 중인 권고를 구현 완료나 성능 개선 성과로 바꾸지 않는다.
- 측정하지 않은 수치를 만들지 않는다.
- 정답이 성립하는 서버 수, 동시성, 데이터 상태 같은 조건을 보존한다.
- 핵심 주장 하나는 공식 문서와 교차 확인한다.
- 작성자의 “내가 헷갈렸던 점”은 사실이 있을 때만 사용한다.
- AI 생성물만으로 검수와 게시를 끝내지 않는다.

SNS 자동 게시, 로그인 기반 진도, 간격 반복, 개인화, 전용 카드 스키마, 모든 글의 source hash는 파일럿 이후로 보류한다. 76편 일괄 변환, 원문 삭제, 퀴즈 통과 전 본문 잠금, Mermaid 확대 기능 중복 구현은 제외한다.

## 네 차례 모의 토론에서 바뀐 판단

`career-debate`의 MBTI 관점은 실제 성격 진단이나 실제 채용 담당자 의견이 아니라 반론을 강제로 만드는 모의 렌즈로 사용했다.

| 초기 아이디어 | 최종 판단 |
|---|---|
| 인스타식 질문 카드층을 기본 추가 | 기존 summary와 본문 흐름부터 개선 |
| 세 가지 카드 포맷을 바로 구축 | 기존 편집으로 부족할 때 선택 실험 |
| 퀴즈로 시작 | 선택 사항, 본문과 증거 바로 접근 |
| 원문 변경 감지 자동화부터 구축 | 세 글은 Git diff로 검수, 반복 누락이 생기면 자동화 |
| 모든 그림을 짧게 분할 | 사건과 결과의 근접성을 높이되 전체 인과 보존 |
| 한 개념을 한 화면에 고정 | 기술적 조건과 설명 흐름을 우선 |

남은 이견도 있다. summary만 보여줘도 충분하다는 의견과 새로운 예측 경험이 있어야 다시 찾는다는 의견은 아직 모두 가설이다. A, B, C 파일럿으로 판단한다.

## 조사 근거와 한계

- [개발자 포트폴리오 작성 가이드](C:/career-data/career-writing-guides/02-portfolio/developer-portfolio.md)는 포트폴리오의 역할을 문제, 판단, 검증 근거로 본다. 로컬 경로 밖의 문서이므로 이 보고서 링크는 환경에 따라 열리지 않을 수 있다.
- [Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/)는 처음에는 핵심 선택을 보여주고 심화 내용을 뒤에 제공하는 원칙의 참고 자료다.
- [Retrieval Practice](https://www.retrievalpractice.org/retrievalpractice/)는 다시 읽기만 하는 대신 기억에서 답을 꺼내는 활동을 학습 전략으로 설명한다.
- [Carnegie Mellon의 multiple means](https://www.cmu.edu/teaching/designteach/teach/classroomclimate/strategies/multiplemeans.html)는 텍스트, 이미지, 다이어그램 등 여러 표현 수단을 학습 목표에 맞춰 사용하도록 권한다.
- [Anthony Sistilli의 개발자 포트폴리오 리뷰](https://www.youtube.com/watch?v=rWB0cQRcLWs)는 긴 텍스트 덩어리와 숨은 탐색의 피로를 보조 근거로 사용했다. 학습 효과를 검증한 영상은 아니다. 영상은 watch의 Gemini 관찰이며 실시간 조회 수는 직접 검증하지 않았다.
- [Tech with Tim의 학습 영상](https://www.youtube.com/watch?v=3E0dqwQwX4k)은 구체 목표, 직접 문제 해결, 학습과 적용의 반복을 보조 근거로 사용했다. 제품 홍보 맥락이 있어 독립적인 학습 연구로 취급하지 않았다.

감사는 데스크톱 864×726 화면과 현재 소스 코드를 기준으로 했다. 모바일 캡처는 도구 사용 한도 때문에 완료하지 못했다. 스크린샷만으로 키보드 탐색, 스크린 리더 읽기 순서, 색 대비의 전체 적합성을 확정하지 않았다. 코드에는 Mermaid 확대의 키보드 진입과 포커스 스타일이 있으나 실제 보조기기 테스트가 필요하다.
