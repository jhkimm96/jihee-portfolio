# Study 게시와 학습 로드맵 개편 설계

## 1. 목표

Study를 긴 기술 문서 모음이 아니라, 비전공자도 질문 하나를 짧게 이해하고 다음 개념으로
이동할 수 있는 학습 경로로 개편한다.

콘텐츠 개수 자체는 제한하지 않는다. 각 콘텐츠가 요구하는 이해 부담을 줄이고, 로드맵이
선수 개념과 다음 개념의 순서를 책임지게 한다.

> Study는 질문 하나를 짧게 이해시키고, 로드맵은 그 질문들이 지식으로 쌓이는 순서를 설명한다.

## 2. 현재 확인된 문제

### 2.1 장문 Study가 여러 질문을 한 파일에 담고 있다

- `async-event-processing-foundations.mdx`: 731줄, 주요 절 11개
- `kafka-offset-lag-reprocessing-idempotency.mdx`: 577줄, 주요 절 11개
- `stock-concurrency-control.mdx`: 439줄, 주요 절 11개

세 파일은 조사와 게시가 완료된 자료지만, 독자가 한 번에 읽기에는 한 편의 Study보다 여러
학습 단위를 합친 장에 가깝다.

### 2.2 다이어그램이 두 번째 긴 글처럼 작동한다

노드가 많고 기술 용어가 그대로 들어간 다이어그램은 비전공자에게 쉬운 설명이 아니라 해석해야
하는 압축 문서가 된다. 그림과 최종 결과가 멀리 떨어져 있으면 독자는 앞 장면을 기억하며
스크롤해야 한다.

### 2.3 현재 로드맵은 분류와 수동 정렬에 가깝다

현재 `lib/study-roadmap.ts`는 다섯 단계와 카테고리별 slug 배열로 구성되어 있다. 선수 관계,
각 글에서 얻는 답, 다음 글로 이어지는 이유를 표현하지 않는다. 목록에 없는 새 글은 사실상
끝에 배치되므로 학습 순서를 보장하지 못한다.

### 2.4 Codex와 Claude 게시 스킬이 서로 어긋나 있다

Codex와 Claude의 `publish` 및 `publish-study` 규칙이 동일하지 않다. Study 작성 규칙도 라우터와
하위 스킬에 중복되어 있어 한쪽만 수정될 수 있다.

### 2.5 게시 승인과 민감정보 확인이 반복된다

현재 스킬과 평가 시나리오는 초안 승인 뒤에도 사용자가 체크리스트에 직접 `없음`이라고 답해야
진행하도록 강제한다. 여러 Study를 개편할 때 같은 확인이 파일마다 반복된다.

## 3. 설계 원칙

### 3.1 한 콘텐츠는 핵심 질문 하나를 다룬다

한 Study에는 독자가 읽고 답할 핵심 질문 하나를 둔다. 하나의 제목 아래 독립적인 질문이 여러
개라면 다음 중 하나를 선택한다.

1. 기존 글을 장 개요로 유지하고 짧은 Study로 분리한다.
2. 이미 존재하는 Study와 연결한다.
3. 같은 답을 반복하는 절은 합치거나 제거한다.

글 수를 줄이기 위해 서로 다른 질문을 한 파일에 합치지 않는다. 반대로 짧게 보이기 위해 하나의
인과관계를 의미 없이 잘게 쪼개지도 않는다.

### 3.2 스크롤 한 번에 이해 단위 하나를 배치한다

고정 높이 또는 강제 scroll snap을 사용하지 않는다. 화면 크기와 접근성을 해치지 않으면서 다음
편집 리듬을 만든다.

```text
상황 → 사건 → 결과 → 이유
```

각 단위는 주장 하나를 다룬다. 같은 내용을 문단, 표, 다이어그램, 결론에서 반복하지 않는다.
이미 예시나 그림으로 전달한 내용은 결과 한 문장만 덧붙인다.

### 3.3 필수 용어는 본문에서 설명한다

처음 나오는 핵심 용어는 다음 순서로 설명한다.

1. 쉬운 말
2. 현재 예시에서 하는 역할
3. 기술 용어

이 설명을 모르면 다음 장면을 이해할 수 없는 경우 본문에 둔다. 구현 변형, 엄밀한 정의, 선택적
배경처럼 없어도 흐름을 따라갈 수 있는 내용만 `<details>` 토글에 둔다. 토글을 열지 않으면
본문을 이해할 수 없는 구조는 허용하지 않는다.

### 3.4 다이어그램은 장면 하나만 설명한다

- 다이어그램 하나는 질문 하나에만 답한다.
- 정상, 실패, 복구를 한 그림에 몰아넣지 않는다.
- 화살표에는 `요청`, `저장`, `실패`, `재시도`처럼 사건을 적는다.
- 요청 수, 재고 값, `eventId`처럼 추적할 값을 다음 장면에서도 유지한다.
- 그림 바로 아래에 최종 결과를 한 문장 또는 작은 표로 붙인다.
- 문장보다 그림이 복잡하면 그림을 제거한다.
- 전체 구조가 꼭 필요할 때만 심화 토글에 큰 그림을 둔다.

## 4. 공통 게시 계약

Codex와 Claude가 함께 읽을 수 있도록 포트폴리오 저장소에 공통 계약을 둔다.

예정 파일:

- `docs/publishing/publish-contract.md`
- `docs/publishing/study-content-contract.md`

`publish-contract.md`는 모든 게시 유형의 승인 범위, 민감정보 검사, 간결성, 근거 확인, 검증과
커밋 규칙을 담당한다. `study-content-contract.md`는 Study 구조, 비전공자 설명, 다이어그램,
로드맵 배치와 기존 글 분할 규칙만 담당한다.

각 스킬에는 공통 규칙을 복사하지 않는다. 필요한 계약을 읽어야 하는 시점과 해당 스킬만의
차이만 남긴다.

## 5. 승인 흐름

### 5.1 단일 게시

```text
근거 확인
→ 제목·핵심 질문·한 줄 답·변경 파일을 포함한 초안 제시
→ 사용자 승인
→ 승인 범위 안에서 파일 작성
→ 민감정보 자동 검사
→ 렌더링과 빌드 검증
→ 승인된 경우에만 커밋
```

### 5.2 여러 Study의 단계별 개편

로드맵 한 구간의 제목, 질문, 한 줄 답, 기존 글 처리 방식과 대상 파일을 한 번에 제시한다.
사용자의 승인은 표에 명시된 파일과 주장에 적용된다. 승인 범위 안에서 각 파일마다 같은 질문을
반복하지 않는다.

다음 상황에서는 다시 확인한다.

- 승인한 핵심 주장이나 파일 수가 바뀐다.
- 기존 글을 삭제하거나 URL을 변경해야 한다.
- 기존 글의 결론을 뒤집는 근거가 발견된다.
- 민감정보 후보를 일반화하면 글의 의미가 달라진다.
- Learning Path 또는 프로젝트 문서를 승인 범위 밖에서 수정해야 한다.

## 6. 민감정보 자동 검사

모든 Codex 및 Claude `publish-*` 스킬에 같은 정책을 적용한다.

검사 범위:

- 게시 초안과 생성·수정할 콘텐츠 파일
- 이번 게시와 관련된 Git diff
- 글의 근거로 직접 인용한 설정, 코드, 문서

검사 항목:

- 회사나 조직 실명 중 공개가 확인되지 않은 이름
- 내부 도메인과 비공개 URL
- DB 자격증명, API 키, 토큰, Secret
- 팀원과 고객의 실명
- 고객사명과 미공개 사업 정보
- 운영 식별자, 내부 IP, 접근 경로처럼 결합 시 위험한 정보

처리 방식:

1. 문자열 패턴과 문맥을 함께 검사한다.
2. 명백한 민감정보는 글에서 제외하거나 일반화하고 다시 검사한다.
3. 후보가 없으면 사용자 확인 없이 통과한다.
4. 일반화가 사실관계나 기여 범위를 바꾸는 애매한 후보만 사용자에게 묻는다.
5. 발견한 Secret 원문을 채팅이나 보고서에 그대로 출력하지 않는다.
6. 검사 범위와 결과를 최종 보고에 남긴다.

저장소 전체를 게시마다 무차별 검사하지 않는다. 이번 글과 실제로 연결된 파일을 검사해 오탐과
불필요한 지연을 줄인다.

## 7. 스킬 개편 범위

두 에이전트의 아래 스킬을 같은 계약에 맞춘다.

### Codex

- `publish`
- `publish-study`
- `publish-troubleshooting`
- `publish-decision`
- `publish-reviews`
- `publish-quality`

### Claude

- `publish`
- `publish-study`
- `publish-troubleshooting`
- `publish-decision`
- `publish-reviews`
- `publish-quality`

`publish`는 근거 분류와 하위 스킬 선택만 담당한다. Study의 구조와 다이어그램 규칙은
`publish-study`와 공통 Study 계약에서만 관리한다.

각 하위 스킬은 공통 게시 계약을 따른 뒤 기록 유형에 필요한 고유 구조만 추가한다. Study의
학습 템플릿을 Decision, Troubleshooting, Review, Quality에 억지로 적용하지 않는다.

## 8. Study 콘텐츠 계약

새 Study와 개편 대상 Study는 다음 질문에 답해야 한다.

- 이 글이 답하는 질문은 하나인가?
- 첫 화면에서 한 줄 답을 알 수 있는가?
- 답이 성립하는 최소 조건이 보이는가?
- 예시의 값과 사건을 끝까지 추적할 수 있는가?
- 결과와 이유가 가까이 있는가?
- 비전공자가 모를 필수 용어를 본문에서 설명했는가?
- 적용되지 않는 조건 또는 실패 경계가 있는가?
- 기억에서 답을 꺼내는 확인 질문이 있는가?
- 선수 개념과 다음 Study가 정해졌는가?

모든 항목을 같은 제목으로 강제하지 않는다. 글의 주제에 따라 자연스러운 소제목을 사용하되,
핵심 질문, 한 줄 답, 구체적인 사건과 결과, 회상 질문은 반드시 제공한다.

### 8.1 모든 Study는 초안 작성 시점에 웹과 프로젝트 근거를 조사한다

새 Study를 작성하거나 기존 Study의 핵심 내용을 개편할 때 모델의 기억과 기존 글만으로 쓰지
않는다. 실제 오늘 날짜를 확인하고 Google·Naver 등 일반 검색, 공개 기술 블로그, 공개 SNS와
영상 자료, 공식 문서, 현재 프로젝트의 코드·설정·테스트를 함께 조사한다.

자료의 역할을 구분한다.

- Google·Naver 검색은 다양한 공식 자료와 설명 자료를 발견하는 입구로 사용한다.
- Instagram·YouTube·공개 SNS는 독자가 어려워하는 지점, 쉬운 비유와 콘텐츠 전개 방식을
  참고하는 데 사용한다.
- 기술 블로그와 공개 장애 사례는 실제 적용 조건, 흔한 실수와 조사할 쟁점을 찾는 데 사용한다.
- 공식 문서, 명세, 릴리스 노트와 공식 구현 소스는 기술적 사실과 현재 지원 상태를 확인하는
  기준으로 사용한다.
- 프로젝트 코드, 설정, 테스트, 이슈와 PR은 포트폴리오에 적을 실제 사용 여부와 기여 범위를
  확인하는 기준으로 사용한다.

블로그나 SNS에서 발견한 내용을 사실로 바로 옮기지 않는다. 핵심 기술 주장은 1차 자료나 실제
프로젝트 근거로 다시 확인한다. 설명 방식은 참고할 수 있지만 문장, 이미지와 구성을 복제하지
않고 새 예시와 표현으로 작성한다. 로그인이 필요한 비공개 게시물이나 접근할 수 없는 자료를
본 것처럼 쓰지 않는다.

버전, 지원 상태, 권장 구성, 보안 기본값, API와 운영 방식이 바뀔 수 있는 기술은 과거 Study만으로
작성하지 않는다. 초안을 만들 때 최신 공식 자료와 릴리스 노트를 다시 확인한다.

근거는 다음 순서를 우선한다.

1. 공식 명세와 표준
2. 프로젝트가 실제 사용하는 버전의 공식 문서
3. 현재 최신 안정 버전의 공식 문서와 릴리스 노트
4. 공식 구현 저장소와 마이그레이션 가이드
5. 논문 또는 기술을 만든 조직의 자료
6. 신뢰할 수 있는 보조 자료

검색 결과는 다음 기준으로 사용한다.

- 기술 검색의 핵심 주장은 공식 문서, 명세, 릴리스 노트처럼 1차 자료로 확인한다.
- 프로젝트가 사용하는 버전과 최신 안정 버전을 각각 명시한다.
- 최신 버전의 기능을 현재 프로젝트에 이미 적용된 것처럼 쓰지 않는다.
- deprecated, removed, experimental, preview 상태를 구분한다.
- 날짜가 중요한 주장은 조사 기준일과 확인한 버전을 남긴다.
- 중요한 외부 근거는 독자가 다시 확인할 수 있도록 본문 가까이에 출처를 연결한다.
- 공식 자료끼리 표현이 다르면 확인된 범위와 불확실성을 본문에 밝힌다.
- 최신이라는 이유만으로 기존 선택을 낡았다고 단정하지 않고 호환성, 운영 조건과 전환 비용을
  함께 설명한다.
- 기존 Study를 보완할 때도 변동 가능성이 있는 핵심 주장만 다시 조사하고, 안정적인 기초 개념을
  불필요하게 전면 재작성하지 않는다.

공식 자료를 찾지 못했거나 현재 버전을 확인할 수 없으면 추측으로 채우지 않는다. 확인하지 못한
범위를 표시하고, 그 내용이 글의 핵심이면 초안 승인을 요청하기 전에 조사를 보완한다.

## 9. 로드맵 구조

### 9.1 내부 편집 로드맵

아직 작성하지 않은 내용까지 관리하는 내부 문서다.

- `게시됨`: 독립 MDX와 근거가 확인됨
- `부분 포함`: 장문 Study 안에 있지만 독립 학습 단위가 아님
- `미작성`: 공부할 개념 목록에만 있음
- `개편 필요`: 게시됐지만 새 콘텐츠 계약을 충족하지 않음
- `학습 단위 완료`: 새 계약과 실제 화면 검증을 통과함

날짜 계획, 분리 후보, 중복 후보와 다음 작업 순서는 내부 로드맵에서 관리한다.

### 9.2 공개 학습 로드맵

실제로 열어 읽을 수 있는 Study만 보여준다. 미작성 주제를 작성된 것처럼 노출하거나 빈 링크를
만들지 않는다.

각 노드는 다음을 보여준다.

- 독자가 답할 질문
- 읽은 뒤 얻을 한 줄 답
- 선수 Study
- 다음 Study
- 관련 프로젝트 적용 근거

개인 완료율, 공개 일정과 학습 진도는 넣지 않는다.

### 9.3 콘텐츠 메타데이터

기존 76개 파일을 한 번에 수정하지 않도록 필드는 점진적으로 도입한다.

- `question`: 이 Study가 답하는 핵심 질문
- `prerequisites`: 먼저 읽을 Study slug 목록

기존 `summary`는 읽은 뒤 얻을 한 줄 답으로 우선 재사용한다. 다음 글은 공개 로드맵 순서에서
계산해 중복 저장하지 않는다.

새 필드는 처음에는 선택 사항으로 추가하고, 새 글과 개편한 글에는 필수로 적용한다. 모든 기존
파일의 마이그레이션이 끝난 뒤 스키마 필수화 여부를 결정한다.

## 10. 기존 장문 Study의 보존과 분할

기존 URL, 작성일과 커밋 기록을 보존한다.

1. 기존 장문을 해당 주제의 장 개요로 유지한다.
2. 이미 독립 Study가 있는 내용은 링크하고 중복 글을 만들지 않는다.
3. 독립 질문이 충분한 절만 새 Study 후보로 분리한다.
4. 개요는 전체 관계와 읽는 순서를 설명하고 세부 구현은 짧은 Study로 보낸다.
5. 기존 글을 단번에 비우지 않고, 분리된 Study가 검증된 뒤 중복 절을 줄인다.

현재 완료된 세 장문은 다음 로드맵 구간의 근거 자료로 사용한다.

- 비동기 이벤트 처리
- Kafka 소비 흐름
- DB 동시성 제어

로그와 관측성, 장애 전파 방지, 배포와 운영, 정산과 배치, 이후 심화 목록은 작성된 콘텐츠로
간주하지 않고 내부 로드맵의 `미작성` 상태로 관리한다.

## 11. 첫 파일럿

### 11.1 Cache Stampede

이미 제작한 B안의 짧은 진입부와 C안의 학습 흐름을 결합한다.

- 한 줄 답과 핵심 질문
- 서버 수, 요청 수와 캐시 만료 조건
- 같은 값을 유지하는 짧은 사건 장면
- DB 호출 수와 연결 풀 결과
- Single Flight 적용 전후
- 적용 범위와 반례
- 조건을 바꾼 회상 질문

관련 선수 글과 다음 글을 포함하는 작은 공개 로드맵 구간도 함께 구현한다.

### 11.2 범용성 검증

- `stock-concurrency-control.mdx`: 비교가 많은 장문에서도 분할 원칙이 작동하는지 확인
- `n-plus-one-problem.mdx`: 짧은 사례형 글을 불필요하게 늘리지 않는지 확인

파일럿이 통과하기 전에는 76편 일괄 변환을 하지 않는다.

## 12. 성공 기준

- 첫 화면만 보고 글의 질문과 한 줄 답을 말할 수 있다.
- 30초 동안 훑은 뒤 사건의 최종 결과를 설명할 수 있다.
- 다이어그램과 결과를 찾기 위해 여러 화면을 오가지 않는다.
- 필수 기술 용어는 토글을 열지 않아도 이해할 수 있다.
- 조건이 바뀐 사례에 자기 말로 답할 수 있다.
- 로드맵에서 이 글을 왜 지금 읽는지와 다음 글을 알 수 있다.
- 긴 글을 줄이는 과정에서 공식 조건, 수치와 프로젝트 사실이 사라지지 않는다.
- 승인한 여러 파일을 처리할 때 동일한 승인과 민감정보 질문을 반복하지 않는다.

조회 수, 글 수와 완독률은 보조 지표다. 핵심은 사용자가 다시 찾아 읽고 설명할 수 있는지다.

## 13. 검증

### 제품 코드

- 로드맵에 중복 slug와 존재하지 않는 slug가 없는지 테스트한다.
- 선수 관계가 자기 자신을 참조하거나 순환하지 않는지 검사한다.
- 기존 Study는 새 선택 필드가 없어도 빌드되어야 한다.
- 상세 상단과 이전·다음 탐색을 데스크톱 및 390px 화면에서 확인한다.
- 키보드로 토글, 링크와 로드맵을 탐색할 수 있어야 한다.
- `npm test`, `npx tsc --noEmit`, `npm run build`를 통과한다.

### 스킬

- 각 변경 스킬의 frontmatter와 링크를 검증한다.
- Codex와 Claude의 공통 계약 참조가 같은지 확인한다.
- 민감정보 후보가 없으면 자동 통과하는 시나리오를 검증한다.
- Secret 후보는 값을 노출하지 않고 중단하는지 검증한다.
- 애매한 고객사명은 사용자 확인으로 보내는지 검증한다.
- 장문 Study 요청이 여러 질문으로 분리되어 제안되는지 검증한다.
- 단계별 승인 후 같은 확인을 파일마다 반복하지 않는지 검증한다.
- 최신 기술 주제가 기존 기억만으로 작성되지 않고 공식 자료 검색을 거치는지 검증한다.
- 새 Study가 공식 자료, 설명 자료와 프로젝트 근거를 목적에 맞게 조사했는지 검증한다.
- 블로그나 SNS의 주장을 검증 없이 기술적 사실로 사용하지 않는지 검증한다.
- 프로젝트 사용 버전과 최신 안정 버전을 혼동하지 않는지 검증한다.
- deprecated, removed, experimental 상태를 근거 없이 현재 권장 방식으로 쓰지 않는지 검증한다.

## 14. 구현 순서

1. 공통 게시 계약과 Study 콘텐츠 계약 작성
