# 내부 Study 편집 로드맵 — 진행 중

기준일: 2026-10-07. 공개 학습 순서의 확정본이 아니다. 79편 구조 집계, 79편 본문 검토를
바탕으로 우선순위 후보를 기록했다. 본문 읽기는 완료했으며 기술 근거 재검증과 화면 검증은 별도다.
미검토 글을 내용 부족·완료로 자동 판정하지 않는다. 아직 글을 수정하거나 새 글을 게시하지 않았다.

## 다음 실행 순서

1. 완료: 79편의 본문을 읽고 유지/설명 보완/근거 보완/개요·분리 후보를 기록했다.
   다음은 아래 우선 후보의 공식 자료·프로젝트 근거 검증이다. 글 길이만으로 전면 재작성하지 않는다.
2. N+1·재고·데드락의 시각 장면 보완 범위를 확정한다. 기존 비교표를 모두 그림으로 바꾸지 않는다.
   코드와 핵심 설명의 분리, 모바일에서 장면·결과가 함께 읽히는지 검증한다.
3. 선수 글의 오류·과도한 단정 후보를 공식 자료와 실제 프로젝트 근거로 확인한다.
   판정 후보를 확인된 오류처럼 취급하지 않는다. 기존 핵심 결론이 달라지는 경우 게시 범위를 다시 확인한다.
4. 독립 글과 장문 개요의 중복을 대조하고, 공개 로드맵 변경 범위를 제안한다.
5. 사용자의 미작성 CS 계획을 기존 글에 포함/별도 글 필요/미작성으로 대조한다.
   구조 집계의 키워드 등장만으로 학습 내용이 충분하다고 판정하지 않는다.
6. 승인한 작은 구간부터 기존 글을 개편하고 미작성 글을 조사·작성한다.

## 시각화 편집 후보

### 전체 본문 확인 후 추가한 우선 근거 후보

- 검색 선수 글: nori의 실제 토큰 출력, query/filter 캐시 조건, should 기본 일치 조건부터 확인한다.
  이후 RRF의 원시 코사인/ES 점수 구분과 양자화의 탐색 메모리/전체 디스크 비용을 확인한다.
- 프로젝트 검색 현황: 8/4 종합 글과 후속 Jina 글의 후보 수·최종 재조회·정렬 정책을 같은 코드
  기준으로 대조한다. 서로 다른 시점의 설계를 동시에 현재 구현이라고 쓰지 않는다.
- Outbox/Inbox: 키가 있다는 사실만으로 자연 멱등을 판정하지 않는다. unique/upsert와 업무 반영의
  트랜잭션 경계를 확인한다. 'product만 Inbox 필요'라는 제목은 같은 글의 order 표와 대조한다.
- 영상 실험 수치: 비동기 처리량, filesort, 연결 풀, graceful shutdown, Redis, 복제 지연, 타임존의
  수치들은 실험 환경·출처를 다시 확인한다. 내 프로젝트 측정처럼 쓰지 않는다.
- 보안 전환 글: 부분 인증 설정 시 무인증 연결은 당시 구현 사실과 권장 정책을 분리한다.
  bootstrap 예외와 API key 전환 순서는 공식 자료를 먼저 확인한다.
- Kafka 버전: 글의 '최신 4.3.1/4.1.1' 주장과 링크의 실제 버전을 확인한다.
  최신 문서 확인과 프로젝트 버전 적용 여부는 별개로 기록한다.

### 중복과 학습 진입 후보

- 역색인: CS 용어 구분 글과 ES 진입 글의 상품3개 예시를 재사용하고 역할을 나눈다.
- 캐시: TTL/eviction → stampede → 중복 진단 → single-flight → 공유 작업 취소를 대조한다.
- 데이터 지연: 트랜잭션 경계 → 이벤트 발행/Outbox → 소비 위치 → 멱등 재처리 → 관측으로 연결한다.
- 검색: 같은 상품명이 어떤 토큰으로 저장되는지 → 조건으로 거르기 → 점수/순위 → 두 후보 병합
  → 최종 재평가를 짧은 단위로 연결한다. 종합 글은 각 단계의 입구로 유지한다.
- 두 MSA 학습 지도는 '기술 학습 순서'와 '프로젝트 업무 여정'으로 역할을 구분한다.
  모든 서비스·PR을 본문에서 한 번에 외우게 하지 않는다.

새 글 분리 수와 공개 순서는 아직 확정하지 않았다. 먼저 기존 독립 글에 연결할 수 있는지 확인한다.

- N+1: 상품 목록 → 판매자별 조회 → 묶은 조회 전후. 표는 방법 비교에 사용.
- 재고: 재고1의 두 읽기와 두 저장 → 조건부 차감의 대기/재검사. 비교표는 선택 기준용으로 유지.
- 데드락: 잠금 소유와 대기 방향의 고리 → 동일 잠금 순서의 단계 장면.
- 커넥션 풀: 연결 두 개를 빌림/반납 → 다음 요청의 대기. 풀 크기를 크게 만들기 전 무엇을 측정할지 연결.
- Java 진입부: 입력값 하나의 생성/참조/변경/반환. DTO/Port 등 추상 박스를 값 그림 대신 먼저 넣지 않음.

## 이번 묶음에서 추가한 선수 관계 후보

공개 로드맵에 적용한 순서가 아니라, 본문 검토로 발견한 연결 후보다. 선수 관계 전체의 순환은
현재 공개 모델과 대조한 뒤 확정한다.

- Java: 기본형/참조형 → 값과 참조복사 → 동일성/동등성 → 컬렉션 → HashMap → equals/hashCode → 실제 검색순위
- 메모리: 객체 도달가능성 → heap 회수와 OS 반환 → 파일 업로드 저장 경로
- JPA: ORM → 영속성 컨텍스트와 fetch → N+1 → Specification/페이지 조회
- 배포: Docker 이미지/멀티스테이지 → Kubernetes 배치/교체 → Service 연결 → 저장소/설정
- 버전 관리: 공개 버전 유지 → 관리자 승인 교체 → 요청 ID와 대표 버전의 관계

같은 값의 전후 그림이 이미 좋은 Java 글은 유지·보완하고 새 템플릿으로 전면 재작성하지 않는다.

## 새 CS 계획 — 대조 대기

로그·메트릭·트레이싱부터 공부하려던 계획은 보존한다. 기존 ES 글에는 이벤트 수집 경로와 집계가
있고, 백엔드 학습 지도에는 관측 신호의 개요가 있다. 이것만으로 각 도구의 사용·진단 학습이
완성됐다고 보지 않는다. 다음 단계에서 아래 주제별 포함/보완/독립 글 필요를 대조한다.

1. 로그·관측성
2. 장애 전파 방지
3. 배포·운영
4. 정산·배치
5. 이후 심화

세부 목록과 기존 일정의 취급은 [인수인계 문서](../study-redesign-handoff.md)의 4단계를 따른다.
작성 완료·학습 완료·화면 검증 완료·운영 구현 완료는 서로 다른 상태로 관리한다.
