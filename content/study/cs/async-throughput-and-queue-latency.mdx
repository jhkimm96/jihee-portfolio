## 01 · 민지는 접수 번호7을 받았지만 결과는 아직 없다

상품7의 보고서를 만드는 설명용 작업이다. 아래 시각은 같은 시작점을 기준으로 한 가정값이다.

```text
0ms        요청
30ms       접수 번호7 응답 / 대기 시작
1,830ms    작업 시작
2,030ms    결과 완성
```

**접수 응답 30ms와 결과 완료 2,030ms는 다른 시간이다.** 이번 장면의 대기는 1,800ms, 실제 처리는 200ms다. “접수됨”을 “성공 완료”로 보여주면 사용자가 결과 상태를 오해한다.

## 02 · 일을 잠시 보관한다고 처리 속도가 늘지는 않는다

Queue는 순서를 기다리는 일의 보관함, worker는 일을 실제로 처리하는 실행자다. 구현에 따라 메시지 소비자를 consumer라고 부르기도 한다.

한 실행자가 매번 40ms 동안 작업 하나를 끝낸다고 단순화하면 초당 처리 능력은 25건이다.

```text
매초 들어오는 일 50건
매초 끝내는 일   25건
차이            25건 → 처리하지 못한 일이 계속 쌓임
```

실패·재시도·다른 병목이 없는 단순 모델이다. 일시적 몰림을 담는 것과 지속적 과부하를 해결하는 것은 다르다. 큰 대기열은 오래 기다리는 일을 더 많이 보관할 뿐일 수 있다. [Java Executor의 대기열 선택](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/ThreadPoolExecutor.html)

## 03 · 실행자를 세 명으로 늘리면 항상 세 배일까?

```text
독립 처리 가능 / 실행자3명 → 이론상75건/초 → 유입50건을 넘길 수 있음
공유 DB가30건/초 한계     → 실행자3명이어도 DB에서 다시 기다림
```

DB 풀, 외부 API 한도와 락도 함께 확인한다. Kafka라면 파티션 배치가 실제 병렬 처리를 제한할 수 있다. 단순히 스레드나 consumer 숫자만으로 처리량을 계산하지 않는다.

## 04 · 무한히 기다리게 하지 않는 선택도 있다

| 포화 시 선택 | 달라지는 일 |
| --- | --- |
| 제한된 대기열 | 일시적 몰림을 보관하되 한도 밖 정책 필요 |
| 바로 거절 | 접수하지 못한 일을 호출자가 알 수 있게 함 |
| 호출자가 직접 처리 | 접수하는 쪽도 느려져 유입을 누를 수 있음 |

각각 재시도·시간 제한·결과 안내가 필요하다. 메모리의 작업 큐는 서버 종료 뒤 복구를 자동 보장하지 않는다. 재시작 후에도 남는 메시지 저장, 업무 상태와 재처리 안전성은 별도 설계다.

## 05 · 프로젝트에는 큐에 쌓지 않는 비동기 경로가 있다

PromptHub AI 정산 대화의 `SettlementRunExecutionConfig`는 실행 스레드의 core/max 수를 같은 설정값으로 두고 `queueCapacity=0`과 거절 정책을 사용한다.

```text
실행 자리 있음 → 실행자에게 직접 전달
자리 포화      → 대기열에 무한 적재하지 않고 제출 거절 가능
```

`ThreadPoolTaskExecutor`는 Spring 의존성에서 가져오는 실행 관리 클래스다. `ThreadPoolExecutor`는 별도 설치 없이 쓰는 Java 기본 클래스다. 큐0은 “아무 제한 없이 즉시 실행”이 아니라 **작업을 쌓아두지 않는 전달 방식**이다. [Spring 실행기 설정](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/scheduling/concurrent/ThreadPoolTaskExecutor.html)

호출 서비스는 제출 거절을 처리하는 경로를 갖고, 정상 제출 뒤에는 결과 대신 실행 식별자를 반환한다. 이 코드 존재만으로 운영 처리량이나 복구 안전성을 입증하지 않는다.

같은 작업 ID로 접수·실행 시작·최종 성공/실패를 연결한다. 접수 수, 완료 수, 가장 오래 기다린 작업, 진행 중 수와 거절 수를 함께 본다.

Kafka Lag은 설정·계측 방식에 따른 위치 차이이므로 일반 메모리 큐의 길이나 성공 완료 건수와 무조건 같은 값이 아니다. [Kafka Lag 진단](/study/cs/kafka-lag-diagnosis)으로 이어 읽는다.

## 프로젝트 근거와 확인 범위
