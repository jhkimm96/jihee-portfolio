## 01 · 한 사람의 요청이 서버 A와 B로 나뉘어 들어온다

사용자 민지가 상품 검색을 다섯 서버 중 어느 곳으로든 보낸다. 정책은 “같은 사용자에게 고정된 1초 구간당 3번”인데 각 서버가 혼자 세면 어떻게 될까? 학습 예시이며 실제 장애 기록이 아니다.

```text
서버 A의 민지 한도: 3번
서버 B의 민지 한도: 3번
서버 C/D/E도 각각: 3번
────────────────────
서버별 한도의 합: 15번 ≠ 전체 한도 3번
```

**같은 사용자의 사용량을 한곳에서 공유하고, 확인과 변경을 끊기지 않게 처리한다.** 이 방식으로 여러 서버의 한도를 맞출 수 있다. **Redis**는 여러 서버가 접속해 작은 상태를 빠르게 읽고 바꾸는 별도 저장 시스템이다. Java 기본 클래스가 아니다.

## 02 · 같은 저장소라도 다른 이름으로 세면 공유가 아니다

```text
서버 A ── 민지의 검색 요청 ──┐
서버 B ── 민지의 검색 요청 ──┼→ Redis: 민지 / 검색 / 이번 구간
서버 C/D/E ────────────────┘          사용량 0 → 1 → 2 → 3
```

저장 위치를 찾는 이름을 **키(key)**라고 한다. 같은 제한 대상이라면 모든 서버가 같은 키와 시간 구간 규칙을 사용해야 한다. 서버 번호를 키에 넣으면 다시 서버별 한도가 된다. 외부 서비스 전체 호출량을 제한하려면 사용자 키가 아니라 그 공유 경계에 맞는 키를 정한다.

## 03 · 남은 한 번을 두 서버가 동시에 읽으면

기본적인 “읽기 → 비교 → 저장”을 서버마다 따로 실행하면 같은 사용량을 읽을 수 있다.

```text
사용량 2 / 한도 3
A: 2를 읽음 → 허용 → 3 저장
B: 2를 읽음 → 허용 → 3 저장
결과: 두 요청을 허용했는데 기록은 한 번만 증가
```

이 충돌을 막으려면 판정에 필요한 읽기와 갱신을 Redis 안에서 한 작업으로 처리한다. **원자적 처리**는 그 작업 사이에 다른 요청이 끼어들지 못하게 한다는 뜻이다.

```text
A의 작업: 2 확인 → 허용 → 3 기록 → 끝
B의 작업: 3 확인 → 거절 → 끝
```

Redis에서는 Lua 스크립트로 필요한 명령들을 묶을 수 있다. Lua는 Redis에서 실행하는 스크립트 언어다. 단순 증가 명령 `INCR`도 원자적이지만, 따로 하는 판정/만료 설정까지 자동으로 한 작업이 되지는 않는다. 긴 스크립트는 다른 작업을 막으므로 짧게 유지한다. [Lua의 원자적 실행](https://redis.io/docs/latest/develop/programmability/eval-intro/), [카운터와 만료를 묶는 이유](https://redis.io/docs/latest/commands/incr/)

## 04 · Redis가 응답하지 않으면 정책을 먼저 정한다

| 선택 | 이득 | 잃는 것 |
| --- | --- | --- |
| 제한 확인 실패 시 임시 허용 | 기능을 계속 제공할 여지 | 공유 한도를 넘길 수 있음 |
| 제한 확인 실패 시 보류/거절 | 보호 대상의 부담을 줄임 | Redis 장애가 사용자 실패로 이어짐 |

어느 쪽이 항상 맞지는 않다. 보호할 기능과 비용에 따라 결정하고 Redis 대기도 제한한다. 이미 소비했는데 응답만 못 받았다면 다시 소비해 이중으로 셀 수도 있다. 원자적 실행과 네트워크 결과 확인은 다른 문제다.

<details>
<summary>원자적 스크립트면 장애 때도 한도를 절대 넘지 않을까?</summary>

그렇지 않다. 만료/삭제/상태 유실로 한도가 초기화될 수 있고, Redis 기본 복제는 비동기여서 장애 전환 때 기록이 사라질 수 있다. `WAIT`도 모든 상황의 강한 일관성을 보장하는 것은 아니다. 정책에 필요한 장애 허용 범위를 정하고 시험한다. [Redis 복제의 보장 범위](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)

</details>

## 05 · 프로젝트의 현재 한도는 공유 한도가 아니다

PromptHub의 `TossRateLimiterConfig`는 메모리 Registry를 만든다. 확인한 코드/설정 검색에서는 Redis 기반 RateLimiter 연결을 찾지 못했다. 따라서 이 글은 **분산 제한의 학습 설계**이며 프로젝트 구현 완료가 아니다.

구현한다면 같은 사용자 요청을 두 서버로 보내 총 허용량이 3인지, 구간 변경·Redis 실패·응답 유실에서 정책대로 동작하는지 확인한다. 실제 Redis 연결/스크립트/부하 시험은 이번에 수행하지 않았다.
