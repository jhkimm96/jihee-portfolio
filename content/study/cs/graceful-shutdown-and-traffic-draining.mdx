## 01 · 민지는 A에서 기다리고 지수는 새로 들어온다

상품 앱 A를 새 버전 B로 바꾸는 설명용 장면이다. A는 민지의 상품 7 요청을 아직 처리 중이다.

```text
민지: 이미 A에 들어간 요청 → A가 마무리 → 정상 응답
지수: 새 상품 7 요청      → 준비된 B로 이동 → 정상 응답
```

**기존 요청을 마무리하는 일과 새 요청을 A로 보내지 않는 일은 둘 다 필요하다.** Graceful Shutdown은 갑자기 끊지 않고 종료를 준비하는 절차다. B가 준비돼 있고 실제 요청 경로가 새 대상을 반영해야 위 장면이 성립한다.

## 02 · A만 기다리면 어디가 비어 있을까?

```text
A: 기존 요청을 끝낸 뒤 종료
연결 담당: 아직 A 주소를 사용
지수: 종료된 A로 연결 → 연결 실패 → 프록시 오류가 날 수 있음
```

앱이 진행 중 요청을 보호해도 프록시·로드밸런서의 대상 갱신을 자동 완료해주지는 않는다. **502**는 프록시가 정상적인 상위 서버 응답을 받지 못한 상태이며, 종료 외에도 포트·주소·네트워크 문제가 원인일 수 있다.

## 03 · Kubernetes 종료는 한 줄짜리 순서도가 아니다

Pod는 컨테이너 실행 단위다. 삭제가 시작되면 서로 다른 구성 요소가 종료와 연결 대상 변경을 처리한다.

```text
노드 쪽       종료 유예 시작 → preStop(있으면) → 종료 신호 → 앱 정리
대상 관리 쪽   종료 상태 반영 → 일반 요청 대상의 ready=false
실제 요청 쪽   대상 정보 전파 → 새 요청이 다른 앱으로 이동
```

이 처리는 병행될 수 있으며 모든 곳에 같은 순간 반영되지 않는다. 종료 중 EndpointSlice 대상은 즉시 삭제되기보다 terminating 상태와 ready=false로 표시될 수 있다. 반드시 Readiness 실패를 먼저 수동 유발해야만 Pod 삭제가 되는 것은 아니다. [Kubernetes Pod 종료](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/)

## 04 · 30초는 항상 기다리는 시간이 아니라 끝내야 할 예산이다

PromptHub 상품 Pod에는 `terminationGracePeriodSeconds: 30`이 있다. Kubernetes 기본 종료 설정이며 Java 라이브러리가 아니다.

```text
같은 30초 안에서 → preStop 시간 + 앱 요청 마무리·자원 정리
기한 초과       → 남은 프로세스가 강제 종료될 수 있음
```

고정 sleep만 늘리면 실제 원인은 남고 앱 정리에 쓸 시간이 줄 수 있다. 대상 전파·요청 마무리 시간이 종료 예산에 맞는지 관찰한다. Spring Boot 웹 서버의 graceful 처리는 새 요청을 제한하며 진행 중 요청에 유예를 제공하지만 모든 Kafka 작업·외부 작업 완료까지 보장하지는 않는다. [Spring Boot 종료 처리](https://docs.spring.io/spring-boot/reference/web/graceful-shutdown.html)

<details>
<summary>앱의 유예 설정과 Pod의 유예는 다르다</summary>

Spring Boot의 `spring.lifecycle.timeout-per-shutdown-phase`는 앱 생명주기 종료 단계의 제한이다. Pod의 전체 종료 제한과 같은 숫자라고 같은 범위를 뜻하지 않는다.

현재 공식 Boot 문서는 웹 graceful 종료가 기본 활성화라고 설명한다. 프로젝트는 Boot 4.1.0을 선언하지만 실행 중 설정·종료 신호·모든 작업의 실제 완료는 별도로 확인해야 한다.

</details>

## 05 · 프로젝트에서는 무엇을 보고 검증할까?

2026-10-09 `k8s/base/services/product/deployment.yaml`의 종료 유예 30초와 Readiness 경로를 읽었다. 이 파일에는 preStop이 없지만 그것만으로 배포 실패를 판정하지 않는다.

배포 시각, A로 향한 새 연결, A의 진행 중 요청과 종료 시각, B의 준비 상태를 같은 시간축에 놓는다. 현재 프로젝트의 실패 횟수나 무중단 결과를 측정하지 않았다.

기존 글의 Instagram 실험 수치는 원본을 재확인할 수 없어 제외했다. 위 민지·지수 장면은 학습 예시다.
