## 01 · 상품 조회 하나가 느려지면 문제가 여러 곳에 생긴다

서버 A에서 상품 7의 외부 조회가 느려졌다고 해 보자. 새로운 요청이 계속 들어오고, 처리 자리가 묶이며, 재시도까지 늘어난다. 하나의 학습 상황이며 실제 장애 기록은 아니다.

```text
들어오는 요청 → 실행 자리 → 외부 조회 대기 → 재시도 → 사용자 응답
    많아짐       묶임          길어짐        늘어남      늦어짐
```

**보호 장치는 같은 장애에서도 서로 다른 경계를 지킨다.** 이름이 비슷하다고 하나가 나머지를 모두 대신하지 않는다.

## 02 · 같은 길에서 서로 다른 질문을 한다

| 장치 | 이번 장면에서 묻는 질문 |
| --- | --- |
| Rate Limiting | 이 시간 동안 이렇게 많이 보내도 되는가? |
| Bulkhead | 이 기능이 지금 처리 자리를 너무 많이 쓰는가? |
| Timeout | 이번 외부 호출을 얼마나 더 기다릴까? |
| Retry | 다시 보낼 안전한 실패인가? 몇 번, 언제 보낼까? |
| Circuit Breaker | 최근 계속 나쁜 상대에게 새 호출을 보내도 될까? |
| Fallback | 실패 뒤 결과의 뜻을 지키면서 무엇을 대신 줄까? |

Rate Limiting을 통과해도 느린 호출은 자리를 붙잡을 수 있다. Bulkhead를 통과한 호출도 너무 오래 기다릴 수 있다. Timeout 뒤에도 상대가 일을 완료했을 수 있다. [Bulkhead의 격리와 다른 보호 장치 조합](https://learn.microsoft.com/en-us/azure/architecture/patterns/bulkhead)

## 03 · 서로의 빈틈을 메우되 무조건 모두 붙이지 않는다

```text
조회량이 과함     → 유입량과 전체 외부 호출량부터 제한
한 기능만 느림    → 공유 자원과 동시 점유부터 확인
대기가 끝나지 않음 → 호출별 대기와 전체 요청 예산 확인
반복해서 실패함   → 실패 분류와 차단/회복 정책 확인
결과를 못 받음    → 안전한 대체 또는 실패 안내 선택
```

측정한 실패 원인과 보호하려는 경계에 맞는 최소 장치를 선택한다. 대체 DB로 부하를 옮기거나 Retry를 여러 계층에 겹치면 보호하려던 장애를 키울 수 있다. 개별 장치 설명은 [Fallback](/study/cs/fallback-safe-results)과 [Retry](/study/cs/retry-backoff-jitter-budget)로 이어 읽는다.

## 04 · 프로젝트에서는 코드 작성 순서와 실행 순서도 다르다

PromptHub 승인 Gateway는 안쪽부터 래퍼를 만들지만 실제 호출은 바깥쪽에서 시작한다. **래퍼**는 원래 호출 전후에 판단을 추가하는 감싸기다.

```text
실행 진입
Circuit Breaker → Retry → RateLimiter → Bulkhead → 외부 승인 호출
```

이 배치에서는 Retry가 각 시도마다 RateLimiter와 Bulkhead를 다시 지난다. 호출권을 얻은 뒤 Bulkhead가 거절하면 실제 HTTP 호출 없이도 구간 호출권을 쓸 수 있다. Breaker는 내부 Retry 묶음의 최종 결과를 본다. 다른 배치가 같은 통계와 효과를 낸다고 보지 않는다.

Timeout은 HTTP 클라이언트에도 별도로 있다. 확인한 코드는 연결 대기 5초와 읽기 대기 60초를 설정한다. 두 값이나 내부 대기를 단순히 하나의 요청 전체 제한으로 해석하지 않는다. 이번에는 소스만 읽었으며 운영 효과를 측정하지 않았다.

## 05 · 비교의 끝은 어떤 결과를 확인할지다

같은 느린 상품 조회 상황에서 실제 외부 호출 수, 진행 중 호출 수, 거절 이유, 대기 시간, 재시도 수와 다른 기능의 지연을 함께 본다. 지표 하나가 좋아졌다고 전체 흐름이 개선됐다고 단정하지 않는다.
