## 01 · 민지는 저장됐다는 답을 받았는데 목록에는 없다

상품 7을 저장하는 학습 장면이다. 쓰기를 받는 Primary와 변경을 복제하는 읽기 Replica가 있다고 가정한다.

```text
원본 Primary   상품7 커밋 → 민지에게 저장 성공
복제본 Replica 아직 적용 전 → 민지의 목록에는 상품7 없음
잠시 뒤 Replica 적용 완료 → 다음 조회에는 상품7 있음
```

**원본 저장 성공과 복제본에서 조회 가능은 다른 사건이다.** 비동기 복제에서는 그 사이에 읽을 수 있다. Replication Lag은 이런 복제 진행의 지연이다. [PostgreSQL 복제](https://www.postgresql.org/docs/18/warm-standby.html#STREAMING-REPLICATION)

## 02 · 30ms만 기다리면 해결일까?

```text
가벼운 날   복제 적용 → 30ms 뒤 읽음 → 보일 수 있음
바쁜 날     30ms 뒤 읽음 → 복제 적용 전 → 안 보일 수 있음
```

기다린 시간이 복제 완료를 증명하지는 않는다. 복제본 CPU·I/O와 네트워크, 원본 변경량에 따라 달라진다. 위 시간은 비교를 위한 가정값이며 운영 측정 결과가 아니다.

## 03 · 읽을 대상이나 확인할 조건을 바꾼다

| 선택 | 확인해야 할 조건 |
| --- | --- |
| 방금 쓴 결과는 Primary에서 읽기 | 커밋 후 새 읽기와 올바른 원본으로 연결 |
| Replica 적용 지점까지 기다리기 | 같은 복제 이력의 지점과 새 조회 시점 |
| 일정 시간 Primary로 우회 | 구간 종료 뒤 Replica가 따라왔는지는 별도 |

짧은 우회 구간이 끝났다는 것만으로 최신 읽기가 계속 보장되지는 않는다. Primary에서 읽어도 오래된 트랜잭션 snapshot이나 앱 캐시를 보면 이전 값일 수 있다.

## 04 · 받은 것과 적용한 것을 구분한다

설명용 진행 번호 120을 기준으로 본다. PostgreSQL의 실제 로그 위치 출력 형식은 아니다.

```text
내 커밋을 포함할 지점    120
Replica 받은 지점       120
Replica 적용한 지점     115 → 아직 내 변경은 조회 불가
Replica 적용한 지점     120 → 그 뒤 새 조회로 확인
```

WAL은 PostgreSQL의 변경 기록, LSN은 그 기록의 위치다. Java 라이브러리가 아니라 DB 복제 기능이다. **수신 위치와 replay(적용) 위치는 다르다.** 대기 제한을 정하고 기한 내 못 따라오면 원본 조회나 명시적 실패 등 정책을 선택한다. [PostgreSQL 위치 확인 함수](https://www.postgresql.org/docs/18/functions-admin.html)

## 05 · 동기 복제라고 항상 조회까지 준비됐을까?

PostgreSQL은 확인 범위가 다르다. `on`의 standby 디스크 기록 확인과 `remote_apply`의 적용 확인을 구분한다. 동기 standby 구성이 없으면 옵션 이름만 바꿔도 복제본을 기다리지 않는다. [PostgreSQL 18 커밋 확인 범위](https://www.postgresql.org/docs/18/runtime-config-wal.html)

확인한 동기 대상이 아닌 다른 Replica를 읽거나 기존 snapshot을 재사용하면 그 보장과 다를 수 있다. 더 강한 확인은 쓰기 대기와 복제본 장애 영향도 늘릴 수 있다.

<details>
<summary>읽기 보장을 조사하는 순서</summary>

커밋 성공 → 읽기 요청의 실제 DB 대상 → Replica 적용 지점 → 조회 트랜잭션·캐시를 확인한다. Lag 표시 하나만으로 특정 요청이 최신 값을 봤다고 확정하지 않는다.

Read-your-writes는 특히 자신이 방금 쓴 변경을 다시 읽을 수 있는 보장에 초점을 둔다. 그 보장이 필요한 저장 직후 화면과 지연을 허용하는 집계를 같은 정책으로 묶지 않는다.

</details>

## 현재 프로젝트에서는 어디를 확인할까?

2026-10-09 PromptHub `k8s/base/infrastructure/postgres/statefulset.yaml`은 Pod 수 1과 PostgreSQL18 계열 이미지 태그를 선언한다. **Pod 수를 늘리는 것만으로 DB 복제가 만들어지지 않는다.**

해당 인프라 파일과 상품 서비스 코드·설정 검색 범위에서는 읽기 Replica 라우팅 구현을 확인하지 못했다. 따라서 이 글은 복제 구조의 학습 예시이지 PromptHub의 실제 복제 장애 기록이 아니다. DB에 접속해 설정·지연을 측정하지 않았다. 기존 Instagram 실험 수치는 원본을 재확인할 수 없어 제외했다.
