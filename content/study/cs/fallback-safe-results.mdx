## 01 · 자동완성만 고장 나도 검색창 전체를 막아야 할까?

상품 검색창에 `프롬`을 입력했다고 해 보자. 원래는 아래에 검색어 제안이 나오는데, 제안을 가져오는 서비스가 응답하지 않는다. 실제 장애 기록이 아닌 학습용 화면이다.

```text
평소                         자동완성 조회가 실패했을 때
┌──────────────────┐         ┌──────────────────┐
│ 프롬         검색 │         │ 프롬         검색 │
├──────────────────┤         └──────────────────┘
│ 프롬프트 작성 도구 │         제안은 생략한다.
│ 프롬프트 예제     │         직접 입력하고 검색할 수 있다.
└──────────────────┘
```

**없어도 검색을 계속할 수 있는 제안만 생략하고, 검색 기능은 남긴다.** 이런 대체 처리 또는 기능 축소를 **Fallback(폴백)**이라고 한다. 특정 라이브러리 이름이 아니라 실패 뒤 무엇을 대신 제공할지 정하는 방식이다.

단, 자동완성과 실제 검색은 별도 요청이다. 제안을 생략했다고 실제 상품 검색까지 성공한다는 뜻은 아니다. 화면의 처리 방식은 설계 예시이며 프로젝트 프런트엔드에서 확인한 동작은 아니다. [일부 기능을 줄여 핵심 기능을 유지하기](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_mitigate_interaction_failure_graceful_degradation.html)

## 02 · 같은 빈 목록인데 뜻은 완전히 다르다

“실패하면 빈 목록을 보내자”는 규칙을 모든 조회에 붙이면 곤란하다.

```text
자동완성 조회 실패 → 제안 []
                    제안 없이 직접 검색할 수 있음

상품 검색 실패    → 상품 [] → "검색 결과 0개"
                    사실은 못 찾은 게 아니라 확인하지 못함
```

자동완성은 보조 기능이라 생략을 허용할 수 있다. 반면 상품 검색 실패를 0개로 바꾸면 사용자는 **상품이 없다고 오해한다.** 이때는 “검색 결과를 불러오지 못했어요”처럼 확인하지 못한 상태를 알리는 편이 맞다.

빈 제안도 정상적으로 제안이 없는 경우와 실패로 생략한 경우를 서버에서 구분해 기록해야 한다. 화면에도 그 구분을 보여줄지는 응답 형식과 UX 정책으로 정한다. 빈 목록 하나만 보내면 클라이언트는 두 이유를 구별할 수 없다.

## 03 · 대신 줄 값이 없으면 실패를 알려도 된다

Fallback은 무조건 성공처럼 보이게 만드는 기능이 아니다. 결과의 뜻과 안전을 먼저 지킨다.

| 상황 | 허용할 수 있는 대체 | 하면 안 되는 대체 |
| --- | --- | --- |
| 자동완성 실패 | 제안을 생략하고 직접 입력 허용 | 실제 검색까지 성공했다고 가정 |
| 상품 설명 조회 실패 | 오래된 설명 사용을 허용하는 정책이 있다면 보관본 표시 | 오래된 가격/재고를 현재 값으로 보장 |
| 결제 응답을 못 받음 | 처리 상태를 확인하도록 안내 | 확인 없이 결제 성공이나 실패로 확정 |
| 접근 권한 확인 실패 | 접근을 보류하고 실패 안내 | 보관 중인 비공개 자료를 그대로 제공 |

보관본은 **캐시**, 즉 이전에 받아 저장해 둔 데이터다. 사용한다면 허용할 수 있는 오래됨과 현재 사용자의 접근 권한부터 확인한다. “일단 예전 값”은 안전한 정책이 아니다. [핵심 기능과 데이터 일관성을 함께 고려하기](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_mitigate_interaction_failure_graceful_degradation.html)

<details>
<summary>Circuit Breaker가 있으면 Fallback도 자동으로 생길까?</summary>

아니다. Circuit Breaker는 “지금 외부 호출을 보낼까?”를 판단한다. Fallback은 호출 실패 또는 차단 뒤 “무엇을 대신 제공할까?”를 정한다. 차단을 오류로 알릴 수도 있고, 안전한 보관본을 제공할 수도 있다. 대체 처리는 별도로 연결해야 한다.

또한 모든 예외를 대체할 이유는 없다. 잘못된 입력, 권한 거절, 일시적인 외부 장애와 코드 버그를 같은 실패로 취급하지 않는다. 어떤 실패를 대체할지 먼저 분류한다.

## 04 · 다른 곳으로 보내면 그곳도 버틸 수 있어야 한다

상품 검색용 서버가 실패하면 기본 DB로 검색하는 방법도 있다. **DB는 상품 원본을 저장하는 데이터베이스**, 검색용 서버는 검색을 빠르게 처리하는 별도 시스템이라고 생각하면 된다.

```text
평소:       상품 검색 ──→ 검색용 서버
            상품 저장 ──→ 기본 DB

검색 장애:  상품 검색 ──┐
            상품 저장 ──┴→ 기본 DB에 함께 몰림
```

검색을 살리려다 상품 저장까지 느려질 수 있다. 대체 경로도 실패할 수 있으므로 처리할 요청량과 기다릴 시간을 제한하고, 여러 서버가 동시에 그 경로로 몰리는 상황도 시험해야 한다. [대체 경로가 장애를 키울 수 있는 이유](https://aws.amazon.com/jp/builders-library/avoiding-fallback-in-distributed-systems/)

“대체 응답을 몇 번 사용했는가”, “원래 실패 이유는 무엇인가”, “대체 경로도 느려지는가”를 따로 관찰한다. 사용자에게 일부 기능을 남기는 것과 운영자가 장애를 못 보게 만드는 것은 다른 일이다.

## 05 · 내 프로젝트에는 세 가지 다른 대체가 있다

PromptHub의 현재 소스에서 다음 경로를 확인했다. **ES(Elasticsearch)는 별도 검색 시스템**, **RDB는 관계형 데이터베이스**를 뜻한다.

1. **상품 검색 — ProductQueryService.getProducts:** ES 검색 경로에서 `RuntimeException`이 나면 경고 로그를 남기고 RDB 조회를 시도한다. 검색 방식이 달라 같은 순위와 결과를 보장하는 것은 아니다.
2. **자동완성 — ProductQueryService.suggest:** 조회 중 `RuntimeException`이 나면 경고 로그를 남기고 빈 제안 목록을 반환한다. 상품 검색 결과를 0개로 바꾸는 처리가 아니다.
3. **검색어 의미 분석 — QueryEmbeddingCache → 검색 Querier:** 검색어를 숫자 배열로 바꾸는 작업이 제한 시간 안에 끝나지 않거나 실패하면, 그 배열 없이 단어 기반 검색 경로를 사용한다.

첫 번째는 다른 조회 경로, 두 번째는 보조 기능 생략, 세 번째는 검색 방식 축소다. 전부 같은 빈 값을 반환하는 방식이 아니다.

<details>
<summary>코드와 테스트를 어디서 확인했을까?</summary>

상품 조회와 자동완성의 진입점은 프로젝트의 `ProductQueryService`다. 직접 작성한 Java 클래스이며 캐시 라이브러리 이름이 아니다. `suggest`의 `List.of()`는 Java 기본 제공 기능으로, 이 호출에서는 빈 목록을 만든다. 새 라이브러리를 설치하는 부분은 아니다. [프로젝트에서 선언한 Java 21의 List API](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/List.html#of())

테스트 소스에는 ES 검색 실패 후 RDB 결과를 반환하는 사례와 자동완성 실패 후 빈 목록을 반환하는 사례가 있다. QueryEmbeddingCache 테스트에는 느린 의미 분석에서 결과를 기다리지 않는 사례도 있다. 이번에는 소스를 읽었으며 테스트 실행, 실제 장애, 대체 DB의 처리 용량과 화면 동작은 검증하지 않았다.

현재 상품 조회의 catch는 ES 통신 실패만 정확히 가려내는 규칙이 아니라 `RuntimeException`을 넓게 받는다. 검색 결과 변환 중 예외도 포함될 수 있으므로, 이 코드를 “모든 오류를 DB로 보내면 안전하다”는 권장안으로 읽지 않는다. 실패 분류와 대체 부하 검증은 별도 개선 과제다.

</details>
