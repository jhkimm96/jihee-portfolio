## 01 · 민지의 상품7 조회에 920ms가 걸렸다

한 요청을 추적하는 설명용 장면이다. 숫자는 운영 실측이 아니다.

```text
0ms          연결 빌리기 시작
500ms        연결 획득
920ms        관찰한 DB 사용 구간 끝
```

연결 획득은 500ms, 그 뒤 관찰 구간은 420ms다. **이 420ms를 순수 DB 내부 실행 시간이라고 부를 수는 없다.** SQL 호출, 결과 전달·변환과 다른 앱 작업 등이 포함됐을 수 있다.

SQL은 DB에 조회·변경을 요청하는 명령이다. 무엇을 재기 시작하고 끝냈는지부터 정해야 어느 단계가 느린지 좁힐 수 있다.

## 02 · 풀 앞에 줄이 서 있는지 확인한다

```text
사용 중 연결 2 / 풀 상한2
남는 연결   0
대기 요청   민지·지수
```

이 상태가 지속되면 연결을 기다리는 요청이 있다는 증거다. 아직 “풀이 너무 작다”는 결론은 아니다. 연결을 오래 붙잡는 작업이나 DB 지연 때문에 같은 줄이 생길 수 있다.

Spring Boot는 조건에 맞는 DataSource에 `jdbc.connections` 지표를 붙이고, HikariCP 전용 지표는 `hikaricp` 접두어를 사용한다. 실제 등록된 이름·풀·인스턴스를 확인한다. [Spring Boot 풀 지표](https://docs.spring.io/spring-boot/reference/actuator/metrics.html)

## 03 · p95는 같은 요청의 타임라인이 아니다

**p95**는 시간 측정값 분포의 95번째 백분위 지점이다. 같은 구간·작업의 대부분은 얼마나 빨랐고 느린 쪽은 어땠는지 보는 수치다. 계산법이나 히스토그램에 따라 추정 방식이 달라질 수 있다.

```text
개별 요청 추적   민지의 획득500ms / 이후420ms
집계 지표       여러 요청의 획득 p95 / 여러 요청의 SQL p95
```

서로 다른 분포의 p95를 빼거나 더해 민지의 DB 내부 시간을 구할 수 없다. 집계는 경향을 찾고, 개별 추적은 어느 구간에서 기다렸는지 연결하는 데 쓴다.

## 04 · DB 안에서 기다리는 이유도 나눈다

| 함께 관찰할 흔적 | 다음에 확인할 후보 |
| --- | --- |
| 연결 획득이 느리고 점유가 김 | 긴 거래·외부 대기·반납 문제 |
| SQL 호출이 길고 CPU·읽기 부하 증가 | 실행 계획·읽는 행·자원 |
| SQL 호출이 길지만 락 대기가 있음 | 막고 있는 트랜잭션 |
| 앱 시간은 긴데 DB 증거가 다름 | 네트워크·결과 크기·앱 처리 |

후보 표이지 자동 판정표가 아니다. PostgreSQL의 `pg_stat_activity`는 DB 활동을 읽는 기본 뷰이며 wait_event로 기다리는 종류를 확인할 수 있다. Java 라이브러리가 아니다. [PostgreSQL18 활동과 대기](https://www.postgresql.org/docs/18/monitoring-stats.html)

## 05 · 진단 명령이 실제 작업을 실행할 수도 있다

실행 계획은 DB가 어떤 방법으로 데이터를 찾을지 보여준다. PostgreSQL의 **EXPLAIN ANALYZE는 쿼리를 실제 실행한다.** 읽기 부하도 만들고 변경문·함수는 부작용을 낼 수 있다. 운영 DB에 그대로 복사해 실행하지 않는다. [EXPLAIN의 실행 조건](https://www.postgresql.org/docs/18/sql-explain.html)

안전한 시험 환경과 데이터, 권한·비용을 먼저 확인한다. 한 조건만 바꾸고 같은 부하에서 완료 시간·오류·처리량을 비교한다. 풀·쿼리·서버 사양을 한꺼번에 바꾸면 효과의 원인을 구분하기 어렵다.

## 프로젝트 근거와 확인 범위

2026-10-09 PromptHub의 Data JPA starter 선언과 중앙 상품 datasource 설정을 읽었다. 실제 풀 지표·DB 활동·추적·실행 계획을 수집하거나 부하 시험을 하지 않았다. 위 시간과 연결 수는 학습 예시다.

기존 글의 “920−500=DB 내부420ms” 설명을 계측 구간의 한계에 맞게 바꿨다. 숫자 하나만으로 풀 증설이나 DB 사양 확장을 권하지 않는다.
