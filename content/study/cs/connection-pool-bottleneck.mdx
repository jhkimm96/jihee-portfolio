## 01 · 민지의 요청은 아직 DB에 들어가지도 못했다

앱의 DB 연결이 두 개라고 가정하자. 연결은 앱이 DB와 통신하는 통로다. 커넥션 풀은 그 통로를 재사용하며 빌려주는 관리 기능이다.

```text
연결1 [A가 사용 중]  연결2 [B가 사용 중]
민지의 상품7 조회   [빈 연결을 기다림]
A가 연결 반납      [민지가 빌려 조회 시작]
```

**느린 요청이 모두 느린 SQL 때문은 아니다.** 먼저 연결을 기다리는지, 빌린 뒤 오래 걸리는지 구분한다. HikariCP는 이 풀을 제공하는 외부 Java 라이브러리이며 DB 자체의 실행 엔진은 아니다. [HikariCP 연결 획득 계약](https://github.com/brettwooldridge/HikariCP)

## 02 · 연결을 늘리면 줄이 어디로 옮겨질까?

DB가 이미 바쁜 학습 상황이다.

```text
연결2개   A/B는 DB에서 처리 / 민지는 풀 앞에서 대기
연결3개   A/B/민지 모두 입장 / DB 안에서 자원·락 대기 가능
```

입구의 줄이 줄어도 DB의 CPU·디스크·락 처리 능력이 늘어난 것은 아니다. 더 많은 동시 작업이 경합을 키울 수도 있다. 늘린 뒤 전체 완료 시간과 처리량이 좋아졌는지 봐야 한다. [HikariCP 풀 크기 선택](https://github.com/brettwooldridge/HikariCP/wiki/About-Pool-Sizing)

## 03 · 같은 요청의 세 시간을 따로 본다

| 관찰 구간 | 알아내려는 것 |
| --- | --- |
| 연결 빌리기 전후 | 획득 대기가 길었는가 |
| 연결 획득~반납 | 오래 붙잡고 있었는가 |
| SQL 호출 전후 | 어떤 조회가 오래 걸렸는가 |

예를 들어 획득 500ms, SQL 호출 20ms라면 입구 대기 원인을 확인한다. 획득 10ms, SQL 호출 900ms라면 쿼리·락·자원 증거를 찾는다. 둘 다 설명용 값이며 이것만으로 원인을 확정하지 않는다.

**앱에서 잰 SQL 호출 시간도 순수 DB 내부 시간은 아니다.** 네트워크, 드라이버와 결과 전달 등이 포함될 수 있다. 전체 요청 시간에서 획득 대기를 뺐다고 DB 내부 실행 시간이 되는 것도 아니다.

## 04 · DB가 한가한데 연결은 다 빌려져 있을 수도 있다

```text
연결1: DB 조회 → 외부 API 응답 대기 ─────→ 추가 DB 작업 → 반납
민지: 연결1이 돌아올 때까지 대기
```

빌린 연결을 외부 대기 동안 붙잡는지, 긴 트랜잭션이나 반환 누락이 있는지 확인한다. 거래의 원자성을 깨면서 무조건 먼저 반납하라는 뜻은 아니다. 트랜잭션 경계를 바꾸면 데이터 안전성도 함께 검토한다.

## 05 · 숫자를 바꿀 때는 작은 비교 시험으로 확인한다

같은 부하에서 연결 사용 수·대기 수, 획득 시간, 점유 시간과 DB 자원을 본다. 의도적으로 한 조건만 바꾸고 완료 시간·오류·처리량을 다시 비교한다. DB CPU가 낮다는 사실만으로 풀 부족을 확정하지 않는다.

```text
서버5대 × 서버별 풀 최대30개 = 최대150개
                           + 다른 앱·배치·관리 연결도 필요
```

모든 연결이 같은 DB로 향하는 가정이다. 각 풀의 합계를 DB 연결 예산과 비교해야 한다. `connectionTimeout`은 연결을 기다리는 제한이지 SQL이나 전체 HTTP 요청 제한이 아니다.

`maximumPoolSize`는 유휴·사용 중 연결을 포함한 풀의 상한이다. 최적값은 배치 환경과 작업에 따라 달라진다. 같은 이름의 설정이 있어도 실행 중 최종 적용값을 확인해야 한다.

HikariCP 사용 여부, 풀 지표와 DB 활동을 먼저 확인하고 [DB 병목 진단](/study/cs/database-bottleneck-diagnosis)으로 이어 읽는다.

## 프로젝트 근거와 확인 범위

2026-10-09 PromptHub 중앙 `product-service.yml`의 datasource와 JPA 설정을 읽었다. 이 파일과 상품 main 코드 검색에서는 풀 크기·획득 제한의 명시적 튜닝을 확인하지 못했다.

다른 설정 공급원과 실행 중 풀 값은 확인하지 않았다. “기본값으로 충분하다고 팀이 판단했다”거나 풀 증설 효과를 측정했다는 주장은 하지 않는다. 기존 영상의 숫자는 원본을 재확인할 수 없어 제외했다.
