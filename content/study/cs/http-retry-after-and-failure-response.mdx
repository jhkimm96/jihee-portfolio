## 01 · 실패 숫자만 보고 다시 보내면 안 된다

서버 A가 상품 7을 외부 API에서 조회했더니 `429 Too Many Requests`와 `Retry-After: 2`를 받았다. 학습용 응답이다.

```text
상품7 조회 → 외부 API
          ← 429 / Retry-After: 2
바로 재호출 ×     우선 2초 대기 지침 확인
```

**응답을 보낸 곳, 기다리라는 시간, 남은 호출 예산과 재시도 안전성을 함께 본다.** `429`는 요청량 제한을 뜻하며 기다릴 지침이 반드시 들어 있는 것은 아니다. [429의 의미](https://www.rfc-editor.org/rfc/rfc6585#section-4)

## 02 · 2는 횟수가 아니라 기다릴 초다

`Retry-After`는 응답에 붙는 추가 정보인 **HTTP 헤더**다. 위의 숫자 2는 응답을 받은 뒤 기다릴 2초를 뜻한다. 특정 날짜/시각으로 올 수도 있다. 해당 지침을 따른 뒤 보내더라도 성공을 보장하지는 않는다. [Retry-After 형식](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3)

```text
응답 수신     대기                 다시 요청할 수 있는 후보 시점
0초 ───────── 2초 ───────────────→
```

헤더가 없거나 잘못된 형식이면 무한 대기가 아니라 정한 제한 안의 Backoff/Jitter 정책을 적용한다. 기다리는 중에는 같은 요청을 즉시 반복하지 않는다.

## 03 · 남은 예산이 1초인데 2초를 기다리라면

```text
요청 전체 예산: 앞으로 1초 남음
외부 대기 지침: 최소 2초
─────────────────────────
이번 요청 안에서는 재시도하지 않음
```

대기 지침을 1초로 잘라 더 빨리 재시도하지 않는다. 대기 후 재시도 시간을 감당하지 못하면 이번 요청을 종료하고, 별도 작업으로 미룰지 실패를 알릴지 결정한다. [Retry의 전체 예산](/study/cs/retry-backoff-jitter-budget)과 연결해서 생각한다.

## 04 · 응답 없는 결제는 “안 됐다”가 아니다

| 받은 상황 | 먼저 할 판단 |
| --- | --- |
| 429 | 누가 어떤 한도를 적용했는지, 대기 지침과 예산 |
| 일시적 5xx | 재시도 가능한 실패인지, 중복 방지와 횟수 |
| 잘못된 입력/권한 거절 | 입력이나 권한 문제 해결 없이 반복하지 않음 |
| 결제 응답이 안 옴 | 처리됐는지 모름. 상태 확인과 멱등 계약부터 확인 |

**멱등성**은 같은 작업을 다시 보내도 업무 효과가 중복되지 않게 하는 성질이다. POST라는 이름이나 헤더 하나만으로 보장되지 않는다. 서버가 약속한 키 범위·유효 기간·요청 내용 규칙까지 필요하다. [안전한 자동 재시도의 조건](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)

## 05 · 현재 프로젝트가 하는 일과 하지 않는 일을 나눈다

PromptHub `TossRetryPredicate`는 특정 서버 오류와 일부 네트워크 예외를 재시도 대상으로 분류한다. 직접 cause가 `SocketTimeoutException`인 네트워크 예외는 제외한다. 모든 중첩 timeout을 빠짐없이 제외한다는 뜻은 아니다.

`TossPaymentGateway`는 승인 요청에 멱등 키를 넣지만, 확인한 실행 경로에는 `Retry-After`를 읽어 동적 대기 시간을 정하는 처리가 없다. 외부 4xx 응답은 오류 코드로 바뀌며, 내부 RateLimiter 거절은 별도로 `PG_RATE_LIMITED`가 된다. 그 오류는 503으로 선언되어 있다.

그러므로 이 글의 429 대응은 **개념과 설계 지침**이다. 프로젝트가 외부 429를 자동 재시도하거나 사용자에게 원래 헤더를 전달한다는 구현 설명이 아니다. 실제 응답·테스트·PG 운영 동작을 실행 검증하지 않았다.
