## 01 · 검색이 많아졌는데 사람도 늘었을까?

이어폰 검색 화면을 개선한 뒤 검색 횟수가 늘었다. 사람이 더 온 것인지, 같은 사람이 원하는 결과를 못 찾아 반복한 것인지 알고 싶다.

**집계는 기록을 정한 범위에서 묶거나 숫자로 요약하는 작업이다.** 횟수와 사용자 수는 다른 질문이므로 같은 숫자로 취급하지 않는다.

다음은 **2026-10-12 오전의 설명용 검색 기록 5건**이다. 실제 사용자 정보나 프로젝트 로그가 아니다. 검색 한 번이 문서 한 건으로 저장됐고 중복·누락이 없다고 가정한다.

| 기록 | 사용자 표시 | 검색어 | 결과 수 |
|---|---|---|---|
| E1 | A | 이어폰 | 2 |
| E2 | A | 이어폰 | 0 |
| E3 | B | 키보드 | 3 |
| E4 | A | 키보드 | 1 |
| E5 | B | 이어폰 | 2 |

A와 B는 **같은 사용자를 구별하기 위한 가짜 값**이다. 결과 수는 그 검색에서 반환된 상품 수이며 검색 횟수와 다르다.

## 02 · 기록 5장을 검색어별로 나눠 담는다

```text
이어폰 묶음              키보드 묶음
[E1 A] [E2 A] [E5 B]     [E3 B] [E4 A]
        3건                     2건
```

같은 검색어 값을 가진 문서끼리 모으는 기능이 **terms 집계**다. 묶음은 **버킷(bucket)**, 묶음 안 문서 수는 **doc_count**라고 부른다.

```text
이 5건에서의 검색 횟수
이어폰  ■■■  3
키보드  ■■   2
```

이어폰이 세 번 검색됐지만 세 사람이 검색했다는 뜻은 아니다. 같은 A의 두 검색이 함께 들어 있다. 이 예시는 검색어가 값 하나인 필드다. 한 문서에 여러 값이 있으면 여러 묶음에 들어갈 수 있으므로 버킷 개수 합을 항상 전체 문서 수로 생각하지 않는다. [terms 집계](https://www.elastic.co/docs/reference/aggregations/search-aggregations-bucket-terms-aggregation)

## 03 · 이번에는 사용자 표시의 중복을 뺀다

```text
검색 기록의 사용자 값    A  A  B  A  B
                             ↓ 중복된 값을 한 번만 보기
고유 사용자 표시         A     B
                            2개
```

이 자료를 손으로 세면 **검색 5번, 고유 사용자 표시 2개**다. ES의 **cardinality 집계**는 고유값 개수를 적은 메모리로 **추정**하는 기능이다. 이 그림은 원리 설명이며 실제 ES 응답이 아니다. [고유값 추정](https://www.elastic.co/docs/reference/aggregations/search-aggregations-metrics-cardinality-aggregation)

사용자 ID 두 개가 반드시 실제 사람 두 명이라는 뜻도 아니다. 한 사람이 여러 계정을 쓰거나 여러 사람이 계정을 공유할 수 있다. 순방문자를 보고 싶다면 어떤 식별값과 기간을 기준으로 셌는지 함께 정해야 한다.

또 E1이 다른 문서 ID로 중복 저장되면 문서 수는 6건이 될 수 있지만 고유 사용자 값은 여전히 2개다. **고유 사용자 수를 세는 것과 중복 이벤트를 막는 것은 다르다.**

## 04 · 무엇을 센 숫자인지 먼저 확인한다

숫자가 예상과 다르면 집계 함수부터 바꾸기 전에 아래를 확인한다.

1. **어떤 사건인가?** 검색 실행만 센 것인지, 클릭이나 자동완성 요청까지 섞였는지 본다.
2. **어떤 기간인가?** 사건 발생 시간인지 수집 시간인지, 한국 날짜인지 UTC 날짜인지 확인한다.
3. **같은 사건이 한 번만 기록됐는가?** 누락·재전송·중복 저장과 필드가 없는 기록을 본다.
4. **정확한 수인가, 추정값인가?** 집계 응답과 실패·시간 초과 여부를 확인한다.

이 예시에서 결과가 0개였던 검색은 **E2 한 건**이다. 결과 수를 모두 더하는 것은 “검색 횟수”도 “검색한 사용자 수”도 아니다.

일반적인 집계 대상은 `query`로 선택한 문서들이다. 목록으로 돌려받을 문서 수와 집계 대상 수는 별개다. **size: 0은 목록을 받지 않겠다는 뜻이지 0건을 집계한다는 뜻이 아니다.** [집계 범위와 size](https://www.elastic.co/docs/explore-analyze/query-filter/aggregations)

<details>
<summary>이 5건의 검색어와 사용자 수는 어떻게 요청할까?</summary>

아래는 설명용 인덱스 `study-search-events`의 조회 요청이다. ES에 HTTP로 보낼 JSON이며 Java 함수가 아니다. `aggs`는 집계들을 넣는 곳, `by_query`와 `unique_users`는 우리가 결과에 붙인 이름이다. terms와 cardinality는 ES가 제공하는 기능이다.

조건: query와 userId는 **keyword**로 준비하고, eventType도 keyword, occurredAt은 date다. 같은 기간의 SEARCH_EXECUTED 문서만 대상으로 한다. 실제 프로젝트의 현재 로그 스키마가 아니다.

```http
POST /study-search-events/_search
{
  "size": 0,
  "query": {
    "bool": {
      "filter": [
        { "term": { "eventType": "SEARCH_EXECUTED" } },
        { "range": { "occurredAt": {
          "gte": "2026-10-12T00:00:00+09:00",
          "lt": "2026-10-13T00:00:00+09:00"
        } } }
      ]
    }
  },
  "aggs": {
    "by_query": {
      "terms": { "field": "query", "size": 10 }
    },
    "unique_users": {
      "cardinality": { "field": "userId" }
    }
  }
}
```

읽는 순서는 **검색 실행 기록 선택 → 기간 제한 → 검색어별 묶기와 사용자 고유값 추정**이다. 5건의 모든 기록이 조건에 맞는다면 손계산 기준으로 검색어 묶음은 3/2, 사용자 표시는 2개다. 여기서는 요청을 실행하지 않았고 응답을 만들어 붙이지 않았다.

</details>

<details>
<summary>cardinality의 정확도를 높이면 정확한 값이 될까?</summary>

cardinality는 **HyperLogLog++** 방식으로 고유값 개수를 추정하며, 단일 샤드에서도 근사 방식이다. `precision_threshold`는 메모리와 정확도를 조절하는 값이지 “이 개수 아래는 무조건 정확하다”는 경계가 아니다.

보통 오차가 작다고 모든 데이터에서 1% 이내라고 보장할 수도 없다. 정확한 대사나 정산 수치가 필요하다면 추정값을 확정값으로 쓰지 않고 원본과 정확한 집계 방법을 따로 검증한다. [정확도 조건](https://www.elastic.co/docs/reference/aggregations/search-aggregations-metrics-cardinality-aggregation)

</details>

<details>
<summary>인기 검색어 TOP 10도 잘못 나올 수 있을까?</summary>

여러 샤드에서 상위 후보를 가져와 합치는 terms 집계는 일부 후보의 문서 수를 놓칠 수 있다. “상위 10개는 항상 믿고 하위 순위만 주의”라고 나눌 수는 없다.

기본 문서 수 내림차순에서 오차 관련 정보를 보고, 필요하면 `show_term_doc_count_error`로 버킷별 `doc_count_error_upper_bound`를 확인한다. `sum_other_doc_count`는 반환하지 않은 묶음에 속한 문서 수이며, 개별 버킷의 오차와 같은 뜻은 아니다.

`shard_size`를 늘리면 후보를 더 가져오지만 비용이 늘고 무조건 정확해지는 것은 아니다. 다른 정렬 방식에서는 오차 정보의 의미나 계산 가능 여부도 달라진다. [terms 오차와 정렬 조건](https://www.elastic.co/docs/reference/aggregations/search-aggregations-bucket-terms-aggregation)

</details>

<details>
<summary>날짜별 검색량은 자정 기준을 어떻게 정할까?</summary>

시간 구간별로 문서를 묶는 기능이 **date_histogram**이다. 기본 구간 경계는 UTC이므로 한국의 하루를 원하면 `time_zone: "Asia/Seoul"`을 명시한다. 집계 구간만 바꾸지 말고 query의 조회 기간도 맞춰야 한다.

별도의 날짜 경계 예시로, **한국 10/13 00:10은 UTC 10/12 15:10**이다. 같은 기록이지만 한국 일별 묶음은 10/13, UTC 일별 묶음은 10/12에 들어간다.

`calendar_interval: "day"`는 달력의 하루, `fixed_interval: "1h"`는 시간 길이를 기준으로 한다. 일광절약시간제를 쓰는 지역에서는 실제 구간 길이도 주의한다. [날짜 경계와 시간대](https://www.elastic.co/docs/reference/aggregations/search-aggregations-bucket-datehistogram-aggregation)

</details>

## 05 · 내 프로젝트 로그로도 바로 계산할 수 있을까?

2026-10-12에 공개 기록과 현재 관련 소스를 대조했다.

- [행동 로그 최소 설계](/decisions/prompthub/product-service/behavior-log-minimum-design-for-measurement)는 **미구현 설계**로 표시돼 있다. 관련 상품 서비스의 main 소스와 로그 설정에서도 SEARCH_EXECUTED/behavior-events/behavior-logs 구현 경로를 찾지 못했다. 조사 범위 밖의 배포 상태까지 단정한 것은 아니다.
- `GatewayAccessLog.java`와 `GatewayAccessLogWriter.java`는 경로, 상태, 소요 시간, 요청 ID 등을 기록한다. 검색어, 검색 결과 수와 사용자 ID를 위 예시처럼 제공하지 않는다.
- `GatewayAccessLogFactory.java`는 쿼리 문자열이 아닌 요청의 path를 기록한다. 검색 API 경로로 요청을 세는 것은 가능하더라도 **검색어별 인기나 고유 사용자를 자동으로 계산할 자료가 있다는 뜻은 아니다.**
- `logstash.yaml`에는 게이트웨이 기록을 gateway 아래로 옮겨 `gateway-access-*`에 넣고, 애플리케이션 로그는 별도 인덱스로 보내는 설정이 있다. 그러므로 실제 집계 필드와 인덱스를 먼저 확인한다.

Kibana는 ES 데이터를 조회해 시각화하는 별도 프로그램이다. 로그가 없는데 그래프를 만들기만 해서 검색어 정보가 생기지는 않는다. 이 작업에서는 집계 기능이나 로그 수집 코드를 추가하지 않았다.

프로젝트 ES 배포 파일의 이미지 선언은 9.4.3, 조사일 공식 릴리스 최신 항목은 9.5.5다. 실제 클러스터, 로그 적재나 대시보드 실행 상태는 조회하지 않았다. [공식 릴리스 노트](https://www.elastic.co/docs/release-notes/elasticsearch)
