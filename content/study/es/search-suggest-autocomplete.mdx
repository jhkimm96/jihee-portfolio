## 01 · 이름을 다 몰라도 상품을 찾고 싶다

민지는 검색창에 **무선**까지만 입력했다. 아직 검색 버튼은 누르지 않았다.

```text
검색창 [ 무선│ ]
         ↓ 입력에 맞는 상품명 후보를 찾는다
제안 목록
  무선 이어폰 PRO
  무선 마우스
         ↓ “무선 이어폰 PRO”를 선택
검색창 [ 무선 이어폰 PRO ]
```

이것이 **자동완성**이다. 입력 중인 글자에서 선택할 후보를 보여준다. 후보 선택 뒤 바로 검색할지, 검색 버튼을 기다릴지는 화면 설계에 달려 있다.

**입력을 서버에 보내고, 서버가 찾은 후보를 화면에 표시한다. ES 기능 하나를 켠다고 검색창까지 자동으로 만들어지지는 않는다.** 위 목록은 실제 응답이 아닌 설명용 예시이며, 실제 프로젝트는 디지털 상품을 다룬다.

## 02 · “이어”가 상품명 중간에 있어도 찾을까?

상품명이 **무선 이어폰 PRO**라면 이름의 첫 글자와, 이름 안의 단어 시작은 다르다.

```text
상품명: [무선] [이어폰] [PRO]

입력 “이어”
  이름 전체의 시작?   아니오 — “무선”부터 시작한다
  단어의 시작?        예     — “이어폰” 앞부분이다
```

**접두어(prefix)**는 글자의 앞부분이다. “이어”를 어디의 앞부분으로 볼지에 따라 필요한 검색 방식이 달라진다.

프로젝트는 **match_phrase_prefix**라는 ES 검색 조건을 쓴다. 입력을 검색용 단위로 나눈 뒤 마지막 단위의 앞부분을 비교한다. 여러 단위를 입력하면 앞선 단위의 순서도 맞아야 한다. 따라서 상품명 맨 앞에서만 찾는 기능은 아니다.

실제 분석 규칙과 색인된 단위에 따라 결과가 달라진다. 앞부분이 같은 단어가 많으면 확장 한도 때문에 기대한 상품을 놓칠 수도 있다. “글자가 포함됐으니 반드시 나온다”로 이해하지 않는다. [검색 조건과 확장 한도](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-match-query-phrase-prefix)

## 03 · 늦게 온 응답이 화면을 되돌릴 수 있다

민지가 “무선”을 입력했다가 지우고 “키보드”로 바꿨다. 요청은 먼저 보냈어도 응답은 나중에 올 수 있다.

```text
요청1: “무선”   ────────────────→ 늦게 도착
요청2: “키보드” ─────→ 먼저 도착

현재 검색창 [ 키보드 ]
먼저 표시   [ 키보드 후보 ]
나중 덮기   [ 무선 이어폰 ]  ← 지금 입력과 맞지 않는다
```

**화면은 최신 입력에 해당하는 응답만 반영해야 한다.** 요청 번호나 입력 변경 번호로 최신 여부를 확인할 수 있다. 이전 요청 취소는 불필요한 브라우저 작업을 줄이는 보조 수단이며, 서버 처리가 반드시 멈췄다는 뜻은 아니다. [브라우저 요청 취소 기능](https://developer.mozilla.org/en-US/docs/Web/API/AbortController)

입력이 잠깐 멈추면 요청하는 **debounce**도 사용할 수 있다. 예를 들어 200ms를 기다리는 것은 설계 예시이지 ES의 필수값이 아니다. 최소 글자 수와 대기 시간은 실제 입력 경험과 요청량을 보고 정한다.

한글 입력은 “ㅁ → 무”처럼 글자를 조합하는 과정이 있다. **IME**는 이런 글자 조합을 돕는 입력 방식이다. 조합 중 요청을 미룬다면 조합 종료 때 최종 입력을 다시 처리해야 한다. 초성 검색과는 별개의 화면 처리다. 이번 작업에서는 프로젝트 프론트엔드의 이 동작을 확인하지 않았다. [조합 중 여부](https://developer.mozilla.org/en-US/docs/Web/API/InputEvent/isComposing), [조합 종료 이벤트](https://developer.mozilla.org/en-US/docs/Web/API/Element/compositionend_event)

<details>
<summary>Completion Suggester와 다른 선택지는 무엇일까?</summary>

모두 ES에서 제공하는 기능이나 설정이다. Java 기본 클래스나 검색창 UI 라이브러리가 아니다. 현재 프로젝트에서 확인한 것은 match_phrase_prefix이며, 나머지는 비교할 선택지다.

| 선택지 | 미리 준비하는 것 | 어떤 후보를 찾을까? |
|---|---|---|
| match_phrase_prefix | 검색 가능한 상품명 text 필드 | 입력의 마지막 단위로 시작하는 단어가 있는 상품 |
| Completion Suggester | completion 필드에 제안 문구 저장 | 저장한 제안 문구의 앞부분에 맞는 후보 |
| edge n-gram | 색인할 때 단어의 앞 조각 저장 | 조각과 맞는 입력으로 상품 검색 |
| search_as_you_type | 전용 필드와 그 하위 필드 | 단어 묶음과 앞 조각을 활용한 입력 중 검색 |

Completion Suggester는 빠른 조회용 자료구조를 메모리에 두지만 구축·메모리 비용이 있다. 모든 자동완성의 기본 정답은 아니다. `input`에 제안 문구, `weight`에 순위용 가중치를 저장한다. “이어폰”으로도 제안하려면 해당 입력 문구를 준비하는 식이다. 판매량이 바뀌었다고 가중치가 저절로 갱신되지는 않는다. [Completion 공식 설명](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/search-suggesters#completion-suggester)

edge n-gram은 예를 들어 “이어폰”에서 “이 / 이어 / 이어폰” 같은 앞 조각을 만드는 방식이다. 만들 조각 길이와 검색 시 분석 규칙을 함께 정한다. [앞 조각 필터](https://www.elastic.co/docs/reference/text-analysis/analysis-edgengram-tokenfilter)

search_as_you_type은 단순히 edge n-gram 하나만 켜는 기능이 아니다. 연속된 단어 묶음과 접두어용 하위 필드를 만들며, 공식 문서는 해당 필드들을 대상으로 `bool_prefix` 방식의 검색을 안내한다. [전용 필드와 검색 예시](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/search-as-you-type)

</details>

<details>
<summary>“ㅅㅅ”으로 “삼성”도 찾을 수 있을까?</summary>

이 글의 상품명 제안만으로 초성 검색이 구현되는 것은 아니다. 별도 설계 예시는 다음과 같다.

```text
상품명 “삼성” → 초성용 값 “ㅅㅅ” 저장
입력   “ㅅㅅ” → 같은 초성 표현으로 비교
```

초성만 추출하는 것과 모든 자모를 분해하는 것은 다르다. “삼ㅅ” 같은 조합 중 입력까지 처리하려면 **저장할 때와 검색할 때의 변환 규칙을 맞추고** 실제 입력으로 시험해야 한다. 상품명만 분해해서 저장했다고 모든 입력이 맞아지는 것은 아니다.

한글 형태소 분석기 Nori를 설치했다는 사실만으로 초성·자모 검색이 완성됐다고 보지 않는다. 변환은 앱에서 전처리하거나 검증한 플러그인 등으로 준비할 수 있다. 현재 확인한 상품명 매핑에는 이 전용 설정이 없다. [Nori가 담당하는 분석](https://www.elastic.co/docs/reference/elasticsearch/plugins/analysis-nori)

</details>

<details>
<summary>오타 교정은 자동완성과 무엇이 다를까?</summary>

자동완성은 “무선”에서 후보 문구를 찾는다. 오타 교정은 잘못 쓴 글자에 가까운 **대안**을 찾는다.

“아이푠 → 아이폰을 찾으셨나요?”는 원하는 화면 예시일 뿐 항상 나오는 ES 응답이 아니다. **Term Suggester**는 분석된 단위별로 철자가 가까운 후보를 제안하고, **Phrase Suggester**는 단어 조합의 통계도 활용한다. 후보는 색인된 어휘, 분석 규칙과 설정에 영향을 받는다. Phrase 예시에 `name.trigram`을 쓴다면 그 필드와 분석 규칙부터 준비해야 한다.

결과가 0건일 때 교정을 제안할지는 서비스의 선택이다. ES가 요청 시점을 강제하지 않는다. Completion도 fuzzy 옵션으로 철자가 조금 다른 입력을 허용할 수 있지만, 이를 문맥 교정과 동일하게 보지는 않는다.

한영 키보드 배열을 잘못 고른 입력은 별도 변환 후보를 설계할 수 있다. 철자 거리만으로 원하는 한영 변환을 보장하지 않는다. [제안 기능별 조건](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/search-suggesters)

</details>

## 04 · 내 프로젝트에서는 어디를 확인할까?

2026-10-12에 상품 서비스의 직접 관련 코드와 테스트를 대조했다.

```text
GET /api/v2/products/suggest?q=프롬
  → 입력 앞뒤 공백 제거 / 소문자화
  → 빈 입력이면 조회하지 않고 빈 목록
  → ES name에 match_phrase_prefix / 판매량 높은 순 / 최대5문서
  → 상품명만 꺼내 같은 이름 중복 제거
  → 문자열 목록 반환
```

- `ProductController.java`와 `ProductQueryService.java`: 위 요청의 진입점과 입력 처리다. 서비스에는 최소 2글자 제한이 없으며, 조회 실패도 빈 목록으로 반환한다. **목록이 비었다고 일치 상품이 없었다고 단정할 수 없다.**
- `ProductSearchQueryBuilder.java`: 검색 조건을 만들고, `ElasticsearchProductSearchQuerier.java`가 공식 외부 Java 클라이언트로 실행한다. 두 클래스는 프로젝트 자체 코드다. 후보는 인기 검색어 로그가 아니라 상품 문서에서 찾는다.
- `products-v1-mapping.json`: name은 text이고 keyword 하위 필드가 있다. completion, search_as_you_type, 초성 전용 설정은 이 파일에 없다.
- `ProductSearchQueryBuilderTest.java`, `ProductQueryServiceTest.java`: 조건 구성과 빈 입력·실패 처리를 검사한다. 통합 테스트에는 중간 단어 검색, 판매량 순서, 건수 제한 사례가 있다. **이번에는 테스트 코드를 읽었고 백엔드 테스트를 실행하지 않았다.**

최대5문서를 가져온 **뒤** 이름 중복을 제거하므로 최종 제안이 5개보다 적을 수 있다. “무조건 서로 다른 이름 5개”를 보장하는 구현은 아니다.

테스트 지원 파일의 ES 이미지 선언은 9.4.3이고, 조사일 공식 릴리스 최신 항목은 9.5.5다. 운영 버전, 실제 토큰·응답·속도와 배포 상태는 확인하지 않았다. [공식 릴리스 노트](https://www.elastic.co/docs/release-notes/elasticsearch)

후보가 이상하면 **현재 입력 → 실제 요청값 → 분석된 단위와 조건 → 응답 목록 → 화면 반영 순서**를 따라 확인한다. 초성 누락과 오래된 응답 덮어쓰기는 원인이 달라, 검색 기능을 바꾸기 전에 구분해야 한다.
