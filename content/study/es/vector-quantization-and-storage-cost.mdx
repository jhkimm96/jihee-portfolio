벡터 검색을 붙이면 저장 공간과 메모리가 늘어난다. 얼마나 늘어나는지, 그리고 그걸 줄이는
방법이 무엇을 포기하는지 정리한다.

## 벡터 하나의 무게

임베딩 벡터는 **소수 여러 개**다. 기본적으로 각 숫자는 `float32`(4바이트)로 저장된다.

```
1,536차원 × 4바이트 = 6,144바이트 ≈ 6KB
```

문서 하나당 6KB다. 문서 수를 곱해보면 이렇게 된다.

| 문서 수 | 벡터 총량 |
|---|---|
| 1,000 | 6MB |
| 10,000 | 60MB |
| 100,000 | 600MB |
| 1,000,000 | **6GB** |

**본문 텍스트보다 무거워지는 지점이 온다.** 상품명·설명이 문서당 1KB라면, 벡터가 그 여섯
배다. "텍스트 몇 KB짜리 문서"라고 생각하던 것이 벡터를 붙이는 순간 성격이 달라진다.

## 진짜 문제는 디스크가 아니라 메모리다

6GB는 디스크로는 별것 아니다. 문제는 **HNSW 인덱스가 메모리에서 돌아야 빠르다**는 데 있다.

HNSW는 "이웃을 타고 이동"하는 방식이라 탐색 중에 여러 지점의 벡터를 계속 읽는다. 이게
디스크에서 일어나면 매 홉마다 디스크 접근이 생겨서, 인덱스를 쓰는 의미가 크게 줄어든다.

게다가 벡터 자체 말고도 **그래프 구조가 따로 메모리를 먹는다.** 각 점이 이웃 목록을 들고
있어야 하기 때문이다. 이웃 수(`m`)가 16이면 문서당 이웃 링크 16개어치가 추가된다.

<summary><b>🔍 그럼 문서 수만큼 메모리를 항상 확보해야 하나요?</b></summary>

전부는 아니다. 운영체제가 자주 읽는 부분을 캐시에 올려두기 때문에, 인기 있는 영역만 메모리에
있어도 대체로 빠르게 동작한다.

문제는 **여러 인덱스가 한 노드를 공유할 때**다. 검색용 인덱스와 로그 인덱스가 같은 노드에
있으면 서로 캐시를 밀어낸다. 로그가 대량으로 들어오는 순간 검색 벡터가 캐시에서 밀려나
갑자기 느려지는 식이다.

그래서 벡터 인덱스를 붙일 때는 **그 노드에 누가 또 세들어 사는지**를 같이 봐야 한다.

</details>

## 양자화 — 정밀도를 내주고 크기를 줄인다

**양자화(quantization)**는 숫자를 더 적은 비트로 표현하는 것이다.

### 비유 — 사진 압축

원본 사진은 색을 아주 미세하게 구분해서 저장한다. JPEG로 압축하면 비슷한 색끼리 묶어서
표현이 거칠어지지만, 사람 눈으로는 차이를 알기 어렵고 파일 크기는 크게 준다.

양자화가 정확히 이것이다. `float32`(4바이트)로 저장하던 숫자를 `int8`(1바이트)로 바꾼다.
**크기가 4분의 1이 된다.**

```
1,536차원 × 1바이트 = 1,536바이트 ≈ 1.5KB   (6KB → 1.5KB)
```

Elasticsearch에서는 매핑에 이렇게 지정한다.

```json
"embedding": {
  "type": "dense_vector",
  "dims": 1536,
  "similarity": "cosine",
  "index_options": { "type": "int8_hnsw" }
}
```

### 어떻게 4분의 1로 줄이나

`float32`는 아주 넓은 범위의 소수를 표현할 수 있다. 그런데 임베딩 값은 실제로는 대체로
`-1 ~ 1` 근처의 좁은 구간에 몰려 있다. **넓은 표현력을 거의 안 쓰고 있는 셈이다.**

그래서 그 구간을 256단계(1바이트로 표현 가능한 수)로 나눠 각 값을 가장 가까운 단계로
반올림한다. 원래 값 `0.4213`이 `0.42`쯤으로 뭉뚱그려지는 것이다.

### 무엇을 잃나

각 숫자가 부정확해지므로 **계산된 거리도 조금 부정확해진다.** 유사도 0.8213이 0.8199로
나오는 식이다.

**이게 대체로 괜찮은 이유는 우리가 필요한 게 절대값이 아니라 순서이기 때문이다.** 추천에서
필요한 건 "이 상품과 가장 비슷한 것 4개"이지 "유사도가 정확히 0.8213인 것"이 아니다. 오차가
순위를 뒤집을 만큼 크지 않으면 결과는 같다.

다만 **아주 근소한 차이로 갈리던 순위는 뒤집힐 수 있다.** 유사도 0.8213과 0.8209가 양자화
후 둘 다 0.82가 되면 순서가 임의로 정해진다.

<details>
<summary><b>🔍 그럼 항상 양자화하는 게 좋은가요?</b></summary>

규모에 따라 다르다.

문서가 수천 건이면 벡터 총량이 수십 MB라 양자화해도 아끼는 절대량이 작다. 정밀도를 내줄
이유가 없다.

문서가 수십만 건을 넘어가면 얘기가 달라진다. 6GB가 1.5GB가 되는 건 **메모리에 다 올라가느냐
마느냐**를 가르는 차이일 수 있고, 그건 정밀도 손실과 비교가 안 되는 이득이다.

**"지금 규모에서 무엇이 병목인가"를 보고 정하면 된다.**

</details>

## 크기를 줄이는 세 갈래

| 방법 | 무엇을 하나 | 대가 |
|---|---|---|
| **양자화** | 숫자 하나의 정밀도를 낮춤 (4바이트 → 1바이트) | 거리 계산이 약간 부정확 |
| **차원 축소** | 숫자 개수를 줄임 (1536 → 512 등) | 표현력 자체가 줄어 의미 구분이 무뎌짐 |
| **저장소 분리** | 벡터 원본은 다른 곳에, 검색용 사본만 검색 엔진에 | 복사 파이프라인이 생김 |

**차원 축소**는 모델이 지원해야 한다. 일부 임베딩 모델은 출력 차원을 지정할 수 있게 해주는데,
차원을 줄이면 크기가 비례해서 준다. 대신 잃는 게 양자화보다 크다 — 양자화는 "같은 정보를
거칠게" 표현하는 것이고, 차원 축소는 "정보 자체를 덜" 갖는 것이다.

**저장소 분리**는 크기를 줄이는 게 아니라 **어디에 부담을 지울지**를 고르는 것이다. 벡터
원본을 데이터베이스에 두고 검색 엔진에는 사본만 두면, 검색 엔진 인덱스가 유실돼도 원본이
남는다. 임베딩은 외부 API를 호출해 만든 값이라 다시 만들려면 비용이 드는데, 그 비용을
0으로 만들 수 있다.

## 정리

- `1536차원 × 4바이트 = 6KB`. 문서 100만 건이면 벡터만 6GB
- **병목은 디스크가 아니라 메모리다.** HNSW는 메모리에서 돌아야 빠르고, 그래프 구조도 따로
  메모리를 먹는다
- 한 노드를 여러 인덱스가 공유하면 서로 캐시를 밀어낸다. **누가 같이 사는지**를 봐야 한다
- **양자화는 정밀도를 내주고 크기를 4분의 1로 줄인다.** 필요한 건 절대값이 아니라 순서라서
  대체로 괜찮지만, 근소한 차이로 갈리던 순위는 뒤집힐 수 있다
- 규모가 작으면 양자화의 이득도 작다. 무엇이 병목인지 보고 정한다
- 크기를 줄이는 갈래는 양자화·차원 축소·저장소 분리 셋이고, 잃는 것이 각각 다르다
