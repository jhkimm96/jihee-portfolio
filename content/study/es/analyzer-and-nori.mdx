## 01 · 같은 이어폰인데 검색어를 다르게 쓴다

상품7의 이름에 모델명을 붙여 **무선 이어폰 PRO**라고 해 보자. 민지는 “이어폰 pro”로 검색한다. 앱은 상품명 전체와 검색어 전체가 똑같은지만 비교하는 게 아니라, 검색에 쓸 단위로 준비한 뒤 비교한다.

**분석기는 문장을 검색용 단위로 나누고 정리하는 규칙 묶음이다.** 만들어진 단위는 **토큰(token)**이라고 부른다. 분석된 단어가 색인에서 비교할 단위로 쓰일 때 **term**이라는 말도 나온다.

이 글은 `text` 필드의 일반적인 단어 검색을 다룬다. 토큰이 겹쳐도 필터나 여러 단어의 일치 조건 때문에 제외될 수 있다. 순위와 최종 결과는 다음 글에서 다룬다.

## 02 · 자르기와 정리하기는 서로 다른 단계다

아래는 **공백에서 자르고 영문을 소문자로 바꾸는 설명용 규칙**이다. 프로젝트의 현재 분석기나 Nori 실행 결과가 아니다.

```text
상품7 이름       무선 이어폰 PRO
                       ↓ 공백에서 자르기
중간 토큰        [무선] [이어폰] [PRO]
                       ↓ 영문 소문자로 정리하기
검색용 토큰      [무선] [이어폰] [pro]
```

자르는 기능을 **토크나이저(tokenizer)**, 잘린 토큰을 바꾸거나 걸러내는 기능을 **토큰 필터(token filter)**라고 한다. 위 장면에서 소문자 필터는 PRO만 pro로 바꾸며 상품 원본 이름을 수정하지 않는다.

분석기는 토크나이저 하나와 필요한 토큰 필터들을 조합한다. 자르기 전에 HTML 태그 같은 문자를 정리하는 **문자 필터**도 넣을 수 있다. 모든 단계를 반드시 넣어야 하는 것은 아니다. [분석기의 구성](https://www.elastic.co/docs/manage-data/data-store/text-analysis/anatomy-of-an-analyzer)

## 03 · 검색어도 준비한 뒤 비교한다

같은 설명용 규칙으로 검색어 “이어폰 pro”를 나눠 보자.

```text
상품7에 준비된 단어     [무선] [이어폰] [pro]
검색어에서 나온 단어          [이어폰] [pro]
                               └ 둘 다 겹침 ┘
```

다른 필터가 없고 **검색어의 두 단어 모두 일치해야 하는 조건**이라면 상품7이 맞는다. 중요한 것은 분석기 이름 자체가 아니라, 비교할 토큰과 검색 조건이다.

예를 들어 상품7에 `이어폰`이 있고 다른 검색 분석기도 `이어폰`을 만든다면, **분석기 이름이 다르다는 이유만으로 검색이 실패하지 않는다.** 반대로 한쪽은 `PRO`, 다른 쪽은 `pro`를 만들면 해당 단어는 그대로 일치하지 않을 수 있다.

보통 같은 분석 규칙으로 시작하지만 자동완성이나 검색 시 동의어 처리 때문에 다르게 설계하기도 한다. `analyzer`는 필드의 분석기 설정, `search_analyzer`는 검색할 때의 별도 설정이다. [색인과 검색 분석](https://www.elastic.co/docs/manage-data/data-store/text-analysis/index-search-analysis), [검색 분석기를 따로 쓰는 경우](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/search-analyzer)

## 04 · Nori는 언제 검토할까?

상품명이 “무선이어폰을”처럼 붙어 있다면 공백에서만 자르는 규칙은 우리가 원하는 “이어폰”을 따로 만들지 못한다. 여기서 **한글의 단어 구성과 조사 등을 분석하는 Nori**를 후보로 검토할 수 있다.

Nori는 ES의 공식 `analysis-nori` 플러그인이 제공하는 기능이다. Java 기본 클래스도, 프로젝트가 만든 코드도 아니다. 사전을 사용하므로 **모든 브랜드명이나 붙여쓴 상품명이 원하는 대로 잘린다는 보장은 없다.** [Nori 공식 설명](https://www.elastic.co/docs/reference/elasticsearch/plugins/analysis-nori)

기본 `standard` 분석기는 단순히 공백만 기준으로 자르는 규칙이 아니라 Unicode의 단어 경계 규칙을 사용한다. “한글이면 standard는 전부 실패한다”거나 “영어면 충분하다”고 단정하지 않는다. 실제 상품명과 검색어로 비교해야 한다. [standard 분석기](https://www.elastic.co/docs/reference/text-analysis/analysis-standard-analyzer)

선택 기준은 간단하다. **찾아야 할 상품을 더 잘 찾는지, 무관한 상품까지 더 나오지는 않는지** 함께 확인한다. Nori 설치 자체가 검색 품질 검증은 아니다.

<details>
<summary>Nori의 none, discard, mixed는 무엇을 바꿀까?</summary>

`decompound_mode`는 Nori가 인식한 복합어를 어떻게 다룰지 정한다.

- `none`: 복합어를 분해하지 않는다.
- `discard`: 분해하고 원형을 버린다. 기본값이다.
- `mixed`: 분해한 토큰과 원형을 함께 남긴다.

이 설정이 “무선이어폰”을 언제나 “무선 / 이어폰”으로 만든다는 뜻은 아니다. 사전과 사용자 사전, 품사 필터에 따라 결과를 확인해야 한다. mixed가 모든 상품 검색에 가장 안전한 것도 아니다. [복합어 처리와 사용자 사전](https://www.elastic.co/docs/reference/elasticsearch/plugins/analysis-nori-tokenizer)

Nori 분석기는 토크나이저뿐 아니라 품사 필터와 읽기 변환 등도 묶는다. 토크나이저만 시험한 결과와 전체 분석기의 결과를 혼동하지 않는다. [Nori 분석기 구성](https://www.elastic.co/docs/reference/elasticsearch/plugins/analysis-nori-analyzer)

</details>

## 05 · 실제 단어는 _analyze로 확인한다

`_analyze`는 ES에 **“이 입력을 이 규칙으로 분석하면 무엇이 나오나?”** 묻는 API다. 상품 저장이나 검색 요청과는 다르다.

다음은 테스트용 ES에 보낼 수 있는 HTTP 요청 예시다. `POST /_analyze`는 경로이고 JSON은 요청 데이터다. Java 코드가 아니다. 여기서는 요청을 실행하지 않았으며 응답 로그를 만들어 붙이지 않았다.

```http
POST /_analyze
{
  "tokenizer": "whitespace",
  "filter": ["lowercase"],
  "text": "무선 이어폰 PRO"
}
```

`whitespace`와 `lowercase`는 ES 기본 제공 기능이라 Nori 설치가 필요 없다. 앞 장면의 **자르기 → 소문자 변환**을 지정한 것이며 공식 동작상 `무선 / 이어폰 / pro`가 예상된다. 응답의 토큰 목록을 실제로 확인하고 입력을 “이어폰 pro”로 바꿔 비교하면 된다. 이 요청은 상품을 색인하지 않는다. [공백 토크나이저](https://www.elastic.co/docs/reference/text-analysis/analysis-whitespace-tokenizer), [소문자 필터](https://www.elastic.co/docs/reference/text-analysis/analysis-lowercase-tokenfilter)

현재 프로젝트 필드를 확인하려면 테스트 환경의 실제 인덱스를 대상으로 `field`를 지정한다.

```http
POST /products-v1/_analyze
{
  "field": "name",
  "text": "무선이어폰을"
}
```

이는 **name 필드의 색인 분석 규칙**을 확인하는 예시다. 별도 검색 분석기가 있다면 그 규칙도 확인해야 한다. 토큰이 비어 있지 않은지만 보지 말고, 필요한 단어가 나왔는지 본다. 토큰 검사만으로 상품이 검색에 반영됐는지, 판매 상태 필터를 통과하는지까지 알 수는 없다. [분석 API](https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-indices-analyze)

<details>
<summary>설치나 설정 변경은 어떻게 구분할까?</summary>

직접 운영하는 ES에서 Nori를 쓰려면 해당 ES 버전에 맞는 플러그인을 준비해야 한다. 공식 설치 안내는 클러스터의 모든 노드에 설치하고 각 노드를 재시작하도록 요구한다. 운영 중 즉석 설치는 이 글의 작업 범위가 아니다. 관리형 서비스는 해당 배포 방식의 제공 여부와 설정을 따로 확인한다. [설치 조건](https://www.elastic.co/docs/reference/elasticsearch/plugins/analysis-nori)

설치한 뒤에도 사용할 필드의 분석기 설정이 필요하다. **설치 → 필드 설정 → 실제 토큰 확인 → 검색 결과 확인**은 별개의 단계다. 색인 분석 규칙을 바꿔도 기존 문서의 검색용 단어가 자동으로 다시 만들어지는 것은 아니다.

</details>

<details>
<summary>동의어를 넣으면 항상 더 잘 찾을까?</summary>

동의어는 우리가 정의한 다른 표현을 검색에 연결하는 규칙이다. 무선과 블루투스를 모든 문맥에서 같은 뜻으로 연결하면 무관한 상품도 찾을 수 있다.

검색 시 적용하면 기존 색인 단어를 다시 만들지 않는 방식으로 변경할 수 있지만, 지원되는 설정과 동의어 갱신·재로드 절차가 필요하다. 파일만 고치면 언제나 즉시 반영된다고 가정하지 않는다. 여러 단어 동의어에는 `synonym_graph` 같은 검색 분석용 기능을 검토한다. [동의어 설정과 검증](https://www.elastic.co/docs/solutions/search/full-text/search-with-synonyms)

</details>

## 06 · 내 프로젝트에서는 어디를 볼까?

2026-10-12에 상품 서비스의 다음 파일을 대조했다. 실제 상품은 디지털 상품이며 이어폰은 설명용이다.

- `products-v1-mapping.json`: name은 `text`지만 Nori나 커스텀 분석기 선언은 없다. 이 파일만으로 운영에 적용된 분석기를 확정하지 않는다.
- `ProductIndexBootstrap.java`: 기존 별칭이 있으면 인덱스 생성을 건너뛴다. 코드의 파일과 현재 클러스터 설정을 나눠 확인해야 한다.
- `ProductIndexBootstrapIntegrationTest.java`: “회의록 정리 노션 템플릿”을 name 필드로 분석해 **토큰이 비어 있지 않은지** 확인한다. 원하는 토큰 목록이나 전체 검색 품질까지 검증하는 조건은 아니다.
- `ProductSearchQueryBuilder.java`: 글자 검색은 name 등 여러 필드를 쓰고 단어 일치 조건도 지정한다. 토큰이 하나 겹친다는 이유로 반드시 결과에 포함되는 것은 아니다.

테스트 지원 파일의 이미지 선언은 ES 9.4.3이다. 현행 공식 문서와 조사일 릴리스 최신 항목 9.5.5를 대조했지만, 운영 버전이나 플러그인 목록은 조회하지 않았다. 이번 작업에서 ES API와 백엔드 테스트를 실행하지 않았다. [공식 릴리스 노트](https://www.elastic.co/docs/release-notes/elasticsearch)

## 기억해 볼 질문

색인 분석기는 A, 검색 분석기는 B인데 양쪽에 `이어폰`이라는 단어가 나왔다. 이름이 다르다는 이유만으로 실패할까? _analyze가 성공하면 상품 검색도 성공했다고 말할 수 있을까?

<details>
<summary>답 확인</summary>

분석기 이름만으로 실패를 판단하지 않는다. 실제 토큰과 검색 조건을 본다. _analyze는 분석 결과만 확인하므로 문서 반영, 검색 필드와 필터, 최종 검색 결과는 따로 검증해야 한다.

</details>
