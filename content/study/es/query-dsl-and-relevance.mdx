## 01 · “이어폰, 5만원 이하, 판매 중”을 찾는다

민지는 이어폰을 사고 싶다. 검색어는 **이어폰**, 유형은 **오디오**, 예산은 **5만원 이하**다. 같은 단어가 들어 있다고 이어폰 케이스나 판매 중지 상품까지 보여주면 안 된다.

**검색은 결과에 들어올 조건과, 들어온 결과의 순서를 나눠 설계한다.** 이 글은 일반적인 글자 기반 검색 예시다. 상품이 ES 검색에 반영됐고, 이름에서 “이어폰”을 찾을 수 있는 분석 규칙이 준비됐다고 가정한다.

다음은 프로젝트 실측이 아닌 설명용 상품이다. 실제 프로젝트는 디지털 상품을 다룬다.

| 상품 | 이름 | 유형 | 가격 | 판매 중 |
|---|---|---|---|---|
| 상품7 | 무선 이어폰 PRO | 오디오 | 50,000원 | 예 |
| 상품8 | 무선 이어폰 기본형 | 오디오 | 30,000원 | 예 |
| 상품9 | 블루투스 이어폰 | 오디오 | 70,000원 | 예 |
| 상품10 | 이어폰 케이스 | 액세서리 | 10,000원 | 예 |
| 상품11 | 무선 이어폰 구형 | 오디오 | 20,000원 | 아니오 |

## 02 · 단어가 맞아도 필수 조건에서 빠진다

```text
이름에 “이어폰”이 맞는 후보
[상품7] [상품8] [상품9] [상품10] [상품11]
                  ↓ 예산 / 유형 / 판매 상태 확인
[상품7] [상품8]    상품9: 7만원이라 제외
                  상품10: 액세서리라 제외
                  상품11: 판매 중이 아니라 제외
```

이 그림은 **조건을 이해하기 위한 순서**다. ES가 반드시 이 순서로 모든 문서를 훑는다는 뜻은 아니다.

여러 조건을 묶는 ES 기능이 **bool 쿼리**다. `must`는 맞아야 하며 점수 계산에 참여하는 조건, `filter`는 맞아야 하지만 점수에는 참여하지 않는 조건이다. 금지할 조건은 `must_not`으로 제외할 수도 있다.

가격 조건을 filter에 두면 **싼 상품에 점수를 더 주는 것이 아니라, 예산을 넘은 상품을 빼는 것**이다. [bool 조건과 점수](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-bool-query)

## 03 · 남은 두 상품의 순서는 무엇으로 정할까?

검색에 얼마나 잘 맞는지 표현한 값이 **관련도 점수 `_score`**다. 일반적인 text 검색의 기본 유사도 방식은 **BM25**이며, 단어의 등장 횟수와 희소성, 필드 길이 등이 영향을 준다. 단어를 반복하면 점수가 끝없이 비례해 오르는 방식은 아니다. [BM25 공식 설명](https://www.elastic.co/docs/reference/elasticsearch/index-settings/similarity)

여기서는 상품7의 점수가 8, 상품8이 5라고 **가정**하자. 실제 계산 결과나 이 상품명에서 자동으로 나오는 점수가 아니다.

```text
같은 후보: 상품7 / 상품8

관련도 높은 순            가격 낮은 순
1. 상품7 — 점수8           1. 상품8 — 30,000원
2. 상품8 — 점수5           2. 상품7 — 50,000원
```

**후보는 그대로인데 정렬 기준만 바뀌었다.** 가격순은 관련도 점수가 더 높은 상품을 먼저 놓는 기준이 아니다.

`sort`에는 여러 기준을 순서대로 지정할 수 있고 `_score`도 포함할 수 있다. “sort를 넣으면 점수 기준을 무조건 버린다”는 설명은 맞지 않는다. [정렬 기준의 우선순위](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/sort-search-results)

## 04 · 판매량 같은 신호로 점수를 조정할 수도 있다

관련도만으로는 서비스가 원하는 순서가 아닐 수 있다. ES의 **function_score**는 기존 후보의 점수를 문서의 판매량, 평점 같은 값으로 조정하는 기능이다. Java 메서드 이름이 아니라 ES 검색 조건의 일부다.

다음은 **기존 점수와 추가 점수를 더하는 규칙**을 선택한 설명용 계산이다. 추가 점수도 임의의 값이며 판매량 원문이나 실제 프로젝트 점수가 아니다.

```text
상품7: 관련도8 + 추가점수1 = 9
상품8: 관련도5 + 추가점수6 = 11

조정 전: 상품7 → 상품8
조정 후: 상품8 → 상품7
```

상품9는 예산에서 이미 제외됐으므로 점수를 높인다고 이 예시의 결과에 되살아나지 않는다. 다만 `min_score` 같은 추가 조건을 지정하면 점수로 결과를 제외하는 설계도 가능하다. [점수 조정과 조건](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-function-score-query)

이 순서를 바꿨다고 개인화 추천을 구현한 것은 아니다. 판매량은 여러 사용자에게 공통인 신호이고, 개인화는 사용자별 신호와 별도 검증이 필요하다.

<details>
<summary>이 조건은 ES에 어떻게 보낼까?</summary>

Query DSL은 **검색 조건을 JSON으로 표현하는 방식**이다. 아래 HTTP 요청은 설명용 인덱스 `study-products`에 보내는 예시이며 현재 프로젝트에 그대로 실행하는 요청이 아니다.

조건: name은 text, productType은 keyword, amount는 숫자, onSale은 boolean으로 준비된 테스트 데이터다. 매핑을 만들거나 상품을 저장하는 요청이 아니라 이미 검색 가능한 문서들을 조회한다.

```http
POST /study-products/_search
{
  "query": {
    "bool": {
      "must": [
        { "match": { "name": "이어폰" } }
      ],
      "filter": [
        { "term": { "productType": "오디오" } },
        { "range": { "amount": { "lte": 50000 } } },
        { "term": { "onSale": true } }
      ]
    }
  },
  "sort": [
    { "amount": "asc" }
  ]
}
```

`match`는 검색어를 분석해 비교하고, `term`은 색인된 단위와 비교한다. `range`는 값의 범위를 검사하며 `lte`는 “이하”다. 앞 예시의 상품7/8 중 가격순으로 상품8을 먼저 반환할 조건이다. 여기서는 실제 ES 요청을 실행하지 않았다.

</details>

<details>
<summary>should는 언제 필수 조건이 될까?</summary>

`should`는 일치하면 점수에 기여하는 조건이지만 언제나 선택 사항은 아니다. 같은 bool 안에 should가 있고 must와 filter가 **둘 다 없으면**, 기본적으로 should 한 개 이상이 맞아야 한다. must 또는 filter가 있으면 기본 필수 개수는 0이다.

“필터에 맞는 상품 중 브랜드A나 브랜드B 중 하나도 반드시 맞아야 한다”면 `minimum_should_match: 1`처럼 필요한 개수를 명시한다. 필터가 있는데 should를 필수로 지정하지 않으면 브랜드가 안 맞는 상품도 나올 수 있다. [should 기본 조건](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-bool-query)

</details>

<details>
<summary>filter로 쓰면 항상 캐시되어 빠를까?</summary>

항상은 아니다. filter는 점수를 계산하지 않는다는 의미가 먼저다. 노드 쿼리 캐시는 반복 사용 이력과 세그먼트 조건 등을 보고 적용되며, term 쿼리는 이 캐시 대상이 아니다. 작은 데이터의 조회가 반복됐다는 이유로 캐시가 사용됐다고 단정하지 않는다. [노드 쿼리 캐시 조건](https://www.elastic.co/docs/reference/elasticsearch/configuration-reference/node-query-cache-settings)

</details>

<details>
<summary>name^3이면 모든 필드 점수를 더한 뒤 3배가 될까?</summary>

`name^3`는 name 필드에 가중치를 주는 표기다. 문서 전체의 점수나 최종 순위를 무조건 3배로 만드는 뜻은 아니다.

여러 필드를 검색하는 `multi_match`의 `best_fields`는 보통 가장 잘 맞는 필드의 점수를 쓴다. `tie_breaker`가 있으면 다른 일치 필드 점수의 일부를 더한다. 모든 필드 점수를 항상 단순 합산하는 방식으로 설명하면 안 된다. [multi_match 방식별 차이](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-multi-match-query)

function_score의 `score_mode`는 **추가 함수끼리** 합치는 방식이고, `boost_mode`는 그 결과를 **기존 검색 점수와** 합치는 방식이다. 두 이름의 합산 대상이 다르다. [점수 결합 옵션](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-function-score-query)

</details>

## 05 · 내 프로젝트에서는 어디를 확인할까?

2026-10-12에 상품 서비스의 다음 파일을 대조했다. 위 이어폰/오디오/onSale 예시는 현재 구현의 데이터나 필터가 아니다.

- `ProductSearchQueryBuilder.java`: name, tags.text, description, model.text를 `best_fields`로 검색하고 `tie_breaker: 0.3`과 단어 일치 조건을 지정한다. 상품 유형은 filter로 제한한다.
- 같은 파일의 `withPopularityBoost()`: popular일 때 판매량, 조회수, 평점, 등록일 신호를 넣는다. 함수끼리도, 기존 점수와도 `sum`으로 결합한다. 실제 추가 점수는 가중치와 변환을 거치므로 원래 판매량을 그대로 더하는 것이 아니다.
- 같은 파일의 `buildSort()`: rating은 평점 내림차순, price-asc는 amount 오름차순이다. 같은 값이면 familyRootId로 순서를 정한다.
- `ElasticsearchProductSearchQuerier.java`: 요청을 실행한다. 검색어가 있고 popular이며 요청 범위가 정해진 창 안이고 검색어 벡터를 얻으면, 글자 검색과 의미 검색의 순위를 합친다. **최종 popular 결과를 function_score만의 결과로 설명하지 않는다.**
- `ProductSearchQueryBuilderTest.java`: 요청에 필터와 검색 필드, 점수 함수, 정렬 필드가 들어가는지 검사한다. 코드 구성 검사와 실제 ES의 검색 품질 검증은 다르다.

공식 외부 Java 클라이언트는 요청을 조립·전송하는 라이브러리다. 프로젝트의 위 클래스들은 무엇을 검색하고 어떻게 정렬할지 정하는 자체 코드이며, Java 기본 제공 기능과 구분한다.

테스트 지원 파일의 ES 이미지 선언은 9.4.3, 조사일 공식 릴리스 최신 항목은 9.5.5다. 실제 운영 버전과 가중치 적용값은 조회하지 않았다. 이번 작업에서 백엔드 테스트나 ES 요청을 실행하지 않았다. [공식 릴리스 노트](https://www.elastic.co/docs/release-notes/elasticsearch)

이상한 결과는 **실제로 보낸 조건 → 포함·제외된 상품 → score 또는 sort 값 → 앱의 결과 병합** 순으로 확인한다. 기대한 상품이 후보에 없는데 가중치부터 높이면 원인을 놓칠 수 있다.
