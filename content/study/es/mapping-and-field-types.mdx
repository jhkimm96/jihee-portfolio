## 01 · “이어폰”을 찾기와 “무선 이어폰”만 고르기

민지는 상품7 **무선 이어폰**을 등록했다. 구매자는 “이어폰”만 입력해도 찾고 싶고, 운영자는 **이름 전체가 “무선 이어폰”인 상품만** 모아 보고 싶다.

**같은 값도 찾는 목적에 따라 검색용 형태를 다르게 준비한다.** 단어 검색에는 `text`, 이름 전체 비교에는 `keyword`가 흔히 쓰인다. 이 글은 기본적인 문자열 필드와 검색을 설명하며, 별도 정규화나 동의어 규칙은 넣지 않은 예시다.

ES에 어떤 필드를 어떤 타입으로 준비할지 정하는 설정이 **매핑(mapping)**이다. 필드는 `name`처럼 값의 이름이고, 타입은 그 값을 어떻게 다룰지 정하는 종류다.

## 02 · 원본 이름은 하나, 검색용 준비는 두 갈래

```text
입력: 상품7의 name = "무선 이어폰"
                  │
          ┌───────┴─────────┐
          ▼                 ▼
name: text             name.keyword: keyword
무선 / 이어폰          무선 이어폰
단어로 찾을 준비       이름 전체로 비교할 준비
```

그림의 단어 분리는 이해용이며 실제 분석기 출력이 아니다. 단어를 나누고 정리하는 **분석기**에 따라 결과가 달라진다. 이름이 “무선이어폰”처럼 붙어 있어도 언제나 같은 단어가 나온다고 보장하지 않는다.

한 원본 필드를 여러 방식으로 색인하는 설정이 **multi-field**다. 개발자가 이름을 두 번 입력하거나 원본 JSON에 `name.keyword` 값을 따로 넣는 것이 아니다. `.keyword`도 모든 필드에 자동으로 존재하는 이름은 아니다. 이 예시에서는 우리가 붙인 하위 필드 이름이다. [multi-field 공식 설명](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/multi-fields)

## 03 · 같은 상품에 다른 질문을 보낸다

상품7이 검색에 반영됐고, `name`에 “무선”, “이어폰”이 각각 검색 단위로 준비됐다고 가정하자.

| 우리가 묻는 질문 | ES가 보는 필드와 방식 | 상품7 |
|---|---|---|
| “이어폰” 단어를 가진 상품인가? | `name`에 `match` | 찾음 |
| 이름 전체가 “이어폰”인가? | `name.keyword`에 `term` | 못 찾음 |
| 이름 전체가 “무선 이어폰”인가? | `name.keyword`에 `term` | 찾음 |

`match`는 입력을 분석해서 검색하는 ES 기능이다. `term`은 이미 색인된 검색 단위와 비교하는 기능으로, 위 예시에서는 이름 전체를 비교한다. Java 기본 함수나 새로 설치할 라이브러리가 아니다. [text 필드](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/text), [term 검색](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-term-query)

**단어 검색은 임의의 글자 조각 검색과 다르다.** “이어” 두 글자만 입력해 “이어폰”을 항상 찾는 것은 아니다. 자동완성은 별도 검색 조건과 색인 방식을 검토한다.

`keyword`도 “정확 비교만 가능하고 다른 검색은 불가능하다”는 뜻은 아니다. 이 글은 대표 용도인 전체 값 비교를 보여준다. 이름 전체로 묶어 개수를 세거나 정렬할 때도 보통 이 필드를 쓴다. `text`의 단어를 정렬하기 위해 메모리 기능을 켜는 것과 이름 전체를 정렬하는 것은 다르다. [keyword 용도](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/keyword)

## 04 · 설정에서는 어디를 바꿀까?

아래는 **매핑의 name 부분만** 떼어낸 JSON이다. JSON은 설정 데이터를 표현하는 형식이다. 이것만 실행하는 Java 코드나 완전한 인덱스 생성 요청은 아니다.

```json
{
  "name": {
    "type": "text",
    "fields": {
      "keyword": { "type": "keyword" }
    }
  }
}
```

읽는 순서는 간단하다.

1. `name` 값을 `text`로 준비한다.
2. `fields` 안에 같은 값을 다른 방식으로 준비할 하위 필드를 둔다.
3. `keyword`라는 이름의 하위 필드를 `keyword` 타입으로 준비한다.

이 설정으로 만들어진 인덱스에 상품7을 넣으면 앞 장면처럼 두 방식으로 검색할 수 있다. **이미 저장된 인덱스는 설정 파일만 고쳤다고 바뀌지 않는다.**

<details>
<summary>없는 필드가 들어오면 자동으로 만드는 게 좋을까?</summary>

타입을 값에서 추정하는 것이 **동적 매핑**이고, 우리가 미리 선언하는 것이 **명시적 매핑**이다. 두 방식은 함께 쓸 수 있다. 날짜처럼 보이는 문자열, 템플릿과 인덱스 설정에 따라 추정 결과가 달라지므로 문자열이 항상 똑같은 매핑이 된다고 가정하지 않는다.

일반 비-columnar 인덱스에서 `dynamic: false`는 새 필드를 매핑에 추가하지 않으며, 기본적으로 켜져 있는 원문 보관 영역 `_source`에는 값이 남는다. `dynamic: strict`는 선언하지 않은 필드가 오면 문서를 거부한다. 오타를 일찍 발견할 수 있지만 생산자가 필드를 추가할 때도 실패하므로 무조건 실무 정답은 아니다. [dynamic 공식 설명](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/dynamic)

한글 분석기 Nori 역시 모든 상품 검색의 필수 조건이 아니다. 데이터와 필요한 검색어를 놓고 기본 분석기와 비교해 선택한다.

</details>

<details>
<summary>원본에는 값이 있는데 keyword로 못 찾는 경우</summary>

일반 비-columnar 인덱스에서 `ignore_above: 256`을 설정했다면 256자를 넘는 값은 해당 keyword 필드의 색인 대상에서 빠진다. 기본 `_source`에는 원문이 남아도 그 하위 필드의 정확 비교나 집계에는 나오지 않는다.

다만 256은 모든 keyword 필드의 기본값이 아니다. 흔한 동적 문자열 매핑의 하위 keyword에 붙는 값이며, 직접 선언한 매핑과 실제 적용 설정을 확인해야 한다. [ignore_above](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/ignore-above), [keyword 기본값 구분](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/keyword)

</details>

<details>
<summary>기존 매핑은 정말 아무것도 못 바꿀까?</summary>

기존 필드 타입을 `text`에서 `keyword`로 직접 바꿀 수는 없다. 새 인덱스를 원하는 타입으로 만들고 데이터를 다시 색인하는 방법을 검토한다. 하지만 새 필드나 multi-field 추가, 지원되는 일부 매핑 옵션 변경은 가능하다. [매핑 변경 공식 예시](https://www.elastic.co/docs/manage-data/data-store/mapping/update-mappings-examples)

**하위 필드를 나중에 추가해도 기존 문서에 값이 자동으로 채워지지는 않는다.** 기존 문서를 다시 반영하는 작업과 검증이 필요하다. 별칭(alias)은 조회 대상을 가리키는 이름이며, 별칭 전환만으로 데이터 복사나 전환 중 발생한 새 변경까지 해결되는 것은 아니다. [기존 문서의 multi-field 주의점](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/multi-fields)

</details>

<details>
<summary>옵션의 색상과 재고도 text/keyword만 정하면 될까?</summary>

옵션 배열은 **값 사이의 짝**도 중요하다. 다음은 프로젝트 구현이 아닌 설명용 옵션이다.

```text
실제 옵션                 짝을 잃고 각각 비교하면
빨강 → 재고0              색상: 빨강, 파랑
파랑 → 재고5              재고: 0, 5
```

일반 `object` 배열에서 필드를 독립적으로 비교하면 “빨강이 있고 재고5도 있다”는 이유로 빨강 재고가 있는 것처럼 잘못 매칭할 수 있다. 같은 옵션 안에서 두 조건을 확인하려면 `nested` 매핑과 `nested` 검색을 검토한다. 별도 비용이 있으므로 모든 객체 배열에 강제하지 않는다. [nested와 객체 배열](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/nested)

</details>

## 05 · 내 프로젝트에서는 어디를 확인할까?

2026-10-12에 상품 서비스의 파일을 직접 대조했다. 실제 상품은 디지털 상품이며 이어폰은 이해용 예시다.

- `products-v1-mapping.json`: 상품명에 위와 같은 `text`와 하위 `keyword`가 있다. Nori, `ignore_above: 256`, `dynamic: strict`는 이 파일에 선언돼 있지 않다.
- `ProductSearchQueryBuilder.java`: 글자 검색은 `name`, `tags.text`, `description`, `model.text`를 사용한다. 상품 유형은 `productType`에 `term` 조건을 건다. **name.keyword 선언이 있다고 현재 이름 전체 비교 기능까지 사용 중이라고 말하지 않는다.**
- `ProductIndexBootstrap.java`: `products` 별칭이 있으면 생성 작업을 건너뛴다. 파일의 매핑과 운영에 이미 만들어진 매핑은 다를 수 있다.
- `ProductIndexBootstrapIntegrationTest.java`: name 분석 결과가 비어 있지 않은지 확인한다. 원하는 단어가 정확히 나오는지, 모든 검색어의 품질이 좋은지까지 보장하는 테스트는 아니다.

테스트 지원 파일의 ES 이미지 선언은 9.4.3이다. 현행 공식 문서를 함께 대조했지만 실제 실행 버전과 적용 매핑은 조회하지 않았다. 이번 작업에서는 ES 요청이나 백엔드 테스트도 실행하지 않았다. 최신 문서의 다른 인덱스 모드와 기본값을 현재 프로젝트에 그대로 적용하지 않는다. [공식 릴리스 노트](https://www.elastic.co/docs/release-notes/elasticsearch)

확인은 테스트 환경에서 **적용 매핑 → name의 실제 분석 결과 → 같은 상품에 대한 match와 term 결과** 순으로 하면 된다. 코드가 틀렸다는 추측부터 하지 않고 요청한 필드, 값과 검색 반영 여부를 함께 본다.
