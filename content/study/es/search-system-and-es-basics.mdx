## 01 · 등록한 상품을 검색으로 찾고 싶다

민지가 상품7 **무선 이어폰**을 등록했다. 이름을 검색하면 관련 상품을 찾고, 가격이나 평점으로 정렬하고 싶다.

**검색용 사본은 원본 상품을 찾기 좋은 형태로 다시 준비한 데이터다.** Elasticsearch(이하 ES)는 별도 서버로 실행하는 검색엔진이다. Java 기본 클래스나 캐시 라이브러리가 아니다.

이 글은 상품 원본을 관계형 DB에 두고, ES에 검색용 사본을 보내는 구조를 설명한다. 모든 서비스가 ES를 써야 한다는 뜻은 아니다.

```text
상품7 원본                 상품7 검색용 사본
이름: 무선 이어폰          이름: 무선 이어폰
가격: 50,000원             가격: 50,000원
    DB에 저장   ──복사──▶      ES에 색인
```

**색인(indexing)**은 ES에 데이터를 넣어 검색에 쓸 구조를 만드는 작업이다. 원본 저장과 색인은 별개이므로 사본이 뒤늦게 따라올 수 있다. 이 그림은 설명용이며 프로젝트의 실제 상품은 디지털 상품이다.

## 02 · 상품 목록을 단어 찾아보기로 바꾼다

이름 세 개를 단어로 나눴다고 가정하자. 아래 단어는 이해용이며 실제 분석기 실행 결과가 아니다.

```text
상품7  무선 이어폰       ┌ 무선     → 상품7, 상품8
상품8  무선 마우스  ───▶ ├ 이어폰   → 상품7, 상품9
상품9  블루투스 이어폰   └ 마우스   → 상품8
```

왼쪽은 **상품 → 이름**, 오른쪽은 **단어 → 그 단어를 가진 상품**이다. 오른쪽처럼 방향을 뒤집은 찾아보기를 **역색인**이라고 한다.

검색어가 “무선 이어폰”이면 두 단어의 후보를 찾는다. **두 단어 모두 필수**인 조건이라면 상품7이 남는다. 하나만 맞아도 허용하면 상품8이나 상품9도 후보가 될 수 있다.

후보 포함 여부와 최종 순위는 검색 조건과 점수 계산에 달렸다. 두 단어가 있다는 이유만으로 언제나 1등이 되는 것은 아니다. [텍스트 분석 공식 설명](https://www.elastic.co/docs/manage-data/data-store/text-analysis)

단어를 나누고 정리하는 규칙이 **분석기(analyzer)**다. 붙여쓰기, 조사, 동의어가 자동으로 전부 해결되는 것은 아니다. 한글 분석용 Nori도 선택지이며 설정과 실제 결과를 확인해야 한다. 다음에는 [분석기와 Nori](/study/es/analyzer-and-nori)에서 그 차이를 본다.

## 03 · DB로 검색하면 안 되는 건 아니다

관계형 DB는 테이블에 데이터를 저장하는 PostgreSQL 같은 DB다. PostgreSQL도 전문 검색과 관련도 정렬을 제공하고, `pg_trgm` 확장 인덱스는 앞에 `%`가 있는 `LIKE` 검색도 지원한다.

그러므로 **“DB는 검색을 못 하니 ES를 쓴다”는 설명은 틀리다.** 검색 요구, 데이터량과 운영 부담을 비교해 선택해야 한다. 별도 검색엔진을 두면 사본 동기화도 관리해야 한다. [PostgreSQL 전문 검색](https://www.postgresql.org/docs/18/textsearch-intro.html), [pg_trgm 인덱스](https://www.postgresql.org/docs/18/pgtrgm.html)

이 구조에서는 주문이나 결제의 기준을 원본 DB에 두고, ES는 검색을 담당한다. 검색에 표시된 가격만 믿고 결제를 확정하지 않고 구매 시점의 원본 가격과 판매 상태를 다시 확인하는 식이다.

## 04 · 색인 성공인데 검색 결과는 아직 비었다

상품7의 사본을 ES에 보냈다. ES가 성공 응답을 줘도 **검색에 바로 보인다는 뜻은 아니다.**

```text
① 원본 저장         ② ES 색인 성공       ③ refresh 이후
DB: 상품7 있음      ES: 상품7 반영 접수   검색: 상품7 보임
검색: 아직 없을 수 있음  검색: 아직 없을 수 있음
```

**refresh**는 새 변경을 검색에서 읽을 수 있도록 여는 동작이다. 브라우저 새로고침 버튼과 다르다. 이런 짧은 검색 반영 지연을 **근실시간(Near Real-Time)**이라고 부른다. [검색 반영 공식 설명](https://www.elastic.co/docs/manage-data/data-store/near-real-time-search)

일반 Elastic Stack의 기본 refresh 주기는 1초지만, **사용자가 등록한 뒤 최대 1초면 보인다는 보장은 아니다.** DB에서 ES로 보내기까지의 지연도 있고, 설정과 부하도 영향을 준다. 기본 동작은 최근 검색 여부에 따라 달라질 수 있으며, Elastic Cloud Serverless의 기본 주기는 5초다. [refresh 설정과 조건](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/refresh-parameter)

## 05 · “안 보임”부터 원인을 나눠 확인한다

상품7이 검색에 없다고 바로 refresh 문제로 단정하지 않는다.

1. **원본 DB에 상품7이 있는가?** 없으면 원본 저장부터 확인한다.
2. **원하는 ES 인덱스에 색인이 성공했는가?** 실패했으면 동기화와 오류 기록을 확인한다.
3. **검색 반영 뒤에도 같은 조건으로 안 나오는가?** 분석기, 검색 필드, 판매 상태 필터 등을 확인한다.

반영 지연은 테스트 환경에서 같은 상품을 넣고 **색인 응답 시점과 검색에 처음 등장한 시점**을 따로 기록해 확인한다. ID로 한 건을 가져오는 조회가 성공했다고 검색도 성공했다고 판단하지 않는다.

등록 직후 보여야 한다면 선택지가 다르다.

| 화면의 요구 | 검토할 방법 |
|---|---|
| 등록한 내용만 즉시 보여주면 됨 | 등록 응답으로 확인 화면을 구성 |
| ES 검색에 반영된 뒤 성공 응답이 필요 | 색인 요청에 `refresh=wait_for` 검토 |
| 강제 반영이 꼭 필요한 제한된 작업 | 명시적 refresh 또는 `refresh=true`, 비용 확인 |

`wait_for`는 해당 변경이 검색 가능해질 때까지 응답을 기다리는 ES 요청 옵션이다. **DB에서 ES로 보내는 작업 자체를 대신하지 않는다.** 자동 refresh가 꺼져 있으면 별도 refresh 전까지 기다릴 수 있다. 매 요청 강제 refresh는 작은 세그먼트를 많이 만들어 비용을 늘리므로 기본 해결책으로 삼지 않는다. [옵션별 동작과 비용](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/refresh-parameter)

<details>
<summary>검색 가능과 디스크 보존은 다른 이야기인가?</summary>

그렇다. refresh는 검색 가시성, flush는 Lucene의 저장 확정 지점(commit)을 만들고 새 translog 세대를 시작하는 작업이다. Lucene은 ES 내부 검색을 담당하는 라이브러리이며 별도 앱 코드가 아니다.

translog는 장애 복구에 사용하는 작업 기록이다. 기본 `index.translog.durability=request`에서는 성공 응답 전에 주 샤드와 할당된 복제본의 translog를 디스크에 동기화한다. 따라서 “flush 전에는 성공한 변경도 전부 메모리에만 있다”는 설명은 맞지 않는다. `async` 설정은 최근 변경 유실 위험이 다르며, 어떤 설정도 디스크 자체의 영구 손실까지 해결해 주지는 않는다. [translog와 flush 공식 설명](https://www.elastic.co/docs/reference/elasticsearch/index-settings/translog)

</details>

<details>
<summary>인덱스, 노드, 샤드는 어디에 해당할까?</summary>

- **문서**: ES에 넣은 데이터 한 건. 여기서는 상품7의 검색용 사본이다.
- **인덱스**: 상품 문서처럼 같은 목적의 문서 묶음.
- **노드**: ES 프로세스 하나. 여러 노드가 클러스터를 구성한다.
- **샤드**: 인덱스를 나눈 저장·검색 조각. **레플리카**는 샤드의 복제본이다.
- **세그먼트**: 샤드 내부의 검색 자료 단위. 새 변경과 병합을 통해 관리한다.

서버를 추가한다고 검색 성능이 자동으로 비례해 늘지는 않는다. 샤드 배치, 복제본, 자원과 요청 특성도 봐야 한다. [인덱스와 분산 구조](https://www.elastic.co/docs/manage-data/data-store/index-basics)

클러스터 이름만 맞추는 것도 합류 조건 전부가 아니다. 노드 발견과 초기 구성 설정이 따로 있다. [클러스터 구성 공식 설명](https://www.elastic.co/docs/reference/elasticsearch/configuration-reference/discovery-cluster-formation-settings)

</details>

## 06 · 내 프로젝트에서는 어디를 볼까?

2026-10-10에 상품 서비스의 다음 파일을 대조했다. 코드와 설정의 존재를 확인했으며 실제 클러스터 조회나 백엔드 테스트 실행은 하지 않았다.

- `ProductIndexBootstrap.java`: 검색용 이름 `products`를 실제 인덱스 `products-v1`에 연결한다. 기존 이름이 있으면 생성을 건너뛰므로 파일 수정만으로 운영 설정이 바뀐다고 볼 수 없다.
- `products-v1-mapping.json`: 상품명은 `text`, 정확한 값 조회용 하위 필드는 `keyword`다. 이 파일에는 Nori 분석기나 refresh 주기 설정이 없다. 운영에 적용된 분석기와 주기는 별도 조회가 필요하다.
- `ElasticsearchProductSearchIndexer.upsert()`: 공식 외부 Java 클라이언트의 `client.index(...)`로 사본을 보낸다. 이 경로에는 `refresh=wait_for` 지정이 없다.
- `ElasticsearchProductSearchQuerierIntegrationTest.java`: 색인 뒤 명시적 refresh를 하고 검색하는 테스트가 있다. 이 테스트 구조만으로 자연 반영 시간이나 운영 검색 품질이 검증됐다고 말하지 않는다.

테스트 지원 파일의 ES 이미지 선언은 **9.4.3**이다. 조사일 공식 릴리스 노트의 최신 항목은 **9.5.5**이며, 프로젝트 실행 버전과 같다는 뜻은 아니다. 구버전의 보안 기본값이나 API를 기억으로 가져오지 않고 실제 설정과 해당 버전 문서를 확인한다. [공식 릴리스 노트](https://www.elastic.co/docs/release-notes/elasticsearch)
