데이터베이스의 내용을 검색 엔진이나 캐시 같은 다른 저장소에 복사해 두는 일은 흔하다. 문제는
**원본이 계속 바뀐다**는 것이다. 이 노트는 "바뀐 것만 옮기는" 방식과 그 함정을 정리한다.

## 전체 복사 vs 증분

가장 단순한 방법은 **주기적으로 전부 다시 쓰는 것**이다. 정확하고 구현이 쉽다. 다만 데이터가
늘면 매 주기마다 전체를 읽고 쓰는 비용이 그대로 늘어난다. 아무것도 안 바뀐 주기에도 똑같이
비싸다.

**증분 방식**은 "마지막으로 본 이후에 바뀐 것"만 처리한다. 이걸 하려면 **어디까지 봤는지를
기억**해야 하는데, 그 기억을 **워터마크(watermark)**라고 부른다. 책갈피와 같은 개념이다.

<details>
<summary><b>🔍 워터마크는 정확히 무엇을 저장하나요?</b></summary>

워터마크는 배치가 **마지막으로 성공한 처리 지점**이다. 물에 찍힌 높이 표시처럼 “여기까지
처리했다”는 경계를 나타낸다.

시간을 기준으로 동기화한다면 워터마크에는 마지막 처리 시각이 들어간다.

```text
워터마크: 10:00:00

다음 조회:
updated_at >= 10:00:00
```

상품 ID가 순서대로 증가하고 그 순서를 신뢰할 수 있다면 마지막 ID를 저장할 수도 있다. 중요한
것은 값의 종류가 아니라, 다음 실행이 어디서 다시 시작해야 하는지 기억한다는 점이다.

워터마크는 처리 시작 전에 옮기지 않는다. 처리에 성공했을 때만 전진시켜야 실패한 데이터를 다음
실행에서 다시 찾을 수 있다.

</details>

```sql
SELECT id FROM product WHERE updated_at >= :워터마크;
```

처리가 끝나면 워터마크를 지금 시각으로 옮긴다. 다음 주기에는 그 이후 것만 본다.

간단해 보이지만 함정이 세 개 있다.

## 함정 1 — 커밋 가시성: 시각이 찍히는 때와 보이는 때가 다르다

이런 상황을 생각해보자.

```
10:00:00  트랜잭션 A 시작 → updated_at = 10:00:00 으로 기록
10:00:03  배치 실행 → "10:00:00 이후 바뀐 것" 조회 → A는 아직 커밋 전이라 안 보임
10:00:05  트랜잭션 A 커밋 → 이제 보임
          워터마크는 이미 10:00:03으로 전진했다
```

**A의 변경은 영원히 누락된다.** `updated_at`은 10:00:00인데 워터마크는 이미 그 뒤로 넘어갔기
때문이다.

원인은 **시각이 찍히는 시점(트랜잭션 시작·수정)과 그 행이 다른 세션에 보이기 시작하는
시점(커밋)이 다르다**는 데 있다. 긴 트랜잭션일수록 이 틈이 벌어진다.

### 해결 — 워터마크를 뒤로 물린다 (오버랩)

```sql
WHERE updated_at >= :워터마크 - 30초
```

기준 시각을 조금 뒤로 물려서 조회한다. 이미 처리한 구간을 다시 훑게 되지만 그래도 괜찮다.
**동기화 작업이 멱등(여러 번 해도 결과가 같음)이기 때문이다.** 같은 문서를 다시 덮어써도
내용이 같다.

> **놓치는 것보다 중복이 낫다.** 중복은 비용이지만 누락은 오류다.

오버랩 폭은 "가장 긴 트랜잭션이 얼마나 걸리는가"를 넘겨 잡으면 된다.

<details>
<summary><b>🔍 오버랩 대신 트랜잭션 ID를 쓰면 안 되나요?</b></summary>

가능하고 더 정확하다. Postgres의 `xmin`이나 논리 복제 슬롯을 쓰면 커밋 순서를 기준으로
정확히 자를 수 있다.

다만 데이터베이스 내부 기능에 의존하게 되고 구현이 복잡해진다. 오버랩은 몇 초의 중복 처리로
같은 문제를 막는 **훨씬 싼 해법**이라, 중복 처리가 저렴한 상황에서는 이쪽이 실용적이다.

</details>

## 함정 2 — 실패했는데 워터마크를 전진시키면 유실된다

```
10:00:00  배치 시작 → 100건 발견 → 30건 처리 후 대상 저장소 장애로 실패
          워터마크를 10:00:00으로 전진시킴  ← 잘못
10:00:20  다음 배치 → 10:00:00 이후만 조회 → 나머지 70건은 대상에서 빠짐
```

**규칙은 하나다 — 성공했을 때만 워터마크를 전진시킨다.**

```java
boolean 성공 = 동기화_수행(워터마크);
if (성공) {
    워터마크 = 시작시각;   // 실패하면 그대로 둔다
}
```

실패하면 워터마크가 제자리에 남아서, 다음 주기에 같은 구간을 다시 조회한다. 장애가 회복되면
밀린 변경분이 한꺼번에 따라잡힌다. **영구 손실이 없다.**

여기서 "시작 시각"을 쓰는 것도 중요하다. 처리가 끝난 시각을 쓰면, 처리하는 동안 발생한
변경이 워터마크 뒤로 밀려 누락된다.

### 워터마크를 어디에 두나

| 위치 | 성질 |
|---|---|
| **메모리** | 재시작하면 사라진다 → 첫 주기가 전체 동기화가 됨 |
| **DB·파일** | 재시작해도 이어간다. 대신 저장·조회 코드가 늘고 그 자체가 실패 지점 |

메모리에 두는 게 무조건 나쁜 건 아니다. **워터마크가 없을 때 전체 동기화로 폴백**하도록
만들어 두면, 재시작이 곧 "완전히 맞춰놓고 다시 시작"이 된다. 오히려 안전한 성질이다.
전체 동기화 비용이 감당 가능한 규모에서 쓸 수 있는 방법이다.

## 함정 3 — 동기화가 자기 자신을 다시 부른다

가장 알아채기 어려운 함정이다.

동기화 과정에서 원본 테이블에 뭔가를 쓰는 경우가 있다. 계산 결과를 캐싱하거나, 처리 상태를
표시하거나, 임베딩 같은 파생 값을 저장하는 경우다.

그런데 그 쓰기가 **`updated_at`을 갱신**한다면?

```
배치 실행 → 대상 처리 → 파생 값 저장 → updated_at 갱신
                                              ↓
다음 배치 → "바뀐 것" 조회 → 방금 그 행이 또 걸림 → 또 처리 → 또 갱신 → ...
```

**배치가 자기 꼬리를 문다.** 아무도 데이터를 수정하지 않는데도 매 주기마다 전체를 처리한다.
증분으로 바꾼 이득이 통째로 사라진다.

### 해결 — 파생 값 쓰기는 감사 시각을 건드리지 않는다

```java
@Modifying
@Query(value = "UPDATE product SET embedding = :embedding WHERE id = :id",
       nativeQuery = true)
void updateEmbedding(UUID id, String embedding);
```

JPA의 자동 감사(`@LastModifiedDate`)를 우회하는 네이티브 쿼리로 파생 값만 갱신한다.
"사용자가 바꾼 것"과 "시스템이 계산해 넣은 것"을 구분하는 셈이다.

<details>
<summary><b>🔍 조회수처럼 자주 변하는 값도 같은 문제 아닌가요?</b></summary>

맞다. 조회수를 올릴 때마다 `updated_at`이 갱신되면, **사람이 상품을 열어보기만 해도** 그
상품이 동기화 대상으로 잡힌다.

동기화 자체는 그래도 괜찮다(어차피 조회수도 복사해야 하니까). 문제는 그 과정에 **비싼
작업**이 끼어 있을 때다. 외부 AI API를 호출해 임베딩을 만드는 경우, 글이 하나도 안 바뀌었는데
조회수 때문에 매번 호출하게 된다.

그래서 별도의 장치를 둔다 — **내용의 해시를 저장해두고, 해시가 같으면 비싼 작업을 건너뛴다.**
동기화 대상으로 잡히는 것과 비싼 작업을 실제로 수행하는 것을 분리하는 것이다.

</details>

<details>
<summary><b>🔍 검색 원본 해시는 왜 저장하나요?</b></summary>

해시는 상품명·설명·콘텐츠처럼 임베딩에 사용하는 문자열을 짧은 고정 길이 값으로 바꾼 것이다.

```text
상품명 + 설명 + 콘텐츠
        ↓ SHA-256
3a9f... 같은 64자리 값
```

문자열이 같으면 같은 해시가 만들어진다. 저장된 해시와 현재 해시가 같다면 임베딩에 들어갈
내용도 바뀌지 않았다는 뜻이므로 기존 벡터를 재사용한다.

해시는 상품의 중복 여부를 판단하려는 값이 아니다. **임베딩을 다시 계산해야 하는지 빠르게
판단하기 위한 변경 감지 값**이다.

</details>

## 증분 동기화가 API 호출 폭주까지 막아주지는 않는다

증분 동기화와 임베딩 재계산 방지는 서로 다른 필터다.

```text
워터마크
→ 마지막 성공 이후 변경된 대상을 고른다

검색 원본 해시
→ 변경 대상 중 임베딩 원문이 실제로 달라진 것만 고른다
```

예를 들어 조회수만 바뀐 상품은 워터마크 조회에 포함될 수 있다. 조회수도 검색 문서에 반영해야
하기 때문이다. 하지만 상품명·설명·콘텐츠로 만든 검색 원본 해시가 이전과 같다면 임베딩은 다시
만들 필요가 없다.

따라서 스케줄러가 20초마다 실행된다고 해서 모든 상품을 20초마다 재임베딩하는 것은 아니다.

```text
20초 스케줄 실행
→ 변경된 상품 패밀리 조회
→ 판매 중인 대표 상품 선택
→ 검색 원본 해시 비교
→ 해시가 달라진 상품만 임베딩 API 호출
→ 검색 문서 갱신
```

전체 재조정도 곧 전체 재임베딩을 뜻하지 않는다. 전체 상품을 다시 확인하더라도 저장된 해시와
현재 해시가 같으면 기존 임베딩을 재사용할 수 있다.

<details>
<summary><b>🔍 재대사(reconcile)는 다시 색인한다는 뜻인가요?</b></summary>

재대사는 원본과 사본을 비교해 다시 맞추는 작업이다.

```text
PostgreSQL 상품 원본
        ↓ 비교
Elasticsearch 검색 문서
        ↓
추가·수정할 문서는 upsert
판매 중이 아닌 문서는 delete
```

단순한 “재색인”은 문서를 다시 쓰는 행위에 가깝다. 재대사는 현재 원본 상태를 확인하고
Elasticsearch 문서를 추가할지, 수정할지, 삭제할지 결정하는 과정까지 포함한다.

</details>

### 그래도 429가 가능한 경우

증분 처리는 평상시 호출량을 줄여주지만 외부 API의 처리 한도를 보장하지는 않는다. 다음
상황에서는 짧은 시간에 임베딩 요청이 몰릴 수 있다.

- 기존 데이터에 임베딩 또는 원본 해시가 없는 최초 색인
- 상품 설명이나 콘텐츠를 일괄 변경하는 마이그레이션
- 오랫동안 실패한 변경분이 한꺼번에 다시 처리되는 경우
- 여러 애플리케이션 파드가 같은 스케줄러를 동시에 실행하는 경우
- 전체 재조정 시 실제로 원문이 바뀐 상품이 많은 경우

이때 발생하는 HTTP 429는 Elasticsearch가 아니라 외부 임베딩 API의 요청 수·토큰 수 제한일
수 있다. 반대로 Elasticsearch도 쓰기 큐가 포화되면 429를 반환할 수 있으므로 로그에서는 어느
외부 시스템이 응답했는지 구분해야 한다.

<details>
<summary><b>🔍 HTTP 429는 서버 오류와 무엇이 다른가요?</b></summary>

HTTP 429는 서버가 고장 났다는 의미가 아니라, 정해진 시간 동안 허용된 요청량을 넘었다는
의미다.

임베딩 API는 주로 다음 제한을 둔다.

- 분당 요청 수
- 분당 입력 토큰 수
- 동시에 처리할 수 있는 요청 수
- 계정 또는 모델별 사용량 한도

같은 429라도 응답을 보낸 곳을 구분해야 한다. 임베딩 API의 429는 외부 AI 호출량 문제이고,
Elasticsearch의 429는 색인 요청이 처리 큐보다 빠르게 들어온 문제일 수 있다.

</details>

### 배치 크기 하나로 끝나지 않는다

대량 처리에서는 세 가지 크기를 별도로 조절해야 한다.

```text
DB에서 한 번에 조회할 변경 대상 수
→ 임베딩 API 한 요청에 넣을 문서 수
→ Elasticsearch bulk 요청에 넣을 문서 수
```

임베딩 요청을 지나치게 작게 나누면 분당 요청 수 제한에 걸릴 수 있고, 너무 크게 묶으면 토큰
제한과 실패 재처리 범위가 커진다. 따라서 실제 대량 데이터가 생기면 다음 항목을 함께 측정해
조정한다.

- 임베딩 요청 배치 크기
- 동시 요청 수
- 분당 요청·토큰 사용량
- `Retry-After`를 존중하는 백오프 재시도
- 실패한 항목만 다음 주기에 다시 처리하는 체크포인트
- 다중 파드에서 한 번만 실행되게 하는 분산 락 또는 단일 worker

<details>
<summary><b>🔍 백오프는 그냥 다시 요청하는 것과 무엇이 다른가요?</b></summary>

즉시 재시도하면 제한에 걸린 서버에 요청을 더 보내므로 429가 반복될 수 있다. 백오프는 재시도
사이의 대기 시간을 점점 늘린다.

```text
첫 실패  → 1초 후 재시도
두 번째 → 2초 후 재시도
세 번째 → 4초 후 재시도
```

여러 서버가 같은 순간에 다시 요청하지 않도록 작은 무작위 지연도 더할 수 있다. 서버가
`Retry-After` 헤더로 다시 요청할 시점을 알려주면 그 값을 우선한다.

재시도 횟수는 제한해야 하며, 계속 실패한 항목은 완료 처리하지 않고 다음 배치에서 다시 찾을 수
있게 남긴다.

</details>

평상시 변경량이 작고 해시 비교가 동작한다면 이 장치를 모두 미리 구현할 필요는 없다. 최초
색인이나 대량 변경 테스트에서 실제 호출량과 429를 측정한 뒤 필요한 제한부터 추가한다.

<details>
<summary><b>🔍 PromptHub의 20초 스케줄러는 매번 무엇을 처리하나요?</b></summary>

PromptHub는 마지막 성공 시점 이후 변경된 상품 패밀리만 재대사한다. 그중 판매 중인 대표
상품의 검색 원본 해시가 기존 값과 다를 때만 임베딩 API를 호출한다.

따라서 평상시 20초 증분 처리에서는 전체 상품을 재임베딩하지 않는다. 서버 최초 실행, 일일
전체 재대사, 해시가 없는 기존 데이터, 대량 수정과 다중 파드는 별도의 운영 위험이다.

현재 임베딩 갱신은 상품을 순차적으로 처리하지만 별도의 429 백오프와 처리량 제한은 없다.
지금 당장 발생한 장애는 아니므로 현행 기능이 아니라 대량 데이터가 생길 때 확인할 개선
조건으로 구분한다.

</details>

## 다른 방식들과 비교

| 방식 | 원리 | 장점 | 대가 |
|---|---|---|---|
| **워터마크 폴링** | 주기적으로 `updated_at` 조회 | 구현이 단순. 원본 스키마 변경 없음 | 주기만큼 지연. 삭제 감지가 어려움 |
| **아웃박스** | 변경과 같은 트랜잭션으로 이벤트 테이블에 기록 | 유실 없음. 순서 보장 | 테이블·릴레이 프로세스 추가 |
| **CDC** | DB 트랜잭션 로그를 직접 읽음 | 앱 코드 변경 없음. 거의 실시간 | 인프라(Debezium 등) 추가. 운영 복잡도 |

**삭제 감지**가 워터마크 방식의 약점이다. 행이 사라지면 `updated_at`으로 잡을 수 없다.
소프트 삭제(`deleted_at`)를 쓰면 해결되고, 아니면 주기적으로 **양쪽 ID 목록을 비교해
고아를 찾는** 보정이 필요하다.

선택 기준은 **지연 허용치와 운영 여력**이다. 수십 초 지연이 괜찮고 인프라를 늘리기 싫으면
워터마크 폴링이 가장 싸다. 실시간이 요건이거나 유실이 치명적이면 아웃박스나 CDC로 간다.

## 정리

- 워터마크는 "여기까지 봤다"는 책갈피다. `WHERE updated_at >= :워터마크`
- **함정 1 — 커밋 가시성.** 시각이 찍히는 때와 보이는 때가 달라 누락이 생긴다 → 워터마크를
  몇 초 뒤로 물린다. 중복은 멱등성으로 흡수한다
- **함정 2 — 실패 처리.** 성공했을 때만 전진시킨다. 기준은 처리 시작 시각
- **함정 3 — 자기 트리거.** 동기화가 `updated_at`을 건드리면 배치가 자기 꼬리를 문다 →
  파생 값 쓰기는 감사 시각을 우회한다
- 워터마크는 변경 대상을 고르고, 검색 원본 해시는 그중 비싼 임베딩을 다시 계산할 대상을 고른다
- 증분 처리도 최초 색인·대량 변경·다중 파드에서는 429가 가능하다. 실제 규모가 생기면
  배치 크기·동시성·백오프·단일 실행을 함께 조정한다
- 삭제 감지가 약점이다. 소프트 삭제나 주기적 고아 탐지로 보완한다
- 실시간이 요건이면 아웃박스·CDC로 간다. 수십 초 지연이 괜찮으면 폴링이 가장 싸다
