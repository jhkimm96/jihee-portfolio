## 01 · 배치는 책갈피 뒤쪽만 읽는다

상품 원본을 검색 저장소로 복사할 때 매번 전부 읽는 대신 지난 성공 시점을 기억한다. 그 시점이 **워터마크**, 다음에 어디서 읽을지 알려주는 책갈피다.

```text
지난 책갈피 10:00:00
다음 조회: updated_at이 10:00:00 이후인 상품
```

updated_at은 수정 시각을 기록한 필드다. 이번 예제는 이를 기준으로 변경분을 찾는다.

## 02 · 상품7은 바뀌었는데 아직 보이지 않는다

**커밋**은 트랜잭션의 변경을 확정하는 동작이다. 상품7의 수정 시각이 찍혀도 다른 세션에서 그 변경을 볼 수 있는 시점은 늦을 수 있다.

```text
10:00:00  A가 상품7 수정. updated_at=10:00:00
10:00:03  배치 조회. A는 미커밋이라 상품7 변경이 안 보임
          배치 성공 후 책갈피=10:00:03
10:00:05  A 커밋. 이제 상품7 변경이 보임
다음 조회 10:00:03 이후만 찾음 → 상품7은 범위 밖
```

결과: 그 순간 보이는 변경을 처리했어도 늦게 커밋된 상품을 놓칠 수 있다. 이는 독립 설명 예제이며 실제 누락 발생 기록은 아니다. [PostgreSQL 가시성](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-READ-COMMITTED)

## 03 · 책갈피를 조금 뒤로 물리면?

**오버랩**은 이미 읽은 구간의 일부를 다시 조회하는 방법이다.

```text
책갈피=10:00:03
30초 뒤로 물린 조회 시작=09:59:33
A 커밋 뒤 다음 조회가 실행됨 → 상품7도 다시 찾을 수 있음
```

결과: 앞 예제의 늦은 커밋을 다음 조회에서 잡을 수 있다. 그러나 30초보다 오래 지연된 변경까지 자동으로 보호하지는 않는다.

이미 옮긴 상품을 다시 처리할 수 있으므로 같은 반영을 반복해도 결과가 어긋나지 않게 만든다. 그 성질이 **멱등성**이다. 오래된 결과가 새 결과를 덮어쓰는 경합 등도 따로 확인한다.

## 04 · 호출 성공과 모든 상품 반영 성공은 다르다

```text
상품7: 반영 성공
상품8: 반영 실패
응답:  상품별 결과 포함

실패를 확인하지 않고 책갈피 전진
→ 상품8의 재처리 기회가 빠질 수 있음
```

결과: 책갈피를 옮기기 전 항목별 결과를 확인하고 실패 항목을 다시 찾을 방법을 둬야 한다. Elasticsearch bulk도 개별 실패를 응답에 담는다. [Bulk API 응답](https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-bulk)

성공 기준점은 실행 종료 시각이 아니라 조회 범위를 정한 시작 시각으로 잡는 설계를 검토한다. 이것만으로 누락이 모두 없어지는 것은 아니다. 늦은 커밋과 삭제는 전체 대조 같은 별도 안전망도 필요할 수 있다.

메모리에 저장하면 재시작 때 사라지므로 첫 실행을 전체 재조정으로 만들 수 있다. DB나 파일에 저장하면 이어 읽을 수 있지만 기준점 저장 자체의 실패도 관리해야 한다. 전체 재조정 역시 부분 실패 검출 등 성공 조건을 갖춰야 한다.

PostgreSQL의 xmin은 행 버전을 만든 트랜잭션 ID다. 쓰기 때 ID를 먼저 받은 A가 B보다 늦게 커밋할 수 있으므로 xmin을 단순 커밋 순번처럼 사용하면 해결된다고 쓰지 않는다. 논리 복제 로그를 사용하는 CDC와도 다른 개념이다. [System columns](https://www.postgresql.org/docs/18/ddl-system-columns.html), [Transaction IDs](https://www.postgresql.org/docs/18/transaction-id.html)

</details>

## 함정 3 — 동기화가 자기 자신을 다시 부른다

가장 알아채기 어려운 함정이다.

동기화 과정에서 원본 테이블에 뭔가를 쓰는 경우가 있다. 계산 결과를 캐싱하거나, 처리 상태를
표시하거나, 임베딩 같은 파생 값을 저장하는 경우다.

그런데 그 쓰기가 **`updated_at`을 갱신**한다면?

```
배치 실행 → 대상 처리 → 파생 값 저장 → updated_at 갱신
                                              ↓
다음 배치 → "바뀐 것" 조회 → 방금 그 행이 또 걸림 → 또 처리 → 또 갱신
```

**배치가 자기 꼬리를 물 수 있다.** 사람이 데이터를 수정하지 않아도 방금 처리한 행이 다음 주기에 또 대상이 된다.
증분으로 바꾼 이득이 통째로 사라진다.

### 해결 — 파생 값 쓰기는 감사 시각을 건드리지 않는다

```java
@Modifying
@Query(value = "UPDATE product SET embedding = :embedding WHERE id = :id",
       nativeQuery = true)
void updateEmbedding(UUID id, String embedding);
```

이 발췌는 Spring Data JPA의 @Modifying과 @Query를 사용하는 저장소 메서드다. JPA 엔티티 자동 감사(@LastModifiedDate)를 거치지 않고 파생 값만 갱신한다. DB 트리거가 updated_at을 바꾸는 구성인지도 별도로 확인한다.
"사용자가 바꾼 것"과 "시스템이 계산해 넣은 것"을 구분하는 셈이다.

<details>
<summary><b>🔍 조회수처럼 자주 변하는 값도 같은 문제 아닌가요?</b></summary>

맞다. 조회수를 올릴 때마다 `updated_at`이 갱신되면, **사람이 상품을 열어보기만 해도** 그
상품이 동기화 대상으로 잡힌다.

동기화 자체는 그래도 괜찮다(어차피 조회수도 복사해야 하니까). 문제는 그 과정에 **비싼
작업**이 끼어 있을 때다. 외부 AI API를 호출해 임베딩을 만드는 경우, 글이 하나도 안 바뀌었는데
조회수 때문에 매번 호출하게 된다.

그래서 별도의 장치를 둔다 — **내용의 해시를 저장해두고, 해시가 같으면 비싼 작업을 건너뛴다.**
동기화 대상으로 잡히는 것과 비싼 작업을 실제로 수행하는 것을 분리하는 것이다.

</details>

<details>
<summary><b>🔍 검색 원본 해시는 왜 저장하나요?</b></summary>

해시는 상품명·설명·콘텐츠처럼 임베딩에 사용하는 문자열을 짧은 고정 길이 값으로 바꾼 것이다.

```text
상품명 + 설명 + 콘텐츠
        ↓ SHA-256
3a9f... 같은 64자리 값
```

문자열이 같으면 같은 해시가 만들어진다. 저장된 해시와 현재 해시가 같다면 임베딩에 들어갈
내용도 바뀌지 않았다는 뜻이므로 기존 벡터를 재사용한다.

해시는 상품의 중복 여부를 판단하려는 값이 아니다. **임베딩을 다시 계산해야 하는지 빠르게
판단하기 위한 변경 감지 값**이다.

</details>

## 증분 동기화가 API 호출 폭주까지 막아주지는 않는다

증분 동기화와 임베딩 재계산 방지는 서로 다른 필터다.

```text
워터마크
→ 마지막 성공 이후 변경된 대상을 고른다

검색 원본 해시
→ 변경 대상 중 임베딩 원문이 실제로 달라진 것만 고른다
```

예를 들어 조회수만 바뀐 상품은 워터마크 조회에 포함될 수 있다. 조회수도 검색 문서에 반영해야
하기 때문이다. 하지만 상품명·설명·콘텐츠로 만든 검색 원본 해시가 이전과 같다면 임베딩은 다시
만들 필요가 없다.

따라서 스케줄러가 20초마다 실행된다고 해서 모든 상품을 20초마다 재임베딩하는 것은 아니다.

```text
증분 스케줄 실행
→ 변경된 상품 패밀리 조회
→ 판매 중인 대표 상품 선택
→ 검색 원본 해시 비교
→ 해시가 달라진 상품만 임베딩 API 호출
→ 검색 문서 갱신
```

전체 재조정도 곧 전체 재임베딩을 뜻하지 않는다. 전체 상품을 다시 확인하더라도 저장된 해시와
현재 해시가 같으면 기존 임베딩을 재사용할 수 있다.

<details>
<summary><b>🔍 재대사(reconcile)는 다시 색인한다는 뜻인가요?</b></summary>

재대사는 원본과 사본을 비교해 다시 맞추는 작업이다.

```text
PostgreSQL 상품 원본
        ↓ 비교
Elasticsearch 검색 문서
        ↓
추가·수정할 문서는 upsert
판매 중이 아닌 문서는 delete
```

단순한 “재색인”은 문서를 다시 쓰는 행위에 가깝다. 재대사는 현재 원본 상태를 확인하고
Elasticsearch 문서를 추가할지, 수정할지, 삭제할지 결정하는 과정까지 포함한다.

</details>

### 그래도 429가 가능한 경우

증분 처리는 평상시 호출량을 줄여주지만 외부 API의 처리 한도를 보장하지는 않는다. 다음
상황에서는 짧은 시간에 임베딩 요청이 몰릴 수 있다.

- 기존 데이터에 임베딩 또는 원본 해시가 없는 최초 색인
- 상품 설명이나 콘텐츠를 일괄 변경하는 마이그레이션
- 오랫동안 실패한 변경분이 한꺼번에 다시 처리되는 경우
- 여러 애플리케이션 파드가 같은 스케줄러를 동시에 실행하는 경우
- 전체 재조정 시 실제로 원문이 바뀐 상품이 많은 경우

이때 발생하는 HTTP 429는 Elasticsearch가 아니라 외부 임베딩 API의 요청 수·토큰 수 제한일
수 있다. 반대로 Elasticsearch도 쓰기 큐가 포화되면 429를 반환할 수 있으므로 로그에서는 어느
외부 시스템이 응답했는지 구분해야 한다.

<details>
<summary><b>🔍 HTTP 429는 서버 오류와 무엇이 다른가요?</b></summary>

HTTP 429는 서버가 고장 났다는 의미가 아니라, 정해진 시간 동안 허용된 요청량을 넘었다는
의미다.

임베딩 API는 주로 다음 제한을 둔다.

- 분당 요청 수
- 분당 입력 토큰 수
- 동시에 처리할 수 있는 요청 수
- 계정 또는 모델별 사용량 한도

같은 429라도 응답을 보낸 곳을 구분해야 한다. 임베딩 API의 429는 외부 AI 호출량 문제이고,
Elasticsearch의 429는 색인 요청이 처리 큐보다 빠르게 들어온 문제일 수 있다.

</details>

### 배치 크기 하나로 끝나지 않는다

대량 처리에서는 세 가지 크기를 별도로 조절해야 한다.

```text
DB에서 한 번에 조회할 변경 대상 수
→ 임베딩 API 한 요청에 넣을 문서 수
→ Elasticsearch bulk 요청에 넣을 문서 수
```

임베딩 요청을 지나치게 작게 나누면 분당 요청 수 제한에 걸릴 수 있고, 너무 크게 묶으면 토큰
제한과 실패 재처리 범위가 커진다. 따라서 실제 대량 데이터가 생기면 다음 항목을 함께 측정해
조정한다.

- 임베딩 요청 배치 크기
- 동시 요청 수
- 분당 요청·토큰 사용량
- `Retry-After`를 존중하는 백오프 재시도
- 실패한 항목만 다음 주기에 다시 처리하는 체크포인트
- 다중 파드에서 한 번만 실행되게 하는 분산 락 또는 단일 worker

<details>
<summary><b>🔍 백오프는 그냥 다시 요청하는 것과 무엇이 다른가요?</b></summary>

즉시 재시도하면 제한에 걸린 서버에 요청을 더 보내므로 429가 반복될 수 있다. 백오프는 재시도
사이의 대기 시간을 점점 늘린다.

```text
첫 실패  → 1초 후 재시도
두 번째 → 2초 후 재시도
세 번째 → 4초 후 재시도
```

여러 서버가 같은 순간에 다시 요청하지 않도록 작은 무작위 지연도 더할 수 있다. 서버가
`Retry-After` 헤더로 다시 요청할 시점을 알려주면 그 값을 우선한다.

재시도 횟수는 제한해야 하며, 계속 실패한 항목은 완료 처리하지 않고 다음 배치에서 다시 찾을 수
있게 남긴다.

</details>

평상시 변경량이 작고 해시 비교가 동작한다면 이 장치를 모두 미리 구현할 필요는 없다. 최초
색인이나 대량 변경 테스트에서 실제 호출량과 429를 측정한 뒤 필요한 제한부터 추가한다.

<details>
<summary>프로젝트의 스케줄 설정은 무엇까지 확인했나?</summary>

2026-10-08에 읽은 로컬 PromptHub 스케줄러는 변경된 상품 패밀리를 재조정하고, 대표 상품의 해시가 달라지면 임베딩 갱신을 시도한다. 전체 재조정도 모든 상품을 반드시 재임베딩하는 것은 아니다.

기본값 20초는 fixedDelay, 즉 실행 종료 후 다음 실행까지의 대기다. 처리 시간, 재시도와 검색 가시성 지연이 더해질 수 있으므로 최대20초 반영 보장이 아니다. 로컬 코드 확인과 운영 반영 지연 실측은 구분한다.

</details>

## 다른 방식들과 비교

| 방식 | 원리 | 장점 | 대가 |
|---|---|---|---|
| **워터마크 폴링** | 주기적으로 `updated_at` 조회 | 구현이 단순. 원본 스키마 변경 없음 | 주기만큼 지연. 삭제 감지가 어려움 |
| **아웃박스** | 변경과 같은 트랜잭션으로 이벤트를 기록 | DB 변경 후 발행 누락을 복구할 근거가 남음 | 릴레이·중복 방어 필요. 순서는 별도 설계 |
| **CDC** | DB 변경 로그에서 변화를 전달 | 변경 전달을 애플리케이션 쓰기 경로와 분리 | 커넥터·로그 보존·재처리 운영 필요 |

**삭제 감지**가 워터마크 방식의 약점이다. 행이 사라지면 `updated_at`으로 잡을 수 없다.
소프트 삭제(`deleted_at`)를 쓰면 변경분 조회에서 삭제 상태도 대상으로 잡도록 설계할 수 있고, 물리 삭제가 있다면 주기적으로 **양쪽 ID 목록을 비교해
고아를 찾는** 보정을 검토한다.

선택 기준은 **지연 허용치와 운영 여력**이다. 수십 초 지연이 괜찮고 인프라를 늘리기 싫으면
워터마크 폴링이 가장 싸다. 더 강한 전달·복구 요구가 있으면 아웃박스나 CDC의 보장 조건과 운영 비용을 비교한다.
