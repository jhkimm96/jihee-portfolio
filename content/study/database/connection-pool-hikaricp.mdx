## 01 · 상품 조회마다 DB와 처음 인사할 필요는 없다

DB 연결은 앱이 DB와 통신하는 통로다. 새로 열 때는 네트워크 연결과 인증 등이 필요하다. 커넥션 풀은 통로를 관리하며 여러 요청에 재사용한다.

```text
준비된 연결     [연결1 대기] [연결2 대기]
A의 상품7 조회  [연결1 사용] [연결2 대기]
조회가 끝남     [연결1 반납] [연결2 대기]
민지의 조회     [연결1 재사용]
```

**정상 반납은 통로를 매번 없애는 것과 다르다.** 위는 건강한 연결이 재사용되는 학습 장면이다. 끊기거나 수명이 끝난 연결은 폐기·교체할 수 있다.

## 02 · HikariCP는 Java 기본 클래스일까?

아니다. **HikariCP는 연결 풀을 제공하는 외부 Java 라이브러리**다. 앱 의존성으로 가져온다. Spring Boot의 JDBC 또는 Data JPA starter는 이 의존성을 포함한다. [Spring Boot 데이터 접근](https://docs.spring.io/spring-boot/reference/data/sql.html)

Java 기본 API인 `DataSource`는 연결을 얻는 접점, `Connection`은 빌린 연결을 다루는 접점이다. HikariCP는 이 API 뒤에서 연결 관리와 재사용을 구현한다. 쿼리 계산이나 DB 락을 대신 해결하지는 않는다.

## 03 · close라고 적혀 있는데 왜 반납일까?

```text
풀에서 getConnection() → 이번 요청이 쓸 연결 접점
그 접점의 close()     → 풀에 사용 종료를 알림
다음 요청             → 재사용 가능한 연결을 다시 빌림
```

HikariCP가 돌려준 연결 접점의 정상 close는 풀로 돌려주는 처리다. 모든 종류의 Connection에서 close가 같은 내부 동작을 한다고 일반화하지 않는다. [HikariCP 연결 반환 구현](https://github.com/brettwooldridge/HikariCP/blob/dev/src/main/java/com/zaxxer/hikari/pool/ProxyConnection.java)

Spring/JPA가 관리하는 트랜잭션에서는 프레임워크가 연결 생명주기를 관리한다. 이 설명을 보고 서비스 코드에서 관리 중인 연결을 임의로 닫으면 안 된다.

## 04 · 두 연결을 모두 빌렸다면?

```text
연결1 A 사용 / 연결2 B 사용
민지의 요청 → 반납될 때까지 대기 → 얻거나 제한 시간 뒤 실패
```

| 설정 | 무엇을 정하나 |
| --- | --- |
| maximumPoolSize | 유휴·사용 중을 포함한 풀 연결 상한 |
| connectionTimeout | 연결을 얻기 위해 기다릴 최대 시간 |

2026-10-09 공식 README의 기본값은 각각 10개와 30초다. **우리 앱의 실제 값이나 권장 크기라는 뜻은 아니다.** 연결 대기 제한은 SQL 실행 시간이나 전체 HTTP 요청의 제한도 아니다. [HikariCP 설정 계약](https://github.com/brettwooldridge/HikariCP)

<details>
<summary>나머지 설정도 같이 읽고 싶다면</summary>

`minimumIdle`은 유지하려는 최소 유휴 연결 수다. `idleTimeout`은 남는 유휴 연결을 정리하는 설정이며 minimumIdle이 최대 크기보다 작은 경우에 적용된다. “안 쓰면 모든 연결이 정확히 10분 뒤 끊긴다”로 해석하지 않는다.

자동 설정은 의존성·클래스 경로와 앱이 직접 정의한 DataSource 여부에 따라 달라진다. 최종 선택과 적용값은 실행 환경에서 확인한다.

</details>

## 프로젝트에서 어디를 확인할까?

PromptHub 루트 `build.gradle`은 Boot 4.1.0과 Data JPA starter를 선언한다. 중앙 `product-service.yml`에는 DB 연결 설정이 있지만 풀 상한과 획득 제한을 명시하지 않았다.

2026-10-09 두 근거를 대조했으며, 실행 중 DataSource 종류·최종값·부하를 확인하지 않았다. 따라서 기존의 “기본값을 그대로 쓰며 현재 규모에 충분하다고 판단했다”는 설명은 제외했다.

다음은 [풀이 커져도 빨라지지 않는 이유](/study/cs/connection-pool-bottleneck)다. 연결을 재사용하는 원리와 최적 연결 수는 다른 질문이다.
