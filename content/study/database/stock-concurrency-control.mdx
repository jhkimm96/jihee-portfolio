## 01 · 마지막 재고 1개를 A와 B가 동시에 주문한다

상품 P의 재고가 1개 남았다. A와 B가 거의 같은 순간 구매 버튼을 눌렀다. 주문 하나는 앱 서버에서 다음 순서로 처리된다.

```text
재고 읽기 → 남았는지 확인 → 1을 빼서 저장 → 주문 생성
```

주문 처리 전체는 하나의 **트랜잭션**으로 묶여 있다. 트랜잭션은 여러 DB 작업을 “모두 성공 또는 모두 취소”로 묶는 단위다. 주문 생성이 실패하면 재고 차감도 되돌린다.

이번 예시는 DB 한 대(PostgreSQL 기본 격리 수준 READ COMMITTED), 서버에서 동시에 처리되는 주문 2건을 가정한다.

## 02 · 둘 다 “1개 남음”을 봤다

| 시점 | 주문 A | 주문 B | DB의 재고 |
| --- | --- | --- | --- |
| 1 | 재고 1 읽음 | | 1 |
| 2 | | 재고 1 읽음 | 1 |
| 3 | 1 − 1 = 0 저장, 주문 성공 | | 0 |
| 4 | | 1 − 1 = 0 저장, 주문 성공 | 0 |

**결과: 주문 2건이 성공했는데 재고는 한 번만 줄었다. 1개를 두 사람에게 판 것이다.**

B는 A가 바꾸기 전의 재고를 보고 계산했고, 그 결과로 A의 변경을 덮어썼다. 이렇게 다른 트랜잭션의 변경이 사라지는 문제를 **Lost Update(갱신 손실)**라고 한다. 재고가 10이었다면 두 주문 뒤 8이어야 할 재고가 9로 남는다.

트랜잭션으로 묶었다고 막히지 않는다. 트랜잭션은 “내 작업을 한 덩어리로” 만들 뿐, 다른 트랜잭션이 같은 값을 동시에 읽는 것까지 막지 않는다. 어디까지 서로의 변경을 보는지는 격리 수준이 정하며, PostgreSQL 기본값인 READ COMMITTED에서는 시점 1과 2처럼 둘 다 1을 읽을 수 있다. [격리 수준 자세히](/study/database/isolation-levels-and-locking)

JPA 코드로는 이런 모습이다.

```java
Product product = productRepository.findById(productId).orElseThrow(); // 재고 1을 읽음
product.decreaseStock(1);   // 앱 메모리에서만 1 → 0
// 트랜잭션이 끝날 때 JPA가 "stock = 0"을 저장
```

`findById`는 Spring Data JPA가 제공하는 조회이고 `decreaseStock`은 우리가 만든 상품 메서드다. 문제는 **읽은 시점과 저장 시점 사이**에 다른 주문이 끼어들 수 있다는 것이다.

## 03 · 확인과 차감을 SQL 한 문장으로 묶는다

재고처럼 숫자를 줄이는 일이라면, 앱에서 읽고 계산하지 말고 DB에 “남아 있으면 줄여라”를 한 번에 시킨다.

```sql
UPDATE product
SET stock = stock - :quantity
WHERE id = :productId
  AND stock >= :quantity;
```

| 시점 | 주문 A | 주문 B | DB의 재고 |
| --- | --- | --- | --- |
| 1 | UPDATE 실행 → 1행 변경 | | 0 (A 미확정) |
| 2 | | 같은 UPDATE → A가 끝날 때까지 대기 | 0 (A 미확정) |
| 3 | 주문 생성, commit | | 0 |
| 4 | | 바뀐 재고로 조건 다시 확인 → 0행 변경, 재고 부족 | 0 |

**결과: A만 성공하고 B는 재고 부족으로 끝난다. 재고는 정확히 0이다.**

PostgreSQL은 이미 다른 트랜잭션이 바꾸고 있는 행을 만나면 그 트랜잭션이 끝날 때까지 기다린 뒤, 바뀐 행으로 `WHERE` 조건을 다시 검사한다. [PostgreSQL 18 공식 문서](https://www.postgresql.org/docs/current/transaction-iso.html) 앱은 변경된 행 수가 1이면 성공, 0이면 재고 부족 또는 없는 상품으로 처리한다.

Spring Data JPA에서는 조회가 아닌 변경 쿼리에 `@Modifying`을 붙이고, 변경된 행 수를 돌려받는다.

```java
@Modifying
@Query("update Product p set p.stock = p.stock - :quantity where p.id = :id and p.stock >= :quantity")
int decreaseStock(@Param("id") Long id, @Param("quantity") int quantity);
```

<details>
<summary>격리 수준을 REPEATABLE READ 이상으로 올리면 결과가 달라질까?</summary>

PostgreSQL의 REPEATABLE READ나 SERIALIZABLE에서는 B가 기다린 뒤 조건을 다시 검사하지 않고 `could not serialize access due to concurrent update` 오류로 실패한다. 재고는 여전히 정확하지만, B는 “재고 부족”이 아니라 “다시 시도해야 하는 실패”를 받는다. 위 표는 기본값 READ COMMITTED 기준이다.

</details>

## 04 · 한 문장으로 표현할 수 없다면, 충돌 빈도로 고른다

할인 계산, 여러 테이블 검증처럼 앱에서 판단해야 하는 수정이라면 조건부 UPDATE 하나로 끝나지 않는다. 이때는 같은 데이터를 동시에 수정하지 못하게 막거나, 수정 사이에 바뀐 것을 감지한다.

| 방법 | 한 문장 설명 | 적합한 상황 | 주의점 |
| --- | --- | --- | --- |
| 조건부 UPDATE | DB 명령 하나로 조건 확인과 변경 | 단순한 숫자 차감 | 복잡한 도메인 판단 표현이 어려움 |
| 낙관적 락 | 먼저 작업하고, 저장할 때 바뀌었는지 확인 | 충돌이 드문 일반 수정 | 충돌이 많으면 재시도 증가 |
| 비관적 락 | 읽을 때 먼저 잠그고 작업 | 충돌이 잦고 DB 한 곳에서 처리 | 락 대기와 [데드락](/study/database/deadlock-lock-ordering) |
| Redis 원자적 연산 | Redis 명령 하나를 중간 간섭 없이 처리 | 대량의 단순 카운터 | DB와 Redis 사이의 정합성 |
| Redis 분산 락 | 여러 서버 중 한 곳만 작업하게 제한 | 여러 서버의 작업을 하나로 제한 | 만료 시간, 장애와 락 소유권 관리 |

고르는 순서는 세 질문이다.

1. **SQL 한 문장으로 확인과 변경을 묶을 수 있나?** 그렇다면 조건부 UPDATE.
2. **아니라면, 같은 데이터에 충돌이 자주 나나?** 드물면 낙관적 락과 제한된 재시도, 잦으면 비관적 락.
3. **부하 측정에서 DB 경합이 실제 병목으로 확인됐나?** 그때만 단순 카운터는 Redis 원자적 연산, 작업 구간 제한은 분산 락을 검토하고, Redis와 DB 사이의 정합성 점검과 재처리를 함께 마련한다.

<details>
<summary>비관적 락은 코드에서 어떻게 걸고, 언제 풀릴까?</summary>

SQL로는 `SELECT ... FOR UPDATE`, Spring Data JPA에서는 조회 메서드에 `@Lock`을 붙인다.

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select p from Product p where p.id = :id")
Optional<Product> findByIdForUpdate(Long id);
```

`FOR UPDATE`는 조회한 행을 다른 트랜잭션이 잠그거나 바꾸지 못하게 하고, 현재 트랜잭션이 끝날 때 풀린다. [PostgreSQL 18 Explicit Locking](https://www.postgresql.org/docs/current/explicit-locking.html) 실제 영향 범위는 쿼리, 실행 계획과 DB 종류에 따라 달라질 수 있다. 잠근 채로 외부 API 응답을 오래 기다리는 방식은 피한다. 여러 행을 서로 다른 순서로 잠그면 데드락이 생길 수 있다. [데드락과 잠금 순서](/study/database/deadlock-lock-ordering)

</details>

<details>
<summary>낙관적 락은 무엇을 확인하고, 충돌하면 어떻게 다시 시도할까?</summary>

엔티티에 `@Version` 필드를 두면 JPA 구현체가 수정할 때 읽었던 version을 조건으로 쓰고 값을 올린다. 직접 증가시키지 않는다.

```sql
UPDATE product
SET stock = ?, version = version + 1
WHERE id = ?
  AND version = ?;
```

다른 트랜잭션이 먼저 version을 바꿨다면 변경 행이 없으므로 충돌이다. Jakarta Persistence 명세는 이때 `OptimisticLockException`을 발생시키도록 규정한다. Spring에서 변환되는 실제 예외 타입과 시점은 통합 테스트로 확인하는 것이 안전하다. [Jakarta Persistence `@Version`](https://jakarta.ee/specifications/persistence/3.2/apidocs/jakarta.persistence/jakarta/persistence/version)

충돌한 트랜잭션은 rollback 대상이므로 **새 트랜잭션**에서 최신 재고를 다시 읽고 조건을 다시 검사한다. 이전에 읽은 값을 재사용하지 않는다. 재시도를 조정하는 바깥 서비스와 실제 차감 트랜잭션을 분리하면 시도마다 새 트랜잭션을 쓸 수 있다. 최대 횟수, 대기 정책과 대상 예외를 코드에 분명히 둔다.

</details>

<details>
<summary>재시도 간격은 어떻게 정할까? — Backoff와 Jitter</summary>

`Backoff`는 재시도 전에 기다리는 시간을 점점 늘리는 방법(예: 100ms → 200ms → 400ms)이고, `Jitter`는 여러 요청이 같은 순간에 다시 몰리지 않도록 대기 시간에 작은 무작위 차이를 주는 방법이다.

둘 다 충돌 가능성을 낮출 뿐 해결을 보장하지 않는다. 낙관적 락 충돌이나 짧은 네트워크 오류는 재시도할 수 있지만, 재고 부족처럼 다시 실행해도 결과가 같은 실패는 재시도하지 않는다. 최대 횟수와 전체 timeout, 최종 실패 처리를 함께 정한다.

</details>

<details>
<summary>Redis로 옮기면 무엇을 더 챙겨야 할까?</summary>

`DECR stock:product-100`처럼 Redis 명령 하나는 다른 명령과 섞이지 않고 처리된다. [Redis `INCR`](https://redis.io/docs/latest/commands/incr/) 하지만 “0보다 클 때만 감소”처럼 조건이 필요하면 확인과 변경을 Lua Script 등으로 하나의 원자적 작업으로 묶어야 한다. `DECR` 뒤 음수면 다시 올리는 방식은 두 명령 사이에 장애가 끼어들 수 있다.

Redis 재고 차감과 DB 주문 생성은 서로 다른 저장소의 작업이다. Redis 차감 뒤 DB 저장이 실패할 수 있으므로 이벤트 기록, 보상, 재처리와 정합성 점검이 필요하다.

서버가 여러 대라면 Java의 `synchronized`로 다른 서버의 실행을 막을 수 없다. Redis 분산 락은 공통 Redis에 락 key를 두어 한 서버만 작업 구간에 들어가게 한다. 소유자를 구분하는 고유 값, 자동 만료 시간, 락 획득 timeout, 소유자만 해제하는 검증, 작업보다 락이 먼저 만료되는 상황의 대응이 필요하다. 단순 `SETNX`만 쓰면 서버가 죽었을 때 락이 남을 수 있으므로 생성과 만료 시간을 한 명령으로 설정하고, 해제할 때 자신의 토큰인지 확인한다. 만료 뒤 첫 작업이 계속 실행 중이면 두 서버가 동시에 작업할 수도 있다. [Redis Distributed Locks](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

</details>

## 자기 말로 답해보기

재고가 10인 상품에 주문 3건이 동시에 들어왔다. 각 주문은 1개씩 산다. “읽고 계산해서 저장” 방식에서 최악의 경우 최종 재고는 얼마일까? 조건부 UPDATE로 바꾸면?

<details>
<summary>답 확인</summary>

세 주문이 모두 10을 읽고 각자 9를 저장하면 최종 재고는 9다. 주문 3건이 성공했는데 1개만 줄었다. 조건부 UPDATE에서는 두 번째·세 번째 UPDATE가 앞 변경이 끝나길 기다린 뒤 바뀐 재고로 다시 계산하므로 최종 재고는 7이고, 세 주문 모두 성공한다.

</details>

## 프로젝트에서는 어디를 볼까?

PromptHub는 디지털 상품이라 재고 차감이 없다. 같은 구조는 판매 수 증가에 있다. 2026-10-07에 `7a4c363f` 기준으로 확인한 `ProductSalesCountService`는 주문 완료 이벤트를 받으면 상품을 읽고, 메모리에서 `salesCount`를 1 올린 뒤 저장한다. `Product`에는 `@Version`이 없다. [확인한 코드](https://github.com/prgrms-be-adv-devcourse/beadv6_6_3JMT_BE/blob/7a4c363f04ca96c9f641f66906a301cf22055c3b/product-service/src/main/java/com/prompthub/product/application/service/ProductSalesCountService.java)

같은 상품의 주문 이벤트 두 개가 동시에 처리되면 위 02의 표처럼 판매 수 증가 하나가 사라질 수 있다. 코드에서 확인한 위험이며, 운영에서 실제로 판매 수가 어긋났다는 기록이나 측정은 아니다. 트래픽을 보고 이 위험을 감수한 팀의 판단은 [격리 수준과 락](/study/database/isolation-levels-and-locking) 글에 정리했다.
