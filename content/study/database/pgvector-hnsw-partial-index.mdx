벡터 검색은 Elasticsearch에서만 하는 게 아니다. Postgres에도 확장을 붙이면 된다. 이 노트는
**pgvector**로 "비슷한 것 찾기"를 하는 법과, 그게 빠르게 도는 조건을 정리한다.

## pgvector — Postgres에 좌표를 저장한다

pgvector는 Postgres **확장(extension)**이다. 기본으로 들어있지 않아서 따로 설치해야 한다.

```sql
CREATE EXTENSION IF NOT EXISTS vector;

ALTER TABLE product ADD COLUMN embedding vector(1536);
```

`vector(1536)`은 **숫자 1536개짜리 배열**이다. 이 숫자들은 문장을 AI 모델에 넣어서 얻은
"의미 좌표"다. 뜻이 비슷한 문장은 좌표도 비슷하게 나오도록 학습돼 있다.

### 거리를 재는 연산자

pgvector는 두 좌표가 얼마나 먼지를 재는 연산자를 제공한다.

| 연산자 | 무엇 | 언제 쓰나 |
|---|---|---|
| `<=>` | 코사인 거리 | **방향**이 비슷한지 볼 때. 텍스트 임베딩은 대개 이것 |
| `<->` | 유클리드 거리(L2) | 실제 공간상의 직선 거리가 의미 있을 때 |
| `<#>` | 내적의 음수 | 벡터 길이까지 의미가 있을 때 |

```sql
SELECT id, name
FROM product
ORDER BY embedding <=> (SELECT embedding FROM product WHERE id = :기준상품)
LIMIT 10;
```

"기준 상품의 좌표에서 가까운 순으로 10개"라는 뜻이다.

<details>
<summary><b>🔍 코사인 거리와 코사인 유사도는 다른 건가요?</b></summary>

같은 것을 반대로 표현한 값이다.

- **코사인 유사도**: 1에 가까울수록 비슷하다. 0이면 관계없음
- **코사인 거리**: `1 - 유사도`. 0에 가까울수록 비슷하다

`<=>`는 **거리**를 돌려준다. 그래서 `ORDER BY ... ASC`(작은 것부터)가 "비슷한 것부터"가 된다.
유사도로 바꾸고 싶으면 `1 - 거리`를 계산하면 된다.

</details>

## 그냥 하면 느리다

위 쿼리는 **전체 행의 좌표를 하나씩 다 비교**한다. 1536개 숫자를 곱하고 더하는 계산을 행마다
반복한다. 행이 100만 개면 100만 번이다.

그래서 인덱스가 필요한데, 벡터에는 **B-tree를 쓸 수 없다.** B-tree는 "이 값이 저 값보다 크다"는
순서가 있어야 동작하는데, 1536차원 좌표에는 그런 절대적 순서가 없다. "누가 더 큰가"가 아니라
"누구와 가까운가"의 문제라서 완전히 다른 방식이 필요하다.

## HNSW — 친구의 친구를 타고 간다

HNSW는 벡터 검색용 인덱스다. 이름은 **H**ierarchical **N**avigable **S**mall **W**orld의 약자다.

### 비유 — 모르는 사람 찾아가기

서울에 사는 사람이 부산의 특정 동네 주민을 찾아간다고 하자. 전 국민을 한 명씩 만나볼 수는
없다. 대신 이렇게 한다.

1. **비행기로 부산까지** — 한 번에 멀리 점프
2. **부산에서 지하철로 그 구까지** — 중간 거리 이동
3. **그 동네에서 걸어서 집집마다** — 촘촘하게 탐색

HNSW가 정확히 이 구조다. **층이 여러 개 있고, 위층은 듬성듬성해서 멀리 점프하고 아래층은
촘촘해서 정밀하게 찾는다.** 위층에서 대략의 위치로 이동한 다음 아래층으로 내려가며 좁혀간다.

```
위층  ●───────────────●───────────────●      (멀리 점프)
       ↓
중간층 ●───────●───────●───────●───────●     (중간 이동)
       ↓
아래층 ●─●─●─●─●─●─●─●─●─●─●─●─●─●─●─●     (촘촘하게)
```

각 점은 "내가 아는 이웃들"의 목록을 들고 있다. 탐색은 **현재 위치에서 이웃들 중 목적지에
가장 가까운 쪽으로 계속 이동**하는 방식이다. 전체를 보지 않고도 가까운 곳에 도달한다.

### 이건 "근사"다 — 가끔 진짜 정답을 놓친다

HNSW는 **ANN(Approximate Nearest Neighbor, 근사 최근접 이웃)** 방식이다. 전부 비교한 게
아니므로 **진짜 1등을 놓치고 2등을 1등으로 돌려줄 수 있다.**

이게 괜찮은 이유는 용도 때문이다. "비슷한 상품 추천"에서 진짜 1등 대신 3등이 먼저 나와도
사용자는 알아채지 못한다. **정확도를 조금 내주고 속도를 크게 얻는 거래**이고, 대부분의
추천·검색에서는 남는 장사다.

<details>
<summary><b>🔍 정확한 답이 꼭 필요하면 어떡하나요?</b></summary>

인덱스를 안 쓰면 된다. 전부 비교하는 방식(brute force)이 항상 정확하다.

행이 몇천 개 수준이면 전부 비교해도 충분히 빠르다. **인덱스가 필요한 시점은 규모가 커진
뒤**이고, 그전에 미리 붙일 이유는 없다.

</details>

### 파라미터 두 개

```sql
CREATE INDEX ON product USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);
```

| 파라미터 | 뜻 | 올리면 |
|---|---|---|
| `m` | 각 점이 기억하는 이웃 수 | 정확도 ↑, 인덱스 크기 ↑, 생성 시간 ↑ |
| `ef_construction` | 인덱스를 만들 때 후보를 얼마나 넓게 볼지 | 정확도 ↑, 생성 시간 ↑ (조회 속도는 그대로) |

**둘 다 명시하지 않으면 기본값이 쓰인다.** 데이터가 적을 때는 기본값으로 충분하고, 튜닝은
"느리다" 또는 "결과가 이상하다"는 관측이 생긴 뒤에 하는 게 맞다.

연산자 클래스(`vector_cosine_ops`)는 **쿼리에서 쓸 연산자와 맞춰야 한다.** `<=>`로 조회할
거면 `vector_cosine_ops`, `<->`로 조회할 거면 `vector_l2_ops`다. 안 맞으면 인덱스가 있어도
안 탄다.

## 부분 인덱스 — 필요한 행에만 인덱스를 건다

```sql
CREATE INDEX idx_product_embedding_on_sale
    ON product USING hnsw (embedding vector_cosine_ops)
    WHERE status = 'ON_SALE';
```

`WHERE`가 붙은 인덱스를 **부분 인덱스(partial index)**라고 한다. 조건에 맞는 행만 인덱스에
들어간다.

**왜 이렇게 하나.** 검색 결과에 노출되는 건 판매 중인 상품뿐인데, 인덱스에 전부 넣으면
판매 중지된 상품·과거 버전까지 탐색 대상이 된다. 인덱스가 커지고, 찾아놓고 나서 걸러내는
낭비가 생긴다.

### 부분 인덱스가 타는 조건

**쿼리의 `WHERE`가 인덱스의 `WHERE`를 포함해야 한다.** Postgres가 "이 쿼리는 인덱스에 들어있는
행만 본다"고 증명할 수 있어야 쓴다.

```sql
-- 탄다: 인덱스 조건이 쿼리에 그대로 있다
WHERE status = 'ON_SALE' AND deleted_at IS NULL

-- 안 탄다: status 조건이 없어서 인덱스 밖의 행도 봐야 한다
WHERE deleted_at IS NULL
```

### ORDER BY에 계산을 얹으면 못 탄다

이게 실무에서 자주 걸리는 함정이다.

```sql
-- 탄다
ORDER BY embedding <=> :기준벡터

-- 안 탄다
ORDER BY (embedding <=> :기준벡터) + 보너스점수
```

인덱스는 **거리 순서**로 만들어져 있다. `ORDER BY 거리`는 그 순서를 그대로 읽으면 되지만,
`거리 + 무언가`는 인덱스가 모르는 새로운 순서다. Postgres는 인덱스를 포기하고 전체를 훑는다.

**해결은 역할을 나누는 것이다.** 데이터베이스에는 순수한 거리 순으로 후보를 넉넉히 받고,
가산점 계산과 재정렬은 애플리케이션에서 한다. 후보 스무 개를 정렬하는 비용은 무시할 수 있다.

<details>
<summary><b>🔍 인덱스를 탔는지 어떻게 확인하나요?</b></summary>

`EXPLAIN`을 앞에 붙여서 실행 계획을 본다.

```sql
EXPLAIN ANALYZE
SELECT id FROM product
WHERE status = 'ON_SALE'
ORDER BY embedding <=> '[0.1, 0.2, ...]'
LIMIT 10;
```

결과에 `Index Scan using idx_product_embedding_on_sale`이 보이면 탄 것이고,
`Seq Scan`이 보이면 전체를 훑고 있다는 뜻이다.

주의할 점 하나 — 행이 아주 적으면 Postgres가 **일부러** 인덱스를 안 쓴다. 전체를 훑는 게
더 빠르다고 판단하기 때문이다. 그래서 개발 환경에서 `Seq Scan`이 나온다고 인덱스가 잘못된
건 아니다.

</details>

## 정리

- pgvector는 Postgres 확장이고, `vector(N)` 타입과 거리 연산자(`<=>`, `<->`, `<#>`)를 준다
- 인덱스 없이 조회하면 전체 행과 비교한다. 벡터에는 B-tree를 쓸 수 없다
- HNSW는 층을 나눠 **멀리 점프 → 촘촘히 탐색**하는 구조다. 근사 방식이라 진짜 1등을 놓칠 수
  있지만 추천·검색에서는 대개 문제가 안 된다
- `m`·`ef_construction`은 정확도와 비용의 거래다. 관측 없이 미리 튜닝하지 않는다
- 부분 인덱스는 쿼리의 `WHERE`가 인덱스의 `WHERE`를 포함해야 탄다
- **`ORDER BY`에 산술을 얹으면 인덱스를 못 탄다.** 거리 순 후보만 DB에서 받고 재정렬은 앱에서
