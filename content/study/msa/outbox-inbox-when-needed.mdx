## 01 · 주문은 저장됐는데 상품 서비스가 소식을 못 받았다

민지가 상품7을 샀다. 주문 DB에는 결제 완료가 기록됐지만, 다른 서비스에 보낼 이벤트 E7은 아직 못 보냈다고 가정하자. 이벤트는 다른 서비스에 알리는 사건 기록이고 E7은 설명용 식별자다.

```text
주문 DB: 결제 완료 ✓
메시지: E7 발행 전에 앱 종료
상품 서비스: 구매 소식을 모름
```

**DB 저장과 메시지 발행은 별개의 작업이다.** Outbox와 Inbox는 이 흐름의 서로 다른 실패를 다루며 반드시 짝으로 설치하는 기능이 아니다.

## 02 · 보낼 기록을 주문 변경과 함께 남긴다

```text
같은 주문 DB 트랜잭션
[결제 완료 변경] + [Outbox: E7 보낼 기록] → 함께 커밋
                                          ↓
                                  Relay가 나중에 발행
```

트랜잭션은 DB 변경을 함께 확정하거나 되돌리는 범위다. Outbox는 보낼 일을 같은 범위에 저장하는 패턴, Relay는 그 기록을 읽어 보내는 실행자다. Java 기본 클래스나 특정 라이브러리 이름이 아니다. [Transactional Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

기록이 남아도 재시도·보관·실패 관리가 필요하다. “테이블을 만들면 어떤 장애에서도 전달 완료”라는 보장은 아니다.

## 03 · 한 번 보냈는데 두 번 도착할 수 있다

```text
Relay: E7 보내기 성공 → 보냈다는 DB 표시 전에 종료
재시작: E7이 아직 대기 중 → 다시 발행
소비자: E7 / E7 두 번 받음
```

상품 판매수10에 증가를 그대로 두 번 반영하면 11이 아니라 12가 된다. **같은 사건을 반복해도 결과를 한 번과 같게 유지하는 성질**이 멱등성이다. Inbox는 처리한 사건을 기억해 중복 반영을 막는 방법 중 하나다.

## 04 · “처리 기록 없음” 조회만으로는 동시에 온 두 건을 막지 못한다

추가 방어가 없는 학습 상황이다.

```text
A: E7 기록 조회 → 없음 → 증가하려 함
B: E7 기록 조회 → 없음 → 증가하려 함
                  둘 다 통과 가능
```

그래서 같은 사건·처리자 조합이 두 번 저장되지 않는 **유니크 제약**과 업무 변경의 트랜잭션을 함께 본다. 제약은 DB의 중복 저장 금지 규칙이다. [DB 유니크 제약](https://www.postgresql.org/docs/18/ddl-constraints.html)

```text
안전성을 위한 학습 설계
[같은 사건의 처리권 확보] + [판매수10→11] + [처리 기록]을 함께 확정
중복으로 확정 못 한 시도: 그 시도의 DB 변경도 함께 되돌림
```

먼저 처리권을 확보하는 방법도 있고, 뒤의 중복 기록 충돌로 전체 변경을 되돌리는 방법도 있다. **충돌한 시도가 업무 변경만 따로 커밋해서는 안 된다.** [Idempotent Consumer](https://microservices.io/patterns/communication-style/idempotent-consumer.html)

## 05 · 프로젝트에서는 어디를 확인할까?

현재 상품 `OrderEventHandler`는 기존 기록 조회 → 판매수 변경 → 처리 기록 저장 순서이며 `@Transactional`을 선언한다. 이 클래스와 조회 메서드는 프로젝트 자체 코드다. 어노테이션은 Spring이 제공하지만 실제 호출이 트랜잭션에 참여하는지도 확인해야 한다.

`ProductProcessedEvent`와 baseline SQL에는 `event_id + consumer_group` 유니크 제약이 있다. 선언만으로 운영 DB 적용을 증명한 것은 아니다. **뒤의 기록 충돌 때 판매수까지 롤백되는지와 재시도 경로를 실제 DB로 검증해야 한다.**

같은 업무가 서로 다른 eventId로 만들어지면 eventId 기록만으로 알아보지 못한다. 필요한 경우 주문·환불 요청 같은 업무 식별자와 상태 규칙도 확인한다.

외부 결제·이메일은 DB 롤백으로 자동 취소되지 않는다. 처리 이력 보관 기간이 끝난 뒤 오래된 이벤트가 오거나 서로 다른 이벤트가 같은 상품을 동시에 바꾸는 문제도 별도다.

## 확인 범위

2026-10-09 상품 Handler·판매수 서비스·처리 이력 저장소·엔티티와 baseline 제약을 읽었다. 단위 테스트는 최초/이미 처리한 분기를 mock으로 확인하는 내용이었다. 동시 DB 처리·롤백·재시도 시험은 이번에 실행하지 않았다.

현재 서비스별 경로는 [적용 근거 글](/study/msa/outbox-inbox-per-service)에서 이어 본다. 이름이 있거나 키가 있다는 것만으로 안전성을 확정하지 않는다.
