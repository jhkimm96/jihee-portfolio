이 문서는 일반적인 MSA 이론을 임의로 PromptHub에 끼워 맞춘 글이 아니다. **2026-08-04 `develop`의 실제 코드**, 저장소의 `docs/architecture`, `docs/api-spec`, `docs/domain-glossary`, 배포 설정, 그리고 팀이 머지한 PR을 함께 읽기 위한 순서표다.

문서를 읽을 때 모든 기능을 현재 사용 중이라고 가정하지 않는다.

| 표시 | 뜻 |
|---|---|
| 현재 사용 | FE·서비스·배치·운영 설정 중 실제 소비자가 확인됨 |
| 운영 전용 | 사용자 화면이 아니라 배치·Logstash·관리 작업에서 사용 |
| FE 미연결 | BE 계약은 있으나 현재 FE 런타임 호출이 확인되지 않음 |
| 개선 후보 | 현재 동작하지만 성능·안전성·책임 분리 보강이 필요 |
| 과거/완료 | 이미 대체되거나 PR에서 제거·수정된 내용 |

<details>
<summary>왜 PR 제목만 읽지 않고 현재 코드를 다시 확인해야 하나?</summary>

PR은 그 시점의 변화다. 뒤 PR이 설계를 다시 바꾸거나 제거할 수 있다. 예를 들어 product의 검수 잔여 메서드는 과거 리뷰에 남아 있었지만 PR #439에서 이미 제거됐다. 따라서 학습 기준은 항상 `현재 코드 → 최신 문서 → 변경 이유를 보여주는 PR` 순이다.

</details>

## 0단계 — 전체 지도를 먼저 고정한다

먼저 다음 저장소 문서를 읽는다.

1. `docs/architecture/overview.md`
2. `docs/architecture/event-flow.md`
3. `docs/architecture/grpc-contract-ownership.md`
4. `docs/erd/overview.md`
5. 각 서비스 `docs/api-spec/*.md`

이 단계의 목표는 서비스 이름을 외우는 것이 아니라 **누가 원본 데이터를 소유하고, 누가 동기 응답을 주며, 누가 이벤트를 소비하는지** 설명하는 것이다.

```text
user ─ 인증·회원·판매자·판매자 정산 조회
product ─ 상품 원본·검색·유사 상품·구매 콘텐츠
order ─ 장바구니·주문·구매 스냅샷·환불 접수
payment ─ PG 승인·환불 연동·결제 감사
settlement ─ 정산 원천·계산·대사·전달
admin ─ 운영 조회·상태 전환·전달 재처리
notification ─ 이벤트 기반 알림·SSE
ai ─ 상품 자동 검수·정산 챗·개인화 추천
```

<details>
<summary>REST, gRPC, Kafka를 각각 왜 쓰나?</summary>

- **REST**: 브라우저나 외부 클라이언트가 요청하고 즉시 응답을 받아야 할 때 사용한다.
- **gRPC**: 내부 서비스가 타입이 고정된 계약으로 즉시 데이터를 받아야 할 때 사용한다. PromptHub에서는 상품 조회와 정산 전달 같은 내부 계약에 쓰인다.
- **Kafka**: 요청을 보낸 서비스가 소비자의 완료를 기다릴 필요가 없거나, 상태 변경 사실을 여러 소비자가 받아야 할 때 사용한다.

“MSA니까 Kafka”가 아니라, 즉시 결과가 필요한지와 발행·소비 실패를 어떻게 복구할지가 선택 기준이다.

</details>

## 1단계 — 사용자와 gateway: 요청의 신원은 어떻게 전달되는가

읽을 흐름:

1. 로그인·access/refresh token
2. gateway의 JWT 검증
3. user-service `/internal/authorize`
4. 역할과 사용자 ID 헤더 전달
5. 탈퇴·역할 변경 시 epoch 기반 무효화

현재 gateway는 인증 요청마다 user-service authorize를 호출한다. user-service에는 Redis 인가 스냅샷이 있지만 gateway 로컬 TTL 캐시는 없다. 이것은 오류가 아니라 즉시 무효화와 호출 비용 사이의 선택이다.

근거 PR: 탈퇴 계정 재가입 [#696](https://github.com/prgrms-be-adv-devcourse/beadv6_6_3JMT_BE/pull/696), 전체 KST 통일 [#514](https://github.com/prgrms-be-adv-devcourse/beadv6_6_3JMT_BE/pull/514).

<details>
<summary>epoch 기반 세션 무효화란?</summary>

사용자별 세션 세대 번호를 두고 JWT가 발급될 때의 번호와 현재 번호를 비교하는 방식이다. 강제 로그아웃이나 역할 변경 때 현재 번호를 올리면 이전 토큰은 서명이 유효해도 거부할 수 있다.

</details>

## 2단계 — product: 상품 하나가 왜 여러 row인가

다음 순서로 읽는다.

1. `docs/domain-glossary/product.md`
2. 상품 유형별 sparse 컬럼 결정
3. `ProductContent` 값 객체
4. `parent_id` row-chain 버전 이력
5. 판매량 family 합산
6. 구매 전 설명과 구매 후 산출물 접근 경계

핵심은 “상품 CRUD”가 아니다. 판매 중 상품을 크게 수정해도 검수 전 버전이 기존 구매자와 검색 결과를 깨뜨리지 않도록 **새 row를 만들고 상품군 단위로 읽는 모델**이다.

관련 PR: 검수 승인 시 구버전 전환 누락 수정 [#700](https://github.com/prgrms-be-adv-devcourse/beadv6_6_3JMT_BE/pull/700), MAJOR 수정 검수 이벤트 수정 [#691](https://github.com/prgrms-be-adv-devcourse/beadv6_6_3JMT_BE/pull/691), 구매 콘텐츠 조회 [#556](https://github.com/prgrms-be-adv-devcourse/beadv6_6_3JMT_BE/pull/556).

<details>
<summary>aggregate와 familyRootId는 무엇인가?</summary>

aggregate는 한 트랜잭션에서 일관성을 지켜야 하는 도메인 묶음이다. PromptHub 상품은 버전별 row가 따로 있어도 사용자에게는 한 상품군으로 보인다. `familyRootId`는 이 버전들을 같은 상품군으로 묶어 판매량·평점·검색 문서를 계산하는 기준이다.

</details>

현재 개선 후보:

<details>
<summary>reconcile과 outbox의 차이는?</summary>

outbox는 상태 변경과 이벤트 기록을 같은 DB 트랜잭션에 묶어 발행 유실을 줄인다. reconcile은 원본과 사본을 다시 비교해 누락·불일치를 고친다. PromptHub 검색은 변경분 재조정과 주기 안전망을 사용한다. 둘은 경쟁 패턴이 아니라 필요한 복구 보장에 따라 선택한다.

</details>

<details>
<summary>주문 snapshot이 왜 필요한가?</summary>

</details>

<details>
<summary>멱등성과 Idempotency-Key란?</summary>

같은 결제 승인 요청이 네트워크 재시도로 여러 번 도착해도 실제 결제가 한 번만 일어나게 하는 성질이 멱등성이다. Idempotency-Key는 PG가 같은 요청임을 식별하도록 보내는 키다. 내부 DB의 상태 전이와 PG의 멱등 보장은 둘 다 필요하다.

</details>

<details>
<summary>대사(reconciliation)란?</summary>

두 독립 계산이나 전달 결과가 같은지 비교하는 절차다. 주문 원천 합계와 정산 대상 합계, 계산 전후 금액, 전달한 건수와 받은 건수를 비교해 조용한 누락을 찾는다. 금전 시스템에서는 중복 코드처럼 보여도 독립 검증 경계가 의도일 수 있다.

</details>

## 7단계 — notification: 이벤트를 화면의 실시간 상태로 바꾸기

흐름은 Kafka 이벤트 소비 → 사용자별 알림 저장 → Redis pub/sub → SSE 연결 전달이다. 알림 삭제와 수신 설정은 PR [#647](https://github.com/prgrms-be-adv-devcourse/beadv6_6_3JMT_BE/pull/647), 실시간 안정화는 [#621](https://github.com/prgrms-be-adv-devcourse/beadv6_6_3JMT_BE/pull/621)에서 확인한다.

현재 설정·삭제 API 네 개는 BE가 완결됐지만 FE 화면이 연결되지 않았다. “죽은 코드”가 아니라 **FE 미연결** 상태다. notification만 `/api/v1`인 것은 계약 정리 후보지만 하위 호환 계획 없이 바꾸지 않는다.

<details>
<summary>SSE와 WebSocket의 차이는?</summary>

SSE는 서버→브라우저 단방향 스트림이며 HTTP 재연결 모델이 단순하다. 알림과 LLM 진행 상황처럼 서버가 계속 밀어주는 용도에 맞다. 양방향 실시간 통신이 핵심이면 WebSocket을 검토한다.

</details>

## 8단계 — ai-service: 이름은 하나지만 세 책임을 구분한다

ai-service에는 서로 다른 세 흐름이 있다.

1. 상품 자동 검수 — PR [#636](https://github.com/prgrms-be-adv-devcourse/beadv6_6_3JMT_BE/pull/636)
2. 셀러 정산 어시스턴트 — PR [#527](https://github.com/prgrms-be-adv-devcourse/beadv6_6_3JMT_BE/pull/527)
3. 개인화 추천 — 김지희 구현 PR [#701](https://github.com/prgrms-be-adv-devcourse/beadv6_6_3JMT_BE/pull/701)

개인화 추천은 product-service가 pgvector 기반 유사 상품 후보를 gRPC로 주고, ai-service가 장바구니 1.0·구매 0.7 신호를 weighted RRF로 결합한다. 모듈 분리는 파일 정리가 아니라 상품 유사도와 사용자 행동 조합의 책임 경계를 나누기 위한 요구사항이었다.

현재 추천 개선 후보는 가중치 근거 측정, recency 계약, cold-start, 후보 부족률·클릭/구매 전환 지표, controller 계약 테스트다.

<details>
<summary>추천이 실패할 때 빈 목록을 반환하는 이유와 한계</summary>

추천은 핵심 구매 조회를 막으면 안 되는 부가 기능이므로 gRPC 실패 때 빈 목록으로 격리한다. 하지만 빈 목록만 반환하면 장애를 숨길 수 있으므로 실패율·latency·후보 부족 지표를 반드시 남겨야 한다.

</details>

## 9단계 — admin: 별도 서비스지만 다른 스키마를 읽는 이유

## 마지막 — 코드 품질과 리팩토링은 흐름을 이해한 뒤 한다

우선순위는 다음과 같다.

1. 데이터 유실·부분 실패: product ES bulk item 실패, alias 무결성
2. 규모 증가 결함: 10k 색인 한계, `getProductsByIds` `2N`
3. 장애 은폐: 넓은 `RuntimeException` fallback, 빈 추천의 무관측
4. 책임 집중: admin `SettlementController`, ai Redis chat repository, product query service
5. 계약 드리프트: notification v1, FE 미연결 API의 owner와 제거 기한

LOC가 크다는 이유만으로 먼저 쪼개지 않는다. 실제 변경 이유가 섞이고 테스트 경계가 흐려지는 곳부터 나눈다.
