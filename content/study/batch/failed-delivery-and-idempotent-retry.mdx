## 01 · 응답이 없다고 상대가 저장하지 않은 것은 아니다

민지 정산 계산액 6,800원을 다른 서비스에 등록하는 학습 장면이다. 은행 송금 장면이 아니다.

```text
보낸 쪽     정산 등록 요청 R1 ───────────────→ 상대가 저장
            응답을 못 받음 ←── 네트워크 단절
판단        저장 안 됨? 이미 저장됨? 아직 모름
```

**이때 새 정산을 만들기보다 같은 전달 업무를 식별하고 결과를 확인해야 한다.** 같은 업무를 반복해도 중복 효과를 내지 않는 성질이 멱등성이다. 도구가 아니라 처리 규칙이다.

## 02 · 실패 종류를 한 칸에 넣으면 재처리도 위험해진다

| 상태 구분 | 다음 판단 |
| --- | --- |
| 계산은 완료, 전달 전 | 저장한 계산 결과 전달 |
| 통신 실패 또는 결과 불명 | 같은 식별자와 결과로 확인·재시도 |
| 상대 결과가 다름 | 불일치 조사, 무조건 반복하지 않음 |
| 전달 결과 일치 | 이미 확인한 성공을 중복 처리하지 않음 |

실패 이유와 시도 횟수, 마지막 시각, 재시도 대상 식별자를 보관한다. 전체 기간 재계산과 특정 전달 재시도는 다른 작업이다.

## 03 · 프로젝트는 계산과 전달 기록을 나눈다

`SettlementDelivery`는 전달 요청 ID와 정산 ID, 상태, 시도 횟수·시간·이유를 저장한다. 현재 상태에는 CALCULATED, RECONCILED, DELIVERY_FAILED, MISMATCH가 있다. Java 기본 클래스가 아니라 프로젝트 모델이다.

```text
같은 정산 → 보관한 전달 요청 ID 유지 → 다시 등록
                                         ↓
                          상대 저장 결과와 비교 → 일치 / 불일치
```

받는 쪽은 같은 전달 요청 ID의 기존 정산을 찾고, 보내는 쪽은 응답 결과를 비교한다. “HTTP/gRPC 성공”과 “원하는 금액이 등록됨”을 구분한다.

## 04 · 재시도 횟수를 끝없이 늘리지 않는다

현재 전달 서비스는 한 실행에서 최대 3회 시도하며 재시도 가능한 통신 실패를 분류한다. 재전송용 경로도 실패 상태와 누적 시도 수를 확인한다. MISMATCH는 단순 전달 실패와 분리한다.

일반 API도 멱등 키를 활용할 수 있지만 보관 기간·같은 키에 다른 내용·동시 요청 정책은 서비스마다 다르다. [Stripe의 멱등 요청 계약](https://docs.stripe.com/api/idempotent_requests)을 PromptHub의 동일 구현으로 혼동하지 않는다.
