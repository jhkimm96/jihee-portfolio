## 01 · 단계 1은 끝났고 단계 2에서 실패했다

```text
지난주 정산
  [원본 확인 ✓] → [계산 도중 실패] → [결과 확인 미실행]
                       ↓ 다시 시도
  같은 지난주 업무를 이어갈까? 새 업무를 처음부터 만들까?
```

**재시작은 같은 업무를 다시 시도하는 것이지 실패한 줄을 무조건 자동 재개하는 마법이 아니다.** 실행 기록과 실제 처리 대상 상태가 함께 필요하다.

## 02 · 네 이름을 같은 장면에 붙인다

| 이름 | 장면의 의미 |
| --- | --- |
| Job | ‘판매자 정산’ 전체 작업 정의 |
| Step | 원본 확인·계산 등 작업 단계 |
| JobInstance | ‘10/5~10/11 정산’이라는 업무 실행 |
| JobExecution | 그 업무를 시도한 첫 번째·두 번째 실행 기록 |

이름들은 Spring Batch 외부 프레임워크의 개념이다. Java 기본 라이브러리가 아니다. Job 이름과 **식별용 파라미터**가 JobInstance를 구분한다. 다른 업무 식별자로 새로 시작하면 이전 기록을 자동 이어 쓰는 것이 아니다. [Batch 업무 식별](https://docs.spring.io/spring-batch/reference/domain.html)

## 03 · 완료 단계는 항상 건너뛸까?

일반 재시작에서는 완료된 Step을 건너뛰지만 `allowStartIfComplete(true)`면 다시 실행할 수 있다. 어떤 데이터를 읽을지는 Reader의 책임이다. [Step 재시작 정책](https://docs.spring.io/spring-batch/reference/step/chunk-oriented-processing/restart.html)

```text
실행 기록   완료 단계 / 실패 단계
처리 대상   이미 정산 연결된 원본 / 아직 처리 가능한 원본
판단        Step 설정 + Reader + DB 상태를 함께 확인
```

프로젝트의 계산 Step에는 이 옵션이 true이며 Reader는 해당 기간의 정산 가능한 판매자를 조회한다. 따라서 “완료된 계산은 무조건 건너뛴다”거나 “마지막 반복문의 위치를 자동 기억한다”고 설명하지 않는다.

## 04 · 프로젝트는 재시작할 업무도 확인한다

파라미터 Factory는 기간 시작·끝을 식별용, 요청 시각·트리거 유형은 비식별용으로 만든다. Restarter는 정산 Job인지, 마지막 실행이 FAILED인지, 요청한 배치와 실행 context가 맞는지 확인한 뒤 재시작한다.

```text
기간 고정 → 업무 실행 찾기 → 마지막 실패·배치 일치 확인 → 재시작
```

다른 기간을 새로 시작하는 것, 같은 배치를 재시작하는 것, 실패 전달 한 건만 재전송하는 것은 구분해야 한다.

<details>
<summary>프로젝트 전체 단계 연결</summary>

```text
배치 생성 → 소스 적재 → 원본 대사 → Chunk 계산
        → 계산 대사 → 업무 완료 처리 → 판매자 정산 전달
```

원본·계산 대사 실패는 정상 완료 흐름으로 진행하지 않는다. 업무 완료 처리와 전달 결과는 별도 상태로 확인한다. Job 성공 표시 하나만으로 모든 전달·은행 지급이 성공했다고 읽지 않는다.

</details>

## 확인 기준과 검증 한계

2026-10-09 `SettlementJobConfig`, `SettlementStepConfig`, `SettlementJobParametersFactory`, `SettlementJobRestarterAdapter`와 Reader를 읽었다. 공식 설명은 안정판 6.0.5이며 프로젝트의 실제 해석된 패치 버전과 재시작 테스트 실행은 확인하지 않았다. 메타데이터 기록만으로 업무 멱등성이 자동 생기지는 않는다.
