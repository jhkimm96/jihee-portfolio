## 상황: 왜 이게 보이기 시작했나

컨트롤러가 호출한 서비스 메서드 안에서, DB에서 값 하나를 조회한 뒤 몇 초~몇십 초 걸리는 외부 API를 호출하는 코드가 있다고 하자.

```java
@Service
public class PrepService {
    public Result create(Request req) {
        var tags = tagRepository.findAll();      // ① DB 조회
        var result = externalApiClient.call(req); // ② 느린 외부 호출
        return save(result);                      // ③ DB 저장
    }
}
```

①에서 커넥션을 하나 쓰고 바로 반납할 것 같지만, Spring Boot 기본 설정에서는 그렇지 않다. ①에서 받은 커넥션이 ②가 끝날 때까지, 심지어 요청 전체가 끝날 때까지 반납되지 않을 수 있다.

## open-in-view가 하는 일

Spring Boot는 `spring.jpa.open-in-view`를 **기본값 true**로 둔다. 이 설정이 켜져 있으면, 요청이 들어와서 응답이 나갈 때까지 하나의 Hibernate 세션을 계속 열어둔다.

```
요청 시작 ─▶ 컨트롤러 ─▶ 서비스(①DB조회 ②외부호출 ③DB저장) ─▶ 뷰 렌더링 ─▶ 응답
          └──────────────── 같은 Hibernate 세션 ────────────────┘
```

이게 왜 편한가 하면, 컨트롤러나 뷰 렌더링 단계에서 엔티티의 지연 로딩(lazy loading) 필드에 접근해도 터지지 않는다. 트랜잭션은 서비스 메서드 안에서만 열리지만(`@Transactional`), 세션 자체는 더 오래 살아있어서 그 뒤에도 지연 로딩이 동작한다.

<details>
<summary><b>🔍 트랜잭션이랑 세션이랑 뭐가 다른가요</b></summary>

트랜잭션은 "이 작업들을 한 단위로 묶어서, 전부 성공하거나 전부 취소한다"는 경계다. 세션(Hibernate의 영속성 컨텍스트)은 그보다 넓은 개념으로, 엔티티를 추적하고 지연 로딩을 가능하게 해주는 "작업 공간"이다. open-in-view는 트랜잭션은 평소처럼 메서드 단위로 짧게 끝내면서, 세션만 요청 끝까지 늘려서 편의를 얻는 설정이다.

</details>

## 대가: 커넥션이 "요청 끝까지" 묶인다

세션이 요청 끝까지 열려 있다는 건, 그 세션이 필요할 때 받아온 DB 커넥션도 똑같이 요청 끝까지(정확히는 커넥션을 실제로 반납하는 시점까지) 붙잡혀 있을 수 있다는 뜻이다. 평소엔 문제가 안 된다 — 보통 요청 하나가 수십 ms 안에 끝나기 때문이다.

문제는 그 요청 안에 **느린 외부 호출**이 섞일 때다. 위 예시의 ②(외부 API 호출)가 몇 초씩 걸리면, ①에서 받은 커넥션이 ②가 끝날 때까지 다른 요청에서 못 쓰는 상태로 묶인다. 동시 요청이 늘어나면 커넥션 풀이 금방 고갈된다 — DB 자체엔 부하가 없는데도 "커넥션을 못 구해서" 전체가 느려지는 상황이 생길 수 있다.

## 대안과 각각의 대가

| 방법 | 효과 | 대가 |
|---|---|---|
| `open-in-view: false`로 끈다 | 트랜잭션이 끝나면 세션도 바로 끝나, 커넥션 점유가 트랜잭션 범위로 줄어든다 | 컨트롤러·뷰에서 지연 로딩을 쓰던 코드가 `LazyInitializationException`을 던진다 — 앱 전체의 지연 로딩 의존 코드를 찾아 서비스 계층에서 미리 로딩하도록 고쳐야 한다 |
| 느린 호출을 트랜잭션 밖으로 뺀다 | 설정은 그대로 두고, DB 조회와 느린 호출의 순서·경계만 바꾼다(먼저 호출 → 그 결과로 한 번에 저장) | 모든 호출 지점을 일일이 점검해서 "DB 조회와 느린 작업이 섞여 있는 곳"을 찾아 고쳐야 한다 |

둘 다 "DB 세션이 열려 있는 동안 느린 작업을 하지 않는다"는 같은 원칙으로 가는 길이고, 전자는 설정 하나로 앱 전체에 그 원칙을 강제하는 방법, 후자는 문제가 되는 지점만 개별적으로 고치는 방법이다.
