## 01 · 상품 7번을 찾는다

상품 상세를 만들다가 상품7이 두 번 필요해졌다. JPA가 조회한 객체를 관리하는 공간을 **영속성 컨텍스트**라고 한다. 도서관에서 빌린 책을 펼쳐 두는 책상처럼 생각하면 된다.

이번에는 처음에 빈 공간에서 같은 상품 ID를 `find`로 두 번 찾는다.

```text
첫 find(7)
[빈 보관 공간] → DB에서 상품7 읽음 → [상품7 객체 P]

두 번째 find(7)
[상품7 객체 P] → 같은 P 반환
                DB 재조회 없음
```

결과: 같은 상품7 객체를 재사용한다. 이 공간 안의 재사용 기능을 **1차 캐시**라고 부른다.

같은 컨텍스트 안에서 객체가 계속 관리되고 있는 예제다. 중간에 공간을 비우거나 객체를 분리하면 결과가 달라질 수 있다.

<details>
<summary>find는 어디서 왔고, 모든 검색이 캐시를 쓸까?</summary>

`EntityManager.find`는 Jakarta Persistence API의 메서드다. Hibernate는 이 API를 구현하는 ORM 라이브러리다. 보관 공간이 실제 메모리 안에 책상처럼 생겼다는 뜻은 아니다.

find와 달리, 조건을 검색하는 JPQL은 SQL을 실행할 수 있다. 검색 결과의 엔티티를 같은 컨텍스트의 객체로 맞추는 것과 SQL 실행 자체를 생략하는 것은 다르다. 공유 캐시 등 다른 조건을 제외한 단순화된 예제다.

</details>

## 02 · 상품이 있으면 판매자 정보도 있을까?

상품 객체와 그 상품이 참조하는 판매자 정보는 별개의 로딩 대상이다.

```text
상품명만 표시       [상품7 이름 있음] [판매자 정보 아직 없음]
판매자 이름도 표시  [상품7 이름 있음] [판매자 정보 로딩 필요]
```

결과: 상품을 이미 찾았더라도 연관된 정보는 추가로 필요할 수 있다.

**LAZY(지연 로딩)**는 연관 데이터의 로딩을 미룰 수 있게 하는 전략이다. **EAGER(즉시 로딩)**는 연관 데이터를 즉시 로딩하도록 요구하는 전략이다.

둘은 '언제 로딩하는가'의 계약이지 'SQL 몇 번인가'의 답은 아니다. EAGER여도 추가 SELECT가 나갈 수 있고, LAZY도 조회 방식에 따라 함께 가져올 수 있다. [Hibernate fetching](https://docs.hibernate.org/orm/current/userguide/html_single/#fetching)

## 03 · 목록에서는 조회 횟수도 따로 본다

상품 목록에서 판매자 이름을 반복해서 읽으면 상품 조회 뒤 판매자별 조회가 붙을 수 있다. 같은 트랜잭션에서도 일어날 수 있는 **N+1 문제**다.

필요한 연관 데이터를 묶어 가져올지, fetch join이나 EntityGraph를 쓸지 조회별로 정하고 실제 SQL을 확인한다. 다음 글: [목록 하나 열었는데 조회가 11번](/study/jpa/n-plus-one-problem).

<details>
<summary>프로젝트 매핑과 보관 공간의 수명</summary>

2026-10-08에 확인한 로컬 PromptHub의 매핑 발췌다. annotation은 Jakarta Persistence가 제공하며 프로젝트의 JPA 의존성으로 사용한다.

```java
// Review.java
@ManyToOne(fetch = FetchType.LAZY)
private Product product;

// User.java
@ElementCollection(fetch = FetchType.EAGER)
private Set<UserRole> roles = new HashSet<>();
```

Review의 product는 로딩을 미룰 수 있고 User의 roles는 즉시 로딩 대상이다. 매핑의 존재만 확인했으며 실제 SQL 횟수나 팀의 선택 이유는 측정하지 않았다. 원격 develop이나 운영 배포 상태를 확인한 결과도 아니다.

트랜잭션 범위 컨텍스트는 트랜잭션 종료와 함께 정리될 수 있지만, [OSIV](/study/spring/open-in-view-connection-hold)처럼 요청 동안 EntityManager를 유지하는 구성도 있다. '트랜잭션 종료=책상 철거'는 모든 구성의 규칙이 아니다.

</details>

## 자기 말로 답해보기

다른 요청에서 상품7을 다시 찾을 때도 같은 공간을 공유할까? EAGER로 바꾸면 판매자 조회는 무조건 SQL1회가 될까?

<details>
<summary>답 확인</summary>

일반적인 요청별 컨텍스트는 서로 다르다. 1차 캐시를 서버 전체 공유 캐시로 해석하면 안 된다. EAGER도 SQL1회를 보장하지 않으므로 조회 방식과 실행 SQL을 따로 확인한다.

</details>
