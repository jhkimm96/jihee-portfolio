## 01 · 상품 10개 목록에 판매자 이름을 붙인다

쇼핑몰 목록 화면이 상품 10개를 보여준다. 각 상품 옆에는 판매자 이름이 있다. 상품은 상품 표에, 판매자는 판매자 표에 따로 저장돼 있고, 상품 행에는 판매자 이름 대신 **판매자 번호**만 있다.

앱은 먼저 상품 10개를 한 번에 가져온다. 이때 판매자는 아직 가져오지 않는다. 판매자 자리에는 “번호만 아는 빈 자리”를 두고, 화면이 판매자 이름을 읽는 순간 그 판매자를 가져온다. 필요할 때 가져오는 이 방식이 **지연 로딩(LAZY)**이다. 필요 없는 데이터를 미리 가져오지 않으려는 기본 설정이다. [지연 로딩 자세히](/study/jpa/persistence-context-and-fetch-strategy)

이번 예시는 상품 10개, 판매자 10명이 모두 다르고, 한 요청 안에서 처리한다고 가정한다.

## 02 · 이름을 하나씩 읽을 때마다 조회가 하나씩 늘어난다

화면을 그리려고 반복문이 상품을 하나씩 돌며 판매자 이름을 읽는다.

| 순서 | 앱이 한 일 | DB 조회 |
| --- | --- | --- |
| 1 | 상품 10개 목록 조회 | 1 |
| 2 | 1번 상품의 판매자 이름 읽기 → 판매자 S1 조회 | +1 |
| 3 | 2번 상품의 판매자 이름 읽기 → 판매자 S2 조회 | +1 |
| … | … | … |
| 11 | 10번 상품의 판매자 이름 읽기 → 판매자 S10 조회 | +1 |
| | **합계** | **11** |

**결과: 목록 조회 1번에 상품 수(N)만큼 조회가 더 붙는다. 그래서 N+1이다.** 상품이 100개면 101번이고, 조회마다 DB 왕복 시간이 쌓인다.

같은 판매자의 상품이 여러 개라면 그 판매자는 한 번만 가져온다. 한 요청 안에서 이미 가져온 데이터는 JPA가 기억해 두었다가 재사용하기 때문이다. 그래서 정확히는 “목록 1번 + 아직 가져오지 않은 판매자 수”만큼 조회한다.

코드로는 이렇게 생겼다.

```java
// 조회 1번
List<Product> products = productRepository.findAll();
for (Product product : products) {
    // 판매자가 아직 없으면 조회 1번 추가
    product.getSeller().getName();
}
```

`productRepository`는 Spring Data JPA(외부 라이브러리, 의존성 추가 필요)가 만들어주는 조회 객체다. `getSeller()`는 우리가 만든 상품 클래스의 메서드이고, 판매자를 실제로 가져오는 SQL은 JPA 구현체인 Hibernate가 대신 보낸다. 그래서 코드에는 조회 문장이 한 줄뿐인데 로그에는 11개가 찍힌다.

원인은 지연 로딩 자체가 아니라, **지연 로딩된 값을 반복문 안에서 하나씩 꺼내는 패턴**이다.

## 03 · 판매자를 미리 묶어서 가져온다

해결 방향은 하나다. 필요한 판매자를 하나씩 가져오지 말고, 목록을 가져올 때 함께 또는 한 번에 묶어서 가져온다.

| 방법 | 하는 일 | 조회 수 (상품 10개) |
| --- | --- | --- |
| 함께 가져오기 (fetch join) | 상품 목록을 가져오는 조회 한 번에 판매자도 붙여 온다 | 1 |
| 묶어서 가져오기 (batch fetching) | 목록을 가져온 뒤, 필요한 판매자 10명을 한 번의 조회로 가져온다 | 2 |

**결과: 상품이 20개, 100개로 늘어도 조회 수가 상품 수만큼 늘지 않는다.**

함께 가져오기는 이 화면에 판매자가 꼭 필요하다는 것을 조회문에 직접 적는다.

```java
@Query("select p from Product p join fetch p.seller")
List<Product> findAllWithSeller();
```

`join fetch`는 JPA 조회 언어(JPQL)의 문법으로, 판매자를 별도로 조회하지 않고 같은 결과에서 채워 넣으라는 뜻이다. 같은 일을 조회 메서드에 `@EntityGraph(attributePaths = "seller")`로 선언할 수도 있다.

묶어서 가져오기는 Hibernate 설정 하나로 켠다. 기본값은 꺼져 있다.

```yaml
spring:
  jpa:
    properties:
      hibernate:
        default_batch_fetch_size: 100
```

이 값을 켜면 판매자 이름을 처음 읽을 때 Hibernate가 아직 가져오지 않은 판매자 번호를 최대 100개까지 모아 한 번에 조회한다. PostgreSQL에서는 번호 목록을 배열로 넘기는 `id = any(?)` 형태가 된다. [Hibernate 7 공식 안내](https://docs.hibernate.org/orm/7.0/introduction/html_single/#batch-subselect-fetch)

<details>
<summary>판매자를 처음부터 즉시 로딩(EAGER)으로 바꾸면 해결될까?</summary>

권하지 않는다. 판매자가 필요 없는 화면에서도 항상 가져오게 되고, JPQL로 목록을 조회하면 즉시 로딩이어도 판매자를 별도 조회로 채울 수 있어 N+1이 그대로 남을 수 있다. Hibernate 공식 안내도 연관 데이터는 기본적으로 지연 로딩으로 두고, 필요한 조회에서만 명시적으로 함께 가져오라고 권한다.

</details>

<details>
<summary>목록을 페이지로 나눠 보여줘도 fetch join을 쓸 수 있을까?</summary>

판매자처럼 상품 하나에 하나만 붙는 데이터는 괜찮다. 문제는 주문 하나에 주문 상품 여러 개처럼 **목록(컬렉션)을 함께 가져올 때**다. 결과 행이 주문 상품 수만큼 늘어나서 DB에서 “주문 20개까지”를 자를 수 없고, Hibernate는 전부 가져온 뒤 메모리에서 자른다. 공식 설정 문서는 이 동작을 성능이 매우 나쁠 수 있다고 경고하며, `hibernate.query.fail_on_pagination_over_collection_fetch`로 이런 조회를 실패시킬 수 있다. [Hibernate 설정 문서](https://docs.hibernate.org/orm/7.0/userguide/html_single/Hibernate_User_Guide.html)

이 경우에는 주문만 페이지로 가져오고, 주문 상품은 묶어서 가져오기로 채우는 방식이 흔히 쓰인다.

</details>

## 04 · 고쳤는지는 조회 수로 확인한다

화면이 빨라졌다는 느낌만으로는 부족하다. 테스트에서 실행된 SQL 수를 센다.

1. SQL 로그를 켜거나(`logging.level.org.hibernate.SQL=debug`), Hibernate 통계를 켜서 실행된 조회 수를 읽는다.
2. 상품을 10개 넣고 목록을 조회해 조회 수를 기록한다.
3. 상품을 20개로 늘려 다시 조회한다.

| 상품 수 | 고치기 전 | fetch join | batch fetching |
| --- | --- | --- | --- |
| 10개 | 11 | 1 | 2 |
| 20개 | 21 | 1 | 2 |

**항목 수를 바꿔도 조회 수가 그대로면 N+1이 사라진 것이다.** 표의 숫자는 판매자가 모두 다르고 batch 크기가 상품 수보다 크다는 조건의 예시다.

## 05 · DB가 아니라 다른 서비스를 불러도 같은 모양이다

N+1은 DB에만 생기지 않는다. 목록을 받은 뒤 항목마다 다른 서비스에 요청을 보내도 같은 구조가 된다.

PromptHub의 [2026-07-20 품질 점검](/quality/prompthub/product-service-2026-07-20)은 상품 목록 조회가 판매자 이름을 얻으려고 **서로 다른 판매자마다 다른 서비스에 원격 호출(gRPC)을 하나씩** 보내는 코드를 발견했다. DB 조회 대신 네트워크 호출이 판매자 수만큼 나가는 N+1이었다.

이 경로는 다음 날 [#440](https://github.com/prgrms-be-adv-devcourse/beadv6_6_3JMT_BE/pull/440)([커밋 `3255deb7`](https://github.com/prgrms-be-adv-devcourse/beadv6_6_3JMT_BE/commit/3255deb7af3ae2e47377cdea38e54f52977e690c))에서 원격 호출 자체를 제거하는 방식으로 정리됐다. 상품 서비스는 판매자 번호만 돌려주고, 커밋 설명에 따르면 화면이 판매자 번호 목록으로 사용자 서비스를 한 번에 조회하는 방향에 맞춘 변경이다. 화면 쪽 구현과 응답 시간 변화는 이 글에서 확인하지 않았다.

해결 방향은 DB와 같다. **필요한 것을 하나씩 여러 번 대신, 묶어서 한 번에** 가져온다.

## 자기 말로 답해보기

상품 50개를 지연 로딩으로 가져왔고, 판매자는 5명뿐이다. 한 요청 안에서 반복문으로 판매자 이름을 모두 읽으면 조회는 몇 번일까? `default_batch_fetch_size`를 100으로 켜면 어떻게 달라질까?

<details>
<summary>답 확인</summary>

켜기 전에는 목록 1번 + 판매자 5명 = 6번이다. 같은 판매자는 한 요청 안에서 한 번 가져오면 재사용한다. 켜면 목록 1번 + 판매자 5명을 한 번에 = 2번이다. 상품 수 50은 조회 수를 정하지 않는다.

</details>
