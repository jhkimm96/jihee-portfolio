## 01 · 내 컴퓨터에서는 되는데 서버에서는 안 된다

상품 앱은 Java 실행 환경과 앱 파일이 함께 있어야 동작한다. 파일 하나만 보내고 서버의 환경을 운에 맡기지 않고, 실행에 필요한 재료를 이미지로 묶는다. 호스트의 커널·CPU 구조 등 실행 조건까지 없어지는 것은 아니다.

```text
Dockerfile        → 이미지                   → 컨테이너
만드는 순서         Java + app.jar 묶음         실제로 켜진 상품 앱
                   같은 묶음에서               A와 B를 각각 실행 가능
```

**이미지는 실행 재료이고, 컨테이너는 그것으로 실행한 독립된 프로세스다.** 이미지를 만들었다고 앱이 켜진 것은 아니다. [Docker 이미지](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-an-image/), [컨테이너](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-a-container/)

## 02 · 만들 때는 공구가 필요하지만 실행할 때는 완성품이 필요하다

PromptHub의 현재 루트 Dockerfile은 Java 21 JDK로 앱을 빌드하고, Java 21 JRE 단계로 완성된 JAR를 옮긴다. **JDK**는 컴파일 등 개발 도구를 포함한 환경, **JRE**는 만들어진 Java 앱을 실행하는 환경이다. JAR는 이 프로젝트의 실행 가능한 앱 묶음이다.

```text
빌드 단계 [JDK / Gradle / 소스 → app.jar 완성]
                                     ↓ JAR만 복사
최종 단계 [JRE / app.jar] → 상품 앱 실행
```

최종 단계에 개발 도구와 소스를 함께 복사하지 않는 것이 핵심이다. 이미지 크기를 이번에 측정한 것은 아니다.

## 03 · 두 번째 FROM은 이전 작업을 삭제하는 명령이 아니다

```dockerfile
FROM eclipse-temurin:21-jdk AS build
# 이 단계에서 앱을 빌드한다

FROM eclipse-temurin:21-jre
COPY --from=build /workspace/product-service/build/libs/*.jar /app/app.jar
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
```

실제 Dockerfile의 핵심을 상품 서비스로 고정한 발췌다. 전체 빌드 파일은 아니다.

첫 `FROM`은 빌드 단계를 시작하고 이름을 `build`로 붙인다. 두 번째 `FROM`은 **JRE 기본 이미지에서 새 단계**를 시작한다. 빈 상자도 아니고 앞 단계가 삭제되는 것도 아니다. `COPY --from=build`가 앞 단계의 완성품을 가져올 수 있다. [멀티스테이지 빌드](https://docs.docker.com/build/building/multi-stage/)

<details>
<summary>나머지 Dockerfile 문법을 읽는 순서</summary>

`ARG`는 빌드 때 받는 값, `WORKDIR`는 작업 폴더, `COPY`는 파일 복사, `RUN`은 이미지 생성 중 명령 실행이다. `ENTRYPOINT`는 컨테이너 시작 때 실행할 명령이다.

`EXPOSE`는 포트 안내이지 네트워크 공개 명령이 아니다. 실제 앱의 포트와 Service의 연결도 맞아야 한다. `COPY . .`의 범위는 빌드 컨텍스트와 `.dockerignore`에 따라 달라진다.

</details>

## 프로젝트에서 어디를 볼까?

루트 `Dockerfile`의 두 `FROM`, `bootJar`, `COPY --from=build`와 실행 명령을 확인했다. 소스 확인 기준은 2026-10-09이며 이미지 빌드·컨테이너 실행은 이번에 하지 않았다.
