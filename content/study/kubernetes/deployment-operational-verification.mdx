## 01 · 새 Pod는 떴는데 상품 7이 열리지 않는다

설명용 상황이다. 배포 도구는 새 Pod를 만들었다고 말한다. 하지만 사용자는 오류를 받는다.

```text
배포 리소스 갱신 ✓ → 새 버전 실행? → Ready? → 연결 대상? → 실제 상품 조회?
```

**배포 성공은 확인하려는 사용자 기능과 관측 기간을 정한 뒤 판단한다.** Pod가 생긴 것만으로 끝내지 않는다.

## 02 · 같은 요청 하나를 끝까지 따라간다

상품 7을 읽는 대표 요청을 선택한다. 결제 같은 쓰기 기능은 승인된 테스트 환경과 테스트 데이터에서만 시험한다.

| 순서 | 확인할 증거 |
| --- | --- |
| 버전 | 새 이미지 식별자와 실제 실행 대상 |
| 준비 | Ready, 재시작 수, Probe·노드 이벤트 |
| 연결 | Service 라벨·EndpointSlice·대상 포트 |
| 요청 | 기대한 응답과 요청 추적 ID |
| 영향 | 오류율·지연·자원·큐 지연의 변화 |

Ready가 실패하면 앱 시작 로그부터, 대상이 비면 라벨과 준비 상태부터 확인한다. 모든 로그를 처음부터 읽는 대신 끊긴 위치를 좁힌다. [Deployment 상태 확인](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)

## 03 · 로그와 지표는 다른 빈칸을 채운다

```text
지표  “배포 뒤 5xx 비율이 늘었나?”
로그  “상품 7 요청에서 어떤 예외가 났나?”
추적  “이번 요청이 어느 구간에서 기다렸나?”
```

수치 하나로 원인을 확정하지 않는다. 트래픽이 거의 없어서 오류율이 0일 수도 있다. 배포 전후의 요청량, 같은 지연 기준과 대표 기능 결과를 비교한다. 세 신호의 역할은 [관측성 첫 글](/study/cs/logs-metrics-traces)을 재사용한다.

## 04 · 실패하면 무조건 즉시 롤백일까?

사용자 영향과 중단 기준을 미리 정한다. 되돌릴 이미지가 있어도 DB 변경이나 외부 처리 결과는 자동 되돌아가지 않는다. 상태를 보존하고 책임자와 복구 절차에 따라 판단한다.

<details>
<summary>읽기 명령도 실행 결과가 있어야 근거다</summary>

Pod 상태·describe·이전 로그·Service EndpointSlice를 읽는 명령은 진단 도구다. 명령 목록을 문서에 적은 것과 실제 출력에서 장애 원인을 확인한 것을 구분한다. 로그에 인증 값이나 개인정보가 있으면 공개 전에 제거한다.

</details>
