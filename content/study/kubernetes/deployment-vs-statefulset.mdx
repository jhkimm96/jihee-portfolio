## 01 · 상품 앱 A를 먼저 끄면 빈 시간이 생긴다

상품 앱 한 대를 새 버전으로 교체한다. 먼저 A를 끈다면 B가 준비될 때까지 상품 7을 조회할 앱이 없다.

```text
먼저 끄기   A 종료 ── 요청 받을 앱 없음 ── B 준비
겹쳐 교체   A 처리 ── B 시작·준비 확인 ── A 종료
```

**Deployment는 원하는 복제본 수와 버전 교체를 관리한다.** 같은 일을 하는 앱 복제본끼리 바꿔도 되는 경우에 적합하다. 단일 Pod도 컨테이너를 재시작할 수 있지만, 없어진 Pod 자체를 다른 Pod로 대체하는 감독과는 다르다.

## 02 · 프로젝트 YAML의 1, 1, 0을 읽어보자

```yaml
replicas: 1
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0
```

현재 상품 Deployment의 발췌다. 원하는 앱은 1개, 교체 중 추가로 만들 여유는 1개, 업데이트 정책상 허용할 사용 불가 수는 0개다. Deployment가 ReplicaSet을 관리하고 ReplicaSet이 Pod 수를 맞춘다. [Deployment 교체 정책](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)

```text
A Ready 1개 → B 추가 시작 → B 사용 가능 확인 → A 종료
```

이 정책만으로 오류 0건이 보장되지는 않는다. B를 놓을 자원, 정확한 준비 검사, 기존 요청의 종료 유예와 트래픽 전파도 필요하다. 종료 문제는 [Graceful Shutdown](/study/cs/graceful-shutdown-and-traffic-draining)으로 이어 읽는다.

## 03 · DB는 이름과 디스크도 이어져야 한다

상품 API의 중요한 데이터는 외부 DB에 있으므로 복제본 교체가 가능하다. 반면 DB는 어느 인스턴스인지와 어떤 저장공간을 쓰는지가 중요하다.

```text
API 복제본 교체       A → B: 외부 DB에 저장한 상품을 계속 조회
DB 인스턴스 재생성    db-0 → db-0: 식별자와 연결할 저장공간 유지 필요
```

StatefulSet은 안정적인 Pod 식별자와 저장공간 연결을 다루는 Kubernetes 기본 관리 객체다. **자동 DB 복제·백업 기능은 아니다.** Deployment도 볼륨을 사용할 수 있다. [StatefulSet의 보장과 제한](https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/)

<details>
<summary>OrderedReady는 무엇일까?</summary>

StatefulSet이 Pod를 순서대로 만들고 준비를 기다리는 기본 정책이다. 순서가 DB의 primary 선출이나 데이터 복제를 자동 구현하지는 않는다. 저장공간 유지 여부도 PVC와 실제 볼륨 정책을 함께 확인한다.

</details>

## 프로젝트 근거와 현재 범위

2026-10-09 현재 `k8s/base/services/product/deployment.yaml`에서 위 교체 정책을 읽었다. 설정 존재를 실제 무중단 배포 성공으로 쓰지 않는다.

과거 글에는 정산 CronJob 파일이 아직 없다고 적었지만, **현재 저장소에는 `k8s/base/services/settlement/cronjob.yaml`이 있다.** [정기 작업과 중복 실행](/study/kubernetes/cronjob-schedule-and-idempotency)에서 현재 설정을 따로 설명한다. 실제 클러스터 적용 여부는 확인하지 않았다.
