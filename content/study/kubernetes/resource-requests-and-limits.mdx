## 01 · 빈자리에 들어가는 일과 너무 많이 쓰는 일은 다르다

상품 앱을 놓을 노드를 고른다. 단순 학습 예시에서 남은 배치 예산이 400Mi인데 앱은 512Mi를 요청했다. 이 앱을 그 노드에 넣을 수 없다. CPU·배치 제약 등 다른 조건도 함께 검사한다.

```text
배치 전  남은 요청 예산 400Mi / 필요한 요청 512Mi → 자리 부족
배치 후  실제 메모리 사용 600Mi / 사용 한도 700Mi → 요청보다 커도 가능
```

**requests는 실제 사용량을 512Mi에 고정하는 값이 아니다.** 스케줄러가 자리를 고를 때 필요한 자원을 계산하는 기준이다.

## 02 · 프로젝트의 실제 설정을 두 칸으로 읽는다

PromptHub 상품 컨테이너 설정은 다음과 같다.

| 자원 | requests | limits |
| --- | --- | --- |
| 메모리 | 512Mi | 700Mi |
| CPU | 100m | 500m |

Mi는 메모리 단위로 1Mi = 1,048,576바이트다. CPU 1000m는 CPU 1개에 해당하므로 100m은 0.1개, 500m은 0.5개다. 순간 사용률 10%/50%와 무조건 같은 말은 아니다.

## 03 · CPU와 메모리는 경계에서 다르게 반응한다

```text
CPU 일을 더 하고 싶음 → CPU 시간을 제한받음 → 지연이 커질 수 있음
메모리를 더 잡음      → 메모리 한도에 압박 → OOM 종료가 생길 수 있음
```

CPU 제한은 throttling, 즉 CPU 실행 시간을 억제하는 방식이다. 메모리 제한은 같은 방식으로 천천히 처리하게 만들지 않고 OOM 종료로 이어질 수 있다. [Kubernetes 자원 관리](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/)

## 04 · 숫자는 어떻게 정할까?

평상시와 피크 사용량, 처리 지연, CPU 제한 시간, 컨테이너 종료 이력을 함께 본다. 요청량을 낮춰 더 많이 넣는 것만 목표로 삼으면 노드 전체가 불안정해질 수 있다. 위 숫자는 프로젝트 설정값이지 모든 Java 앱의 권장값이 아니다.

<details>
<summary>YAML에서 값을 찾는 위치</summary>

```yaml
resources:
  requests:
    cpu: 100m
    memory: 512Mi
  limits:
    cpu: 500m
    memory: 700Mi
```

상품 Deployment의 주 컨테이너 발췌다. Pod 전체 계산에는 다른 컨테이너나 초기화 컨테이너의 규칙도 있으므로 이 한 칸만 보고 노드 여유를 단정하지 않는다.

</details>

## 프로젝트 근거와 확인 범위

2026-10-09 `k8s/base/services/product/deployment.yaml`을 읽었다. 실제 Pending/OOM/CPU 제한 로그와 운영 지표는 측정하지 않았다. 설정은 Kubernetes 기본 기능이며 별도 Java 자원 제한 라이브러리가 아니다.
