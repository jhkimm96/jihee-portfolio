## 01 · 앱은 이사했는데 손님은 예전 주소로 간다

상품 앱 A가 사라지고 B가 생기면 Pod IP가 달라질 수 있다. 호출하는 앱마다 주소를 고치지 않고 Service라는 연결점을 둔다.

```text
교체 전   호출 앱 → product-service:8082 → 상품 Pod A
교체 후   호출 앱 → product-service:8082 → 상품 Pod B
                    호출 이름 유지          대상 갱신
```

**이름이 유지돼도 준비된 대상이 없으면 요청은 실패할 수 있다.** Service가 앱을 생성하거나 정상 상태로 고치는 것은 아니다.

## 02 · 8082로 보냈는데 왜 18082로 들어갈까?

현재 PromptHub 상품 Service와 Deployment를 함께 읽으면 다음 연결이 보인다.

```text
Service port 8082 → targetPort 이름 http → Pod의 http 포트 18082
```

`port`는 호출자가 사용하는 Service 포트, `targetPort`는 연결할 Pod 포트다. 번호 대신 포트 이름을 써도 된다. [Service 포트 연결](https://kubernetes.io/docs/concepts/services-networking/service/)

<details>
<summary>YAML 두 파일을 나란히 읽기</summary>

```yaml
# Service 발췌
selector:
  app.kubernetes.io/name: product-service
ports:
  - port: 8082
    targetPort: http

# Deployment의 Pod template 발췌
ports:
  - name: http
    containerPort: 18082
```

`selector`는 Pod의 라벨과 맞아야 한다. 포트 이름이 맞아도 라벨이나 Ready 조건이 틀리면 정상 연결 대상이 생기지 않을 수 있다. Kubernetes 설정이며 Java 코드나 별도 캐시 라이브러리가 아니다.

</details>

## 03 · Headless가 DB의 쓰기 담당을 골라주지는 않는다

일반 ClusterIP Service는 대표 가상 IP로 연결한다. Headless Service는 대표 IP 없이 대상 주소를 DNS로 알려주는 방식이다.

```text
대표번호 필요       일반 Service → 조건에 맞는 대상
특정 멤버 주소 필요  Headless DNS → 멤버별 주소 확인
```

Headless라는 이유만으로 primary를 알아내지는 않는다. 일반 Service도 역할 라벨로 primary만 선택할 수 있으며, 역할이 바뀔 때 라벨 갱신은 별도로 필요하다. 특정 번호의 DB가 영원히 primary라고 가정하지 않는다.

## 04 · 외부 요청은 어디서 들어올까?

```text
외부 HTTP 요청 → 진입 컨트롤러 → Service → 준비된 Pod
                       ↑
                 Ingress의 경로 규칙
```

Ingress는 외부 HTTP 경로 규칙이며 실제로 처리하는 컨트롤러가 필요하다. Service도 LoadBalancer 등 외부 노출 유형을 가질 수 있으므로 “모든 Service는 내부 전용”이라고 외우지 않는다. [Ingress의 역할](https://kubernetes.io/docs/concepts/services-networking/ingress/)

## 프로젝트에서 확인한 것

2026-10-09 `k8s/base/services/product/service.yaml`과 `deployment.yaml`의 ClusterIP, 라벨, 포트 연결을 읽었다. 실제 통신·DNS·Ingress 컨트롤러 설치 버전과 지원 상태는 검증하지 않았다. 특정 컨트롤러를 신규 도입하라는 추천은 아니다.
