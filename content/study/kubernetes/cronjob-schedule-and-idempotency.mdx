## 01 · 월요일에 깨우는 일과 두 번 정산하지 않는 일

매주 월요일에 지난주 정산을 시작한다. 예약 시스템은 작업을 깨우지만, 통신 문제와 재시도 뒤에도 같은 기간을 안전하게 처리하는 책임까지 대신하지 않는다.

```text
CronJob의 질문   언제 시작할까?
앱의 질문       어느 기간인가? 이미 계산·전달했나? 다시 해도 안전한가?
```

**CronJob은 정확히 한 번을 보장하지 않는다.** 예정 시각에 Job이 두 개 생기거나 생기지 않을 수 있으므로 반복 처리에 안전한 설계가 필요하다. [CronJob 실행의 한계](https://kubernetes.io/docs/concepts/workloads/controllers/cron-jobs/)

## 02 · 프로젝트는 일별이 아니라 주간이다

현재 PromptHub 설정의 핵심이다. YAML은 Kubernetes가 읽는 실행 설정 파일이다.

```yaml
schedule: "0 0 * * 1"
timeZone: Asia/Seoul
concurrencyPolicy: Forbid
startingDeadlineSeconds: 3600
```

서울 시간 월요일 00:00 일정이다. Forbid는 **같은 CronJob**의 이전 Job이 진행 중이면 겹치는 실행을 막는 정책이다. 다른 CronJob이나 수동 실행까지 전부 잠그지는 않는다. 시작 기한 3600초는 늦게 시작할 수 있는 범위이며 실행 시간 한도가 아니다.

<details>
<summary>작업 실행 제한은 어디에 있을까?</summary>

현재 Job template에는 `backoffLimit: 1`, `activeDeadlineSeconds: 7200`, Pod에는 `restartPolicy: Never`가 있다.

Job의 실패 재시도, 총 실행 기한과 컨테이너 재시작은 서로 다른 설정이다. 한도만으로 업무 중복 방지가 생기지 않는다.

</details>

## 03 · API 앱과 배치 앱은 같은 방식으로 켜 두지 않는다

```text
API 실행    시작 → 요청 대기 → 여러 요청 처리 → 계속 실행
배치 실행   시작 → 기간 확정 → 정산 수행 → 결과/종료 코드 → 끝
```

현재 정산 CronJob은 같은 정산 모듈을 `web-application-type=none`과 `execution.mode=cronjob`으로 실행한다. **모듈을 물리적으로 따로 만든 것과 실행 모드를 분리한 것은 다르다.** 배치 실행을 위해 새 프로젝트가 반드시 필요한 것은 아니다.

## 04 · 실행됐는지보다 무슨 결과로 끝났는지 본다

`SettlementCronJobRunner`는 앱 시작 때 지난주 기간을 계산해 유스케이스를 호출하고, 결과가 COMPLETED일 때 종료 코드 0을 선택한다. Java 기본 기능이 아니라 프로젝트가 작성한 클래스다. Spring Boot의 ApplicationRunner는 시작 후 작업을 실행할 진입점을 제공한다.

```text
시작 로그 존재 ≠ 정산 계산 성공 ≠ 전달된 결과 일치
```

실행 종료 코드, Spring Batch 상태, 정산 업무 상태와 전달 결과를 함께 봐야 한다. 코드만으로 최종 프로세스 종료나 클러스터에서의 성공을 확인한 것은 아니다.

## 프로젝트 근거와 확인 범위

2026-10-09 `k8s/base/services/settlement/cronjob.yaml`, `SettlementCronJobRunner.java`와 `SettlementJobLauncherAdapter.java`를 읽었다. 실제 스케줄 실행·누락 복구·프로세스 종료 테스트는 하지 않았다.
