## 01 · 객체 공간만 보고 전체 메모리가 남았다고 생각했다

다음은 같은 단위로 단순화한 학습 장면이다. 운영 측정값이 아니다.

```text
컨테이너 한도 700Mi
  Java 힙 사용       300Mi
  그 밖의 사용      430Mi
  합계              730Mi → 전체 한도에 압박
```

**힙이 남아도 컨테이너 전체는 메모리 부족일 수 있다.** 힙은 Java 객체를 담는 공간이고, 스레드 스택·클래스 정보·직접 버퍼 등 다른 공간도 필요하다. [Java 메모리 진단](https://docs.oracle.com/en/java/javase/21/troubleshoot/diagnostic-tools.html)

## 02 · “힙을 더 키우자”는 반대로 악화시킬 수도 있다

PromptHub 상품 설정은 `-Xmx384m`과 컨테이너 메모리 한도 `700Mi`를 함께 둔다. Xmx는 힙의 최대 크기이지 전체 프로세스 최대 크기가 아니다.

```text
같은 컨테이너 한도 안에서
힙 최대치 증가 → 다른 메모리가 쓸 여유 감소 → 전체 종료 위험은 커질 수 있음
```

설정 차이 316Mi가 언제나 실제 여유로 남는다는 뜻도 아니다. 사용량과 컨테이너 집계 범위를 확인해야 한다.

## 03 · 먼저 무엇 때문에 끝났는지 본다

| 확인할 흔적 | 구분하려는 원인 |
| --- | --- |
| 컨테이너의 마지막 종료 reason | OOMKilled 등 실제 종료 이유 |
| 이전 실행 로그 | Java OutOfMemoryError가 있었는가 |
| 종료 전 전체 메모리와 힙 추이 | 어느 공간이 증가했는가 |
| 노드 이벤트와 압박 | 노드 차원의 부족도 있었는가 |

종료 코드 137 하나로 OOM을 확정하지 않는다. 강제 종료에서도 나올 수 있다. OOMKilled, Java 예외, 노드 부족과 eviction을 같은 증상으로 뭉치지 않는다. [메모리 한도와 종료 확인](https://kubernetes.io/docs/tasks/configure-pod-container/assign-memory-resource/)

## 04 · 원인에 따라 행동도 달라진다

```text
붙잡힌 객체 증가 → 참조와 보관 기간 확인
직접 버퍼·스레드 증가 → 해당 사용량과 동시성 확인
정상 피크가 한도 초과 → 부하·용량을 측정해 한도 조정
노드 전체 부족 → 배치·요청량·노드 용량 함께 점검
```

GC는 도달 가능한 객체를 마음대로 버리지 않는다. [GC와 참조](/study/jvm/gc-roots-reachability-and-memory-reclaim)를 이어 읽는다. 재시작만 반복하면 원인과 직전 상태를 잃을 수 있다.

<details>
<summary>진단 도구와 실제 실행의 차이</summary>

`kubectl describe pod`는 상태·이벤트를 읽고, `kubectl logs --previous`는 남아 있는 이전 컨테이너 로그를 읽는 명령이다. 이번에는 클러스터에 실행하지 않았다.

Java의 NMT는 HotSpot 내부 메모리를 조사하는 기능이다. 별도 캐시 라이브러리는 아니지만 활성화 조건과 비용이 있고 모든 외부 native 할당을 추적하지는 않는다. 최종 JRE 이미지에 모든 JDK 진단 도구가 있다고 가정하지 않는다.

</details>
