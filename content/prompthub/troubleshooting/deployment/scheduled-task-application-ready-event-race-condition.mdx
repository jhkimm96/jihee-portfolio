## 문제

전체 재조정 배치(`ProductReconcileScheduler`)를 추가해 k8s에 배포했는데, 파드가 뜨자마자
스케줄된 작업에서 `index_not_found_exception: no such index [products]` 에러가 로그에
찍혔다.

## 원인

`@Scheduled` 메서드는 `initialDelay`를 지정하지 않으면 앱이 뜨자마자 곧바로 첫 실행이
일어난다. 그런데 ES 인덱스와 alias를 실제로 만드는 `ProductIndexBootstrap`도
`@EventListener(ApplicationReadyEvent.class)`로 앱 시작 시점에 실행되는데, 이 둘의
실행 순서는 스프링이 보장해주지 않는다. 실제 로그를 보니 두 이벤트가 71밀리초 차이로
거의 동시에 실행됐고, 하필 스케줄러가 먼저 실행되면서 아직 만들어지지 않은 인덱스를
조회하려다 실패했다.

이 버그는 그동안 로컬 테스트에서는 한 번도 드러나지 않았다 — 인덱스 부트스트랩 코드는
"alias가 이미 존재하면 즉시 건너뛴다"는 빠른 경로가 있는데, 로컬에서 반복 테스트할 때는
항상 이전에 만들어둔 인덱스가 남아있어서 이 빠른 경로만 타고 끝났다. nori 플러그인을
설치하려고 ES를 재배포하면서 데이터가 초기화됐고, 그 결과 "인덱스를 처음부터 진짜로 새로
만드는" 상황이 처음 발생하면서 경쟁 상태가 드러났다.

<details>
<summary>💡 이게 재발할 수 있는 상황인가?</summary>

"최초 배포 때만 나는 일회성 문제 아닌가?" 싶을 수 있는데, 그렇지 않다. 이 문제의 조건은
"최초 배포"가 아니라 "ES 인덱스가 새로 만들어져야 하는 상황"이다. 실제로 이번 프로젝트에서도
최초 배포 이후 nori 플러그인을 설치하려고 ES를 재배포했을 때 데이터가 초기화되면서 똑같은
상황이 한 번 더 재현됐다.

ES가 `emptyDir`(파드 재생성 시 초기화되는 임시 볼륨)를 쓰고 있어서, 파드가 다른 노드로
재스케줄되거나 ES 자체를 재배포하는 일이 생기면 언제든 다시 발생할 수 있는 조건이다.
반대로 노드가 그냥 재부팅되는 정도(파드는 그대로, 볼륨도 그대로)로는 데이터가 안 지워지므로
문제가 되지 않는다.

## 해결 — 처음 고려했던 방법과 실제로 택한 방법

처음엔 "스케줄러 첫 실행을 인덱스 생성 뒤로 미루면 되지 않을까"(`initialDelay` 추가)를
생각했다. 하지만 실제 이슈를 등록하면서 세 가지 방법을 후보로 올렸다.

1. 스케줄러 실행 전 인덱스 존재 여부를 확인해, 없으면 이번 사이클을 스킵
2. `ProductIndexBootstrap`의 인덱스 생성이 끝날 때까지 기다린 뒤 스케줄러를 활성화
3. `index_not_found_exception`을 인덱서/서비스 레벨에서 특별 처리(로그만 남기고 스킵)

최종적으로 1번을 택해 구현했다.

```java
public void reconcileAll() {
    if (!productSearchIndexer.indexExists()) {
        log.info("ES 인덱스가 아직 없어 이번 재조정 사이클을 건너뜁니다.");
        return;
    }
    // ... 기존 로직(RDB ON_SALE 전체와 ES 색인 전체 비교)
}
```

### 왜 "순서 맞추기"가 아니라 "겹쳐도 안전하게"를 택했나

`initialDelay`(2번에 가까운 접근)는 "인덱스 생성이 몇 초 안에 끝날 것"이라는 시간 추정에
의존한다. 이 추정이 어긋나면(예: ES 응답이 평소보다 느린 날) 똑같은 문제가 다시 날 수 있다
— 문제를 없앤 게 아니라 발생 확률을 낮췄을 뿐이다.

반면 인덱스 존재 여부를 직접 확인하는 방식(1번)은 타이밍을 전혀 추정하지 않는다. 인덱스가
있으면 일하고, 없으면 조용히 다음 기회를 기다린다 — 몇 초가 걸리든 상관없다. 그리고 이
가드를 스케줄러가 아니라 `ProductReindexService.reconcileAll()`(스케줄러와 온디맨드
재색인 API `/internal/search/reindex`가 공유하는 지점) 안에 넣었기 때문에, 스케줄러뿐
아니라 "배포 직후 누군가 수동으로 재색인 API를 호출하는" 경우까지 같이 보호된다 —
`initialDelay`는 스케줄러에만 적용되므로 이 경우는 못 막는다.

### 이 "왜"를 어떻게 알게 됐나

이 트러블슈팅 글의 초안엔 처음에 "`initialDelay`를 추가해서 해결했다"고 잘못 적혀 있었다.
실제로 코드가 그렇게 고쳐졌는지 코드베이스를 다시 확인하는 과정에서, `initialDelay`는 코드
어디에도 없다는 걸 발견했다. 진짜 원인을 찾기 위해 관련 GitHub 이슈(#553) 본문을 다시 읽어보니
"가능한 해결 방향(택1)"으로 위 세 가지가 이미 후보로 정리돼 있었고, 이 이슈를 참조하는 PR을
`gh pr list --search`로 찾아 실제 diff(`gh pr diff`)를 열어본 결과 1번 방식
(`indexExists()` 가드)이 채택된 걸 확인했다. 즉 "왜 이 방법을 택했는가"는 코드를 짐작하지
않고, 이슈에 남겨둔 의사결정 후보 목록과 실제 병합 전 PR의 diff를 직접 대조해서 확인한
것이다.

## 결과

이 수정은 별도 PR(#563)에 담겨 있으며, 이 글 작성 시점 기준 아직 머지 전이다. 머지되면
스케줄러의 첫 실행이 인덱스 생성과 겹치더라도 예외 없이 다음 주기를 기다리게 된다.

## 배운 점

`@Scheduled`(initialDelay 없음)와 `@EventListener(ApplicationReadyEvent)`는 둘 다
"앱이 뜨는 시점"에 실행되지만, 스프링이 그 둘 사이의 순서를 보장해주지 않는다. 이런
타이밍 버그는 "이미 존재하는 상태"에서 반복 테스트하면 절대 드러나지 않고, "완전히
처음부터 시작하는" 조건에서만 나타난다.

또한 두 가지 해결 방향(타이밍을 늦추기 vs 상태를 직접 확인하고 안전하게 넘어가기) 중에서는
후자가 더 견고하다 — 타이밍 추정은 언젠가 어긋날 수 있지만, 상태 확인은 몇 초가 걸리든
정확하다. 그리고 "이 코드를 실제로 고쳤는지, 어떻게 고쳤는지"는 기억이나 짐작이 아니라
GitHub 이슈·PR의 실제 내용을 직접 열어봐야 확실히 알 수 있다 — 이번에도 초안에 남아있던
잘못된 기억(`initialDelay`)을 실제 diff 확인으로 바로잡았다.
