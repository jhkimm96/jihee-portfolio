## 문제

Docker PostgreSQL 초기화 스크립트(`docker-entrypoint-initdb.d/01-init-schemas-and-roles.sh`)가 서비스별 DB 계정 비밀번호에 하드코딩된 기본값을 fallback으로 갖고 있었다. 배포 환경변수를 빠뜨려도 스크립트가 에러 없이 넘어가고, 소스코드에 그대로 노출된 값(예: `user_service_password`)으로 서비스 DB 계정이 만들어졌다.

## 원인

두 가지 문제가 겹쳐 있었다.

1. 초기화 스크립트가 `USER_SERVICE_PASSWORD="${USER_SERVICE_PASSWORD:-user_service_password}"` 형태로 짜여 있어, 환경변수 누락이 "정상 종료"로 처리됐다. 값이 없어도 실패하지 않고 레포에 박힌 기본값으로 조용히 넘어갔다.
2. `docker-compose.yml`의 postgres 컨테이너 `environment`에는 `POSTGRES_USER`/`POSTGRES_PASSWORD`/`POSTGRES_DB`만 연결돼 있고, 서비스별 비밀번호 6개는 애초에 컨테이너로 전달되는 경로가 없었다. `.env`에 값을 채워 넣어도 초기화 스크립트 입장에서는 안 들어온 것과 같아서, 사실상 하드코딩된 기본값이 계속 쓰이고 있었을 가능성이 있었다.

<details>
<summary><b>🔍 왜 이게 "설정은 했는데 안 먹는" 상태가 되나</b></summary>

`.env.example`에 변수를 선언해두는 것과, 그 변수가 실제로 컨테이너까지 전달되는 것은 별개의 일이다. compose는 `environment:` 블록에 명시적으로 나열된 변수만 컨테이너 안으로 넘긴다. `.env` 파일에 `USER_SERVICE_PASSWORD=xxx`를 써 놔도, `docker-compose.yml`의 postgres 서비스 `environment:`에 그 변수가 없으면 컨테이너 프로세스는 그 값을 아예 볼 수 없다. 즉 설정 파일 두 곳(`.env`와 `docker-compose.yml`) 중 한쪽만 고쳐서는 값이 반영되지 않는다.

</details>

## 해결

- 초기화 스크립트의 fallback을 제거하고 `: "${VAR:?VAR is required}"`로 교체해, 환경변수가 없으면 컨테이너 초기화가 즉시 실패하도록 변경했다.
- `docker-compose.yml`의 postgres 컨테이너 `environment`에 서비스별 비밀번호 6개를 실제로 연결해, `.env` 값이 스크립트까지 전달되도록 배선했다.
- `.env.example`에 누락돼 있던 `NOTIFICATION_SERVICE_PASSWORD` 항목을 추가했다.

## 결과

PR로 병합됐다. 이제 배포 시 비밀번호 환경변수가 빠지면 컨테이너가 뜨지 않는 방식으로 즉시 드러나고, 저장소에는 실제 비밀번호 값이 남지 않는다.

## 배운 점

- "환경변수가 없으면 기본값을 써라"는 로컬 개발 편의를 위해 흔히 쓰는 패턴이지만, 비밀번호 같은 민감값에 적용하면 "설정을 깜빡해도 조용히 성공한다"는 것 자체가 보안 리스크가 된다. 실패해야 할 자리에서 실패하게 만드는 게 오히려 방어다.
- 설정값이 "선언돼 있다"와 "실제로 전달 경로가 연결돼 있다"는 다른 문제다. `.env.example`만 보고 안심하지 말고, compose의 `environment:` 배선까지 같이 확인해야 값이 조용히 무시되는 상태를 놓치지 않는다.
