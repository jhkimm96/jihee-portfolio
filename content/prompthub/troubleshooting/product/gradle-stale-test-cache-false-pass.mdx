## 문제

PR5(#729/#730) 작업 중 "product-service 테스트 452개 전부 통과"라고 보고했다. 그런데 이후
재검증 과정에서 이 보고 자체가 틀렸다는 게 드러났다 — 방금 작성한 유닛 테스트 하나가 사실은
실행조차 되지 않는 상태였는데도 "통과"로 표시되고 있었다.

## 원인

Gradle의 `compileTestJava` 태스크가 테스트 소스 파일이 바뀌었는데도 `UP-TO-DATE`로 판정해,
이전 컴파일·실행 결과를 그대로 재사용했다. incremental build가 변경을 못 잡아내면 아무것도
다시 실행하지 않고 캐시된 리포트를 그대로 보여준다.

실제로 깨져 있던 테스트는 `ElasticsearchProductSearchIndexerTest`의 PIT 예외 처리 테스트였다.
Elastic Java client 9.x의 `OpenPointInTimeResponse`를 `OpenPointInTimeResponse.of(b -> b.id("pit-id"))`로만
만들었는데, 이 타입은 `id` 말고 `shards`도 필수 필드라 실제로 실행됐다면
`MissingRequiredPropertyException`이 났을 것이다. 같은 PR 안에서 `IndexAliases.of(a -> a)`도
똑같은 유형(필수 필드 누락)으로 걸렸던 적이 있는데, 그건 정상적으로 실행돼서 바로 잡혔다.
차이는 하나 — 그건 처음 실행될 때 캐시가 없어서 실제로 돌았고, 이번 건 캐시가 껴서 한 번도
제대로 돌지 않은 채 "통과"라고 보고됐다는 것이다.

<details>
<summary><b>🔍 Gradle의 UP-TO-DATE 판정이 뭔가요?</b></summary>

Gradle은 매번 전체를 다시 빌드하지 않으려고, 태스크의 입력(소스 파일 등)과 출력이 지난
실행 이후 안 바뀌었으면 그 태스크를 건너뛰고 `UP-TO-DATE`라고 표시한다. 보통은 효율을 위한
정상 동작이지만, 파일 수정 시각이나 내용 해시를 비교하는 방식이 어떤 이유로든 "안 바뀜"으로
오판하면 실제로 바뀐 코드가 재컴파일·재실행되지 않은 채 이전 결과가 그대로 재사용된다.

</details>

## 해결

`--rerun-tasks` 옵션으로 Gradle의 incremental build 판단을 무시하고 모든 태스크를 처음부터
강제로 다시 실행했다. 그제서야 깨져 있던 테스트가 진짜로 실행되며 실패로 드러났다.
`.shards(s -> s.total(1).successful(1).failed(0))`를 추가해 필수 필드를 채우자 정상 통과했다.

## 결과

`--rerun-tasks`로 재실행해 실제로 452개 테스트가 전부 통과하는 걸 확인했다. 이후 이 작업
세션부터는 "테스트 통과"를 보고하기 전 검증 방식을 `--rerun-tasks` 기준으로 바꿨다.

## 배운 점

"테스트가 통과했다"는 보고를 신뢰하려면, Gradle이 그 테스트를 **실제로 실행했는지**부터
확인해야 한다. 같은 모듈을 여러 번 반복해서 수정하는 작업 세션일수록 캐시가 실제 실행을
대체했을 가능성을 의심해야 하고, 가장 확실한 확인 방법은 적어도 한 번은 `--rerun-tasks`로
강제 재실행해 보는 것이다.
