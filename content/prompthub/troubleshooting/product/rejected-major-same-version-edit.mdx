## 문제

상품 1.0이 판매 중일 때 major 수정으로 2.0을 만들고 검수에서 반려되면 두 row가 함께 남는다.

```text
1.0 ON_SALE
2.0 REJECTED
```

판매자 목록은 `ON_SALE`을 `REJECTED`보다 먼저 선택해 1.0만 보여줬다. 반려된 2.0의 수정·재요청 버튼이 나타나지 않았다.

2.0 ID로 수정 API를 호출해도 서비스는 판매 중인 1.0을 기준으로 새 row를 만들었다. 반려 내용을 고치는 대신 3.0 또는 1.1이 생길 수 있었다.

<details>
<summary><b>🔍 row와 family는 무엇인가요?</b></summary>

상품 버전 하나를 DB의 한 row로 저장한다. 같은 상품에서 생성된 1.0·2.0 등의 row 묶음을 family라고 한다. 구매자는 현재 판매 중인 row를 보고, 판매자는 검수나 수정이 필요한 row를 먼저 봐야 한다.

</details>

## 원인

구매자와 판매자가 서로 다른 대표 row를 필요로 하는데 판매자 선택 순서가 이를 반영하지 못했다.

```text
기존: PENDING_REVIEW → ON_SALE → REJECTED
변경: PENDING_REVIEW → REJECTED → ON_SALE
```

수정 서비스도 요청받은 REJECTED row보다 family의 ON_SALE row를 기준으로 다음 버전을 생성했다.

## 해결

판매자 대표 선택에서 `REJECTED`를 `ON_SALE`보다 앞에 두었다. 반려된 수정본이 있으면 판매자 목록과 상세가 그 row를 반환한다.

REJECTED 수정은 별도 도메인 행위로 분리했다.

- 같은 ID와 version 유지
- 콘텐츠만 변경
- 상태와 기존 반려 사유 유지
- 새 row 생성 없음
- 판매 중인 이전 버전 변경 없음
- 검수 이벤트 발행 없음
- 수정 후 판매자가 별도로 재요청

FE에서는 REJECTED 수정 화면의 버전 선택과 변경 사유 입력을 숨기고, 현재 판매 중인 버전을 함께 표시했다.

## 결과

배포 환경에서 다음 흐름을 확인했다.

```text
1.0 ON_SALE
→ major 수정 2.0 반려
→ 판매자 목록에 2.0 REJECTED 표시
→ 같은 2.0 수정
→ 1.0은 계속 판매
→ 별도 재요청
→ 2.0 승인
→ 2.0 ON_SALE, 1.0 SUPERSEDED
```

반려본을 여러 번 고쳐도 불필요한 버전 row가 늘어나지 않았고, 승인 전까지 기존 판매 상품도 유지됐다.

<details>
<summary><b>🔍 SUPERSEDED는 어떤 상태인가요?</b></summary>

새 버전이 판매를 시작하면서 교체된 이전 버전이다. 이력에는 남지만 구매자에게 현재 상품으로 노출되지 않는다.

</details>

## 배운 점

“가장 최신 버전”은 사용자에 따라 다르다. 구매자에게는 승인된 판매본이 중요하고, 판매자에게는 지금 조치해야 하는 검수 대기·반려본이 중요하다.

상태별 수정 규칙도 서비스의 공통 분기보다 도메인 행위로 표현해야 ID·version·이벤트 유지 조건을 한곳에서 보장할 수 있다.
