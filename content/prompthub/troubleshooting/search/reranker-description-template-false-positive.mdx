## 문제

상품 추천에 Jina reranker와 최소 관련도 `0.05`를 적용했지만, 주식 분석 상품에 Docker 가이드가 추천되는 문제가 발생했다.

처음에는 다음 가능성을 의심했다.

- 이전 이미지가 배포되었을 가능성
- 운영 임계값이 아직 `0.5`이거나 다른 값일 가능성
- 상품 본문 `content`가 Jina 입력에 포함되었을 가능성
- Elasticsearch 후보 검색 결과가 필터 없이 그대로 노출되었을 가능성

하지만 배포 이미지와 설정 로딩을 확인한 결과 최신 코드와 `0.05`가 적용되어 있었다. 코드에서도 `content`는 추천용 임베딩과 Jina 입력에서 제외되어 있었다.

즉, 배포나 설정 문제가 아니라 실제 Jina 입력 자체가 무관 상품을 관련 상품으로 판단하게 만든 문제였다.

## 원인

운영과 동일한 입력으로 주식 분석 상품과 Docker 가이드의 관련도를 다시 측정하자 점수가 `0.11954248`로 나타났다. 임계값 `0.05`보다 높으므로 현재 구현에서는 정상적으로 추천 대상이 된다.

두 상품은 주제가 완전히 달랐지만 설명에는 다음과 같은 일반적인 문구가 반복되고 있었다.

- `10년 차 이상`
- 전문가 또는 페르소나 기반
- 최적의 가이드나 분석을 제공
- 모델명과 상품 형식을 설명하는 표현

기준 상품과 후보 상품 양쪽에 긴 설명을 대칭적으로 넣으면서, 실제 상품 목적보다 공통 템플릿 문장이 관련도에 크게 반영된 것이다.

Jina 쿼리에 “표현 방식이 아니라 목적을 기준으로 판단하라”는 자연어 지시도 추가해 보았지만 점수는 오히려 `0.25010713`까지 상승했다. Reranker 입력에 생성형 모델처럼 지시문을 추가하는 방식은 안정적인 해결책이 아니었다.

결국 문제는 임계값이 아니라 입력 필드의 역할이 구분되지 않은 데 있었다.

## 해결

후보 수집과 최종 관련성 검증의 입력 책임을 분리했다.

Elasticsearch 후보 검색은 기존처럼 넓은 정보를 사용한다.

- 상품명
- 태그
- 설명
- 모델명
- 저장된 임베딩

반면 추천용 Jina 입력은 다음처럼 비대칭으로 구성했다.

- 기준 상품 쿼리: 상품명과 태그
- 후보 상품 문서: 상품명, 태그, 설명
- 추천 입력에서 제외: 기준 상품 설명, 상품 본문, 모델명

기준 상품의 상품명과 태그는 사용자가 기대하는 추천 의도를 대표한다. 후보 설명은 제목과 태그에 드러나지 않은 실제 용도를 보완하는 정보로만 사용한다.

일반 상품 검색에서는 `GPT`, `Claude` 같은 모델명 검색이 필요하므로 모델명을 계속 포함한다. 추천 경로에서만 모델명을 제외해 검색 동작의 회귀를 막았다.

최소 관련도 `0.05`는 변경하지 않았다. 점수 기준을 다시 낮추는 대신, 점수가 비교해야 할 의미를 입력 구조로 바로잡았다.

구현 후 product-service 전체 테스트와 관련 집중 테스트를 통과했으며 `git diff --check`와 민감정보 검토도 완료했다. 실제 운영 반영 후에는 동일한 상품 조합으로 E2E를 다시 확인해야 한다.

## 배운 점

Reranker의 임계값만 조정해서는 입력 분포가 잘못된 문제를 해결할 수 없다. 무관 상품의 점수와 관련 상품의 점수가 겹친다면 먼저 어떤 텍스트가 점수에 영향을 주는지 확인해야 한다.

같은 상품 데이터라도 검색과 추천에서는 역할이 다르다. 검색은 사용자가 입력한 단어를 폭넓게 찾아야 하지만, 추천은 기준 상품의 핵심 의도를 후보의 실제 용도와 비교해야 한다.

기준과 후보에 동일한 필드를 대칭적으로 넣는 것이 항상 공정한 비교는 아니다. 반복되는 설명 템플릿처럼 의미 없는 공통점까지 양쪽에서 증폭될 수 있다.

또한 축약된 테스트 데이터만으로 임계값을 결정하면 운영 입력에서 다른 결과가 나올 수 있다. 실제 서비스가 전송하는 완전한 문자열로 점수를 재현해야 원인을 정확히 분리할 수 있다.
