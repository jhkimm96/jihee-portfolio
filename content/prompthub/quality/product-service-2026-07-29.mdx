트레이드오프를 코드 주석에 촘촘히 남겨둔 게 눈에 띄었다.

## 카테고리별 발견

### integration-robustness (High 1)

- **High** · `ProductEventProducer.java:81,85` — `kafkaTemplate.send(...)`의 반환값
  (`CompletableFuture`)을 확인하지 않는다. AFTER_COMMIT 콜백 경로·즉시 발행 경로 둘 다
  동일. Kafka 전송이 비동기로 실패해도 로그도, 알림도, 재시도도 없이 이벤트가 사라진다 —
  가격 변경·판매중단 이벤트가 유실되면 ES 색인이 조용히 stale해진다.
  `.whenComplete((result, ex) -> { if (ex != null) log.error(...); })` 권장.

  항상 `null`).
- **Medium** · `ProductDetailResponse.java:24` — `features` 필드도 동일 패턴, 항상

  고치면 된다.

### cohesion-coupling (Medium 1) — v2 신규

- **Medium** · `ProductQueryService`(303 LOC·19메서드, 스크립트가 비대로 표시한 4개 중
  하나)가 검색 오케스트레이션(ES/RDB 폴백)·DTO 매핑 3벌·presigned URL 해석·버전 이력
  조립을 한 클래스에 담고 있다 — 바뀌는 이유가 여러 개다.
  *(참고: 비대로 표시된 나머지 3개 — `Product`·`ProductFamily`·`ProductRepositoryAdapter` —
  는 직접 확인 결과 실질 문제는 아니었다. 앞의 둘은 상태 전이 가드/family 규칙마다 작고
  단순한 메서드가 많아 응집도가 높고, `ProductRepositoryAdapter`는 1줄짜리 위임 24개라

- **Medium** · `FileUploadController.resolveContentType`(59-82) — 허용 확장자 정책·

### layer-separation (Medium 2)

- **Medium** · `ProductSellerService`가 `ProductEventProducer`(Kafka 발행 어댑터) 구체
  클래스를 포트 없이 직접 주입받는다. 리포지토리 3종(Product/Review/ProcessedEvent)은
  전부 domain 포트 + infra 어댑터 구조인데, 이벤트 발행만 이 패턴에서 빠져 있다(v1에서도
  지적, 미해소).
- **Medium** · `SellerProductDetailResponse`/`SellerProductListItemResponse`가
  presentation DTO의 정적 팩토리 안에서 `StorageClient`로 S3 presign 원격 호출을 직접
  수행한다. `ProductDetailResponse`/`ProductListItemResponse`는 이미 만들어진 URL 문자열만
  받는 것과 대비된다(v1에서도 지적, 미해소).

### http-semantics · logging-quality · exception-discipline · entity-encapsulation · service-boundary (위반 없음)

- gRPC/HTTP 상태 코드 매핑 전부 의미에 부합.
- 로그 메시지가 맥락 있고 과하지 않음.
- 예외 처리가 대부분 의도가 명확히 문서화됨(멱등성 처리, ES/OpenAI 폴백 등).
- `Product`는 setter 없이 상태 전이 가드로 스스로를 관리, `ProductContent` 값객체가 유형별
  필드 조합을 생성 시점에 검증.
- 타 서비스 DB 직접 접근·순환 호출 없음.

## 개선된 항목 (v1 대비)

- **diagnosability High 1건 해소** — `GetSellerStats`(gRPC) 자체가 삭제됨(#483).
- **diagnosability Medium 1건 해소** — `getProductContent`가 예외 유형별 gRPC status로

- **integration-robustness Medium 2건 해소** — `GrpcSellerClientAdapter`(데드라인 미설정)와
  판매자 정보 N+1 gRPC 호출이 판매자 정보 FE 조합 전환으로 경로 자체가 삭제됨.
- **dead-code Medium 2건 해소** — `findPendingReviewProducts` 체인, `InternalProductController`
  무호출 엔드포인트 모두 제거됨.
- **duplication-semantic Medium 1건 해소** — `ProductInternalService` 자체가 제거되며
  family 해석 중복도 함께 사라짐.
- **entity-encapsulation Low 1건 해소** — `Product` 생성자의 긴 파라미터 목록이
  `ProductContent` 값객체(#405)로 정리됨.
- **exception-discipline Low 1건 해소** — 원시 `RuntimeException`을 감싸던
  `GrpcSellerClientAdapter` 자체가 제거됨.

**판정 번복 2건(투명하게 공개)**: v1의 layer-separation 위반 중 (1) `Product`가
`TagsConverter`를 직접 import하는 것과 (2) application이 presentation DTO에 의존해 응답을
조립하는 것은, 이번에 다시 보니 실질적 문제로 보지 않기로 했다. (1)은 JPA
`@Convert`의 관용적 사용이라 엔티티가 컨버터를 직접 참조하는 게 표준 패턴이다. (2)는
`clean-architecture.md`가 user-service 전용 문서인데, product-service는 애초에 그
Command/Result 계층 구조를 쓰지 않고 Service가 Response를 직접 조립하는 걸 전 서비스
클래스에서 일관되게 쓰고 있어 — 이건 드리프트가 아니라 product-service의 실제 컨벤션으로
판단했다.
