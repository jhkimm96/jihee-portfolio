## 리뷰 범위

상품 파일 업로드 PR에서 presigned URL 발급부터 FE 미리보기, 상품 저장, 임시 파일 승격과 실패 복구까지 전체 흐름을 검토했다.

관련 결정: [업로드 미리보기 URL과 저장 키 분리](/decisions/prompthub/product-service/object-key-upload-and-transaction-compensation)

## 발견하고 고친 것

### 미리보기 URL과 저장 키가 섞여 있었다

FE가 presigned URL을 화면 표시와 상품 저장 요청에 함께 사용했다. 업로드 응답을 `objectKey`와 `previewUrl`로 분리해 미리보기에는 URL, 저장·취소 요청에는 키만 사용하도록 바꿨다. 이미지를 읽기만 하는 목록·상세 화면은 이번 계약 변경 대상이 아니어서 건드리지 않았다.

### 저장할 수 없는 요청도 파일부터 복사할 수 있었다

상품 유형별 필드 검증을 파일 승격 전에 수행하도록 순서를 바꿨다. `ProductContent`도 검증용과 저장용으로 중복 생성하지 않고, 승격된 키가 준비된 뒤 한 번만 생성했다.

public 메서드는 다음 업무 흐름이 위에서 아래로 보이게 유지했다.

```text
상품 유형 해석 → 필드 검증 → 임시 파일 승격 → ProductContent 생성 → 상품 저장
```

### S3 작업은 DB rollback을 따라가지 않았다

임시 파일을 영구 경로로 복사한 뒤 DB 저장이 실패하면 영구 파일만 남을 수 있었다. commit 후에는 임시 원본을 삭제하고, rollback 시에는 새 영구 복사본을 삭제하되 임시 원본은 재시도를 위해 유지하도록 보상했다. 복사 도중 실패하면 그때까지 생성한 복사본도 즉시 정리한다.

### 스토리지 키 검증이 부족했다

단순 prefix 확인 대신 키의 형식, 판매자 ID, thumbnail·image·file 용도를 함께 검증했다. 범용 스토리지 프레임워크로 넓히지 않고 이번 상품 업로드 계약에 필요한 규칙만 담았다.

### Swagger 설명이 컨트롤러 흐름을 가렸다

`X-User-Id`와 `X-User-Role`은 클라이언트가 입력하는 값이 아니라 API Gateway가 JWT 검증 후 주입하는 내부 헤더다. product-service의 Swagger 공통 설정에서 두 헤더를 숨기고 Bearer 토큰만 입력하도록 했다. 컨트롤러에는 실제 요청 매핑과 검증에 필요한 어노테이션만 남겼다.

<details>
<summary><b>Swagger에서 헤더를 숨겨도 인증이 동작하나요?</b></summary>

숨김은 문서 UI의 입력 항목만 제거한다. 운영에서는 사용자가 Bearer 토큰을 보내고 Gateway가 토큰에서 사용자 ID와 역할을 확인해 내부 헤더로 전달한다. 역할별 접근 제어도 Swagger가 아니라 실제 Gateway와 보안 정책이 담당한다.

## 과하게 만들었다가 줄인 것

영구 키에 새 UUID를 추가하는 방안은 적용하지 않았다. 임시 업로드 키가 이미 유일하고 영구 경로에는 상품 ID가 포함돼, UUID를 하나 더 넣어도 해결되는 문제가 없었다.

파일 처리를 얇은 helper 여러 개로 나누는 것도 줄였다. public 메서드에는 전체 업무 순서를 남기고, 키 검증과 트랜잭션 보상처럼 독립된 규칙만 분리했다. 주석은 임시 파일을 영구 경로로 바꾸는 이유와 rollback에서 원본을 보존하는 이유처럼 코드만으로 알기 어려운 부분에만 남겼다.

## 판단이 틀렸던 것

커밋 전 변경을 기준 커밋과의 `git diff`만 보고 새 파일이 누락됐다고 판단할 수 있었다. untracked 파일은 diff에 나오지 않으므로, 커밋 전 리뷰에서는 `git status`와 실제 새 파일까지 함께 확인해야 한다. PR에 포함됐는지는 다시 커밋 기준으로 확인해야 한다.

클래스 수가 늘었다는 사실만으로 과설계라고 볼 수도 없었다. S3 SDK 호출, 키 검증, 업로드 정책, 상품 저장은 서로 다른 규칙이 있었다. 대신 책임 없이 호출만 전달하는 얇은 추상화는 만들지 않았다.

## 검증

- BE product-service 테스트 성공
- FE 빌드 성공
- 변경한 FE 파일의 lint 오류 없음
- 전체 FE lint에는 이번 변경과 무관한 기존 오류가 남아 있음
- `git diff --check` 성공

`cleanTest`는 테스트 실행이 아니라 정리만 수행하는 task 구성이어서 실제 BE 검증 근거는 `:product-service:test` 결과로 기록했다.

## 남긴 범위

파일명이 반드시 UUID여야 한다는 규칙은 실제 계약으로 확정되지 않아 강제하지 않았다. DB commit 후 임시 객체 삭제 실패를 주기적으로 정리하는 작업도 문제가 관측되거나 운영 정책이 정해질 때 추가하기로 했다.
