## 발견한 문제

### 1. 정렬식에 산술을 얹으면 인덱스가 조용히 빠진다 (#380)

추천은 "임베딩이 가까운 순"으로 뽑되 같은 유형에 가산점을 준다. 처음엔 그걸 SQL 한 줄로 끝내려 했다.

```sql
ORDER BY (embedding <=> :vector) - CASE WHEN product_type = :type THEN 0.05 ELSE 0 END
```

**이러면 HNSW 인덱스를 못 탄다.** 벡터 인덱스는 거리 연산자가 정렬식에 **그대로** 있을 때만 쓰인다. 산술이 붙는 순간 표현식이 되어 전체 행을 훑는다.

<details>
<summary><b>🔍 HNSW 인덱스가 뭔가요?</b></summary>

수천·수만 개 벡터 중 "가장 가까운 몇 개"를 찾으려면 원래는 전부와 거리를 재야 한다. 상품이 만 개면 만 번이다.

HNSW는 벡터들을 미리 **이웃 관계 그래프**로 엮어둔다. 검색할 때 아무 지점에서 출발해 "더 가까운 이웃"으로 계속 옮겨가면, 전체를 안 보고도 근처에 도착한다. 지도에서 목적지를 찾을 때 모든 건물을 확인하지 않고 큰길 따라 좁혀 들어가는 것과 비슷하다.

대신 **"가까운 순으로 정렬"이라는 형태를 정확히 지켜야** 그래프를 쓸 수 있다. 정렬 기준이 조금이라도 달라지면 미리 만든 이웃 관계가 무의미해져서 처음부터 다 재게 된다.

</details>

무서운 건 **지금 규모(65건)에선 표가 안 난다**는 점이다. 풀스캔도 즉시 끝난다. 상품이 늘어야 느려지는데, 그때는 원인을 찾기 어렵다.

### 2. 설정으로 빼도 무배포 변경이 안 된다 (#380)

가산점 값(0.05)을 처음엔 설정 파일로 빼려 했다. 이 저장소에 이미 같은 성격의 선례(`SearchRankingProperties`)가 있었다.

그런데 `config/CLAUDE.md`에 이렇게 적혀 있었다.

> **"커밋 ≠ 반영"**: `configs/`는 config server 이미지에 구워진다. develop 머지 → CD가 config 모듈 재빌드·재배포 → 값을 쓰는 서비스 재시작까지 거쳐야 실제로 반영된다.

**설정으로 빼는 주된 이유가 "배포 없이 값만 바꾸기"인데 그게 성립하지 않는다.** 오히려 단계가 는다.

| | 상수 | 설정 |
|---|---|---|
| 값 변경 | 코드 1줄 | yml 1줄 |
| 그다음 | 머지 → 서비스 재배포 | 머지 → **config 재배포** → **서비스 재시작** |

### 3. 로그 레벨을 두 번 틀렸다 (#378 2/2)

지난 배포 후 "해시 가드가 실제로 도는지" 로그로 확인하려 했는데 아무것도 안 나왔다. 원인은 로그 설정에 `com.prompthub.search` 패키지가 빠져 있던 것이었다.

그래서 설정에 패키지를 추가했다. **그런데 정작 보려던 로그가 `log.debug`였고, 나는 레벨을 `INFO`로 넣었다.** 여전히 안 나온다.

"DEBUG라서 안 보인다"고 스스로 진단해놓고, 고칠 때 그 사실을 반영하지 않았다. 같은 사실을 두 번 만나고도 두 번째에 놓쳤다.

### 4. 구현 도중 설계 전제가 깨졌다 (#380)

추천 로직을 새 패키지 `com.prompthub.recommendation`에 두기로 하고, 조회용 Spring Data 인터페이스를 그 안에 만들었다. 기존 `search` 패키지와 같은 모양이라 문제없을 줄 알았다.

**테스트가 컨텍스트 로딩부터 실패했다.**

<details>
<summary><b>🔍 무슨 일이 있었나요?</b></summary>

Spring이 "이 프로젝트의 DB 접근 인터페이스"를 찾는 규칙과, "이 프로젝트의 부품(빈)"을 찾는 규칙이 **서로 다르다.**

- 부품 스캔: 앱 설정에 적힌 패키지 목록을 본다 (`scanBasePackages`)
- DB 인터페이스 스캔: **앱 클래스가 놓인 패키지**를 기준으로 본다

이 프로젝트의 앱 클래스는 `com.prompthub.product`에 있다. 그래서 `com.prompthub.recommendation`에 둔 DB 인터페이스는 목록에 아무리 추가해도 안 잡힌다.

`search` 패키지에서 이 문제가 안 터진 이유는 **거기 DB 인터페이스가 하나도 없어서**다. 검색 엔진 클라이언트를 직접 쓰고, DB가 필요하면 `product`의 것을 빌려 쓴다. "같은 모양"으로 보였지만 DB 접근 방식이 달랐다.

</details>

## 조치

### 1. 후보를 넉넉히 뽑고 앱에서 다시 세운다 (#380)

**무엇을** — SQL은 순수 거리순으로만 정렬해 인덱스를 살리고, 요청 개수의 5배를 후보로 받아 가산점은 앱에서 얹는다.

**왜 그 방법인가** — 대안은 세 가지였다. (a) SQL에 산술을 얹는다 → 인덱스를 잃는다. (b) 같은 유형만 조회한다 → 다른 유형이 영영 안 나온다. (c) 후보를 요청 개수만큼만 받는다 → 같은 유형이 그 자리를 다 채우면 가산점이 순서를 뒤집을 여지가 없다.

후보 수를 고정 상수가 아니라 **요청의 배수**로 둔 것은 매직 넘버를 피하려는 것이다. FE가 4개를 요청하면 20개를 받는다.

**근거** — 인덱스를 실제로 타는지를 `EXPLAIN` 결과로 테스트에 고정했다.

```java
assertThat(plan).contains("idx_product_embedding_on_sale");
```

나중에 누가 정렬식을 손대면 이 테스트가 깨진다. 이게 없으면 성능 저하가 조용히 들어온다.

### 2. 유형을 하드 필터가 아니라 가산점으로 (#380)

**무엇을** — `최종점수 = (1 - 거리) + (같은 유형이면 0.05)`

**왜 그 방법인가** — 유형으로 거르거나 1차 정렬 키로 두면, **FE가 4개만 요청하므로 같은 유형 후보가 4개만 있어도 다른 유형은 절대 화면에 못 오른다.** 내용이 정말 비슷하면 유형이 달라도 보여야 한다는 게 이 기능의 취지다.

**근거** — 코사인 유사도가 0~1로 유계라 0.05는 **"다른 유형이 앞서려면 유사도가 0.05만큼 더 높아야 한다"** 로 직접 읽힌다. 유사도 0.90인 PPT가 0.84인 PROMPT를 앞선다. 이 계약을 테스트로 못박았다 — 하드 필터로 퇴화하면 깨진다.

인기도(`salesCount`) 항은 넣지 않았다. **스케일이 무계라 가중치의 근거도 해석도 없다.** 코사인 공간에서 해석되는 항 하나만 둔다.

### 3. 값은 상수로, 근거는 주석에 (#380)

**무엇을** — 가산점을 `private static final double TYPE_BONUS = 0.05`로 두고, 왜 설정이 아닌지를 주석에 남겼다.

**왜 그 방법인가** — 위 2번 발견 때문이다. 설정의 이점이 이 프로젝트에선 성립하지 않는다.

**근거** — 방향의 비대칭성이 결정적이었다. **상수 → 설정은 안전하게 추가되지만, 설정 → 상수는 어느 환경 yml에 값이 들어갔는지 몰라 제거가 조심스럽다.** 되돌릴 수 있는 쪽으로 시작한다. 조정 신호(추천 클릭률)가 실제로 생기면 그때 외부화한다.

이슈 본문이 설정 프로퍼티로 적혀 있었으므로, **구현 전에 이슈를 먼저 고쳤다.** 코드와 이슈가 어긋난 채로 두면 나중에 읽는 사람이 어느 쪽이 맞는지 모른다.

### 4. 등수로 섞는다 — 점수를 더하지 않고 (#378 2/2)

**무엇을** — 글자 기반과 의미 기반 결과를 RRF로 병합한다.

<details>
<summary><b>🔍 RRF가 뭔가요?</b></summary>

두 검색 결과를 합칠 때 **점수를 버리고 등수만 쓰는** 방법이다. 문서 하나의 최종 점수는 각 목록에서의 등수로부터 `1 / (60 + 등수)`를 더한 값이다.

한쪽에서 1등이어도 다른 쪽에 아예 없으면, 양쪽에서 고르게 상위인 문서에 밀린다. "두 방식이 모두 관련 있다고 본 문서"를 위로 올리는 것이 목적이다.

</details>

**왜 그 방법인가** — 점수를 그냥 더하면 안 된다. **글자 기반 점수(BM25)는 상한이 없고 코사인 유사도는 0~1**이라 스케일이 안 맞는다. 보정 상수를 두면 데이터가 바뀔 때마다 다시 잡아야 해서 유지되지 않는다.

**근거** — 통합 테스트에서 **같은 질의가 글자 기반만으로는 0건임을 먼저 확인**한 뒤 하이브리드 결과를 본다. 이 선행 확인이 없으면 결과가 나오는 게 의미 검색 덕인지 원래 나오던 건지 구분되지 않는다.

배포 후 실측으로도 확인했다.

| 검색어 | 이전 | 이후 |
|---|---|---|
| `발표자료 예쁘게 만들어주는 거` | **0건** | 20건 |
| `회의록 정리해주는 거` | **0건** | 20건 |

### 5. 복제 해시는 임베딩 해시와 따로 (#632)

**무엇을** — 본문 복제 탐지용 해시를 새 컬럼으로 만들었다. 기존 임베딩 해시를 재사용하지 않았다.

**왜 그 방법인가** — 둘 다 SHA-256이지만 **묻는 질문이 반대**다.

| | 임베딩 해시 | 복제 해시 |
|---|---|---|
| 질문 | 이 상품 글이 **바뀌었나** | 같은 글이 **이미 있나** |
| 비교 대상 | 같은 상품의 과거 | 다른 상품들 |

결정적 충돌은 **제목만 바꾸고 본문은 그대로인 경우**다. 임베딩 해시는 바뀌어야 하고(벡터를 다시 만들어야 하므로) 복제 해시는 안 바뀌어야 한다(본문이 같으니 여전히 복제다). 한 값이 둘을 동시에 만족할 수 없다.

**근거** — 해시가 유사도를 전혀 담지 못한다는 것도 실측했다.

| 입력 | SHA-256 앞부분 |
|---|---|
| `프롬프트 입니다` | `c2773345...` |
| `프롬프트  입니다` (공백 1개 추가) | `def2c236...` |
| `완전히 다른 글입니다` | `2fafc9a3...` |

**공백 하나 차이인데 64자 중 5자만 일치한다. 무작위 두 해시의 기대값이 4자다.** 그래서 비교 전에 정규화로 사소한 차이를 미리 지워야 한다.

### 6. 백필을 SQL 한 문장으로 (#632)

**무엇을** — 기존 상품의 해시를 마이그레이션 안에서 채웠다. 별도 배치를 만들지 않았다.

**근거** — Postgres `sha256()`이 Java와 **완전히 같은 hex**를 내는 것을 실측하고 썼다.

```
postgres  c2773345b221201bbb689f38db0762fe6f58f294a2378fe299873a5658496da9
java      c2773345b221201bbb689f38db0762fe6f58f294a2378fe299873a5658496da9
```

두 계산이 어긋나면 기존 상품과 신규 상품의 해시 규칙이 달라져 탐지가 반쪽이 된다. 그래서 통합 테스트에서 **Postgres 값·Java 값·저장된 값 셋이 같은지** 고정했다.

## 직접 만들었다가 고친 것

**포트 인터페이스를 만들었다가 지웠다 (#380).** 조회를 인터페이스로 추상화하고 구현체를 따로 뒀는데, **구현이 하나뿐**이었다. `search` 패키지에 포트가 있는 건 테스트에서 검색 엔진을 가짜로 바꿔 끼우려는 것인데, 이번엔 진짜 Postgres를 컨테이너로 띄워 테스트하므로 가짜가 필요 없었다. 클래스 4개로 시작한 설계가 **1개**로 줄었다.

**표시용 필드를 조회 쿼리에 넣으려다 뺐다 (#380).** 추천 후보에 제목·가격·평점을 함께 담으려 했는데, 그러면 평점 집계와 판매수 합산을 kNN 쿼리에 다시 써야 했다. 목록 조회에 이미 있는 로직이라 **같은 계산이 두 군데**가 된다. 후보는 id만 고르고 표시 데이터는 기존 조회로 채웠다.

## 판단이 틀렸던 것

**"덜 만드는 것"과 "관례를 따르는 것"을 반대로 놨다 (#380).** 새 패키지를 만들면서 하위 폴더(`application`/`infra`)를 파지 않으려 했다. 클래스가 2~3개인데 계층 서랍이 비어 보인다는 이유였다.

지적을 받고 다시 보니 **이 저장소의 최상위 기능 패키지는 전부 그 구조**였다. 새 패키지만 평평하면 읽는 사람이 "얘는 왜 다르지"를 매번 묻는다. **서랍 하나 아끼는 것보다 관례를 따르는 편이 싸다.** 간소화 원칙에도 "이미 코드베이스에 있는 패턴이면 그걸 쓴다"가 앞 순위인데, 내가 뒤 순위를 먼저 적용했다.

**작업 기록이 실제 코드와 달랐다.** 상세 페이지 추천 섹션 제목("비슷한 프롬프트")을 바꿨다고 내 작업 목록에 완료로 찍혀 있었는데, **실제 파일은 그대로였다.** PR 본문에 "FE 변경 필요"를 적으면서 확인해보고 알았다. 기록이 아니라 코드를 봐야 한다.

## 남긴 것 · 하지 않은 것

**JPQL 중복을 안 없앴다.** 목록 조회와 추천 조회가 평점 집계·판매수 합산 블록(15줄)을 각각 갖고 있다. 다만 **개수가 2개 → 2개로 늘지 않았고**(기존 쿼리를 조건만 바꿔 재사용), 없앨 수단도 없다 — 쿼리 조각을 재사용하는 기능이 JPQL엔 없고 Querydsl은 이 프로젝트에 없다.

**추천 순위 품질을 판정하지 않았다.** 상품 65건이 제목 2패턴·태그 11개·설명이 거의 같아 임베딩이 서로 몰려 있다. **정직한 상품끼리도 유사도가 높다.** 이 상태로는 "추천이 좋아졌나"를 잴 수 없다. 완료 조건은 "벡터 기반으로 고른다"까지다.

**FE는 별도 저장소라 못 담았다.** 섹션 제목과 라우팅 테스트 픽스처 두 곳이 남아 있다. API 응답 구조가 안 바뀌어 화면은 정상 동작하므로 배포 순서는 자유롭다.
