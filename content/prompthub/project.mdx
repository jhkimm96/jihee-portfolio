## 프로젝트 개요

PromptHub는 개인과 기업이 만든 AI 프롬프트를 등록하고 거래하는 마켓플레이스입니다. 해외 중심의 프롬프트 마켓과 달리 한국어와 국내 업무 환경에 맞는 프롬프트를 제공하고, 등록 상품의 검수 결과를 공개해 신뢰할 수 있는 거래 환경을 만드는 것을 목표로 했습니다.

## 내가 맡은 범위

5인 백엔드 팀에서 **product-service와 ai-service 담당자**로 참여했습니다. 상품 도메인의 데이터와 API부터 상품이 검색 문서와 벡터로 변환되는 과정, 검색 결과의 결합·정렬, 사용자 행동 기반 개인화 추천까지 담당했습니다.

- 상품 도메인 모델과 등록·조회·수정 API
- PostgreSQL 상품 원본과 Elasticsearch 검색용 사본의 동기화
- OpenAI `text-embedding` 생성 및 pgvector 저장
- Elasticsearch 글자 검색과 벡터 의미 검색
- RRF 기반 하이브리드 검색
- 판매수·조회수·평점·신선도를 이용한 인기 랭킹
- Elasticsearch 장애 시 PostgreSQL 폴백
- 장바구니·구매 활동 기반 개인화 추천 ai-service
- 활동별 후보의 가중치 적용과 RRF 기반 최종 순위 결합

요구사항에서 AI 추천을 별도 모듈로 분리해야 했기 때문에 추천 로직을 product-service 내부에 넣지 않고 `ai-service`로 독립시켰습니다. 두 서비스 모두 직접 구현하되, product-service는 특정 상품과 가까운 후보 제공에 집중하고 ai-service는 사용자의 장바구니·구매 신호를 조합해 최종 추천을 만드는 책임으로 경계를 나눴습니다.

## 검색·추천 데이터 흐름

### 1. 상품 변경과 증분 색인

상품 변경분을 재조정 배치가 확인하고, 원문이 바뀐 경우에만 임베딩을 다시 생성합니다. 임베딩 원본은 PostgreSQL에 저장하고 Elasticsearch에는 검색에 필요한 상품 문서를 색인했습니다. 전체 상품을 매번 다시 만드는 대신 변경된 상품만 반영해 외부 API 호출과 색인 비용을 줄였습니다.

### 2. 통합 검색

형태가 같은 단어를 찾는 글자 검색과 표현이 달라도 의미가 가까운 상품을 찾는 벡터 검색을 함께 실행합니다. 두 결과는 점수 척도가 달라 원점수를 더하지 않고, 순위를 합치는 RRF로 결합했습니다. Elasticsearch가 응답하지 않으면 기본 상품 목록을 PostgreSQL에서 조회해 검색 장애가 전체 상품 조회 장애로 번지지 않게 했습니다.

### 3. 인기순 랭킹

판매수·조회수·평점·신선도를 하나의 인기 점수로 합산했습니다. 판매수와 조회수에는 `log1p`를 적용해 일부 누적 상품이 순위를 독점하지 않도록 했고, 검색 결과와 인기 상품 목록에 같은 기준을 재사용했습니다.

### 4. 독립 ai-service의 개인화 추천

product-service는 pgvector를 이용해 입력 상품과 가까운 후보를 반환합니다. ai-service는 장바구니와 구매 활동별로 product-service에 유사 상품을 요청한 뒤, 장바구니 1.0·구매 0.7의 가중치를 적용하고 RRF로 순위를 합쳐 개인화된 Top 4를 만듭니다. 추천 실패 시 빈 목록을 반환하도록 해 추천 장애가 상품 조회로 전파되지 않게 했습니다.

모듈을 나눈 목적은 단순한 파일 분리가 아니라 책임과 장애 경계를 분명히 하는 것이었습니다. product-service는 사용자가 누구인지 몰라도 유사 상품을 반환하고, ai-service는 상품 저장 구조를 몰라도 사용자 활동을 바탕으로 추천을 조합합니다.

## 검증과 기록

기능 구현 이후 검색 분석기 불일치, 단일 단어 벡터 검색의 무응답, 유사도 임계값 같은 문제를 별도 트러블슈팅과 리뷰로 검증했습니다. 설계 변경은 코드만 고치지 않고 선택지·채택 근거·재검토 조건을 ADR 형태로 남겼습니다.

## 현재 고도화 중인 부분

- 검색·클릭·장바구니·구매 행동 로그 수집
- 검색 성공률, 무결과율, 클릭률 등 오프라인 품질 지표 구축
- 검색·클릭 행동까지 개인화 신호를 확장하고 활동별 가중치 검증
- 임계값과 RRF 가중치를 고정값이 아닌 측정 결과로 조정
- 부하 테스트와 Elasticsearch·PostgreSQL 장애 시나리오 검증

발표 당시 구현 범위와 이후 고도화 범위를 구분해 기록하고, 고도화가 완료될 때마다 관련 결정·리뷰·품질 스냅샷을 갱신합니다.
