## 배경

검색을 Elasticsearch와 벡터로 옮기는 작업은 끝나 있었다. 남은 것은 **"이 사람에게 맞는 상품"**을
보여주는 일이었다.

여기서 두 가지를 정해야 했다.

1. 추천을 **어느 서비스**에 둘 것인가
2. 사용자의 활동이 여러 개일 때 그것을 **어떻게 하나의 기준으로** 만들 것인가

두 질문 모두 처음 답이 틀렸고, 실측으로 뒤집혔다. 그 과정을 포함해 정리한다.

## 전체 흐름 — 네 단계

![검색·추천 전체 흐름 — 색인 파이프라인, 통합 검색, 인기순 랭킹, 맞춤형 추천 네 단계](/prompthub/images/search-recommendation/00-overview.png)

```mermaid
flowchart LR
    subgraph S1["① 색인 파이프라인"]
        A1["상품 변경"] --> A2["재조정 배치<br/>20초"] --> A3["임베딩<br/>생성·비교"] --> A4["Postgres 저장"] --> A5["ES 색인"]
    end
    subgraph S2["② 통합 검색"]
        B1["유형 단어 분리"] --> B2["글자 검색"] & B3["의미 검색"]
        B2 --> B4["RRF 병합"]
        B3 --> B4
    end
    subgraph S3["③ 인기순 랭킹"]
        C1["판매수 · 조회수<br/>평점 · 신선도"] --> C2["인기 점수"] --> C3["정렬"]
    end
    subgraph S4["④ 맞춤형 추천"]
        D1["장바구니 · 구매"] --> D2["ai-service"] --> D3["유사 상품 조회"] --> D4["가중 RRF"] --> D5["Top 4"]
    end
    S1 --> S2 --> S3 --> S4
```

**한 문장으로**: Postgres가 임베딩 원본을 보관하고, Elasticsearch가 검색을 담당하며,
ai-service가 사용자 활동을 조합해 개인화 추천을 만든다.

<details>
<summary><b>🔍 "임베딩"이 뭔가요?</b></summary>

상품 하나를 **숫자 1536개로 바꾼 것**이다. 지도 좌표를 생각하면 된다. 서울 (37.5, 127.0),
인천 (37.4, 126.7), 부산 (35.1, 129.0) — 좌표만 봐도 서울·인천이 가깝고 부산이 멀다는 걸
뺄셈으로 알 수 있다.

임베딩은 이걸 **"의미"에 대해** 한다. 좌표가 2개가 아니라 1536개일 뿐이다.

- "면접 답변 프롬프트" → `[0.12, -0.87, 0.33, …]`
- "자기소개서 첨삭 프롬프트" → `[0.14, -0.85, 0.31, …]` ← 숫자가 비슷 = 의미가 비슷

**단어가 하나도 안 겹쳐도** 의미가 가까우면 좌표가 가깝게 나온다. 글자 검색과의 결정적 차이다.
이 좌표는 OpenAI의 `text-embedding-3-small` 모델이 만든다.

</details>

## ① 색인 파이프라인 — 상품이 바뀌면 좌표도 따라간다

![색인 파이프라인 — 상품 변경, 재조정 스케줄러, 임베딩 갱신, Postgres 저장, Elasticsearch 색인](/prompthub/images/search-recommendation/01-indexing.png)

```
상품 등록·수정 → Postgres(원본)
  → 20초마다 도는 재조정 배치
     · 원문(제목+태그+소개글+본문) 해시가 그대로면 건너뜀
     · 바뀌었으면 OpenAI 호출 → 1536차원 좌표 → Postgres 갱신
  → Elasticsearch 색인
```

**결정 1 — 좌표의 원본은 Postgres, Elasticsearch는 사본이다.**

Elasticsearch가 날아가도 상품 데이터만 있으면 색인은 다시 만들 수 있다. 그런데 **좌표는
외부 API를 호출해 만든 값**이라 다시 만들려면 전 상품을 다시 호출해야 한다. "사본은 언제든
재생성 가능하다"는 전제가 좌표에서만 깨진다. 그래서 좌표만 원본을 DB에 둔다.

**결정 2 — 원문 해시로 한 번 더 거른다.**

배치는 `updated_at`으로 대상을 고르는데, **조회수가 1 오르기만 해도 그 값이 바뀐다.**
해시 비교가 없으면 상품을 열어보기만 해도 OpenAI를 호출하게 된다.

<details>
<summary><b>🔍 "재조정 배치"가 뭔가요?</b></summary>

DB와 검색 색인이 어긋났는지 주기적으로 확인하고 맞추는 작업이다. 도서관에 비유하면
**20초마다 서가를 둘러보는 사서**다. 새 책이 들어왔거나 내용이 바뀌었으면 색인 카드를 고쳐 쓴다.

이벤트로 즉시 반영하지 않고 배치를 쓴 이유는, 관리자 승인처럼 **이벤트가 발행되지 않는
경로**가 있기 때문이다. 그런 변화는 이벤트를 기다려도 영원히 안 온다. 대신 최대 20초 지연을
받아들였다.

</details>

## ② 통합 검색 — 글자와 의미를 동시에

![통합 검색 — 유형 단어 분리, 하이브리드 조건 확인, 질의 임베딩, 글자 검색과 의미 검색, RRF 병합](/prompthub/images/search-recommendation/02-search.png)

```
검색어 → 유형 단어 분리 → ┬ 글자 검색 (이름·태그·설명)
                          └ 의미 검색 (좌표 거리, 유사도 0.35 이상)
                          → RRF로 순위 병합
```

**결정 3 — 두 결과를 점수가 아니라 "등수"로 합친다.**

글자 검색 점수(BM25)는 상한이 없고 의미 검색 유사도는 0~1이다. 그냥 더하면 스케일이 안 맞아
데이터가 바뀔 때마다 보정 상수를 다시 잡아야 한다. **RRF는 점수를 버리고 등수만 쓰기 때문에**
그 문제가 없다.

<details>
<summary><b>🔍 "RRF(순위 합산)"가 뭔가요?</b></summary>

여러 목록의 **등수**만 가지고 하나로 합치는 방법이다. 점수는 버린다.

각 목록에서의 등수로 `1 / (60 + 등수)`를 계산해 더한다. 1등이면 `1/61`, 2등이면 `1/62`…
등수가 낮을수록 조금씩 작아진다.

핵심은 **여러 목록에 공통으로 있는 항목이 위로 올라간다**는 것이다. 한쪽에서만 1등인 항목보다,
양쪽에서 고르게 상위인 항목이 이긴다. "두 방식이 모두 관련 있다고 본 것"을 우선하는 셈이다.

`60`이라는 값은 RRF 논문(Cormack et al., 2009)이 제시한 값이다. 작으면 1·2등 차이가
과도하게 벌어지고, 크면 순위 정보가 뭉개진다.

</details>

**결정 4 — 유형 단어는 글자로 찾지 않고 필터로 해석한다.**

`"주식 프롬프트"`라고 치는 사람이 원하는 건 "프롬프트라는 *글자가 들어간* 상품"이 아니라
**"프롬프트 유형 중 주식 관련"**이다. 유형 단어를 글자로 매칭하면 그 단어를 이름에 단 모든
상품이 꼬리로 딸려온다. 이 서비스는 상품 대부분이 프롬프트라 **"프롬프트"가 카탈로그 전체를
여는 만능 열쇠**가 됐다.

→ 자세한 경위: [보이지 않는 본문이 검색 결과를 결정하고 있었다](/troubleshooting/prompthub/search/search-false-positive-content-field)

**결정 5 — 의미 검색에 하한을 반드시 건다.**

kNN은 관련도와 무관하게 **상위 k건을 채워서** 돌려준다. 하한이 없으면 색인 문서가 k보다 적을 때
어떤 질의를 넣어도 전체 상품이 후보로 들어와 **"검색 결과 0건"이 발생할 수 없게 된다.**

<details>
<summary><b>🔍 "kNN"이 뭔가요?</b></summary>

k-Nearest Neighbors, "가장 가까운 k개 찾기"다. 좌표 공간에서 기준점과 가장 가까운 k개를 고른다.

**주의할 성질이 하나 있다.** 가까운 게 하나도 없어도 k개를 채워서 돌려준다. 반에서 키가 제일 큰
4명을 뽑으라고 하면 반 전체가 작아도 4명은 뽑히는 것과 같다.

그래서 "몇 등인가"와 별개로 **"기준을 넘었는가"**를 따로 물어야 한다. 그게 유사도 하한이다.

</details>

## ③ 인기순 랭킹 — 네 지표를 합산

![인기순 랭킹 — function_score로 판매수·조회수·평점·신선도를 합산해 정렬](/prompthub/images/search-recommendation/03-ranking.png)

```
판매수(log1p) × 0.3
조회수(log1p) × 0.1
평점         × 0.1
신선도(가우시안 감쇠 30일) × 0.2
────────────────────────
합산 → 검색 점수에 더함
```

**결정 6 — 판매·조회에 로그를 씌운다.**

두 값은 상한이 없다. 그대로 더하면 **판매 3000건짜리 하나가 다른 모든 항을 압도한다.**
로그를 씌워 증가폭을 눌러 담는다. 평점은 0~5로 이미 유계라 변환하지 않는다.

<details>
<summary><b>🔍 "log1p"가 뭔가요?</b></summary>

`log(1 + x)`다. 큰 숫자의 차이를 눌러주는 변환이다.

```
판매 0건    → 0.0
판매 10건   → 2.4
판매 100건  → 4.6
판매 3000건 → 8.0
```

판매가 300배 차이나도 점수는 3배 정도만 차이난다. `1+`를 붙이는 이유는 판매 0건일 때
`log(0)`이 음의 무한대가 되는 걸 막기 위해서다.

</details>

**결정 7 — 신선도는 계단이 아니라 완만한 곡선으로.**

"등록 30일 이내면 가산점" 같은 계단식 분기를 쓰면 **경계에서 순위가 튄다.** 어제까지 상위였던
상품이 하루 지나 갑자기 밀린다. 가우시안 감쇠는 연속 함수라 그런 점프가 없다.

**이 가중치 네 개는 아직 실측으로 검증되지 않았다.** 조정 근거가 될 클릭률 지표를 수집하지
않고 있어서, 지금은 초기 추측값 그대로다. 이 사실을 문서에 남겨 "검증된 값"으로 오해하지 않게 했다.

## ④ 맞춤형 추천 — 여기가 이번에 새로 만든 부분

![맞춤형 추천 — 사용자 활동 수집부터 gRPC 유사 상품 조회, 가중 RRF 합산, 최종 추천 반환까지](/prompthub/images/search-recommendation/04-recommendation.png)

```
FE (장바구니 + 구매 목록을 실어 보냄)
  → ai-service
      ├ 활동에서 기준 상품 추림 (신호당 최대 3개)
      ├ gRPC로 product-service에 "이것들과 비슷한 상품" 요청
      ├ 가중 RRF로 합산 (장바구니 1.0 / 구매 0.7)
      ├ 이미 담았거나 산 상품 제외
      └ 상위 4개
```

### 결정 8 — 추천을 product-service가 아니라 ai-service에 뒀다

처음에는 product-service 안에 만들려 했다. 벡터도 상품 데이터도 거기 있으니 자연스러워 보였다.

**바꾼 이유는 요구사항이었다.** "AI 추천 기능을 독립된 서비스 형태로 구현한다"가 명시돼 있었다.
마침 `ai-service`가 이미 독립 서비스로 존재했고(상품 검수·정산 챗봇 담당) gRPC 클라이언트도
쓰고 있어서, 새 서비스를 만들지 않고 거기에 도메인을 하나 추가했다.

**기존 "비슷한 상품"은 옮기지 않았다.** 둘은 다른 기능이다.

| | 비슷한 상품 (기존) | 맞춤 추천 (신규) |
|---|---|---|
| 기준점 | **상품** — 지금 보는 것 | **사람** — 그 사용자의 활동 |
| 결과 | 누가 봐도 같음 | 사람마다 다름 |
| 위치 | product-service | ai-service |
| 계산 | 벡터 거리 | 같음 (gRPC로 위임) |

### 결정 9 — gRPC가 기준별 순위를 "합치지 않고" 돌려준다

이게 이번 설계에서 가장 중요한 선택이다.

```
ai-service  ──"이 상품들과 비슷한 것"──▶  product-service
            ◀──기준마다 순위를 따로──────
            (합쳐진 결과가 아니라 목록 여러 개)
```

product-service가 미리 합쳐서 주면 **"어떤 활동에 얼마나 무게를 둘지, 무엇을 빼고 몇 개를
보여줄지"라는 판단이 product-service로 넘어간다.** 그러면 ai-service는 결과를 통과시키는
껍데기가 되고, 추천을 독립 서비스로 둔 의미가 사라진다.

**product는 "이 상품과 가까운 것"만 답하고, 누구에게 무엇을 추천할지는 모른다.**

### 결정 10 — 여러 활동을 평균이 아니라 가중 순위 합산으로 합쳤다

처음 계획은 **구매한 상품들의 좌표를 평균 내** 취향 벡터를 만드는 것이었다. 흔한 방식이고
직관적이다.

**실측으로 기각했다.** 이 카탈로그는 좌표 공간이 좁게 뭉쳐 있다.

```
상품별 중심성(나머지 전체와의 평균 거리) 상위 15건
0.568 ~ 0.610   ← 폭이 0.042뿐
```

어느 상품도 특별히 중심에 있지 않은데, 이 말은 **주제가 다른 둘을 평균 내면 그 중간 지점이
"모든 것과 어중간하게 가까운 구역"**이 된다는 뜻이다. 그 자리에서 뽑으면 아무거나 나온다.
**평균은 취향을 잡는 게 아니라 지운다.**

```
장바구니: 면접 프롬프트  ●
                           ○ ← 평균 지점. 여기서 뽑으면 아무 상품이나
구매: 엑셀 가계부        ●
```

RRF는 **각 기준의 실제 위치에서 뽑은 등수만** 더하므로 중간 지점을 만들지 않는다. 그리고
여러 목록에서 공통으로 상위인 상품을 올려주므로, 한 목록에서만 우연히 상위인 상품은 밀린다.

### 결정 11 — 가중치는 장바구니 1.0 / 구매 0.7

```
점수 = Σ ( 가중치 × 1 / (60 + 등수) )
```

**장바구니가 더 무겁다.** 장바구니는 *지금* 사려는 것이고 구매는 이미 끝난 과거다. 3주 전
구매보다 방금 담은 것이 현재 관심사에 가깝다.

일반적으로는 "돈을 쓴 구매가 더 강한 신호"라고 보지만, **추천이 뜨는 자리가 탐색 페이지**라는
맥락에서는 지금 의도가 더 중요하다고 판단했다.

### 결정 12 — 활동 내역을 서버에 저장하지 않는다

장바구니와 주문은 order-service가 소유하고, ai-service에는 DB가 없다(Redis만).

세 가지 선택지가 있었다.

| | 방법 | 판단 |
|---|---|---|
| A | ai-service가 order-service를 gRPC로 조회 | 다른 팀원 서비스에 RPC 추가 필요 |
| B | product-service에 `user_purchase` 테이블 신설 | 카프카 `ORDER_PAID`의 `buyerId`를 적재. 테이블·컨슈머·중복 처리 추가 |
| C | **화면이 요청에 실어 보냄** | **채택** — order·product 데이터 모델 무변경 |

**B는 실제로 처음 계획이었다.** 이슈 최초 본문에는 이런 테이블이 있었다.

```sql
create table user_purchase (
    user_id uuid, family_root_id uuid, purchased_at timestamp,
    primary key (user_id, family_root_id)
);
```

추천을 ai-service로 옮기면서 필요가 없어졌다. **ai-service에는 DB가 없어서**(Redis만) 저장할
곳이 없고, 화면이 이미 주문 목록을 갖고 있으니 **서버에 사본을 하나 더 만들 이유가 없었다.**

C를 택하면서 **order-service를 한 줄도 건드리지 않았다.**

**대신 잃은 것도 있다.** 서버에는 개인 단위 행동 기록이 남지 않는다. "누가 무엇을 샀는지"를
아는 서비스는 order-service뿐이고, 나머지는 요청이 올 때만 알게 된다. 나중에 서버가 주도하는
기능(이메일 추천 발송, 취향 분석)이 필요해지면 그때 만들어야 한다.

### 화면이 보내는 두 신호는 비용이 다르다

| 신호 | 출처 | 추가 API 호출 |
|---|---|---|
| 장바구니 | 헤더가 채워 둔 전역 상태 | **0회** |
| 구매 내역 | 추천 섹션이 직접 조회 | **1회** |

장바구니는 헤더가 모든 페이지에서 미리 불러오므로 **읽기만 하면 된다.** 반면 주문 내역은
마이페이지·리더 등에서만 쓰던 것이라, 탐색 페이지에는 **없던 호출이 하나 는다**(로그인 사용자 한정).

없앨 수도 있었지만 각각 대가가 있었다.

- 장바구니만 쓰기 → 호출 0회. 대신 장바구니가 빈 사용자는 추천을 못 받는다
- 헤더에서 주문도 미리 받기 → 추천을 안 보는 페이지에서도 부르게 된다. 더 낭비다
- **추천이 필요한 화면에서만 1회 (채택)**

주문 조회 API에 페이징이 없어 전체를 받아온다는 점이 걸리는데, **추천 섹션이 없으면 아예
호출하지 않으므로** 다른 페이지에는 영향이 없다. 주문 건수가 많아져 이 호출이 부담되면
그때가 위 B안(서버 저장)을 다시 볼 시점이다.

### 결정 13 — 실패하면 조용히 빈 목록

요구사항에 **"AI 추천이 중단되더라도 상품 구매는 정상 동작해야 한다"**가 있었다.

```
활동 없음        → 200 + 빈 배열 → 화면에서 섹션 숨김
gRPC 실패        → 200 + 빈 배열 (warn 로그) → 섹션 숨김
추천 결과 없음   → 200 + 빈 배열 → 섹션 숨김
```

에러를 올리지 않는다. **추천이 안 되는 것과 상품을 못 사는 것은 다른 문제**이기 때문이다.
다만 조용히 사라지면 고장을 아무도 모르므로 `warn` 로그는 남긴다.

이 설계는 실제로 검증됐다. 배포 순서가 어긋나 ai-service가 구버전 product-service를 호출했을 때
`UNIMPLEMENTED` 오류가 났는데, 화면은 섹션만 숨기고 상품 목록·구매 흐름은 그대로 동작했다.

<details>
<summary><b>🔍 "gRPC"가 뭔가요?</b></summary>

서버끼리 통신하는 방식이다. 브라우저가 서버를 부를 때 쓰는 REST(HTTP+JSON)와 목적이 다르다.

- **REST** — 사람이 읽는 JSON. 브라우저·외부 클라이언트용
- **gRPC** — 미리 정한 계약(`.proto` 파일)에 따라 압축된 이진 형식으로 주고받음. 서버 간 통신용

이 프로젝트는 "외부 클라이언트는 REST, 서비스끼리 동기 호출은 gRPC, 비동기는 Kafka"로
통일해 두었다. 그래서 ai-service → product-service도 gRPC를 썼다.

</details>

## 남은 한계 — 숨기지 않고 적어둔다

**추천 목록에 유사도 하한이 없다.**

검색(Elasticsearch)에는 하한 0.35가 있지만, 추천(Postgres 벡터)에는 없다. 두 경로가 저장소도
코드도 공유하지 않아 **같은 종류의 결함이 한쪽에만 고쳐진 상태**다.

거리순으로 줄을 세우고 앞에서 N개를 자를 뿐이라, 아무리 관련이 없어도 "그나마 덜 먼" 상품이
자리를 채운다. 실측하면 이렇다.

```
펭귄 생성 프롬프트 기준
  0.180  동물 이미지 생성 가이드        관련
  0.483  About Me.md 자동 생성          무관
  0.488  Claude Design + Figma          무관
  0.489  블로그 SEO 글쓰기              무관   ← 화면에 보이는 4개 끝
  0.505  웹툰 캐릭터 디자인             관련 — 잘림
  0.531  동화책 일러스트                관련 — 잘림
```

**상위 4건 중 1건만 관련 있고, 정작 관련 있는 상품이 5·8위로 밀려 잘린다.** 맞춤 추천도 같은
엔진을 쓰므로 이 한계를 그대로 물려받는다.

하한 값은 실측했지만 확정하지 못했다. 관련/무관이 거리로 깔끔하게 갈리지 않는 구간이 있었다.

→ 측정 전문: [추천에는 하한이 없었다 — 제안을 두 번 실측으로 뒤집은 기록](/reviews/prompthub/recommendation-similarity-threshold-2026-07-31)

**이미 산 상품을 거르는 기준이 상품 ID다.**

장바구니에 담았거나 구매한 상품은 결과에서 제외한다. 기준으로 삼는 활동은 신호당 3개로
제한하지만, **제외는 받은 목록 전부**에 적용한다 — 20개를 샀으면 3개만 기준이 되고 20개 전부가
빠진다.

다만 비교 단위가 **상품 ID**라서 빈틈이 하나 있다.

```
v1을 구매      → 구매 목록에 v1의 ID
판매자가 v2 등록 → 추천에는 v2의 ID가 나옴
                  v1 ≠ v2 이므로 제외에 안 걸림
```

같은 상품인데 버전이 올라가면 ID가 달라져, **이미 산 상품이 새 버전으로 다시 추천될 수 있다.**

제대로 막으려면 제외를 **상품 계열(family) 단위**로 해야 한다. 화면이 보내는 것은 구매 당시의
상품 ID뿐이라, 계열로 바꾸려면 서버가 변환하거나 계열 ID를 저장해두어야 한다 — 위에서
보류한 `user_purchase` 테이블이 계열 단위 키를 쓰려 했던 이유가 이것이다.

**지금 당장 재현되지는 않는다.** 버전을 올린 상품이 있어야 하고 현재 카탈로그에는 드물다.
그래도 구조적으로 남아 있는 빈틈이라 적어둔다.

## 자주 나오는 질문

<details>
<summary><b>Q. 상세 페이지의 "비슷한 상품"이 개인 맞춤 추천인가요?</b></summary>

**아니다.** 둘은 다른 기능이다.

- `/products/{id}/recommends` — 상세 페이지. **인증이 필요 없고** 사용자 ID를 받지 않는다.
  같은 상품을 열면 누가 봐도 결과가 같다
- `/ai/recommendations` — 탐색 페이지. 사용자 활동을 받아 **사람마다 다른** 결과를 낸다

한 문장으로: 상세 페이지 것은 *상품*이 기준이라 모두에게 같고, 맞춤 추천은 *사람의 활동*이
기준이라 사람마다 다르다.

</details>

<details>
<summary><b>Q. 그럼 추천 알고리즘을 새로 만든 건가요?</b></summary>

**아니다. 계산 엔진은 기존 것을 그대로 재사용한다.**

맞춤 추천도 내부적으로는 "이 상품과 비슷한 상품"을 찾는 같은 벡터 조회를 쓴다. 기존 코드를
한 글자도 고치지 않았다.

새로 만든 것은 그 **위층**이다 — 어떤 활동을 기준으로 삼을지, 여러 결과를 어떤 가중치로 합칠지,
무엇을 뺄지. 그게 ai-service가 하는 일이다.

</details>

<details>
<summary><b>Q. 임베딩은 어떻게 만들고 어디에 저장하나요?</b></summary>

**만들기** — 상품의 `제목 + 태그 + 소개글 + 본문(2000자까지)`을 한 덩어리 텍스트로 합쳐
OpenAI `text-embedding-3-small`에 보내면 숫자 1536개를 돌려준다.

**저장** — Postgres의 `product.embedding` 컬럼(pgvector 확장). Elasticsearch에도 같은 값을
복사해 넣는다.

**갱신** — 20초마다 도는 배치가 원문 해시를 비교해, 텍스트가 바뀐 상품만 다시 호출한다.
해시가 같으면 건너뛴다.

**호출 시점** — 상품 등록·수정 시 1회다. 추천을 조회할 때는 **OpenAI를 호출하지 않는다.**
이미 저장된 좌표끼리 거리만 계산한다.

</details>

<details>
<summary><b>Q. 가중치 1.0 / 0.7은 어떻게 정했나요?</b></summary>

**실측값이 아니라 판단이다.** 그 점을 분명히 해둔다.

근거는 "추천이 뜨는 자리가 탐색 페이지"라는 맥락이다. 지금 사려고 담은 것이 몇 주 전 구매보다
현재 관심사에 가깝다고 봤다.

조정하려면 **어떤 추천이 실제로 클릭됐는지**가 필요한데 그 데이터를 수집하지 않고 있다.
그래서 지금은 검증되지 않은 값이고, 문서에도 그렇게 적었다.

RRF 구조라 값을 바꾸는 것 자체는 상수 하나 수정이다.

</details>

<details>
<summary><b>Q. 전혀 관계없는 상품이 추천되면 어떻게 되나요?</b></summary>

**지금은 그대로 나온다. 이게 알려진 한계다.**

거리 하한이 없어서 "가까운 순으로 N개"만 뽑는다. 관련 있는 상품이 하나도 없어도 4개가 채워진다.
위 「남은 한계」의 펭귄 예시가 그 경우다.

고치는 방법은 쿼리에 조건 한 줄을 더하는 것이지만, **값을 정하지 못했다.** 실측해 보니
관련 있는 상품과 무관한 상품의 거리가 겹치는 구간이 있어서, 어떤 값을 잡아도 한쪽이 희생된다.

- 컷을 낮게(엄격하게) → 확실한 1건만 남고 섹션이 빈약해진다
- 컷을 높게(느슨하게) → 지금과 다를 바 없다

임의의 숫자를 넣기보다 **문제를 명시하고 남겨두는 쪽**을 택했다.

</details>

<details>
<summary><b>Q. 활동 내역을 화면에서 보내면 조작할 수 있지 않나요?</b></summary>

**가능하다. 다만 얻을 게 없다.**

이 API가 하는 일은 "이 상품들과 비슷한 공개 상품 목록"을 돌려주는 것뿐이다. 남의 구매 이력을
넣어도 **그 사람의 개인정보는 나오지 않고**, 공개 상품 정보만 나온다. 상세 페이지의
"비슷한 상품"과 같은 성질의 데이터다.

돈이나 권한이 걸린 판단이었다면 서버가 직접 조회해야 했겠지만, 추천 목록에는 그런 게 없다.

</details>

<details>
<summary><b>Q. 왜 활동을 서버에 저장하지 않았나요?</b></summary>

추천에 필요하지 않아서다.

장바구니·주문은 order-service가 소유하고 화면이 이미 갖고 있다. 저장하려면 테이블·이벤트
소비·정합성 처리가 따라오는데, 그 대가로 얻는 게 "이미 있는 데이터를 한 번 더 갖는 것"뿐이었다.

다만 **다른 목적**으로는 값이 있다. 지금 이 시스템에는 개인 단위 행동 기록이 서버 어디에도
없어서(리뷰 제외), 나중에 취향 분석이나 재구매 방지 같은 기능이 필요해지면 그때 만들면 된다.

</details>

<details>
<summary><b>Q. 사용자가 아무 활동도 안 했으면요?</b></summary>

**섹션을 통째로 숨긴다.** 인기순 같은 것으로 채우지 않는다.

개인화가 아닌 것을 개인화 자리에 채우면 사용자를 속이는 셈이고, 바로 아래에 이미 인기순
목록이 있어서 같은 내용이 두 번 나온다.

</details>

<details>
<summary><b>Q. 추천이 몇 개까지 나오나요? 활동이 20개면요?</b></summary>

**기준으로 삼는 활동은 신호당 최대 3개**다. 장바구니 3개 + 구매 3개 = 최대 6개 기준.

장바구니를 20개 담은 사용자 때문에 서버 호출이 20배가 되는 걸 막기 위한 상한이다. 최근 것이
앞에 온다는 전제로 앞에서 자른다.

최종 노출은 4개이고, 기준 하나당 후보는 16개(4 × 4)를 받아온다. 합산으로 순서가 바뀌고 이미
담았거나 산 상품이 빠지므로 넉넉히 받아야 자리가 안 빈다.

</details>

<details>
<summary><b>Q. 이미 산 상품이 다시 추천되지는 않나요?</b></summary>

**제외된다.** 장바구니에 담은 것과 구매한 것 둘 다 결과에서 걸러진다.

기준으로 삼는 활동은 신호당 3개로 제한하지만 **제외는 받은 목록 전부**에 적용한다. 20개를
샀으면 3개만 "이것과 비슷한 걸 찾아줘"의 기준이 되고, **20개 전부가 결과에서 빠진다.**

배포 환경에서 확인했다. 구매 이력 8건을 넣었을 때 결과 4건에 그 8건은 하나도 없었다.

**다만 한 가지 빈틈이 있다.** 비교 단위가 상품 ID라서, 판매자가 상품을 새 버전으로 올리면
ID가 달라져 걸러지지 않는다. 자세한 내용은 위 「남은 한계」 참조.

</details>

<details>
<summary><b>Q. 같은 상품을 장바구니에도 담고 구매도 했으면요?</b></summary>

**조회는 한 번만 하고, 가중치는 양쪽 다 받는다.** 1.0 + 0.7 = 1.7이 되어 그만큼 강한 신호로
취급된다.

그리고 이미 산 상품이므로 **결과에서는 제외**된다.

</details>

## 설계 판단을 묻는다면

앞의 질문들이 "무엇을 만들었나"라면, 여기는 **"왜 그렇게 판단했나"**다.

<details>
<summary><b>Q. 이미 있던 ai-service에 얹은 것을 "독립 서비스로 구현했다"고 할 수 있나요?</b></summary>

**서비스 경계 기준으로는 그렇다.** 다만 "새 서비스를 만들었다"와는 다르므로 구분해서 말하는 게 맞다.

판단 근거는 **경계가 실제로 성립하는가**였다.

- 추천 판단(가중치·제외·개수)을 ai-service가 **단독으로** 소유한다
- product-service는 "이 상품과 가까운 것"만 답하고 **누구에게 무엇을 추천할지 모른다**
- 두 서비스는 별도 프로세스·별도 배포 단위이고 gRPC 계약으로만 통신한다
- ai-service를 내려도 product-service는 정상 동작한다 (실제로 확인)

새 서비스를 만드는 쪽도 검토했지만, **경계가 같은데 프로세스만 늘리는 선택**이었다. 배포·모니터링·설정이 하나 더 늘고 얻는 건 "새로 만들었다"는 사실뿐이다. 이미 AI 관련 책임(상품 검수·정산 챗봇)을 지고 있는 서비스가 있는데 AI 추천만 따로 두는 게 오히려 응집도를 해친다고 봤다.

**반대 논리도 인정한다.** 검수·챗봇·추천은 "AI를 쓴다"는 것 말고 공통점이 적어서, 나중에 추천 트래픽이 커지면 분리해야 할 수 있다. 지금은 분리 비용이 이득보다 크다는 판단이다.

</details>

<details>
<summary><b>Q. 벡터DB를 썼다고 하는데 전용 벡터 DB가 아니라 Postgres 확장 아닌가요?</b></summary>

맞다. **pgvector**다. 전용 벡터 DB(Pinecone·Weaviate 등)를 도입하지 않았다.

이유는 **운영 대상을 늘릴 근거가 없었기** 때문이다.

| | 전용 벡터 DB | pgvector |
|---|---|---|
| 인프라 | 새 저장소 추가 | **이미 있는 Postgres** |
| 트랜잭션 | 상품 데이터와 분리 | 같은 트랜잭션 |
| 규모 한계 | 수억 건 | 수십만 건까지 무리 없음 |

상품이 수십 건인 서비스에서 전용 벡터 DB를 도입하면 **성능 이득 없이 운영 대상만 하나 는다.**
게다가 상품 데이터와 벡터가 다른 저장소에 있으면 "상품은 지워졌는데 벡터는 남는" 정합성
문제를 직접 관리해야 한다.

Elasticsearch의 `dense_vector`도 함께 쓴다. 검색은 ES, 추천은 pgvector로 갈린 이유는
**검색은 질의↔상품 비교라 글자 검색과 같은 자리에서 병합해야 하고, 추천은 상품↔상품 비교라
원본 옆에서 계산하는 게 자연스럽기** 때문이다.

</details>

<details>
<summary><b>Q. 쿠버네티스 자동 스케일링은 실제로 동작하나요?</b></summary>

**아니다. HPA(오토스케일러)를 설정하지 않았고 `replicas: 1`이다.** 이 부분은 솔직히 미구현이다.

자동 배포(CD)는 동작한다 — develop 머지 시 빌드·이미지 발행·롤링 배포까지 자동이다. 실제로
이번 기능도 그 파이프라인으로 배포했다.

스케일링을 안 넣은 이유는 **노드 여유가 없어서**다. 단일 노드에 서비스 8개가 올라가 있고
메모리가 빠듯하다(product-service가 한도의 93%까지 쓴 실측이 있다). 이 상태에서 HPA를 켜면
스케일아웃이 시작되는 순간 노드가 먼저 죽는다.

**넣으려면** 리소스 요청·한도를 다시 잡고 노드를 늘리는 게 선행이다. "설정만 추가"로 끝나는
일이 아니라 미뤘고, 그 판단을 감추지 않는 편이 낫다고 본다.

</details>

<details>
<summary><b>Q. 서버 간 통신을 왜 gRPC로 했나요? REST면 안 되나요?</b></summary>

동작은 한다. **팀 표준을 따랐고, 그 표준에 근거가 있다.**

```
외부 클라이언트 ↔ 백엔드      REST
서비스 ↔ 서비스 (동기)        gRPC
서비스 ↔ 서비스 (비동기)      Kafka
```

gRPC를 택한 이유 세 가지.

1. **계약이 코드로 강제된다.** `.proto` 파일에서 스텁이 생성되므로, 서버가 필드를 바꾸면
   클라이언트가 **컴파일 단계에서** 깨진다. REST+JSON은 런타임에야 알 수 있다
2. **서비스 디스커버리와 맞물린다.** `static://product-service:포트`로 쿠버네티스 서비스명을
   그대로 쓴다
3. **게이트웨이를 거치지 않는다.** 서비스끼리 게이트웨이를 경유하면 인증 필터·라우팅이
   불필요하게 끼고, 게이트웨이가 내부 트래픽의 단일 장애점이 된다

실제로 이번에 gRPC 계약 덕을 봤다. product-service에 메서드를 추가하고 ai-service에서
호출하는데, 필드 이름을 잘못 쓰자 **빌드에서 바로 걸렸다.**

</details>

<details>
<summary><b>Q. "개인 정보와 활동 내역 기반"이라는데 개인정보는 안 쓰지 않나요?</b></summary>

**맞다. 활동 내역만 쓴다.** 나이·성별 같은 프로필 정보는 추천에 넣지 않았다.

의도적인 선택이다.

- 프로필 정보는 user-service가 소유한다. 가져오려면 **gRPC 계약을 하나 더** 만들어야 한다
- 그 정보로 무엇을 할지가 불분명하다. "30대 남성이면 이런 상품"은 **근거 없는 추측**이고,
  실제로 그런 편향이 맞는지 확인할 데이터가 없다
- 개인정보를 추천에 쓰면 그만큼 **보관·전달 범위가 넓어진다.** 얻는 게 불확실한데 위험만 는다

활동 내역(장바구니·구매)은 **그 사람이 실제로 한 행동**이라 추측이 없다. 근거가 확실한 신호만
쓰는 쪽을 택했다.

넣는다면 프로필 자체보다 **찜 목록**이 먼저다. 그건 명시적인 선호 표현이라 활동 내역과 같은
성질이다. 다만 user-service가 이벤트를 발행해야 해서 이번 범위에서 뺐다.

</details>

<details>
<summary><b>Q. 기존 API가 바뀌지 않았다는 걸 어떻게 보장하나요?</b></summary>

**기존 엔드포인트를 하나도 건드리지 않았다.** 추가만 했다.

```
추가:  GET /api/v2/ai/recommendations          (신규)
추가:  gRPC GetSimilarProducts                 (신규 메서드)

무변경: GET /api/v2/products
       GET /api/v2/products/{id}
       GET /api/v2/products/{id}/recommends    ← 기존 "비슷한 상품"
       그 외 전부
```

`ProductRecommender`·`findSimilarProductRows` 같은 추천 계산 코드도 **한 글자도 고치지
않고** gRPC 핸들러에서 재사용만 했다. 기존 회귀 테스트가 그대로 통과하는 것으로 확인했다.

게이트웨이 라우트도 **경로를 추가**했을 뿐 기존 경로를 바꾸지 않았다.

</details>

<details>
<summary><b>Q. 추천 기능에는 동시성 문제가 없나요?</b></summary>

**없다. 읽기만 하기 때문이다.**

추천 요청은 상태를 바꾸지 않는다 — 저장하는 것도, 카운터를 올리는 것도 없다. 같은 요청이
동시에 100개 와도 서로 간섭할 지점이 없다.

동시성 제어가 필요한 곳은 **주문·재고**이고 그건 다른 서비스의 영역이다. 추천이 그 흐름에
끼어들지 않는 것 자체가 설계 목표였다 — 「실패하면 조용히 빈 목록」이 그 얘기다.

굳이 꼽자면 **활동 내역을 서버에 저장했다면** 동시성 고민이 생겼을 것이다(같은 주문 이벤트가
중복 수신될 때 중복 저장). 저장하지 않기로 하면서 그 문제도 함께 사라졌다.

</details>

<details>
<summary><b>Q. "추천이 죽어도 구매는 된다"를 실제로 검증했나요?</b></summary>

**의도치 않게 실전에서 확인했다.**

배포 순서가 어긋나 ai-service만 새 버전으로 뜨고 product-service는 구버전이던 시점이 있었다.
그때 gRPC 호출이 `UNIMPLEMENTED`로 실패했는데,

```
gRPC 실패 → warn 로그 → 빈 목록 반환 → 200 응답 → 화면에서 섹션만 숨김
```

상품 목록·장바구니·구매 흐름은 **전혀 영향받지 않았다.** 테스트로 만든 시나리오가 아니라
실제 장애 상황에서 설계대로 동작한 것이다.

코드 레벨에서도 고정했다. `SimilarProductQueryClientTest`에 **"상품 서비스가 죽어 있어도
예외 없이 빈 목록을 준다"**는 테스트가 있어, 누군가 예외를 던지도록 바꾸면 빌드가 깨진다.

</details>

<details>
<summary><b>Q. 장애가 전파될 위험은 없나요? ai-service가 product-service를 부르는데.</b></summary>

방향이 **한쪽뿐**이라 순환은 없다.

```
ai-service ──▶ product-service        (추천 조회)
product-service ─╳─▶ ai-service       (없음)
```

product-service는 ai-service의 존재를 모른다. 그래서 ai-service가 죽어도 product-service는
영향이 없고, 반대 방향은 위에서 말한 대로 빈 목록으로 흡수된다.

**지연 전파**는 막아뒀다. gRPC 호출에 **2초 예산**을 걸어서, product-service가 느려져도
추천 요청이 무한정 붙들려 있지 않는다.

다만 이 값에서 문제를 하나 겪었다. 파드가 새로 뜬 **첫 호출**은 연결 수립에만 0.85초가
들어가 예산을 넘겼다. 두 번째부터는 정상이다. 콜드 스타트를 감안하지 않은 값이었고,
여유를 두는 쪽으로 조정할 계획이다.

</details>

<details>
<summary><b>Q. 상품이 10만 건이 되면 이 구조가 버티나요?</b></summary>

**추천 조회 자체는 버틴다. 다만 두 곳을 손봐야 한다.**

pgvector는 HNSW 인덱스로 근사 탐색을 하므로 건수가 늘어도 조회 시간이 선형으로 늘지 않는다.
수십만 건까지는 인덱스만 제대로 걸려 있으면 문제가 없다.

손봐야 할 곳은 이렇다.

1. **기준마다 따로 조회한다** — 활동이 6개면 쿼리가 6번이다. 지금은 상한을 3개씩 둬서
   최대 6번이지만, 응답 시간이 문제되면 한 번에 묶는 쿼리로 바꿔야 한다
2. **거리 하한이 없다** — 건수가 늘면 "가까운 4개"가 실제로 가까워질 가능성은 높아지지만,
   하한이 없다는 구조적 문제는 그대로다

그리고 규모가 커지면 **취향 벡터를 미리 계산해 두는 배치**가 의미를 갖기 시작한다. 지금은
조회 시점 계산이 더 빠르고 신선하지만, 활동이 수백 건인 사용자가 생기면 역전된다.

</details>

<details>
<summary><b>Q. 왜 하필 RRF인가요? 다른 방법은 검토했나요?</b></summary>

세 가지를 놓고 골랐다.

| 방법 | 왜 안 썼나 |
|---|---|
| **좌표 평균(centroid)** | 실측으로 기각. 이 카탈로그는 공간이 압축돼 있어 평균이 "모든 것과 어중간하게 가까운 자리"에 착지한다 |
| **유사도 점수 합산** | 기준마다 점수 분포가 달라 스케일이 안 맞는다. 데이터가 바뀔 때마다 보정 상수를 다시 잡아야 한다 |
| **RRF (채택)** | 점수를 버리고 등수만 쓴다. 스케일 문제가 없고, 여러 기준이 공통으로 꼽은 상품이 올라간다 |

그리고 **이미 이 코드베이스가 RRF를 쓰고 있었다.** 통합 검색에서 글자 순위와 의미 순위를
합치는 데 같은 방식을 쓴다. 새 개념을 도입하는 게 아니라 **이미 팀이 이해하고 있는 도구를
한 번 더 쓰는 것**이라 학습 비용도 없었다.

다만 검색 쪽은 두 목록 고정에 가중치가 없고, 추천 쪽은 목록 개수가 가변이며 가중치가 있다.
시그니처가 달라 공용화하지 않고 각자 두었다.

</details>

<details>
<summary><b>Q. 배포하면서 문제는 없었나요?</b></summary>

**세 번 막혔고 원인이 다 달랐다.** 숨길 이유가 없어 적어둔다.

**① 매니페스트 검증 실패** — 설정 파일에 `${PRODUCT_GRPC_SERVER_PORT}`를 쓰면서 파드에
그 환경변수를 주입하는 설정을 빠뜨렸다. 배포 전 검증 스크립트가 잡아냈다. **게이트가 제
역할을 한 사례**로, 배포 후 런타임에 죽는 것보다 낫다.

**② 배포 대상 없음** — 그 수정이 매니페스트 파일만 바꾼 것이라, 릴리스 파이프라인이
"배포할 서비스 없음"으로 판단하고 전부 건너뛰었다. 이미 만들어진 이미지를 올려야 하는
상황이라 워크플로를 수동 실행했다.

**③ 게이트웨이 라우트 누락** — 가장 오래 걸린 건이다. ai-service에 엔드포인트를 만들었지만
**게이트웨이 라우트 목록은 코드에 고정**돼 있어 자동으로 열리지 않는다. 그걸 빠뜨려 404가 났다.

③에서 진단이 늦어진 이유가 특히 남는다. `curl`로 확인했을 때 **401**이 나와서 "라우팅 정상,
인증만 필요"로 판단했는데 틀렸다. **인증 필터가 라우팅보다 먼저 돌기 때문에, 라우트가 없어도
401이 나온다.** 토큰을 실어 보내는 실제 사용자만 404를 볼 수 있었다.

지금은 `OPTIONS` 요청으로 판별한다 — 인증을 우회해 라우팅까지 가므로 라우트 유무가 그대로 드러난다.

```
OPTIONS /api/v2/ai/recommendations      200  ← 라우트 있음
OPTIONS /api/v2/ai/없는경로              404  ← 대조군
```

같은 실수를 막으려고 라우팅 테스트를 추가했다.

</details>

<details>
<summary><b>Q. 이 기능이 실제로 사용자에게 도움이 되나요?</b></summary>

**모른다. 그걸 잴 수단이 없다.**

추천이 몇 번 노출되고 몇 번 클릭됐는지 수집하지 않는다. 그래서 "도움이 된다"고 말할 근거가 없다.

말할 수 있는 것은 여기까지다.

- 주제가 맞는 상품이 나온다 (구매 이력이 개발 학습 위주면 개발 관련 상품이 나온다 — 실측)
- 상위 4건 중 관련 있는 건 1건 정도다 (하한이 없어서 — 실측)

**후자를 알면서도 출시한 이유**는, 이게 "동작하지 않는 기능"이 아니라 "정확도가 낮은 기능"이고,
정확도를 올리려면 클릭 데이터가 필요한데 그건 기능이 나가야 쌓이기 때문이다.

다만 **그 한계를 문서에 적어두는 것**과 모르는 척하는 것은 다르다고 본다.

</details>

## 정리

이번 작업에서 **두 번 틀렸고 두 번 다 실측으로 바로잡았다.**

1. "추천을 product-service에 두면 된다" → 요구사항이 독립 서비스를 요구해 ai-service로
2. "여러 활동을 평균 내면 취향 벡터가 된다" → 좌표 공간이 압축돼 있어 평균이 취향을 지움. 순위 합산으로

두 번째는 특히, **재보지 않았으면 그럴듯한 코드가 조용히 나쁜 추천을 내고 있었을** 경우다.
"흔한 방식"이라는 이유로 넘어가지 않고 이 카탈로그에서 실제로 어떤 분포인지 잰 것이
설계를 바꿨다.
