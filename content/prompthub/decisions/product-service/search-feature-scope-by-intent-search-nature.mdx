## 배경

상품 검색 고도화를 3단계로 계획했다.

- 1단계: 검색을 Elasticsearch로 전환 (완료)
- 2단계: 의미 기반 검색 · **자동완성** · 비슷한 상품 추천
- 3단계: 행동 로그 수집 · **인기 검색어와 검색 히스토리** · **개인화 홈 추천**

이 중 굵게 표시한 세 가지는 일반적인 이커머스 검색 기능을 참고해 설계한 것이었다. 자동완성은
한글 특성을 고려해 **초성 검색**("ㅍㄹㅍㅌ" → 프롬프트)과 **타이핑 중간 상태 매칭**("프롬ㅍ"),
그리고 오타 교정까지 포함했다.

구현 직전 "이 서비스에 정말 필요한가"를 다시 물었고, 그 과정에서 **서비스의 성격 자체가
일반 이커머스와 다르다**는 점이 드러났다.

## 고려한 선택지

**1. 계획대로 전부 구현**

설계 문서가 이미 상세하게 나와 있었다. 다만 각 기능이 이 서비스에서 실제로 작동할 상황이
있는지는 검증하지 않은 상태였다.

**2. 서비스 성격에 비춰 항목별로 재평가 (택함)**

"사용자가 무엇을 알고 검색창에 오는가"를 기준으로 각 기능의 발동 조건을 따져본다.

## 결정

### 판단의 축 — 아는 물건 검색 vs 의도 검색

일반 이커머스에서 자동완성이 작동하는 이유는 **사용자가 목표물의 이름을 이미 알기
때문**이다. "아이폰"까지 치는 사람은 "아이폰 15 프로"라는 상품이 존재한다는 걸 알고 있고,
자동완성은 타이핑을 줄여주는 도구다.

이 서비스는 반대다. 사용자는 **"시니어 코드리뷰 프롬프트"라는 상품이 있는지 모른다.**
아는 것은 자기 의도("코드 리뷰를 시키고 싶다")뿐이다.

```mermaid
flowchart TB
    subgraph known["아는 물건 검색 — 일반 이커머스"]
        direction LR
        K1[사용자가 상품명을 안다] --> K2["아이폰"까지 입력]
        K2 --> K3[자동완성이 나머지를 채움]
        K3 --> K4[타이핑 절약]
    end

    subgraph intent["의도 검색 — 이 서비스"]
        direction LR
        I1[사용자는 상품명을 모른다] --> I2["코드 리뷰 시키고 싶다"]
        I2 --> I3[의미 기반 검색이 찾아냄]
        I3 --> I4[존재를 몰랐던 상품 발견]
    end
```

이 축으로 보면 결론이 갈린다.

- **초성 검색**은 연락처·앱 실행기처럼 **이름을 정확히 아는 대상을 빨리 찾을 때** 쓰는
  기능이다. 이름을 모르는 카탈로그에서는 발동할 상황 자체가 없다
- 사용자의 실제 문제("원하는 걸 어떻게 찾지")를 푸는 것은 자동완성이 아니라 **의미 기반
  검색**이다. 그건 별도 작업으로 이미 진행 중이었다

### 항목별 결정

| 기능 | 결정 | 근거 |
|---|---|---|
| 상품명 자동완성 | **유지(축소)** | 기존 필드에 접두어 검색 1회. 구현이 작고 탐색 진입에 도움 |
| 초성 검색 | **제외** | 이름을 모르는 카탈로그에서 발동 상황이 없음 |
| 타이핑 중간 상태 매칭 | **제외** | 한글 입력기가 대체로 처리하고, 200ms 지연 요청이면 중간 상태 대부분이 조회되지 않음 |
| 오타 교정 | **제외** | 의미 기반 검색이 오타에 어느 정도 강해 효과가 겹침 |
| 인기 검색어 | **보류** | 집계할 트래픽이 없음 — 지금 집계하면 개발 중 입력한 테스트 검색어가 인기 검색어로 노출됨 |
| 개인 최근 검색어 | **보류** | 브라우저가 이미 입력 기록을 보여줌 |
| 개인화 홈 추천 | **중단** | 행동 데이터가 없으면 인기순 대체 경로로만 동작 |

<details>
<summary><b>🔍 "브라우저가 이미 보여준다"는 게 무슨 말인가요?</b></summary>

웹 브라우저는 사용자가 입력창에 쳤던 값을 자체적으로 기억해뒀다가, 다음에 그 입력창을
클릭하면 목록으로 보여준다(자동 완성 기능). 서버가 아무것도 하지 않아도 동작한다.

서버에 따로 저장하면 얻는 건 "다른 기기에서도 보인다" 정도인데, 그 대신 저장소·조회 API·
삭제 API·사용자별 격리 처리가 필요하다. 프롬프트 마켓에서 검색 기록의 기기 간 동기화가
필요한 요구인지 확인되지 않아 보류했다.

</details>

### 잘라낸 것을 되살릴 조건을 함께 기록했다

제외 항목은 "필요 없다"가 아니라 **"지금은 근거가 없다"**로 정리하고, 판정 가능한 조건을
같이 남겼다. 행동 로그 수집은 별도로 진행하므로, 추측이 아니라 데이터로 다시 판단할 수 있다.

| 확장 항목 | 켜는 조건 | 측정 방법 |
|---|---|---|
| 오타 교정 | 결과 0건인 검색 비율이 유의미하게 높음 | 검색 실행 로그 |
| 초성 검색 | 자음만으로 구성된 검색이 실제로 관측됨 | 검색 실행 로그 |
| 인기 검색어 | 서로 다른 사용자의 검색이 일 수십 건 이상 | 검색 실행 로그 |

되살리는 비용도 낮게 유지했다. 초성·자모용 색인 필드는 이미 만들어져 있어서, 확장 시
**전체 재색인 없이** 값을 채우는 작업만 추가하면 된다.

### 이 결론에 이르기까지

이 재평가는 "자동완성이 과설계 아닌가"라는 물음에서 시작됐다. 처음에는 설계 문서에 상세히
정리된 내용이라 그대로 진행할 생각이었다.

**검증 과정에서 나온 사실들:**

- 상품명이 "시니어 코드리뷰 프롬프트"처럼 **여러 단어로 된 설명형 문장**이다. 브랜드명처럼
  짧고 외우는 이름이 아니다
- 카탈로그가 수십 개 규모라, 유형 필터 4개만으로도 전체가 조망된다
- 개인화 추천의 원재료인 행동 데이터가 **아직 한 건도 없다**

각각은 알고 있던 사실이었지만, "이 서비스에서 이 기능이 발동할 상황이 있는가"를 기준으로
묶어서 보기 전까지는 결론으로 이어지지 않았다. **기능 목록을 참고 사례에서 가져오면, 그
사례의 전제(사용자가 상품명을 안다)까지 같이 딸려 온다.** 전제를 검사하지 않으면 작동하지
않을 기능을 만들게 된다.

보류 판단에서 하나 더 확인한 것이 있다. 최근 검색어를 미루면 그동안의 기록이 유실되는 게
아닌가 하는 우려가 있었는데, **검색 기록은 행동 로그 수집 작업이 이미 남기고 있었다.**
보류하는 기능은 그 데이터를 빠르게 읽기 위한 사본이었을 뿐이라, 미뤄도 이력 손실이 없다.
"미루면 데이터를 잃는다"는 우려는 수집 주체가 어디인지 확인하면 갈린다.

## 결과

- 자동완성 구현 범위가 클래스 3개 분량(초성·자모 변환기, 오타 교정 쿼리)에서 접두어 검색
  1회로 줄었다. 색인 매핑 변경과 재색인도 필요 없어졌다
- 개인화 홈 추천 작업을 중단하면서, 그와 얽혀 있던 외부 서비스 이벤트 계약 협의도 함께
  보류됐다
- 남은 작업이 4개로 정리돼, 실제로 사용자 문제를 푸는 기능(의미 기반 검색, 비슷한 상품
  추천)에 집중할 수 있게 됐다
- 제외 항목마다 되살릴 조건을 수치로 남겨, 나중에 같은 논의를 처음부터 다시 하지 않아도 된다

이 결정은 [검색 로그 파이프라인 스코프 재조정](/decisions/prompthub/product-service/search-log-pipeline-scope-by-fe-dependency)에서
"프론트엔드 수정이 필요한가"를 기준으로 내렸던 판단을 대체한다. 그때는 **작업량**을 기준으로
범위를 갈랐고, 이번에는 **기능이 이 서비스에서 작동하는가**를 기준으로 다시 갈랐다.
