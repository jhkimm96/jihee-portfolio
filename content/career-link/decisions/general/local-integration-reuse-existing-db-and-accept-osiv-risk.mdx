## 배경

새 기능을 로컬에서 끝까지 확인하려고 Docker Compose로 백엔드·신규 AI 서비스·프론트를 한 번에 띄우는 작업을 했다. 처음엔 MySQL·Redis도 Compose 안에 컨테이너로 포함시켜, 매번 깨끗한 상태에서 테스트할 수 있게 구성했다.

## 고려한 선택지

**DB 구성**
- **A. Compose 안에 자체 MySQL/Redis 컨테이너**: 매번 깨끗하게 시작할 수 있다는 장점이 있었지만, 실제로 띄워보니 두 가지 문제가 바로 드러났다. 첫째, 로컬에 이미 쓰고 있던 MySQL/Redis와 포트가 충돌했다. 둘째, 이 저장소엔 마이그레이션 도구가 전혀 없어서 빈 DB엔 로그인에 필요한 기존 테이블·뷰조차 없었고, 새 기능과 무관한 이유로 애플리케이션이 아예 기동하지 않았다.
- **B. 기존에 쓰던 로컬 MySQL/Redis를 그대로 사용**: Compose가 호스트의 DB를 바라보게만 하면, 이미 완전한 스키마와 로그인 가능한 계정이 있는 채로 시작할 수 있다.

<details>
<summary><b>🔍 "마이그레이션 도구가 없다"는 게 무슨 뜻인가요</b></summary>

스키마(테이블 구조) 변경 이력을 코드로 관리하는 도구(Flyway, Liquibase 등)가 이 저장소엔 없다는 뜻이다. 대신 Hibernate의 `ddl-auto: validate` 설정만 쓰는데, 이건 "코드의 엔티티와 실제 DB 구조가 일치하는지 검사만 하고, 안 맞으면 기동을 거부"하는 모드다. 스키마를 만들어주진 않는다.

</details>

**DB 스키마 버전 불일치**

막상 B를 선택해도, 팀 `main` 브랜치의 최신 커밋과 로컬 DB 스키마 사이에 이미 간격이 있었다(다른 작업에서 추가된 컬럼 하나가 로컬 DB엔 없었음). `ddl-auto: validate`는 이 간격을 그대로 기동 실패로 만든다.
- **A. 팀 전체 스키마를 마이그레이션 도구로 관리하기 시작**: 근본적인 해법이지만 이번 작업 범위를 크게 벗어난다.
- **B. 로컬 Compose에서만 `ddl-auto: update`로 완화**: 운영/공유 설정 파일은 그대로 두고, Compose 환경변수로만 이 기동 시점의 로컬 전용 동작을 바꾼다.

## 결정

- DB 구성은 **B(기존 로컬 DB 재사용)**로 정했다. Compose에선 MySQL/Redis 컨테이너를 빼고, `host.docker.internal`로 호스트의 기존 DB·Redis에 연결하게만 구성했다.
- 스키마 불일치는 **B(Compose 한정 `ddl-auto: update`)**로 완화했다. 팀 공유 설정 파일은 건드리지 않고, 로컬 통합 테스트에서만 적용되는 환경변수로 범위를 좁혔다.

## 결과

로컬에서 세 서비스가 실제 데이터로 기동·로그인·AI 호출까지 끝까지 확인 가능해졌다. 다만 이 과정에서 Spring Boot의 open-in-view(기본값 true)가 요청 전체 동안 DB 커넥션을 쥐고 있어서, AI 호출(느릴 수 있음) 앞에 쿼리 하나만 있어도 그 호출 내내 커넥션이 묶인다는 걸 확인했다.

<details>
<summary><b>🔍 open-in-view가 뭔가요</b></summary>

요청이 들어와서 응답이 나갈 때까지 하나의 Hibernate 세션(과 거기서 쓰는 DB 커넥션)을 계속 열어두는 Spring Boot 기본 설정이다. 컨트롤러·뷰 렌더링 단계에서도 지연 로딩(lazy loading)이 그대로 동작하게 해주는 편의 기능이지만, 그 대가로 요청 하나가 DB 커넥션 하나를 처리 시간 내내 붙잡는다.

</details>

끄는 게 맞는 방향이지만, 이 설정은 앱 전체에 영향을 주고 팀 코드 전반의 지연 로딩 의존 여부를 먼저 확인해야 해서, 지금은 끄지 않고 코드에 주석으로 남겨뒀다. 동시 사용자가 늘어 커넥션 풀이 실제로 부족해지면 다시 검토한다.
