## 대상

공고 URL을 입력하면 요구사항을 추출해 보여주는 "지원 준비 시작" 기능. career-link(Spring Boot 백엔드), career-link-ui(Next.js 프론트), career-link-agent(신규 FastAPI 서비스) 세 저장소에 걸쳐 14개 작업으로 나눠 구현했다. 각 작업은 끝날 때마다 개별 리뷰를 거쳤고, 14개가 전부 끝난 뒤 저장소별로 전체 브랜치 diff를 다시 리뷰했다 — 작업 단위로 쪼개진 리뷰로는 여러 작업에 걸친 문제가 잘 안 보이기 때문이다.

## 발견한 문제

**career-link-agent**

1. 사용자가 입력한 URL을 서버가 검증 없이 그대로 가져오는 구조 → [별도 글로 정리](/troubleshooting/career-link/security/ssrf-dns-rebinding-on-posting-fetch)

**career-link**

2. AI 추출 호출(Claude API, 느릴 수 있음)이 DB 트랜잭션 안에서 실행되고 있었다 — 호출이 끝날 때까지 커넥션 풀의 커넥션 하나를 계속 붙잡는다.
3. 외부 agent 응답을 타입만 맞추고 내용 검증 없이 신뢰했다 — null 필드나 알 수 없는 상태값이 오면 원인과 무관한 500/409 에러로 샜다.
4. agent 호출 실패 시 예외 메시지(내부 agent URL, 응답 원문)가 그대로 클라이언트 응답에 담겨 나갔다.
5. 요청 본문(문항 리스트, 입력 모드)을 검증 없이 바로 AI 호출에 썼다 — 잘못된 입력이 **호출 비용을 쓴 뒤에야** NPE로 드러났다.
6. 상세 조회가 `findAll()`로 전체 사용자 행을 불러와 메모리에서 필터링하고 있었다.

**career-link-ui**

7. 제출 성공 경로에서도 버튼을 즉시 재활성화해, 빠른 재클릭으로 중복 생성이 가능했다.
8. Docker 빌드 컨텍스트에 `.dockerignore`가 없어 로컬 `.env.local`(JWT 시크릿 포함)이 빌드 스테이지 레이어에 들어갈 뻔했다.
9. "이용 신청 필요" 에러가 입력 화면에서만 안내로 처리되고, 목록·상세 화면에서는 일반 토스트로만 떠서 "아직 아무것도 안 만든 사용자"와 구분이 안 됐다.

**외부 리뷰(Codex) 추가 발견**

10. 문항 리스트 존재 여부는 검증했지만 문항 개별 필드(빈 텍스트, null 글자수 제한)는 검증하지 않았다. agent 응답 상태값도 "실패 아니면 전부 성공"으로 다뤄, 알 수 없는 상태값이 성공으로 오인됐다.

**실제 API 연동 후 발견**

11. Claude 응답이 마크다운 코드펜스로 감싸져 와서 JSON 파싱이 매번 실패했다. 신규 태그의 `tagKey`가 null로 오면 전체 추출이 크래시났다.

<details>
<summary><b>🔍 트랜잭션 안에서 외부 호출을 하면 왜 문제인가요</b></summary>

트랜잭션이 열려 있는 동안은 DB 커넥션 풀에서 커넥션 하나를 계속 들고 있는다. 그 안에서 몇 초~몇십 초 걸리는 외부 API 호출을 하면, 그 시간만큼 커넥션 하나가 다른 요청에서 못 쓰게 묶인다. 동시 요청이 늘면 풀이 금방 고갈된다.

## 조치

**2. 트랜잭션 분리** — AI 호출을 트랜잭션 밖으로 빼고, 실제 DB 쓰기(지원 준비+문항+요구사항+태그)만 별도의 `@Transactional` 메서드(새 writer 컴포넌트)로 묶었다. "먼저 호출하고 그 결과로 한 번에 저장한다"는 순서만 지키면 호출 구간엔 애초에 트랜잭션이 필요 없었다. HTTP 클라이언트에 명시적 연결·읽기 타임아웃도 추가해 최악의 경우에도 점유 시간에 상한을 뒀다.

**3. agent 응답 검증** — `"ok"` 상태일 때만 성공으로 보고, 각 요구사항의 타입이 알려진 값인지·필수 필드가 null이 아닌지 확인한 뒤에만 다음 단계로 넘겼다. 처음엔 "필드가 있으면 성공"으로 가정했는데, 이건 "agent가 망가진 응답을 줄 수도 있다"는 전제를 안 하고 있었다는 뜻이다. 검증 실패는 전부 하나의 에러코드(`EXTRACTION_FAILED`)로 모았다 — 호출자 입장에선 "왜 실패했는지 세분화"보다 "이건 내 책임이 아니다"가 먼저 전달돼야 했다.

**4. 에러 메시지 분리** — 클라이언트에는 고정된 안내 메시지만 내려주고, 실제 원인(내부 URL, 응답 원문)은 서버 로그에만 남겼다. 에러 메시지에 내부 구조가 그대로 노출되는 건 그 자체로 정보 노출이고, 사용자에게도 쓸모없는 정보였다.

**5. 입력 검증을 AI 호출 앞으로 이동** — 문항 존재 여부, 모드별 필수 필드(URL 모드면 URL, 붙여넣기 모드면 본문·회사명·직무)를 먼저 확인하고 통과해야 agent를 부르게 했다. AI 호출은 비용이 드는 작업이라, 어차피 실패할 요청을 걸러내는 비용이 호출 비용보다 훨씬 싸다.

**6. 조회 범위 축소** — `findByPrepIdOrderByDisplayOrder`를 추가해 필요한 행만 가져오게 했다. 메모리 필터링을 유지할 이유가 없어 다른 대안을 검토할 필요도 없었다.

**7. 중복 제출 차단** — 성공 경로에서는 화면이 곧 다른 라우트로 전환되므로 `loading`을 리셋하지 않고, 실패 경로에서만 리셋했다. 성공 시 라우팅도 `push` 대신 `replace`로 바꿔 뒤로가기로 같은 폼에 돌아와 재제출하는 경로까지 막았다.

**8. 빌드 컨텍스트 정리** — `.dockerignore`를 추가해 `node_modules`·`.next`·`.git`·`.env*`를 제외했다. 가정이 아니라 실제로 이 작업 디렉터리에 `.env.local`이 있어서, 막을 게 실존했다.

**9. 안내 일관화** — 목록·상세 화면에도 입력 화면과 같은 "이용 신청이 필요합니다" 안내를 추가해 세 화면의 처리 방식을 통일했다.

**10. 개별 필드 검증 + 상태ncareer-data 폴더 전체 다 분석해줘서 내가 정말 진심으로 합격하려면 뭐부터 해야하는지 분석해줘 나랑 비슷한 스펙에 최신 기준으로 합격한 사람들 기준으로 10개 이상씩 분석해서 진심으로 알려줘.값 화이트리스트** — 문항 개별 필드 검증을 추가하고, agent 상태값도 `"ok"`가 아니면 전부 실패로 처리하도록 바꿨다(발견 3과 같은 종류의 문제라 같은 방식으로 고쳤다).

**11. 응답 파싱 보강** — 마크다운 코드펜스를 벗기고 파싱하도록 바꿨다. 신규 태그의 `tagKey`가 비어 있으면 라벨에서 슬러그를 만들어 대신 쓰고, 라벨까지 없는 완전히 망가진 응답일 때만 실패로 처리했다.

## 직접 만들었다가 고친 것

- career-link-agent에서 신규 태그 슬러그에 길이 제한을 안 두고 있었다 — "라벨이 짧을 테니 괜찮겠지"라는, 검증 안 된 가정이었다. DB 컬럼 폭(100자)을 넘을 수 있다는 지적을 받고 잘라내는 로직을 추가했다.
- 로컬 Docker Compose에 자체 MySQL·Redis 컨테이너를 포함시켜뒀다가 빼고, 기존에 로컬에서 쓰던 DB를 그대로 쓰도록 되돌렸다 (아래 "판단이 틀렸던 것" 참고).

## 판단이 틀렸던 것

로컬 compose에 자체 MySQL 컨테이너를 새로 만들면 "깨끗한 환경에서 테스트할 수 있다"고 가정했다. 실제로는 이 저장소에 마이그레이션 도구가 전혀 없어서, 빈 컨테이너엔 로그인에 필요한 기존 테이블·뷰조차 없었다 — 실제로 띄워보고 나서야 확인했다. (별도 Decision 글로 더 자세히 남길 예정)

## 남긴 것 · 하지 않은 것

- Spring의 open-in-view(기본값 true)가 요청 전체 동안 DB 커넥션을 쥐고 있어서, AI 호출 앞에 쿼리 하나만 있어도 그 호출 내내 커넥션이 묶인다는 걸 확인했지만, 끄려면 팀 앱 전체의 지연 로딩 의존 여부를 다 확인해야 해서 지금은 주석으로만 남기고 미뤘다. 재개 조건: 동시 사용자가 늘어 커넥션 풀이 실제로 부족해지면.
- "검증 시점과 사용 시점이 분리된 값은 재검증 없이 재사용하면 안 된다"는 원칙(SSRF 수정에서 나온 교훈)을 다른 외부 호출에 전면 적용하는 일반화 작업은 하지 않았다 — 이번엔 이 기능의 agent 호출 하나에만 적용했다.

## 검증

- 세 저장소 모두 단위 테스트로 커버(career-link 44개, career-link-agent 43개, career-link-ui는 `tsc --noEmit`·`npm run build` + 수동 화면 확인).
- 로컬 Docker Compose로 세 서비스를 실제로 띄워 헬스체크·인증·실제 Claude API 호출까지 end-to-end로 확인했다.
- 외부 코드 리뷰 도구(Codex)로 한 번 더 교차 검증해 놓친 항목 2개를 추가로 잡았다.
