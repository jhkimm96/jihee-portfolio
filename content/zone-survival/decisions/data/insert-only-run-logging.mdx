## 배경

게임은 GitHub Pages에 올린 정적 파일이라 기록을 받아줄 서버가 없습니다. 처음에는 판이 끝나면 결과 화면의 "기록 복사"로 JSON 한 줄을 복사해 메신저로 보내게 했습니다. 이 방식은 서버가 필요 없지만, 플레이어가 복사하고 붙여넣는 단계에서 빠질 수 있어 기록이 덜 모일 수 있습니다.

기록은 밸런스를 고치는 근거라서 **판 수와 분모가 곧 신뢰도**입니다. 그래서 자동으로 저장하되, 개인정보와 운영 부담은 최소로 하는 방법이 필요했습니다.

## 고려한 선택지

- **기록 복사 유지:** 서버가 없고 개인정보도 없다. 하지만 플레이어의 수고가 필요해 기록이 줄어든다.
- **구글 폼 연동:** 서버를 만들지 않는다. 다만 입력 단계가 늘고 게임 안의 자동 저장이 되지 않는다.
- **Supabase에 직접 저장(공개 키 + RLS):** 브라우저에서 바로 저장한다. 공개 키가 코드에 들어가므로 권한을 테이블 규칙으로 막아야 한다.

<details>
<summary><b>🔍 RLS와 공개(publishable) 키란</b></summary>

Supabase는 데이터베이스(PostgreSQL)를 HTTP로 바로 열어 줍니다. 브라우저에 넣는 **공개 키**는 누구나 볼 수 있다는 전제의 키라서, 무엇을 할 수 있는지는 **RLS(행 단위 보안)** 규칙이 정합니다. RLS를 켜고 규칙을 만들지 않으면 그 동작은 모두 막힙니다. 이 프로젝트는 "삽입만 허용"하는 규칙 하나만 만들었습니다.

</details>

## 결정

Supabase를 쓰되 권한을 가장 작게 열었습니다.

- 판 기록 테이블과 한 줄 의견 테이블을 두고 **익명 키에는 insert만 허용**했습니다. 조회, 수정, 삭제 규칙은 만들지 않았습니다.
- 테이블에 값의 길이와 허용 값 제약(check)을 걸었습니다. 예를 들어 사망 원인은 정해진 세 값만, 생존 시간은 0~600초만 들어갑니다.
- 브라우저에는 공개 키만 두고, 모든 권한을 가진 `service_role` 키는 쓰지 않습니다.
- 저장이 실패해도 예외를 던지지 않고 결과 화면에 상태만 알립니다. "기록 복사"는 예비로 남겼습니다.
- 닉네임은 선택이고 실명이나 연락처는 받지 않으며, 같은 사람의 여러 판은 처음 열 때 만든 무작위 익명 ID로 묶습니다. 한 줄 의견은 판 기록과 분리된 별도 테이블에 넣었습니다.

## 결과

직접 확인한 것입니다.

- 공개 키로 조회를 시도하면 `permission denied`(HTTP 401)로 막힙니다.
- 허용되지 않은 사망 원인 값을 넣으면 제약 위반(HTTP 400)으로 거부됩니다.
- 한글이 포함된 기록과 의견이 정상적으로 저장됩니다(HTTP 201).
- 게임의 전송 코드는 성공, HTTP 오류, 네트워크 오류, 설정 없음을 각각 예외 없이 처리한다는 자동 테스트가 있습니다.

한계도 있습니다.

- 공개 키를 아는 누구나 형식에 맞는 기록을 넣을 수 있어서, **조작된 기록이 섞일 수 있습니다.** 제약으로 값의 범위만 제한했고 요청 횟수 제한은 두지 않았습니다. 분석할 때는 버전, 환경(로컬/배포), 기기를 기준으로 거릅니다.
- 조회가 막혀 있어서 기록은 대시보드에서 내려받아 분석합니다.
- 사람 기록을 얼마나 모을 수 있는지는 아직 알 수 없습니다.
